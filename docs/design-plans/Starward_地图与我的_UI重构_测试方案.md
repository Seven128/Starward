# Starward 地图／我的 UI 重构：设计 Skill 测试方案

版本：1.0  
日期：2026-09-07  
配套：`Starward_设计资源Skill_开发方案.md`  
本文件是待执行测试计划，不含实测通过结论。

## 1. 测试要回答的四个问题

**不能只测试“能不能在 Figma 生成图”。**需要分别回答：

1. 普通描述下，初稿是否具有足够完成度，而非只有挑中的一张好看？
2. 新 Skill 是否比同模型、同工具、没有新 Skill 时带来稳定收益？
3. 好看的候选是否仍保留 Starward 当前业务与交互职责？
4. 资源是否真的可编辑、能接着修改，并能指导真实小程序实施？

测试分为工程探针、设计质量实验、产品状态检查和采用后的 WEAPP 验证。后者不能被前三者代替。

## 2. 执行前记录与固定条件

记录当前 HEAD、未提交变更摘要、所读需求／设计来源及哈希、当前模型／档位、Codex 与插件版本、Figma 文件和权限、运行路径、素材、测试内容、尺寸、实际使用量。

**原帖报告的模型是 GPT-6 Astra，不是 Figma 内置 AI；精确模型快照和 effort 未公开。**本次必须记录实际配置。无法获得的项标记 unknown，不让模型自报充当运行证据。其他模型可以测试 Skill 工程能力，但不能计作同模型复现。

建议主画板为 390×844 逻辑像素。所有候选使用同一份正式点位示例、地图视口、图片、账户／计划／贡献状态及文案。测试数据不得依赖实时天气波动。使用项目已有合适 fixture；如果缺少，创建最小任务局部示例，保留真实数据模型和缺失／过期语义。

试验数据说明放在评审外壳或说明文件，不能把“测试／Demo”标记变成产品页面装饰，也不能对外称该示例为实时天气或真实已审核贡献。

## 3. T0：真实工具探针

先执行以下小规模探针，通过后才批量生成页面。一次失败后先依据具体错误修复，不在同一错误上无限重试。

| 编号 | 操作 | 期望与证据 |
|---|---|---|
| T0-01 | 在新会话显式调用 `$starward-design-resource` | 读取正确 Skill；其路径和引用存在；没有重复同名入口 |
| T0-02 | 指定一个有编辑权限的测试文件／区域，读回标识 | 身份和目标正确；不自动操作最近打开的另一文件 |
| T0-03 | 创建原生 Frame、中文 Text、Auto Layout、一个图标和一个复用组件 | 能在 Figma 层级里逐项选择和编辑；不接受整页栅格化 |
| T0-04 | 导入已允许使用的普通图片 | 正确图片、裁切及来源；失败有明确原因；不误套其他工具的图片限制 |
| T0-05 | 创建两张小画板并配置基础点击跳转，实际点击 | 跳转目标正确；记录真实运行，不只检查脚本包含某方法 |
| T0-06 | 导出 PNG，读取实际结构并在 Agent 端查看图片 | 图片来自 Figma，中文清晰，节点与导出为同一轮 |
| T0-07 | 将短中文改成长中文，重新导出 | 文本重排、容器适应；字体替代或溢出被发现 |
| T0-08 | 对同一个候选重复执行更新 | 不生成两套重复根节点；不改其他候选或人工内容 |
| T0-09 | 关闭插件／断开桥接再执行 | 明确失败，没有伪造成功／旧截图顶替；恢复后能读回再继续 |
| T0-10 | 在一条包含中途失败的测试修改中观察实际状态 | 能识别部分写入，清理仅限本次所属暂存节点；不声称不存在的事务回滚 |
| T0-11 | 输入错误文件、只读文件或目标节点变化 | 在写入前核对、拒绝越界；不切账号或升级套餐绕过 |
| T0-12 | 检查资源包和 Git diff | 无访问 token、cookie、私人账号内容、未经许可字体文件 |

探针可以合并在一个小片段完成，不必建十二个文件。若原帖 Scripter 路线需要人工每次运行，标为“半自动”；本地 Bridge 路线通过时标为“工程替代路径”，不得声称就是原作者工具。

## 4. T1：初稿美感及 Skill 增益实验

### 4.1 对照设计

| 组 | 保持相同 | 唯一主要差别 |
|---|---|---|
| A：基础能力 | 模型／effort、运行器、当前产品资料、已有必须遵守的项目 Skill、素材、用户简短需求、生成数量与修订上限 | 不加载新 `starward-design-resource` 的设计方法与审美修订流程 |
| B：新 Skill | 同上 | 加载新 Skill |

A 不是无约束地乱画。AGENTS、当前 Screen Contract 及项目必须的交互约束对两组都有效；不能为了做出提升幅度，故意剥夺 A 的基本业务信息或工具。

两组均可使用相同底层运行 helper，避免把“会不会导出截图”与审美能力混为一谈。新 Skill 的额外 token 和执行成本单独计入总成本。A 的输入不能偷偷包含完整新 Skill；B 不能看到 A 的画面后定向超越。

优先独立会话／子任务生成，固定允许读取的输入文件。不能可靠隔离时，在报告中注明潜在污染，降低因果结论强度。

### 4.2 两组使用同一份简短用户描述

> 为《今晚去观星》微信小程序重构地图页和我的页。保留当前业务和交互逻辑，设计三个明显不同但适合这个产品的方向。我要精致、小巧、简约、有高级感，同时有效信息密度高，手机上的字不要太小。请自主完成专业设计判断，交付可编辑 Figma 图层，并查看实际结果后改进。

输入另外附共同的产品范围与数据说明，而不是要求用户再补一页字体和圆角参数。候选允许提出局部视觉修正，但两组的变更边界相同。

### 4.3 样本数量与执行顺序

**第一阶段：一次成对试验。**

- A：三个方向，每方向地图＋我的，共六张核心画板。
- B：同样六张。
- 两组都保留 round-0；分别最多两轮正式视觉修订。
- 初稿和最终稿分开评审，不用最终稿追溯“默认输出”。

如果第一阶段已明显不可用，先记录失败并修 Skill，再开启新的版本试验；不能把修前修后混成一个样本集。工程失败、视觉失败和人为操作成本均保留。

**第二阶段：稳定性复验。**

在输入与 Skill 版本冻结后，再完成两次独立成对试验，总共三次。每组共九个候选方向、十八张两页核心画板。重复同一任务只能支持“小样本稳定性”，不是统计上证明所有项目都高水准。

若只完成第一阶段，报告“初步试验”，不写“稳定性验证通过”。不要求用户为后两次额外写提示词。

### 4.4 三类评分必须分开

#### A. 产品正确性：通过／不通过

当前导航、必要控件、内容和状态正确，详见 T2。业务错误的候选不能因为好看而通过。

#### B. 视觉完成度：每项 1–5 分

| 维度 | 权重 | 看什么 |
|---|---:|---|
| 信息层级与视觉重心 | 25% | 主次明确，用户第一眼知道要看和做什么 |
| 字体、中文与图标比例 | 20% | 手机可读，字重与行高协调，图标不显粗糙 |
| 版式与有效密度 | 20% | 紧凑有序而不拥挤；不存在无用空白或“卡片墙” |
| 跨页一致性 | 20% | 地图和我的属于同一产品，组件语言稳定 |
| 细节完成度 | 15% | 对齐、间距、边界、图片处理、状态细节无明显粗糙感 |

评分锚点：1=明显不可用；2=需大量重做；3=基本协调但仍粗糙；4=明显成熟、值得继续；5=精细且整体统一。**这些是本项目拟采用的评审尺度，不是行业客观量表。**

#### C. 个人偏好：单独记录

“是否是我喜欢的风格”“是否愿意选它继续”“最想保留／修改哪一点”。不喜欢某风格不等于设计质量低；喜欢某张图也不能抵消业务错误。

### 4.5 匿名评审

生成比较页时使用随机编号，隐藏 A/B、工具名、模型名、作者解释和自评分。保留两页成对展示；另外提供单页原始比例查看，不只看缩略图。

Agent 可以做独立辅助评审，但不能由生成者的自评分给自己开通过证明。最终审美和偏好至少由用户进行一次盲评；没有人工评审时，输出“辅助评审完成／用户视觉确认待完成”。自动化几何检查不能替代这一步。

建议对少量样本在不同顺序下复评，观察是否受排列影响；不要把反复给同一张图评分当作新增设计样本。

### 4.6 预先冻结的判定标准

以下为建议试验阈值，在第一次看到候选前写入配置，之后不能为迁就结果下调：

- 每个成对试验中，B 至少两个方向同时满足：两页产品正确、两页视觉加权分均 ≥4，且没有视觉单项低于3。
- B 不应反复出现“一个方向很好、另外两个明显不可用”的情况；报告全部候选最低分、中位数及达标比例，而不只展示最大值。
- 至少一个 B 方向被用户明确认为值得继续；这是偏好确认，不替代视觉评分。
- 比较 A/B 的初稿与最终稿分别的中位数、达标数量、用户修正次数和成本。若 B 没明显提高评分但明显减少人工指令或修改成本，也可构成采用理由。
- 如果 A 本来已经很强，B 只增加流程与成本，则精简 Skill；不强行宣称提升。
- 三次复验均达到上述标准，才给出“对当前两页任务具有初步可重复性”的结论。未做的人工／手机检查不计通过。

不设“自动评分达到 90 就一定好看”之类机器完成阈值。所有失败都保留，并区分模型、输入、素材、工具执行和评价分歧。

### 4.7 不应得出的结论

这项 A/B 主要检验新 Skill 在固定模型与工具上的收益。它不能单独证明：Astra 比所有其他模型好；Figma 比 Open Design 好；Scripter 比本地 MCP 好。

如后续要比较 Open Design，必须同模型、同业务输入、同素材和同预算另开对照。历史旧截图与今天新模型生成图的对比只能说明体验变化，不能确定原因。

## 5. T2：地图及我的产品正确性

### 5.1 地图核心检查

| 编号 | 场景 | 必須保持 |
|---|---|---|
| M01 | 默认地图 | 只有地图／我的主导航；搜索、定位、图层等现有职责清楚；地图仍是主体 |
| M02 | 点选正式点位 | 第一次选中即可打开 medium；名称、选择、状态与点位一致 |
| M03 | small／medium／large | 同一内容顺序和语义映射；档位只是裁切；大档才有文档纵向滚动 |
| M04 | 把手与返回 | 把手是档位拖拽区；单击不切档；large 返回 medium 的语义保留 |
| M05 | 有实景图／无有效图 | 图片的展开顺序正确；无图不保留大空洞或伪造图；把手带合理 |
| M06 | 章节与操作栏 | 章节“概览／天文”；操作“想去／分享／云观星”；没有重复或遗漏 |
| M07 | 图层面板 | 与点位面板互斥，保持现有协调器语义；没有第四个自造图层或重复关闭动作 |
| M08 | 时间预览／确认／取消 | 清楚展示选中时间、预览与提交关系；时间变化只对应真实切片能力 |
| M09 | 搜索与返回衔接 | 浮动搜索仍进入既有子页；保留稳定入口与返回上下文，不新增产品路由 |
| M10 | 静态／过期／部分数据 | 暂无数据与0区分；过期及风险不被装饰隐藏；不伪造实时成功 |
| M11 | 云观星 | 有效正式点位上下文才进入既有天空子页；无有效上下文有恢复说明 |
| M12 | 地图与面板共存 | 地图拖拽、点选、图层、面板各自触控区域可区分；不可被透明大按钮截获 |

静态资源可以检查内容、层级、区域和交互规格，真实手势与 state owner 行为留到 WEAPP 阶段。不得勾选“资源上画了动画”即代表原生手势通过。

### 5.2 我的核心检查

| 编号 | 场景 | 必須保持 |
|---|---|---|
| Y01 | 正常账户 | 账户头部与现有身份状态清楚，设置为单一明确操作，无重复账户摘要 |
| Y02 | 日常入口 | 计划、贡献、主页链接、内容导入及设置保留现有职责；重新分组不改子路由 |
| Y03 | 无计划／草稿／待审核 | 使用实际模型能提供的状态；不能显示编造的观星次数、等级或好友 |
| Y04 | 未登录／鉴权失效 | 只呈现当前产品支持的登录与恢复行为，不新造账号体系 |
| Y05 | 正在加载 | 结构稳定，不先显示假的0、假的成功或明显布局跳动 |
| Y06 | 离线／同步失败 | 显示可用缓存与重试，未刷新状态清楚，非相关入口仍能使用 |
| Y07 | 返回我的 | 保留滚动位置和逻辑焦点，资源交互说明中有对应约定 |
| Y08 | 范围限制 | 无会员／商城／促销／新页签；不把收藏夹迁回我的 |

## 6. T3：推荐方案的主题、状态和尺寸覆盖

只给推荐方向扩展完整验证。最小覆盖建议如下，不机械做笛卡尔积：

- 390×844：两页日／夜／观测三模式，共六张主要画板。
- 日间地图：补 small、large 有图、large 无图、图层面板；medium 已由主画板覆盖。
- 地图：补至少一个部分／过期／风险场景，按当前页面真实语义选定。
- 我的：补无计划、加载、同步失败或离线，以及当前支持的身份恢复状态。
- 320 宽：两页正常文本与200%长文本压力布局。
- 375、430 宽：至少检查两页主要布局，关键差异导出截图。
- 主题样本未覆盖到的状态：在同一组可复用组件状态板检查，不为每个按钮复制整页。

规模由真实覆盖缺口决定。可以导出二十余个有用途的画板；不能以达到一个数量替代完整性。

### 6.1 几何与文字

检查中文标题、长地名、多位数、单位、更新时间和操作标签；无关键内容被裁切。200% 文本时允许换行与重排，不通过缩小字体抵消放大。

设计坐标以逻辑像素记录。导出2×只是图像采样倍率。实现时核实 Taro 编译转换，不把 Figma390 宽直接当750设计稿再次缩小。

特别检查 `88rpx` 与44逻辑px的换算：前者在320宽约37.5px，并非任何尺寸都44。按当前可访问性义务和实际命中区域检查；若精确视觉要求有冲突，记录待采用的修正方案。

可见控件可紧凑，命中区域仍须满足实际要求，且相邻扩展区不重叠。Figma 中绘制检查用命中边界时将其留在非产品检查层；交付截图不把边界线显示给普通用户。

### 6.2 颜色、主题和素材

用当前项目对比度要求检查文字、弱文本、状态与图标。颜色不单独表达收藏、错误和选择；观测模式按已声明调色板检查自有 UI，不简单统计整张含原生底图的图像。

关闭／过渡／加载中的白闪无法仅靠静态图验证，标记给 WEAPP 连续运行测试。原生地图与系统表面不受控时单列，不宣布整屏观测保护已验证。

图片授权、来源、截图区域和外部地图标识不得被装饰裁切误用。相同 A/B 输入必须使用相同图片，避免用更好的图像素材解释为 Skill 审美提升。

### 6.3 组件与图层可编辑性

至少抽查一个地图控制、一个面板内容单元、一个我的列表行及一个状态组件：

1. 能定位组件及代码 owner。
2. 修改文案后能重排，非简单覆盖像素。
3. 同族组件风格一致，实例更新策略明确。
4. 没有第二套图标风格和未声明的字体替换。
5. 不依赖 Starter 没有的团队库、变量模式或高级条件逻辑才能打开基本原型。

## 7. T4：交付与跨会话继续修改

| 编号 | 测试 | 通过要求 |
|---|---|---|
| D01 | 资源包完整性 | 实际文件存在、非空，PNG可解码，链接／节点可定位，哈希对应当前文件 |
| D02 | 证据新鲜度 | 截图和结构快照为同轮导出；修改后旧图标记过期 |
| D03 | 原生结构 | 关键文本、组件、交互目标来自读回节点；非作者手填声明 |
| D04 | 修改边界 | Git diff与Figma影响范围符合目标；未更改全站规范或旧不可变包 |
| D05 | 新会话接手 | 只给交付包和普通修改句，即可定位目标、改动并重导出，不全量重做 |
| D06 | 不相关资源稳定 | 修改我的一条文案时地图资源不变；合理共享组件影响被明确列出 |
| D07 | 模型与成本记录 | 有实际模型／档位来源、工具版本、轮次和可取得用量；缺失不写0 |
| D08 | 失败和选择状态 | 推荐不等于用户选定；失败不等于通过；静态原型不等于生产完成 |
| D09 | 原生文件声明 | 未导出.fig就不提供假.fig；能导出时检查确为原生文件 |
| D10 | 权限与密钥 | 设计文件不擅自公开；无token／cookie／字体文件泄露 |

建议跨会话修改句：

> 我的页面保留这个方向，把“现场反馈与纠错”的说明改长一些，其他地方不要重做。检查手机上的换行和两页一致性。

这检验真实资源复用，不只是第一次生成能力。

## 9. T5：用户选定后的 WEAPP UI 重构验证

这一节是后续实施验收，不计入“本轮 Skill 已交付”的生产成功声明。

先更新选定设计的现有所有者和必要组件映射，保持两页范围及共享影响透明；再改实际 Taro 页面。不要并行保留新版／旧版产品入口，不把 Figma、旧 Open Design 和运行样式设为三套平行规范。

必须在同一最终代码候选上检查：

- 地图／我的真实路由、主导航及返回行为。
- marker、面板三档、把手拖拽／点击、左右边返回、面板／图层互斥。
- 时间 preview／commit／cancel 与静态／动态数据语义。
- 我的身份、计划、贡献和同步异常恢复，不显示编造状态。
- 菜单胶囊、安全区、键盘、320／375／390／430等效宽度、长中文及可用文本缩放。
- 日／夜／观测模式冷启动、切换、加载、错误和过渡；自有 UI 无不允许的闪屏。
- 可访问名称、状态、焦点恢复、非颜色信息及可用替代操作。
- 真正的 Taro→WEAPP 编译效果与至少代表性的 iOS／Android 微信环境。

截图比较以内容区域和当前数据状态对齐；原生地图瓦片和字体栅格差异不能用全屏逐像素一致武断判错，也不能成为忽略明显排版偏差的借口。

浏览器评审页只展示Figma导出，不是WEAPP。没有真机时报告“开发者工具已测／真机未测”；没有连续交互时报告静态证据。依赖接口、传感器或现场条件的项目不凭历史证据关闭。

# 二、从第一性原理看，真正值得买的只有几类东西

判断方式可以很直接：

| 外部能力的本质 | 例子 | 更合理的实现 |
|---|---|---|
| 平台已经提供的能力 | 地图显示、定位、选点、登录、分享 | 优先使用微信平台能力 |
| 必须持续取得的新信息 | 天气、官方预警、空气质量 | 购买合适的数据服务，在自己服务器上共享结果 |
| 更新较慢的基础资料 | 地形、年度夜光、恒星目录、天体图片 | 合法取得后按版本保存，自己处理和发布 |
| 可以根据规律计算的结果 | 日月位置、升落、月相、部分天象 | 复用现有计算服务，不按每次查看购买答案 |
| 需要人确认的现场事实 | 夜间开放、停车、厕所、最后一公里、安全与通行许可 | 自己核验、运营方确认、用户投稿后审核 |

**性价比应当在合规、效果达到要求之后比较。** 开源、能下载、允许商用、允许缓存、允许再发布、允许在中国大陆公开展示，是不同问题，不能互相替代。

# 三、地图：原生地图是主方案，路线计算可以明确收缩

## 1. 微信自带地图，比前两份报告判断得更有依据

本次找到了一条更明确的技术平台说明：**DCloud 官方文档指出，小程序自带的定位接口和地图组件，已经由小程序平台向地图厂商付费，开发者无需自行申请地图密钥和另行付费。** 开发者另外调用地图厂商的后台服务，例如地址查询，则属于另一种授权范围。citeturn818078view1

这比“没查到价格，所以可能免费”更有依据。

但仍需保留边界：**DCloud 不是腾讯的授权签发方，这条说明不等于腾讯给你所有商业使用方式开了无限许可。** 正式上线时，仍要按实际主体、类目、隐私声明和接口规则申请；尤其不能顺带接入需要自己申请地图密钥的商业搜索、路线或高级可视化服务，然后继续按“原生地图免费”理解。

## 2. 逐功能看，哪些保留，哪些真的会损失

| 功能 | 推荐实现 | 是否损失功能 |
|---|---|---|
| 地图拖动、缩放、显示道路 | 微信原生地图 | 核心体验可保留 |
| 显示观星点、选中态、想去状态 | 微信地图标记＋自己的数据 | 可保留 |
| 定位到附近 | 用户主动触发微信定位 | 可保留；拒绝定位后允许手动选点 |
| 搜索正式观星点 | 搜自己的名称、别名、地区、设施资料 | 可保留，符合当前产品 |
| 投稿时选择新地点、填写计划起点 | 微信地点选择窗口 | 页面由微信控制 |
| 完全自定义全国地点联想 | 不包含在这套方案内 | 需要改成平台选点窗口 |
| 任意坐标自动变成完整地址 | 优先使用选点结果和已核验地址 | 缺少来源时只能显示坐标或区域 |
| 两点直线距离 | 自己计算 | 可保留，必须标注“直线距离” |
| 点击“去这里” | 微信位置查看或外部地图导航 | 可保留导航交接 |
| 小程序内真实道路距离、实时车程 | 没有路线数据源时不提供 | **明确损失** |
| “开车一小时内”筛选 | 没有路线数据源时停用 | **不能拿直线距离冒充** |
| 公交、实时路况、多路线比较 | 交给外部地图 | 小程序内不提前完整展示 |
| 自动计算出发时刻 | 无可靠车程时由用户填写 | 不自动倒推出发时间 |

这里的技术边界是：**地图能画线，不代表它能替你计算道路路线；打开导航，也不代表导航结果会回传给你。** 腾讯官方资料将原生地图能力与后台搜索、路线、距离等服务分开。citeturn447564search7

因此，我建议当前小程序保留：

> 找到观星点 → 看事实 → 安排自己的观测时间 → 点击导航出发。

不为此重建全国路网，也不假装已经知道实时车程。

## 3. 地形、夜光能否叠加？有实际技术路径

腾讯官方提供 **`MapContext.addGroundOverlay`**，可以把图片放到指定经纬度范围，随地图缩放，调整透明度和图层顺序。它从基础库 2.14.0 开始支持，文档同时注明**工具侧暂未支持**。

对你意味着：

> 后台生成带地理位置的地形或夜光图片 → 小程序按范围加载 → 叠到微信地图上。

不必先购买一套高级地图可视化服务。

不过，**这项必须在真实手机上检查**：图片是否对齐、缩放是否清晰、图层能否独立开关、加载是否卡顿。模拟器里画出效果，不能证明微信真机已经完成。

## 4. 苹果地图、天地图、自建路线，应该排在哪里？

**苹果地图：保留为“重新设计地图承载方式”的候选，不作为当前替换件。** 苹果中国开发者会员确实是 **688 元/年**；网页地图公开包含每天 25 万次地图展示，以及每天 2.5 万次共享地图服务请求。但苹果地图结果受到配合苹果地图展示、缓存等限制，不能当作给腾讯底图供数的廉价后台。citeturn297818view0turn706471search2turn706471search29turn472364view3

**天地图：值得询证，但目前不能盖章为广东小程序的完整免费替代。** 某个地方节点允许商用，不代表全国接口、广东数据、缓存权、路线和配额全部一样。citeturn706471search3

**自建 OSRM 路线：不列为默认下一步。** 它可以根据路网计算路径，但你仍要承担路网质量、夜间通行、封路、静态车程误差和相关合规问题。OSM 公共瓦片也不允许拿来批量制作离线包，公共地点查询服务存在请求量及自动补全限制。citeturn589478view1turn589478view2turn589478view3

**我的排序：微信原生路线第一；明确不提供的道路能力先收缩；其他方案只有在对应功能价值足够大时再验证。**

# 四、天气：可以明确选择一套，但不能宣称某家已经“广东最准”

## 1. 我给出的选择

**商业落地优先候选：和风天气一套主预报。**

这是结合公开价格、现有适配基础和字段范围作出的采购方向，**不是“它在广东夜间云量上最准确”的结论**。当前项目已经有和风适配基础，但商业使用与实际生产覆盖不能由代码存在推定。

**保留分层云和较长预报的候选：通过付费 Open-Meteo 获取欧洲 IFS 9 公里预报。**

它更接近完整气象字段要求，但中国公众传播路径、实际访问质量、广东当地效果还没有完成核验。因此不能仅凭“欧洲模式”“9 公里”等名字直接判定最优。citeturn398248view3

这里的“一套”是指我们只接入一条主预报，不展示多模型、不取几家里最晴的结果。**官方预警、空气质量属于其他信息类别，不算再买一套天气。**

## 2. 四种单一预报方案，真实差别如下

| 方案 | 优势 | 可核价格 | 关键不足 |
|---|---|---|---|
| **和风天气** | 按量付费，普通天气字段较完整，当前接入基础可复用 | 同计费组前 5 万次/月免费，之后阶梯计费 | 没有低中高分层云；最多约十天小时预报；历史有空间和字段限制 |
| **欧洲 IFS，经 Open-Meteo** | 模式来源清楚，分层云、较长时效方向更接近原要求 | Standard 现价仍未核实；官方文章确认 Pro 从 **99 欧元/月**起 | 免费端不可商用；大陆公众传播路径和当地表现未闭合 |
| **苹果 WeatherKit** | 会员包含较大天气查询量 | **688 元/年**会员含 50 万次/月；100 万次套餐另付 **49.99 美元/月** | 约十天；服务器分层云未完整核实；原始天气收费、长期存档有限制 |
| **彩云天气** | 国内接入，有公开按量方案 | **25 元/万次**；专业版 **5,998 元/月** | 低价按量方案只有约 72 小时逐小时；专业版约十天，不能把总体“15 天”宣传套到低价档 |

这些价格和能力来自各自官方资料，**表中方案只用于选型比较，正式产品不需要同时采购**。citeturn472364view0turn472364view1turn141398view1turn120049view2turn649433view0turn818078view4

## 3. 采用和风方案后，每个天气功能能保留到什么程度？

| 功能 | 处理方式 |
|---|---|
| 温度、体感、湿度、露点 | 保留 |
| 总云量 | 保留 |
| 低云、中云、高云 | **不提供，须明确删减或显示缺失** |
| 风速、阵风、风向 | 保留 |
| 降水量、降水概率 | 保留 |
| 能见度 | 保留，但不改名为“天文透明度” |
| 气压 | 接口是海平面气压，不能直接当山顶地面气压 |
| 未来小时天气 | 最多 240 小时，以实际返回范围为准 |
| 第 11—15 天 | 天文和计划继续可用，天气不强行补齐 |
| 前七天回看 | 只显示来源支持的历史字段，不能冒充任意山头实况 |
| 地图云量色块 | 根据真实有数据的地点或网格生成，不伪装连续高清实时云图 |
| 官方预警 | 独立取得并保留发布单位、时间、更新和解除信息 |
| 空气质量、PM2.5、PM10 | 按对应空气接口取得，不默认与天气同样长时效 |
| 专业视宁度、实测天空透明度 | 普通天气字段不足以支持，当前不承诺 |
| 多模型比较、模型投票 | 删除 |

和风当前小时接口已经换成新的字段结构，包含阵风；云量、湿度、降水概率用 **0—1** 表示。开发时不能只换网址而沿用旧字段和百分比处理。citeturn472364view0

**这是实质功能取舍。和风并没有等价覆盖你原来全部专业气象要求。** 你接受功能调整，但不能把这种调整藏起来。

## 4. 两处值得特别纠正

### 历史天气：有“前七天”不代表有“这个山头前七天的完整天气”

和风时光机支持最近过去十天，但**只接受城市编号，不接受任意经纬度**，小时字段也没有完整云量；其数据性质是历史再分析，不能包装成观星点现场测量。citeturn818078view3

因此，查看一个山顶上周四的情况时，可以展示明确注明地区和性质的历史字段，不能把城市数据换个地点名就当成山顶实况。

### 苹果天气：低价套餐不能自动支持“付费解锁原始天气数据”

苹果协议限制对原始形态天气数据向用户收费，收费增值结果要符合其转换条件；缓存也限于规定的临时、有限用途。**这不等于苹果天气不能用于任何商业产品，但它与收费天气面板、长期计划回看之间需要额外核实。**citeturn297818view4

所以我没有把它列为当前商业主方案第一名，也不会继续在所有小程序预算里默认加上苹果会员费。

## 5. 天气还有一道独立的合规要求

《气象预报发布与传播管理办法》涉及公众预报统一发布、传播来源、发布时间和预警更新。展示云量、温度等客观数值，同样可能涉及这些要求，不能因为没有写“推荐出发”就视为不适用。citeturn297818view2

需要落实的是：

> 这份中国地区预报由谁发布，我们是否获得相应传播使用权，地图着色、历史回看和收费方式是否在允许范围内。

**供应商允许商用，与我们这套页面在大陆公开传播合规，是两件要分别确认的事。**

我的最终建议是：**能接受缺少分层云、远期天气缩短等调整，就优先落实和风一套；这些字段不能删，就继续落实 IFS 或国内有合法来源的专业产品，不暗中恢复双付费主预报。**

|---|---|---|---|
| 地图上的光污染分布 | 年度夜光数据自行裁剪、着色和托管 | NASA Black Marble 相应年度产品 | 不同产品不能直接共用同一颜色阈值 |
| 比较地点附近灯光强弱 | 使用同一年度、同一处理版本 | 增加现场仪器测量 | 卫星夜光不等于地面天空亮度 |
| 现场情况补充 | 有日期、方向和来源的照片、报告 | 实测天空亮度站点 | 手机照片亮度不是标准测量 |
| 时间尺变化 | 年度夜光保持不变 | 高频夜光产品需另外立项 | 不能随 22 点、23 点假变化 |

产品入口继续叫“光污染”可以理解，但来源说明应讲清楚：它实际上反映的是**年度卫星夜光估算**，不能直接换成精确波特尔等级、实时天空亮度或每一点固定误差保证。citeturn162313view2

## 2. 地形：GLO-30 足以支持当前简化后的目标

Copernicus GLO-30 提供约 30 米网格的地表表面模型，可能包含建筑和植被；官方有面向公众的下载与相应使用许可。citeturn120049view0

你当前真正需要的是：

> 真北向上的周边俯视地形、距离圈、比例尺、约 2—50 公里范围，以及地形和夜光独立开关。

当前合同已经明确不要求完整方向遮挡角和所有近障碍。所以没有必要先购买复杂三维地图，也没有必要先做全国最高精度地形。

| 方案 | 效果 | 我的判断 |
|---|---|---|
| GLO-30 裁剪后生成地形图 | 山体、地势、周边环境理解 | **首选** |
| GLO-90 或降低显示分辨率 | 大范围概览，文件更小 | 可作为明确降级 |
| 合法国内高程服务 | 可能减少自行加工 | 需要同口径报价再比较 |
| 现场三维扫描、完整近障碍建模 | 更精细的树木、围墙遮挡 | 超出当前必要范围 |

附件说的“原始约 30 米、显示约 111 米”，是不同层次。本次没有实测当前部署资产的有效分辨率，应以实际发布文件为准；放大低清图片不会生成新细节。

## 3. 这里还有一个不能省略的边界

**数据许可允许商用，不等于地形、等高线、夜光作为公开地理图层的责任已经解决。** 底图许可和你新增的地图内容要分开检查。citeturn174370search5turn174370search2

坐标也要贯穿一致。原始科学坐标、地图显示坐标、高程基准、手机方向，是几套不同含义，不能混用。未经验证的“移动图片外框”不能证明栅格已经正确配准。 citeturn120049view0

# 六、真实星空、星表、深空影像和天象

## 1. 日月行星等计算，继续复用现有服务

| 功能 | 推荐实现 | 是否需要持续购买外部接口 |
|---|---|---|
| 日月行星方位、高度 | 现有天文计算服务 | 通常不需要 |
| 日出日落、暮光、月升月落 | 同一算法服务 | 通常不需要 |
| 月相、照亮比例、盈亏状态 | 连续计算结果映射展示 | 通常不需要 |
| 银河方向与出现时段 | 固定天区资料＋时间地点计算 | 通常不需要 |
| 恒星位置和明暗 | 合法星表＋统一投影 | 不需要逐星查询 |
| 手机指向天空 | 微信传感器能力＋校准 | 不需要为每次转动购买接口 |
| 天体名称、中文简介 | 合法目录＋自己审核的内容 | 不必按每次点击付费 |
| 天象浏览与计划关联 | 同一事件目录＋当地可见性计算 | 不必分入口重复采购 |

Astronomy Engine 采用 MIT 软件许可，可商用并覆盖主要天文计算。当前项目已有统一计算服务，应继续复用；“自己计算”可以在自己的服务器完成，不意味着要让每个小程序页面另外实现一套算法。citeturn466360view1 

## 2. 星表许可，是目前真正需要处理的商业问题

当前仓库记录使用限定亮度范围的 Hipparcos 星表。ESA 当前目录页面显示非商业许可；本次查到的 Gaia@AIP 具体发布渠道也有非商业条件。**所以不能认为“换成 Gaia 就自然解决商用问题”。** citeturn645180search3turn174370search0

这里也不能走向另一个极端：某个页面当前有非商业条款，不代表所有历史版本、所有取得方式都一样。应先核对**项目实际使用的文件、取得时间和当时适用许可**。

| 选择 | 应该怎样处理 |
|---|---|
| 保留现有 Hipparcos 文件 | 能证明适用商业权，或取得额外许可，就不必盲目重构 |
| 换成 HYG 指定版本 | 作者声明允许商业使用的署名—相同方式共享许可，但仍应核查汇入上游数据的授权链 |
| 使用其他合法亮星精选包 | 只要覆盖当前效果并有明确权利，也合理 |
| 随便从 Gaia 镜像导出 | 不能把能查询当作可以商业打包 |

HYG 作者提供的当前版本约有 12 万颗星、压缩约 14MB；OpenNGC 也有明确开放许可。相同方式共享要求应按数据和派生数据库边界处理，不能直接扩大成“整个小程序必须开源”。citeturn645180view0turn645180search0

## 3. 深空影像：当前用的是真实红外数据，不是肉眼照片

仓库当前记录的影像来源是 **NASA SkyView 中的 WISE 12 微米资料**，用于已聚焦的星系、星云。它是真实观测资料，但属于红外波段，不等于用户肉眼看到的效果，也不是实时天空。

我建议把选择分成两档：

| 方案 | 用户得到什么 | 取舍 |
|---|---|---|
| **已获权重点目标影像，自己做不同清晰度** | 放大 M31、M42 等能看到真实细节 | 权利和成本容易控制，但不覆盖任意天区 |
| 完整分级巡天图层，即 HiPS | 更连续、更大范围地缩放浏览真实巡天 | 更多版权核对、加工、存储、下载和配准工作 |

**HiPS 是图像组织方式，不是商业授权。SkyView 是获取工具，也不是它内部所有影像的统一版权许可。**

ESA/Hubble、ESO 的公开版权规则允许很多图片按要求用于商业场景，但仍要排除特殊素材与例外。可优先逐张管理这些来源。citeturn162313view3turn162313view4

同时，照片要知道对应天区、方向和角尺度，才能贴到星空里。缺少配准信息的漂亮图片可以作为对象详情配图，不能随意缩放后宣称已经科学对齐。

## 4. 天象资料：大部分不需要持续购买事件接口

**日食、月食：** NASA 预测资料有明确署名转载说明，可以与本地算法核查当地可见性。citeturn466360view2

**流星雨：** 采用有使用权的年度事实资料，自己审核入库，再计算当地辐射方向、黑夜和月光情况。本次尚未闭合一个具体年度数据包的商业转载权，不能写成“已经确认免费”。

**事件浏览与计划关联：** 你现在本来就是同一套事件数据、同一个组件的浏览与单选模式，不需要为两个入口购买两套服务。

# 七、地点、账户、投稿、提醒这些也有外部依赖

这些经常被“地图＋天气”报告漏掉，但对你的小程序实际运营很重要。

| 功能 | 推荐方案 | 不能忽略的部分 |
|---|---|---|
| 停车、厕所、充电、信号 | 现场核验、运营方确认、有日期的投稿 | 普通地图收录只能作线索 |
| 夜间开放、合法进入、露营过夜 | 场地管理方和有效规则 | “别人去过”不等于合法或现在开放 |
| 最后一公里、入口与步行段 | 有来源的现场资料 | 导航算得通不等于夜间可通行 |
| 现场及设施照片 | 投稿者授权、必要隐私处理 | 网上可见不等于可商业复制 |
| 登录与账户隔离 | 微信身份＋自己后端 | 不默认购买短信登录或另一套账户平台 |
| 想去、草稿、计划同步 | 现有数据库 | 私人数据与正式公开点分开 |
| 内容审核 | 平台能力或合规审核服务＋人工 | 内容安全接口不会替你验证场地安全 |
| 出发、审核状态提醒 | 微信订阅消息＋自己的发送任务 | 意愿保存、订阅授权、实际送达是三个状态 |
| 分享、导出、注销 | 平台通道＋真实服务端操作 | 清本地缓存不等于删除远端账户 |
| 图片存储、下载、监控 | 复用一家合适的境内基础设施 | 存储、下载、回源、请求、处理分开算 |

这些处理方向与当前正式点、贡献、计划、提醒和账户合同一致。特别是仓库已明确：**保存提醒设置不能声称微信消息已经送达；用户投稿也不能直接变成正式事实。**  

商业化也不等于现在必须加支付。最终采用广告、会员还是其他方式，会影响供应商条款、平台类目和交易费用；这部分在商业方式未确定时不应编一个统一价格。

# 八、费用重新计算：按地点刷新和真实下载量算

## 1. 天气不应该简单拿日活乘查询次数

下面是**规划算例，不是你的实测账单**。

假设持续服务 **100 个独立查询地点**，每月 30 天：

| 数据 | 假设刷新方式 | 月请求量 |
|---|---|---:|
| 一套小时天气 | 每地点每小时一次，一次取得完整所需时段 | 72,000 |
| 当前空气质量 | 每地点每小时一次 | 72,000 |
| 空气质量预报 | 每地点每天四次 | 12,000 |
| 官方预警 | 每地点每十分钟一次 | 432,000 |
| 用户历史回看 | 合计预留 | 10,000 |
| **合计** | 不含额外重试和其他接口 | **598,000** |

天气、预警、空气质量、历史等同组累计，**不能给每一种都算一份五万次免费额度**。按公开价格，本例约为：

**（598,000－50,000）×0.0007＝383.60 元/月。**citeturn472364view1

同样使用假设下：

| 持续服务的独立查询地点 | 月请求量 | 天气相关费用/月 |
|---:|---:|---:|
| 20 个 | 119,600 | 约 **48.72 元** |
| 100 个 | 598,000 | 约 **383.60 元** |
| 500 个 | 2,990,000 | 约 **1,660 元** |

本例约 72% 请求来自预警检查。真正值得优化的是合理共享、按实际覆盖去重和减少无效刷新，**不能为省钱延误重要预警**。十分钟只是算例，实际频率还要考虑活跃预警、出发动作和供应商更新节奏。

# 九、现在到底能不能说“已经找到最佳性价比方案”？

**可以收敛总体结构；还不能把全部组合认证成“全功能、已合规、绝对最便宜”。**

原因已经比三份附件具体得多，不需要继续无边界地搜索供应商。

## 可以直接确定的方向

**微信原生地图＋正式点搜索＋外部导航；不重建全国道路；不买多套主预报；主要天文计算复用；年度夜光和区域地形按合法数据自行处理；内容和影像按实际使用版本核权。**

## 需要明确接受的功能损失

采用上述和风分支，就要明确减少：**产品内实时道路距离与车程、驾车时长筛选、自动倒推出发时间、低中高分层云、完整十五天小时天气、任意点完整历史云量。**

影像先覆盖已获权目标，也意味着不承诺任意天区都有高清细节。这些都应落实为产品变更，不能在接口缺失时偷偷用其他值填上。

## 商用前只剩四组真正会改变结论的事项

| 事项 | 需要拿到的结果 |
|---|---|
| **平台与地图表达** | 实际主体和位置能力申请通过；确认自制地形、夜光图层的公开表达责任与坐标处理 |
| **唯一天气主源** | 具体中国地区发布与传播来源、展示方式、缓存、历史和收费范围成立 |
| **实际资料权利** | 现用星表、深空目录、图片、年度天象资料具有适用版本的商用与再发布证据 |
| **真实手机效果** | 地图图层对齐、星空指向、图像缩放、跨午夜、请求取消、预警失败和私人数据隔离通过 |

此外，广东公开运营小程序要执行适用备案要求；位置与私人计划按最小必要原则处理，行踪轨迹属于敏感个人信息。不能认为坐标经过粗化，就自动解决了全部隐私与跨境问题。citeturn589478view0turn598192search5

**最终建议：先按这套结构收敛，而不是继续围绕“换哪家完整地图套餐”打转。地图和科学数据的实现方向已经比较清楚；天气选择需要把“可落地、字段完整、当地最准”分开判断；星表和影像则必须落实到实际文件许可。**

**这次能确认的是：你的观星小程序没有理由默认背上附件三那种范围的预算，也没有必要为了保留核心体验购买五万元地图或长期多模型天气。最终的商业方案，应当由明确保留的功能、明确接受的损失、实际授权和真实账单共同确定。**

> **起点＋终点＋交通方式 → 路线服务计算 → 返回公里数、分钟数和路线 → 我们的小程序展示。**

这里需要的外部能力是“计算并提供路线”，微信地图负责把结果画出来。

## 四、自建服务器“至少两万元/年”，这个结论没有依据

原附件给的其实是：

| 原附件中的范围 | 原月度预算 | 换算成年 |
|---|---:|---:|
| 广东区域路线服务 | 150—800 元/月 | **1,800—9,600 元/年** |
| 全国路网及更高并发 | 500—2,000 元/月 | **6,000—24,000 元/年** |

而且附件明确说了：**这些是工程预算，不是云厂商报价。** 不能把“全国、更高并发的预算上沿”变成你这个项目的最低服务器成本。

更重要的是，应该把两种“自建”分开：

**只自建区域路线计算：** 准备区域道路资料、运行路线软件、维护更新、返回距离与预计时间。

**自建完整地图平台：** 还要做全国地点搜索、地址查询、地图图片、地图样式、公交、动态路况等。

你的问题只需要先评估前一种。OSRM 这样的路线软件本身就能返回道路距离、估计时间和路线形状，没有必要为了得到这些结果把整个地图平台一起建设。citeturn557914view0

但自建也没有“安装成功就完成”的那么简单。应当分开核算：

> **一次性接入与数据处理工时＋持续数据更新和质量检查＋服务器与备份＋必要的合规处理。**

尤其对观星点，真正麻烦的可能是“地图上有路，但晚上封门”“终点吸附到了山另一侧”“停车后还有一段步行”，而不是计算接口的运行费用。这些都需要代表性地点测试。

**所以我既不会继续说它必然两万元以上，也不会换成一个未经测试的“几十元就够”。目前没有完成容量实测，无法给你确定服务器报价。**

## 五、其他功能，也不能归纳成“全部原样实现，而且已确认便宜”

这一点需要避免新的误解。

上一轮采用和风天气的便宜分支，已经有这些取舍：

| 原要求 | 那套组合的实际情况 |
|---|---|
| 总云量＋低、中、高层云量 | 小时接口有云量，但没有完整低中高分层云字段 |
| 未来十五天逐小时天气 | 当前小时接口最多 **240 小时，约十天** |
| 任意观星点前七天完整天气回看 | 时光机按地区编号查询，属于历史再分析，不能当任意山头的完整现场实况 |
| 所有星表、深空图片都可直接商用发布 | 上次还有实际文件版本与授权待核查 |
| 所有地形叠加、手机指向、影像缩放已达到产品效果 | 上次没有完成全部真机验证 |

天气这几项限制有对应官方文档依据；后两项是上一轮尚未完成的核验事项，并没有因为预算较低就自动消失。citeturn851622view5turn557914view1turn851622view3

所以可以说：

> **大部分能力有低运行成本的实现路径。**

还不能说：

> “除了路线，原功能已经全部等价保留，商业许可和效果也全部通过。”

之前每月几百元的表格，也只是指定假设下的数据与图片费用，不是包含开发、人工审核、场地核验和所有授权的项目总成本。

## 六、对你这个产品，我建议保留路线功能，重新完成小范围选型

**路线距离与预计用时会影响用户是否愿意去、几点出发，不能把“打开外部导航后再看”说成完全等价替代。** 完整导航可以交给外部地图，但出发前的路线摘要值得保留。

应当把采购目标限定为：

> **在我们的小程序卡片中，展示用户起点到观星点实际入口或停车点的道路距离、所选交通方式的预计用时；有合法来源时再画路线。**

同时明确三个能力等级：

| 等级 | 用户得到的结果 |
|---|---|
| 基本道路估计 | 沿道路多少公里，按道路资料估计多久 |
| 当前路况估计 | 现在出发，考虑当前拥堵预计多久 |
| 指定时间与公共交通 | 某天某时出发、公交换乘、首末班等 |

腾讯官方接口本身就区分这些交通方式与部分时间条件；它们不能用同一个距离除以不同平均速度来替代。citeturn469751view3

为了控制费用，我建议先在用户**选中观星点或编辑计划时，查询当前选择的交通方式**，不在每次打开地图时自动计算所有点、所有方式。这个设计能减少无用查询，但不会替代授权，也不意味着删掉用户主动查询其他方式的入口。

**最终结论：圆周旅迹说明这项产品体验可实现；本次找到的独立商业路线服务说明低成本并非只剩自建；原报告也不支持“自建服务器至少两万元/年”。目前真正没完成的是：找到并验证一条同时满足“当前小程序展示方式、目标交通方式、广东道路质量、商业使用与大陆合规”的低价接入路径。路线功能应当标为“来源选型待完成”，不应提前判定为做不到或直接删除。**

我重新读取了当前仓库的产品与技术说明。现在的小程序以**地图、我的**为主要入口，展示地点、到达、设施、安全、天气和天文事实，由用户决定是否前往；综合出发推荐属于独立原生 App。云观星也有明确的地点身份与进入条件。 

因此，这次不再把以下内容混入采购和预算：

| 历史材料中的内容 | 本次处理 |
|---|---|
| 旧版“夜空—地图—我的”三入口、综合出发推荐 | 不恢复为当前小程序要求 |
| 原生 App 的地图、原生推送与独立功能 | 不计入小程序默认采购 |
| 旧 Vue 网页星图、全球三维地球、科研级系统 | 不作为当前建设范围 |
| 多套天气模型比较、投票、长期双源采购 | 按你的要求取消 |
| 五万元级地图套餐 | 排除 |
| “12—20 人月、8—30 万元/年”等旧预算 | 功能范围和用量不匹配，不套用 |

第三份报告确实包含旧网页星图与更大的建设范围，其预算不能当作当前小程序报价。fileciteturn2file14

### 2. 已经确定的选择，与尚需确认的删减分开

**已经确定：**不采用五万元地图套餐；只使用一套正式天气预报；合规必须满足；路线数据当前暂不接入。

**尚不能自动视为你已接受：**删除低、中、高分层云；十五天小时天气缩短到十天；缩减历史天气；高清影像只覆盖少数目标；地形只覆盖大湾区。

后面这些是实质功能取舍。**“取消多模型”只表示减少并行预报来源，不等于同意删除专业天气字段。**

### 3. 性价比应当计算全部成本

本次采用的判断是：

> **总成本＝固定许可或订阅＋按量请求＋服务器和下载＋接入测试＋持续维护与核验。**

适合自行处理的，是地形、年度夜光、静态星表等更新较慢的数据；适合购买的，是天气等持续变化的信息；适合复用平台的，是地图、身份和设备能力；停车、夜间开放等，则需要现场和管理方的事实来源。

这能避免两种误判：把免费数据算成零工作量，也把每项外部功能都理解成必须购买长期接口。

## 二、地图、定位、地点搜索：保留微信原生方案

### 推荐方案

**微信自带地图和位置能力，叠加我们自己的观星点、状态、信息面板和专题图层。**

腾讯官方技术资料将地图、定位、地点选择与地图后端搜索、地理编码、路线计算分别列出。DCloud 官方文档也明确说明：小程序自带定位和地图组件由平台向地图厂商付费；开发者自行申请密钥调用地图厂商后端服务，则属于另一种授权范围。 citeturn521029view2

### 逐功能实现

| 功能 | 推荐实现 | 对产品的影响 |
|---|---|---|
| 地图拖动、缩放、道路底图 | 微信原生地图组件 | 保留地图主体验 |
| 正式点、选中、想去、草稿、审核中标记 | 原生标记＋自己的数据与状态 | 可实现，私人身份由后端校验 |
| 点击点位、打开信息面板 | 自有组件 | 不需要采购额外接口 |
| 点聚合、只加载当前可见区域 | 原生能力＋自己的查询 | 按点位规模优化 |
| 获取当前位置 | 微信一次性定位 | 用户主动触发，拒绝后仍可手动使用 |
| 搜索正式观星点 | 搜自己的名称、别名、地区等 | 符合当前公共搜索规则 |
| 投稿选址、计划起点选择 | 微信地点选择窗口 | 搜索窗口由微信控制 |
| 完全自定义全国地点联想 | 当前不购买商业搜索接口 | 改为打开平台选择窗口 |
| 任意坐标自动变成详细地址 | 优先使用选点结果和核验地址 | 缺少来源时显示坐标或区域 |
| 两点直线距离 | 自己计算 | 必须标注“直线距离” |
| 点击“去这里” | 微信位置查看、地图应用交接 | 保留导航交接，不预设结果回传 |
| 地图状态、时间尺、选中状态恢复 | 自有页面逻辑 | 与地图数据采购无直接关系 |

其中，**公共搜索只返回正式观星点**是当前仓库规则。普通地点选择可以用于投稿或计划输入，不能因为取得了坐标，就自动绕过正式点、草稿和审核中提案的身份规则。

### 地形、夜光和云量怎么叠加？

可以优先使用原生图片覆盖物，例如 `MapContext.addGroundOverlay`。后台把数据处理成**有地理范围、按区域和清晰度拆分的图片**，小程序再叠到地图上，不必首先购买一套高级地图可视化产品。

当前产品还有两种不同的图层控制，需要保留：

**主地图：年度夜光与云量选择。**

**地点地形图：地形、光污染两个独立开关，可以分别开关。**

它们不能被实现成同一套互斥规则。 

### 费用与商业边界

**预算按微信原生路径规划，不默认加入五万元级地图费用。** 但 DCloud 的说明不等于腾讯对本项目所有用法的授权合同。正式发布仍需核实实际平台权限、使用规则，以及自制地形、夜光图层的地图内容责任。

特别需要避免：后来接入了需要开发者密钥的商业搜索、路线或高级可视化服务，却继续把整套方案记为“原生地图免费”。citeturn521029view2

## 三、路线：当前暂停自动数据，保留计划和导航交接

这部分本次收束，不再继续围绕腾讯、高德标准套餐反复询价。

| 功能 | 当前处置 |
|---|---|
| 驾车、步行、骑行、公交道路距离与预计用时 | 暂不提供自动结果 |
| “驾车一小时内”“道路距离某范围内”筛选 | 暂停，不能用直线距离替代 |
| 根据车程自动计算出发、到达时间 | 无可靠数据时不计算 |
| 真实道路折线 | 无合法有效路线数据时不画 |
| 手动安排计划、观测时间、交通偏好、清单、备注 | 保留 |
| 停车入口、步行入口、最后一段路说明 | 保留有来源的现场资料 |
| 外部导航 | 保留，并维持实际安全限制 |

圆周旅迹调查证明了“后端提供距离、时间和坐标，前端展示”的技术流程，没有揭示其上游供应商和合同。调查还发现，它会在道路末点与地点标记之间补连接线，所以**图上连接到地点，并不保证整条线都是可通行道路**。fileciteturn2file8

对 Starward，应分别记录**停车点、入口、实际观测点**。没有道路数据的末段可以显示明确的场地说明，不能用一条补线冒充驾车直达。

此前的苹果地图、独立海外路线服务、天地图和自建方案，均未完成本项目所需的条件验证。**它们保留为研究记录，不进入当前正式方案和默认预算。**

## 四、天气：只用一套，和风是有条件的落地首选

### 1. 推荐和风的依据

**接受下面的字段和时间范围取舍时，和风天气是当前证据下较直接的商用落地首选。**

依据是公开价格清楚、按量付费、普通天气字段较完整，而且项目已有对应适配责任。**这不是“已经证明它在广东夜间观星天气上最准”的结论。** 当前没有完成这种当地准确率验证。citeturn521029view0 

“一套天气预报”可以另外获取官方预警和空气质量。这三者提供不同信息，不属于恢复多模型比较。

### 2. 每项天气功能能保留到什么程度？

下面按前两份报告的字段清单整理，结合当前接口复核。fileciteturn2file12 fileciteturn2file13

| 功能 | 和风单一预报组合的处理 |
|---|---|
| 天气现象、温度、体感温度 | 保留 |
| 相对湿度、露点 | 保留 |
| 风速、阵风、风向 | 保留 |
| 降水量、降水概率 | 保留，明确单位和适用时段 |
| 总云量 | 保留 |
| **低云、中云、高云** | **公开小时接口未覆盖，不能从总云量分摊出来** |
| 能见度 | 保留，但不叫作专业天文透明度 |
| 气压 | 是海平面气压，不是山顶地面气压 |
| 未来逐小时预报 | 最多240小时，约十天 |
| 第11—15天 | 天气缺失时如实显示，计划和天文继续可用 |
| 前七天历史天气 | 能取得部分地区历史再分析，不等于任意观星点完整实况 |
| 用户当时看过的旧预报 | 有保存权时可保留，仍标为“当时的预报” |
| 地图云量格子 | 从同一预报的真实点或网格生成 |
| 官方预警 | 独立获取和更新 |
| 空气质量、PM2.5、PM10 | 用对应空气接口，时效分别标注 |
| 气溶胶光学厚度 | 当前组合不默认具备 |
| 专业视宁度、天空透明度 | 普通天气数据不足以直接支持，当前不承诺 |
| 多模型比较、投票、模型分歧 | 按你的要求取消 |

和风当前小时接口的最长范围、字段以及海平面气压定义，可以在官方文档核实。新接口的云量、湿度、降水概率使用 **0—1** 数值，开发时要正确转换成百分比。citeturn521029view1

### 3. 历史天气尤其容易被做错

和风时光机提供最近十天的历史再分析，但查询采用**地区编号**，小时字段也不等于当前小时预报的完整字段集。citeturn401196view0

产品必须分清：

> **当时的预报、事后历史再分析、现场仪器实测。**

把预报存下来，不会让它变成实况；查询到附近城市的历史，也不能换上山顶名称就当作该观星点的现场记录。

### 4. 分层云和十五天不能删时，怎么办？

**改选一套更符合字段要求的主预报，不能让和风缺少的字段由开发者临时补造。**

目前值得保留的单一替代方向，是通过付费 Open-Meteo 获取欧洲 **IFS 9公里预报**。它更接近分层云和约十五天的要求，但大陆公众传播、实际效果、具体套餐及数据留存条件仍未完成确认。其远期原始时间间隔也较长，统一显示为逐小时包含插值，并不代表远期每小时都是独立原始预测。citeturn249504view1

Open-Meteo 免费接口不能直接用于商业生产；官方列有每月100万和500万计费单位的商业档位，但当前可解析价格页仍未给出货币金额。不能直接把旧价当现价，也不能为方便预算而默认购买更贵档。citeturn249504view0

因此，天气的最终选择是：

| 条件 | 选择 |
|---|---|
| 接受缺少分层云、约十天小时预报等调整 | **采用和风一套** |
| 分层云和较长时效必须保留 | **完成单一替代预报的使用条件验证后再定** |
| 苹果天气等此前低价候选 | 留作研究记录，不默认加入当前采购 |

### 5. 地图云量和专业观测条件不要夸大

**地图云量格子可以实现，但不能把少量地点的预报涂成覆盖全区域的高清连续云场。** 自由浏览更多区域、增加真实天气采样点，会增加调用量；不能承诺全国任意视口的连续云量，却只按100个地点预算。

同样，能见度、地面颗粒物、气溶胶、天文透明度、视宁度表达的是不同信息。视宁度主要涉及大气扰动造成的星像抖动和模糊，不能拿一个湿度或空气质量数值直接替代专业结果。原报告也将这些列为需要独立来源或明确估算的能力。fileciteturn2file13

### 6. 官方预警和天气传播是单独的要求

《气象预报发布与传播管理办法》涉及预报来源、发布单位、发布时间，以及预警更新和解除。**买到接口使用权，不自动完成公众传播这一层要求。**citeturn249737view0

正式使用需要确认选定中国地区数据的来源，以及我们的展示、地图着色、缓存、历史回看和收费方式。

预警还必须分清“明确没有预警”和“接口失败”。**请求失败不能显示“暂无预警”，取消综合推荐也不能取消实际危险信息。**

## 五、地形：使用合法高程资料，保留当前周边环境功能

### 推荐方案

**Copernicus GLO-30 地形数据＋自己处理和发布。**

可以把它理解成一份约30米网格的地表高度资料。它描述的是地表表面，可能包含建筑、植被影响；GLO-30与GLO-90有免费许可和明确署名要求。citeturn336055view1

推荐流程：

> 取得适用版本 → 核对质量 → 裁剪实际运营区域 → 生成山体阴影、等高表达和不同清晰度图片 → 自己发布。

### 对应功能

| 功能 | 处理 |
|---|---|
| 查看周围山体、高低起伏 | 保留 |
| 真北向上、东南西北 | 保留 |
| 距离圈、比例尺 | 按实际尺度计算 |
| 2—50公里半径查看 | 按当前方向实现，范围外显示无数据 |
| 地形与光污染独立开关 | 保留 |
| 海拔等信息 | 标注来源，不包装成现场测量 |
| 完整360度地平线遮挡角 | 不属于当前简化后的必要范围 |
| 近处树木、围墙、临时建筑 | 不从30米数据中虚构 |
| 道路是否能走、是否允许进入 | 由场地资料解决 |

这些与当前“基本信息→地形→天文”的连续信息结构及简化地形目标一致。

### 其他方案如何取舍？

**GLO-90**可以用于较大范围概览；国内合法高程服务可以在有实际报价、效果收益后比较。当前没有必要默认购买三维地图套餐，或让每次用户拖动半径都调用外部高程接口。

这里的主要成本是**首次加工、存储、下载和更新**。原始数据30米与最终显示清晰度是两个概念；以前提到的约111米显示层，也不能当作整个项目已完成实测的结论。

**数据许可免费，不等于公开地理图层的内容责任已经解决。** 这一点统一放到后面的商用检查中。

## 六、年度夜光：适合自行处理，但不等于实时天空亮度

### 推荐方案

**许可明确的 EOG 年度 VIIRS 夜光产品＋自己的处理和发布。**

它提供的是卫星看到的地面夜间灯光资料。常用年度产品为约15角秒网格，赤道附近约500米，并包含用于判断观测覆盖的质量资料。EOG 公布了开放许可入口和署名要求，实际采用时要绑定具体产品、年份与获取渠道。citeturn336055view0

### 对应功能与边界

| 功能 | 处理 |
|---|---|
| 主地图光污染颜色层 | 保留 |
| 比较地点周围灯光强弱 | 使用同一年度和处理版本 |
| 地形图内查看周边光源分布 | 保留，独立透明图层 |
| 年度更新 | 后台统一更新，不按用户逐次购买 |
| 用户切换22点、23点 | 年度夜光保持不变 |
| 无数据、观测不足 | 显示未知或质量不足 |
| 精确波特尔等级、仪器天空亮度 | 不能直接从卫星夜光换算并保证 |
| “所有数值误差小于20%” | 没有实样支持，不承诺 |

当前产品已经允许界面使用“光污染”名称，同时在来源中解释其年度卫星估算含义。它没有要求把近处临时灯、天气散射、实测方向天空亮度全部补齐。

NASA Black Marble 是另一种来源方向，但处理方法不同，不能换数据后原封不动沿用旧阈值。实测天空亮度网络属于独立增强，不混入这套年度夜光方案。fileciteturn2file13

**费用判断：开放许可覆盖的资料不需要按每次查看付数据租金，仍要支付获取、加工、存储和下载的实际成本。**

## 七、日月行星、真实星空、天体资料和天象

### 1. 主要天文计算：继续复用现有服务

推荐复用现有 **Astronomy Engine** 计算边界。它采用MIT软件许可；没有必要为了日月升落、月相等能力，重新购买逐次查询的天文接口，或整体重建科研级计算系统。 

| 功能 | 推荐实现 |
|---|---|
| 日月行星高度、方位 | 现有算法按地点与时刻计算 |
| 日出日落、民用/航海/天文晨昏 | 同一计算服务 |
| 月相、照明比例、月升月落 | 同一计算服务 |
| 月亮方向、无月黑夜 | 天文计算与时间区间组合 |
| 银河方向、银河中心位置 | 固定天区资料＋坐标转换 |
| 恒星、行星和目标的几何出现时段 | 按时间、地点计算 |
| 时间尺、跨午夜 | 共用一个观测时刻与观测夜定义 |
| 时区 | 使用版本化规则，不默认采购逐次时区接口 |

这些通常没有逐次外部数据费，但仍有计算、维护和正确性测试成本。

还有一个产品边界要保留：**目标在地平线上，不等于肉眼一定能看见。** 实际可见性还受云、月光、地面灯光、遮挡、设备等影响。

### 2. 星表、星座和中文介绍：静态发布，逐份核权

星表就是恒星名录，包含位置、亮度等数据，适合按版本取得并处理后发布。

前面的资料对 Hipparcos 和部分 Gaia 发布渠道发现过非商业条件；当前仓库说明已描述 Gaia DR3 亮星包的受控获取路径，但**描述获取机制不等于实际商业许可已经核验完成**。fileciteturn2file13 

| 资料 | 推荐方式 |
|---|---|
| 当前实际星表 | 先核对实际文件、版本、来源和许可；有效就复用 |
| HYG星表 | 可作为优先核权候选，核对采用版本和上游汇入权利 |
| 深空天体目录 | 使用OpenNGC等许可清楚的目录 |
| 星座连线、边界、名称 | 按实际数据文件核权 |
| 中文名、别名、简介 | 合法基础事实＋自己编写和审核 |
| 月球、行星纹理、银河背景 | 按实际素材核权，算法许可不覆盖图片版权 |

HYG 作者项目页声明了允许商业使用的署名—相同方式共享许可，但具体采用版本和汇入资料仍需核对。不能把该数据许可直接扩大成“整个小程序都必须开源”。citeturn336055view2

质量上，应优先保证天狼星、织女星、北极星、M31、M42等关键目标的完整性和位置，而不是只追求星表条数。

### 3. 深空真实影像：优先覆盖当前产品已经采用的目标

推荐取得有商业使用和再发布权的真实影像，预先生成不同清晰度，用户放大时再加载细节。

| 方案 | 效果 | 本次判断 |
|---|---|---|
| 当前目标集合的合法影像包 | 选中、放大、看到真实细节 | **优先** |
| 只覆盖少数重点目标 | 工作量和权利更容易控制 | 如果小于当前要求，属于需要确认的删减 |
| 全天天区连续巡天图层 | 任意天区渐进放大 | 更大版权、处理、存储与下载工作，非默认前置 |
| 每次调用公共科研服务取图 | 获取方便 | 不默认具备商业稳定性与再发布权 |

ESA/Hubble 允许许多图片按条件商业使用，但存在署名和例外要求。**SkyView是取图工具，HiPS是组织分级巡天图片的方法，都不自动授予所有内部影像同一种商业许可。**citeturn249504view2 fileciteturn2file13

还必须保证影像对应正确的天区、方向、角尺度和波段。红外图不能包装成肉眼照片，历史拍摄不能叫实时天空；缺少配准信息的宣传图可以放详情页，不应随意贴到星图上。

### 4. 天象：同一资料库服务所有入口

日月食可以由现有算法生成并与NASA目录核查；NASA预测资料有署名转载说明。流星雨采用有权使用、审核过的年度事实，再计算当地辐射方向、黑夜和月光条件。citeturn249504view3 

**事件浏览、事件详情、计划关联共用同一套资料，不重复采购。**

流星雨峰值强度不等于现场每小时一定看到多少颗；全球发生月食，也不等于广东当时能看到。年度资料要更新，但不需要默认建设一个逐用户查询的付费天象系统。

## 八、场地、设施和安全：重要来源是现场与管理方

这部分同样属于外部信息依赖，只是来源通常是人和管理方，而非通用接口。

| 功能 | 最合适的来源 |
|---|---|
| 停车点、步行入口、最后一段路 | 实地核验、管理方、有日期的投稿 |
| 厕所、平台、充电、信号、补给 | 有时效的现场资料 |
| 夜间开放、是否封门、是否预约 | 管理方和有效规则 |
| 合法进入、露营、过夜 | 场地或土地管理规则 |
| 开阔方向、前景、近处光源和遮挡 | 有方向、日期的照片与记录 |
| 临时关闭、道路异常、安全风险 | 官方或管理方更新、待复核现场反馈 |
| 攻略、照片、拍摄经验 | 自有或取得授权的作者内容 |
| 用户新增地点与纠错 | 投稿后审核，再决定是否合入正式点 |

每项重要事实应保存来源、确认时间、适用条件和证据。**投稿、审核通过、正式合入是不同动作**；普通地图收录一个地点，也不能证明它夜间开放、可以露营或能合法进入。

这部分不能记为零成本。实地核验、照片整理、审核、纠错和持续更新，都应单独列账；现在没有实际工作量和报价，不应编一个固定年费。

## 四、天气：只选择和风，不再保留多模型组合

### 1. 为什么最终推荐和风？

我推荐它的依据是：**明确的商业许可和缓存权限、公开按量价格、适合当前境内部署、已有适配基础，以及较低的整体接入成本。**

这是一项综合选型结论，**不是“经过广东实测，和风云量准确率第一”的结论**。当前没有证据支持后一个说法。

同时，和风是一套对外预报产品，供应商内部可能使用多种技术；我们只消费这一套结果，不另建模型对比、投票或选择最晴结果的逻辑。

### 2. 商业展示和缓存有依据

和风开发者协议允许存储、缓存、加工，以及用于商业用途的集合或衍生产品展示、分发。**GeoAPI地理信息服务不享有相同的存储和改编授权。**

所以，多人查看同一个地点时共用一份有效天气缓存，有许可依据；但不能把原始接口转售成另一个天气数据服务，也不能随意复制其地名数据库。citeturn939006view1

来源需要按要求展示。预警和空气质量的原始来源也要保留，不能只放一句“数据来自和风”就删除其他归因信息。citeturn710991view3

### 3. 功能保留和损失必须一起说明

| 天气功能 | 本套方案 |
|---|---|
| 天气现象、温度、体感温度 | 保留 |
| 湿度、露点 | 保留 |
| 风向、风速、阵风 | 保留 |
| 降水量、降水概率 | 保留 |
| 总云量 | 保留 |
| **低云、中云、高云** | **公开小时接口不提供，本套建议移除** |
| 能见度 | 保留，但不称为专业天文透明度 |
| 气压 | 展示海平面气压，不冒充山顶现场气压 |
| 未来逐小时天气 | 最多240小时，约十天 |
| 第11—15天计划、天文 | 继续可用，天气如实缺失 |
| 过去几天回看 | 只展示历史服务真正提供的地区和字段 |
| 当时看过的预报 | 可保存为旧预报，不改称实况 |
| 地图云量格子 | 从同一套真实天气查询点或网格生成 |
| 官方预警 | 独立获取、及时更新 |
| 空气质量、PM2.5、PM10 | 对应空气接口，使用自己的有效时段 |
| 气溶胶光学厚度 | 不纳入本套 |
| 专业视宁度、物理透明度 | 不提供没有可靠来源的数值 |
| 多模型比较、分歧、投票 | 取消 |

小时接口字段与240小时上限有官方文档依据。**取消分层云和缩短远期范围，是本套的实质功能取舍，不是“你不做多模型，就默认同意这些功能消失”。**citeturn433284view1

这份选择没有用第二个免费接口偷偷补回分层云。实际采用时，应把这些取舍写进产品说明，再改现有实现。

### 4. 历史天气和地图云量尤其容易做错

和风时光机提供地区级历史再分析，不能直接当成任意山头的现场实况。**过去保存的预报、事后再分析、现场实测是三种不同资料。**citeturn846641view0

地图云量也一样：100个点的预算只覆盖100个独立查询点。用户自由浏览更多地区、地图增加真实采样，就会增加请求。不能只查少数观星点，却把整片地图涂成看似连续、高清、实时的云场。

### 5. 刷新与故障处理

本次预算固定采用：天气每30分钟、预警每5分钟、当前空气质量每小时、空气预报每天4次。

同一个地点一次取回一段小时预报，用户拖动时间尺不需要每一格重新购买数据。预警失败要显示不可用，不能转换成“暂无预警”。普通天气数据也不能替代官方警报。缓存周期与来源更新应分别管理。citeturn846641view3

## 七、真实星空：替换受限星表，保留核心观测效果

### 1. 日月行星继续自己计算

现有 Astronomy Engine 采用MIT许可，继续用于太阳、月亮、主要行星的位置、升落、晨昏、月相、无月时段和目标几何窗口。没有必要让用户每查看一次，就采购一次天文答案。

时间、地点、时区与跨午夜规则共用一套计算。**几何上出现在地平线上，不等于肉眼一定看得见**；天气、月光、遮挡和设备是另外的信息。

### 2. 亮星目录改选 BSC5P

本次具体推荐：

> **NASA HEASARC 发布的 BSC5P，也就是第五版亮星目录资料表。**

它包含亮星展示需要的位置、亮度、颜色、自行等字段，适合按当前亮度范围生成静态包。NASA针对这个具体数据集的许可字段指向政府作品规则；HEASARC也有资料自由使用政策，并把特定外国任务的限制单独列出。依据这些具体发布材料采用，**不泛化成“NASA网站上什么都能商用”。**citeturn889218view0turn889218view1turn759570view2

实施上要做真正的数据替换、参考历元与单位处理、标识映射，并滤除目录里的非恒星项目。不能只改函数名字，继续加载当前Hipparcos数据。

这会保留消费级真实亮星星空，但它不是最新科研级星表。天狼星、织女星、北极星、典型星座位置和亮度顺序应作为验收样本。

**存在非商业限制或条款冲突的Hipparcos/Gaia发布版本，不再放入本套默认商业数据包。**

### 3. 星座、名称与中文介绍

星座连线可以使用自己绘制、审核的定义，星的位置来自获权目录。中文介绍自己编写和审核，不批量复制来源不明的百科或星座插画。

完整星座边界文件、名称对照表、贴图是独立资料，不能因为天文算法是MIT，就自动把所有素材当成同一许可。

### 4. 深空天体采用 OpenNGC

保留当前目标范围的OpenNGC目录。其指定版本明确采用 **CC BY-SA 4.0**，需要落实数据的署名和相同方式共享等义务；不等于整个小程序代码必须开源。

项目许可证链接也应修正为实际的：

`LICENSES/CC-BY-SA-4.0.txt`

不是失效的 `/LICENSE`。

## 八、深空真实影像：使用指定公开产品，不靠来源不明图片

**推荐 IRSA 管理的 WISE All-Sky 公开影像，优先衔接当前12微米波段。**

IRSA明确区分公开资料、专有资料和受版权限制资料：公开资料没有使用限制，而DSS等被特别列出版权要求。因此这里只采用指定WISE公开产品，不能把所有SkyView或巡天图层一概判为可商用。citeturn440363view2turn759570view1

为当前已采用的目标集合准备图像，预先制作不同清晰度，用户放大时逐级加载。**不把原有约51个星系/星云目标，悄悄缩减为只做M31、M42两张演示图。**

必须保留天区、方向、角尺度和波段信息，保证影像贴对位置。它是真实历史红外观测，不是实时拍摄，也不是肉眼颜色。

全天任意天区最高分辨率巡天，是更大的资产与下载范围；当前100GB预算不保证覆盖这一扩展。

## 九、天象：保留日月食、常见流星雨和计划关联

### 日月食

继续由现有算法计算，使用NASA预测资料核验；对应资料有署名转载说明。全球发生事件与当地可见性分开，太阳观测保留防护提醒。citeturn907434view2

### 流星雨

本次找到的明确许可来源是 **Global Meteor Network，简称GMN，全球流星网络**。其高层数据产品采用CC BY 4.0。citeturn440363view1

推荐使用获权历史资料，整理并审核常见流星雨的活动期、辐射方向和统计参考，再计算目标日期、当地高度、月光和黑夜条件。

**这不是下载后就自动得到一份当年完整预报。** 首次整理、计算和验证需要工作；历史统计峰值不能包装成当年精确极大时刻或突发流量预测。

| 20个 | 220,400次 | **约119.28元** |

这是按30天、全天持续刷新计算的算例。临时测试点按需查询，实际可以更少；反复自动化测试、不同环境重复刷新，也可能更多。**不能只看内测人数少，就默认不会超额度。**

### 内测分两类处理

**界面、逻辑、异常测试：**在本地使用明确标识的固定测试数据，测试空数据、过期、预警失败、地图状态恢复等，不需要每次都请求真实供应商。

**真实接入测试：**选少量真实地点，用同一正式来源验证天气、坐标、图片、设备方向、权限和数据更新时间。

前一种不能替代后一种，但两者配合能减少很多无效费用。

### 实际能省到多少？

| 内测方式 | 费用判断 |
|---|---|
| 本地运行＋已有设备＋少量真实查询 | **新增云/API费用可以接近0** |
| 复用已有服务器＋少量图片下载 | 主要增加少量存储、下载和超额请求费用 |
| 需要新开独立测试服务器 | 腾讯云公开2核4GB参照为**65元/月**，其他费用另计 |
| 要验证生产并发、高可用、真实消息投递 | 需要对应真实环境与权限，不能仅用本地模拟完成 |

65元是云主机公开套餐价，不是所有测试负载的性能保证。citeturn915548view0

还有一个必须纠正的观念：**“内测、不收费”不自动等于供应商所说的“非商业使用”。** 例如Open-Meteo条款把整合进商业产品、商业机构的非公开研究列入商业用途。因此，我不建议为了内测省几十元，重新引入只允许非商业使用的来源。citeturn272874view1

**对你而言，合理路径是：同一代码和数据结构、同一获准来源，内测少量使用，上线扩大额度和服务器。不是先用受限数据做完，再临时解决商业许可。**

## 三、你说的名称是 OSM＋OSRM，但它不是一整个地图平台

你理解的“下载数据和算法，放到自己服务器上运行”，**方向正确**。需要拆开两个名字：

**OSM：OpenStreetMap，开放地图数据。** 可以包含道路、路口、步道、部分地点及通行属性。

**OSRM：Open Source Routing Machine，开源路线计算软件。** 它读取道路数据，计算两个或多个坐标之间的路线、距离、预计用时。官方支持驾车、骑行和步行规则。citeturn981578view1turn646854search2

### 它们如何工作？

```text
下载目标区域的开放道路数据
        ↓
用 OSRM 处理成适合快速查询的道路网络
        ↓
在自己的服务器启动路线接口
        ↓
小程序传起点、终点、交通方式
        ↓
返回道路距离、预计用时、路线坐标
```

OSRM官方已经提供容器和处理流程。**你不需要自己编写路径搜索算法，也不必把全国道路地图一并重做。**citeturn600236view0

这里“离线”指不必每次查询外部地图厂商；**用户手机通常仍要联网访问你的服务器**，不会自动变成手机断网也能计算路线。

### 选点、搜点和路线，是不同能力

| 能力 | OSM＋OSRM是否直接解决？ |
|---|---|
| 根据两个坐标计算道路距离 | **可以** |
| 估计驾车、步行、骑行时间 | **可以，依据道路和速度规则** |
| 返回路线坐标供地图画线 | **可以** |
| 计算当前位置到多个候选点的距离、时间 | **可以** |
| 在地图上点一下选坐标 | 由地图界面实现，继续用微信即可 |
| 输入“某某公园”搜索名称 | **OSRM不负责**，要另外的地点搜索 |
| 把坐标变成完整地址 | **OSRM不负责** |
| 提供道路、地名等底图 | **OSRM不是完整底图服务** |
| 实时堵车、事故、临时封路 | **下载道路包不会自带这些实时数据** |
| 公交换乘、首末班、班次等待时间 | **不包含，需要另外的数据和计算系统** |

OSRM的主要接口是道路吸附、路线、距离/时间矩阵等。名称搜索一般需要Nominatim等另一套系统；公交计算则需要班次、站点等数据，例如OpenTripPlanner会另外读取公交时刻表数据。citeturn893582view1turn893582view2turn981578view4

另外，驾车、步行、骑行通常需要分别处理对应规则和路线数据，**不能只把请求中的“驾车”改成“步行”，就默认同一份已处理数据具备正确步行规则。**citeturn600236view1

### 对你的项目，最值得评估的是“只自建路线”

保持：

> **微信显示地图和选点＋自己搜索观星点＋OSRM提供道路距离和普通预计用时。**

不额外建设全国地点搜索、地址库和底图。

这能补回“这个观星点沿道路大约多远、大概需要多久”的一部分产品价值。但预计用时应标明**未计实时路况**；它也不能保证偏远步道、停车入口和夜间开放状态正确。

**这与“自己造一个高德”相比，工作范围小很多。**

## 六、自建路线的商业化边界，不能再漏掉

**OSRM软件采用允许商业使用的BSD许可；OSM数据允许使用和加工，但需要遵守署名及衍生数据库等许可义务。** 所以，这套组合在代码、数据许可层面具备商用基础，没有五万元的软件年费。citeturn646854search2turn981578view1

但两件事必须另外处理：

**下载的是开放原始数据，不是抓取地图网站图片。** OSM公共瓦片服务器禁止批量下载制作离线包；公共Nominatim也有总量限制，禁止自动补全和系统性抓取，不能顺手当成免费商用搜索后台。citeturn981578view2turn981578view3

**公开提供中国地区路线仍需核对实际地理服务、地图表达、坐标与底图组合规则。** “只在后端算、不画底图”不自动证明所有国内要求都不适用；开源许可不能代替这一层确认。citeturn600236view4

因此，OSRM目前应定位为：

> **有低成本技术路径、值得做有限验证的候选；还不是已经确认可以直接商业上线的完整替代。**

### 对你现在的安排，我的建议

**先保持同一套获准数据做低成本内测；路线只验证“区域道路距离＋非实时预计用时”，继续使用微信地图和选点，不自建搜索与底图。**

这项验证可以先限制在 **0.5—2人日**，用真实观星点的停车入口、山路和海边地点检查数据质量，同时记录内存、处理时间和查询速度。结果合适，再投入后面的5—10人日接入工作。

**最终可记住三个数字：内测的新增API费用可以接近0；上一套有限范围技术运行预算约820元/月；增加低并发区域路线，先按再加100—300元/月评估。三个数字都对应明确范围，不代表原始全部功能和商业手续已被同一个价格包下。**

几何上处于地平线上，不等于现场一定能看见；天气、月光、地形和近处遮挡仍由各自资料说明。

### 2. 亮星目录：采用HEASARC发布的BSC5P

推荐商业数据包采用**NASA HEASARC具体发布的BSC5P亮星目录**。它提供亮星位置、亮度、颜色、自行等资料，适合当前消费级真实星空用途。该具体数据集的许可元数据及HEASARC使用政策，是采用依据；不扩展成“NASA网站上的所有内容都可任意使用”。citeturn206458view0turn206458view1turn593167view2

实施时需要真正替换数据及相应处理，核对参考历元、单位、标识并过滤非恒星项目。**不能只改函数名，继续加载存在非商业许可问题的旧星表。**

本套不默认打包有非商业限制、又没有额外授权的Hipparcos或Gaia发布版本。

与原来的效果差异：保留主要亮星、位置、亮度和方向展示；不声称提供最新科研级全量星表。应验证天狼星、织女星、北极星等关键目标，而不只检查“加载了多少条”。

### 3. 星座、中文介绍和深空目录

星座连线优先使用自己绘制、审核的定义；中文名、别名和简介使用合法基础事实与自己的审核内容。来源不明的百科文字、星座插画和贴图不随目录一起默认采用。

深空目录采用**OpenNGC**。其指定版本明确采用CC BY-SA 4.0，需要落实数据层面的署名及相同方式共享要求；并非整个小程序代码都要因此开放。

### 4. 深空真实影像：采用指定WISE公开产品

采用IRSA管理的**指定WISE公开影像**，按当前已采用目标集合制作逐级清晰的图片。用户放大时加载细节，不为省事把现有目标缩成两张演示图。

IRSA将公开资料与专有、受版权限制资料分开；公开数据使用规则不能推广到所有SkyView图层、DSS或其他巡天素材。citeturn593167view3

展示必须保留正确天区、方向、角尺度、波段与来源。12微米影像是历史红外观测，不能包装成实时拍摄或肉眼颜色。

**全天任意天区无限高清影像不在当前资产预算里。** 扩充目标和清晰度可继续沿用同一管道，但需要重新核算制作、存储和下载。

### 5. 日月食、流星雨与事件提醒

日月食继续用现有算法及有使用依据的NASA资料核验；本地可见性由地点和时间计算。

流星雨采用**GMN全球流星网络已许可资料，经过整理、审核后形成常年活动参考**。GMN高层数据产品采用CC BY 4.0，但它提供的观测资料不会自动变成当年完整预测年历。citeturn206458view3

因此：

| 事件能力 | 本套提供 |
|---|---|
| 日月食发生与当地几何可见性 | 保留 |
| 常见流星雨活动期、辐射方向、历史统计参考 | 通过获权资料整理后提供 |
| 当地黑夜、月光、辐射点高度 | 自己计算 |
| 事件浏览、详情、计划关联 | 共用同一目录 |
| 当年特殊爆发、精确极大时刻和流量预测 | **当前来源不能等价覆盖，不作伪预测** |

资料更新不能自动修改用户已经保存的计划。事件本身的全球强度，也不能直接写成“你现场每小时一定看到多少颗”。

### 2. 天气、预警与空气质量

每个查询点每月：

|---|---:|

> 950,000 × 0.0007＋102,000 × 0.0005  
> ＝**716元/月**。citeturn690333view1

一年期节省计划系数为0.7，同样用量的折后消耗：

> 716 × 0.7＝**501.20元/月**。citeturn690333view2

这个折扣需要预付承诺金额，未用完有到期失效风险；它不是每月501元无限套餐。用量尚未稳定时先按量，不为了折扣过量预付。

### 8. 820元不包含什么？

因此：

> **完整经营成本＝技术运行费用＋必要额外合同及主体平台费用＋开发与运营人工。**

这几部分分别列账。没有报价的不能填零，也不能用一个随意区间冒充真实成本。

## 十一、内测怎么做，才能低成本且不为商用重来？

**内测继续使用同一套有权用于商业产品的来源，减少真实查询量；不要专门换成只能非商业使用的数据。**

界面、状态、异常与恢复测试在本地使用明确标识的固定测试数据；真实接入测试选少量地点。固定测试数据不能替代真实天气、真机方向、地图叠加与消息投递验证。

沿用相同刷新假设：

| 持续维护测试点 | 月请求 | 天气相关费用 |
|---:|---:|---:|
| 4个 | 44,080 | 0元 |
| 5个 | 55,100 | 约3.57元 |
| 10个 | 110,200 | 约42.14元 |

以上利用的是和风本来就有的免费请求额度，不是把“内测”当作免除商业许可的理由。citeturn690333view1

复用已有电脑和服务器时，新增现金支出可以接近零；新开独立测试机则按实际套餐付费。正式上线主要扩大额度、资产和服务器，并完成相应发布条件，核心领域模型和数据结构不重做。

## 十二、最终执行结论

这轮选型可以固定下来：

| 项目 | 执行方向 |
|---|---|
| 地图 | 默认原生地图、自有点位、平台选点、外部导航 |
| 路线 | 当前不接自动道路距离和用时，不建设OSRM |
| 天气 | 和风唯一主预报；保留小时总云量；删除分层云和多模型 |
| 地形、夜光 | GLO-30-F与EOG年度夜光按合法版本加工发布 |
| 星空 | 现有算法＋选定亮星和深空目录，实际替换受限资料 |
| 真实影像 | 指定WISE公开产品，覆盖当前采用的目标集合 |
| 天象 | 现有日月食计算；获权流星资料整理，明确常年参考边界 |
| 账号、计划、内容、设备 | 复用现有后端和微信能力，完成权限与真实闭环 |
| 商业发布 | 完成地图实际使用及地理表达、天气来源与传播两项具体核定 |
| 成本 | **约820元/月年付口径；约1080元/月常规口径**，按固定用量执行 |

**这套方案保留了主要观星体验，最大的主动舍弃是路线具体信息；低中高分层云已经删除，不再是缺口。其余差异主要集中在十天天气时域、历史资料性质、平台搜索界面、底图定制、特殊天象和资料覆盖范围。**

**月成本按820元这一固定口径执行预算，不再把不同地点数、刷新周期和服务器范围混成同一个数字。商业使用有依据的数据直接落实许可义务；两项尚未完成的项目条件单独处理，完成后才能正式发布对应能力。**

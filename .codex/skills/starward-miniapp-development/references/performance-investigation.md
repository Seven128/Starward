# Performance investigations in WEAPP

Use this reference for slow launch, requests, data updates, interactions, rendering or memory growth in a Mini Program. Keep the product's current requirements and [development measurement boundaries](../../../../project_context/development-workflow/development-feedback.md#performance-measurement-boundaries). Device operation and acceptance remain with the existing device skill; this reference does not open another session or define a new acceptance suite.

## Start from the decision

Separate the user's symptom from its possible causes. Interaction delay, increasing process memory and a later exit are different observations; success on one does not close the others. State the next decision, the competing explanations and an observation whose plausible results would change the next action. Reuse existing evidence that already answers it. A small code change or a cheap measurement is useful only when it resolves that uncertainty.

Prefer a working measurement or profiling route that distinguishes those explanations. Record its capability as **unverified**, **blocked at a named boundary**, **unsupported under current conditions**, or **validated by a useful target sample**. Unverified is not unsupported. Check transport, execution target, capture, export and useful interpretation separately; one successful boundary does not establish the next. Perform one bounded check at the first unresolved boundary. A menu, API name, completed command or registered data source is not a successful profile. A command timeout does not establish cancellation or absence of effects: inspect actual state before retrying or replacing the session. Apply successful and failed checks only to the operation, target and conditions they established. A failed session or missing automation method does not establish that the underlying runtime capability is unsupported.

Choose the least costly observation whose plausible outcomes can change the pending decision. Existing evidence, a cheaper counter or a controlled change may replace a profiler when it distinguishes the relevant explanations. If it answers only a supporting question, treat it as supplementary: retain the unanswered question and the observation still needed to resolve it. Preparation already spent or easier tool access does not make an observation a substitute. Do not build a complete profiling stack when existing evidence already decides the issue.

Before adopting an additional profiler or bridge, check current compatibility, target/scene identity and restart/storage effects. Do not install duplicate automation stacks or enable debug ports speculatively.

When a chosen observation remains necessary but cannot run, identify the current blocking boundary and the evidence for it before deferring. Check or restore only the affected readiness through an available authorized route. If that is not presently possible, retain in existing task state the unanswered question, required condition or minimal human action, and next observation on resumption. Independent work can continue, but does not close the blocked result or justify a repair for an unexplained cause. Deferring human actions changes their timing, not the required evidence. Resume when the blocking condition changes; do not repeatedly retry unchanged state.

## Use controls to distinguish remaining causes

For a controlled change, identify what work is removed and what must continue. Compare matching data, cache and lifecycle conditions; check actual nonempty workload and executed calls, not only configuration or cache hit rate. A cache miss may invoke a native method many times. Preserve the feedback from accepted state to real resource demand and retirement, not just final pixels or item counts. A diagnostic that freezes pixels or substitutes success is useful only within its declared scope; return to the complete product path before adopting a repair. Changing execution rate can also change allocation and collection cadence; counts need not be identical when improved throughput is the outcome, but the required work must remain comparable. Preserve output correctness and state the scope of sampled comparisons; endpoint checks do not establish every-frame equivalence.

If a control is narrowed to preserve safety or workload, restate the causal question and reassess its value before running it. A valid negative result limits that narrow hypothesis; it does not automatically justify disabling an adjacent feature or changing implementation shape while leaving the same leading explanations intact. Select the next observation from the remaining uncertainty.

## One run, explicit windows

Record only metadata needed for this question:

- Source plus uncommitted diagnostic identity, complete bundle identity, mode and relevant data/surface generation.
- Target process identity and execution layer. Keep any necessary raw device identifiers in the existing private evidence owner; a process count is not a target binding.
- Clock source, units, availability and resolution or observed uncertainty; actual start/stop events; the interval covered by every counter and memory sample. Distinguish device-side time from host command latency.
- Work that actually happened, failure/retirement and any observer effects that could invalidate comparison.

When a decision requires combining separate observations, distinguish the interval in which the measured behavior actually occurred from each recording's coverage. Establish the relevant operation and target identity through observed bindings, and relate time through a shared event or bounded clock relationship; labels, file order and similar timestamps alone are insufficient. Preserve clock uncertainty and discontinuities. Missing associations limit the conclusion and cannot be reconstructed by assumption. Keep sensitive correlation details with the existing private evidence owner. Reuse sufficient evidence; a new identifier, clock adapter or recording is needed only when it resolves a material gap.

Verify the target clock rather than inferring monotonicity or sufficient precision from an API name. Retain the limited meaning of valid wall-clock millisecond intervals. Mark backward, mixed-clock or unresolved sub-resolution intervals invalid or unknown instead of clamping them to zero. Cost aggregates must identify known-cost subtotals and valid/unknown coverage. A synchronous stage span is elapsed duration, not automatically thread CPU time; independent stage maxima cannot be summed into a frame time or converted into physical FPS. Version producer and consumer contracts when these semantics change.

For sustained-growth observations, useful phases are ready-idle, active workload and idle drain before cancel/hide. Their durations depend on the known failure interval and current question. An export deadline is not an observed stop. Let the existing product owner perform bounded termination with its current-run/lifecycle guards; slow host screenshots, transport latency or model response time must not determine when the app stops. Keep input authorization with the device owner.

Do not divide a whole watch interval's memory delta by a shorter workload window's count. Report qualitative growth if windows cannot be aligned. Keep Android PSS, RSS and Swap meanings distinct, retaining the source's accounting rules rather than adding overlapping fields. Unknown does not identify a JS isolate or allocator. Host-process measurements include engine work; a bounded run or decline after hide does not establish product-exclusive memory, immediate GPU reclamation or an entire-session leak verdict.

Distinguish encoded files, native decodes, GPU residents and transient upload/copy costs. Serialized cache bytes and logical handle counts are not retained heap or physical memory. High memory remaining after activity stops alone is not proof of a leak; use the relevant allocation or retention evidence for that claim.

## Associate work before optimizing it away

For input latency, associate an intent sequence with its admitted preparation and first accepted result. Time strings alone do not distinguish A → B → A or repeated rendering of the final instant. Separate superseded intents, failed/cancelled attempts and duplicate presentations. Conditional matches to only the latest intent are not an unbiased latency distribution.

Request count minus paint count is not wasted preparation. Repeated requests may reuse the same prepared value or drive animation. A scheduling change needs evidence of unconsumed preparation and its cost, plus latest-intent and terminal-state behavior. Preserve the current authoritative scheduling/state owners and real resource-demand ownership; do not introduce competing writers during diagnosis.

Keep producer semantics with each exported field: name, unit, reset/start boundary and covered target. Page setData callbacks, payload key counts, React Profiler data, native copy returns and physical presentation are separate measures. Expand a Page observer to a component only when the current runtime actually routes relevant updates there. A framework's possible component path does not establish that the current screen uses it.

Prefer a small named machine-readable summary through an existing bounded collection path or the tool's native export. A project-specific collector is not a prerequisite for using an adequate profile. Avoid relying on screenshots and manual transcription of abbreviated counters. When changing a collection protocol, version its semantics and retain exact retry/idempotency and privacy rules. Keep probes bounded, non-sensitive and outside per-frame product-state churn; do not add per-frame full JSON, reports, payloads, frame history or closures to the recorder. Add resource counters only for the unresolved owner, at existing create/use/retire boundaries. Release probe resources even when an optional capability is absent, and remove temporary probes from the delivered ordinary build.

## Choose the first useful measurement

Select by the unresolved cause and required detail. The adopted high-load Sky route combines ordinary-preview source observations with relevant Android tools. The application recorder is source instrumentation; Perfetto supplies separate system/provider evidence. Use only the parts that can change the next decision.

### Why high-memory Sky does not use true-debug profiling

**Do not use WeChat DevTools true-debug Heap/Memory/Performance as the collection route for the currently observed high-memory Sky workload.** Entering Sky increases debug round-trip time and the connection changes to disconnected; the required snapshot/record cannot be reliably collected in the scene being investigated. The phone can remain usable after that disconnection. This establishes a failed diagnostic channel, not whether CPU, memory or networking caused it, and not an application crash or leak verdict.

Official DevTools still owns compilation, ordinary preview and its other working development operations. Keep previously valid CPU/allocation profiles and exact source maps. Ordinary-preview delivery does not depend on a live true-debug channel. The phone's separate native CPU-profile menu also needs its own successful capture/export qualification; do not assume it is a working fallback.

Do not repeat the same reconnect, Heap/Timeline, version-switch or long-pressure sequence. Reconsider the failed route only when a relevant target, tool version, eligibility or supported configuration change provides a concrete reason it may now work. Check the first failed boundary once with a bounded real workload; stop if it fails again. Preserve pairing and the required VPN/TUN. No private WeChat IPC, raw CDP bridge, storage clearing or forced GC is a substitute for a working supported route. This decision is scoped to the failed target conditions, not a permanent ban on every Mini Program's profiler.

### Ordinary-preview observations when remote debugging drops

| Unresolved question | First useful route | Required distinction |
| --- | --- | --- |
| Launch or navigation readiness | Actual lifecycle/wx performance entries, package/request timing and useful output | Cold versus warm entry; first event/frame versus completed user journey. |
| Input delay, stale requests or wasted preparation | Existing recorder at intent, request, validated-result, preparation, draw and accepted-result owners | Join actual identities; retain cancellation, supersession and missing links. Request count minus paint count is not wasted work without preparation cost. |
| Expensive JS work | Reuse source-mapped CPU/allocation evidence; add narrowly scoped function/stage timing where attribution remains unresolved | Wall elapsed is not CPU time. Fresh arbitrary JS call-stack recording is not established by the ordinary-preview recorder. |
| Excessive UI/data updates | Actual Page/component update counts, measured payload bytes and supported completion intervals | Keys are not bytes; setData/nextTick/copy completion is not physical presentation. Use [React Profiler](https://legacy.reactjs.org/docs/profiler.html) only with a qualified profiling build. |
| Thread scheduling or process pressure | Local Android Perfetto plus local Trace Processor; targeted `dumpsys meminfo` where needed | Bind the resumed Mini Program to its actual Appbrand process instance. Process counters do not identify JS objects, an isolate or an allocating function. |
| JS object growth or resource lifetime | Bounded allocation/lifetime and actual-owner observations described below | Distinguish allocation churn, surviving samples, current cache data and an observed strong edge. |
| Rendering/native/GPU cost | Scoped renderer observations and supported native/system sources, with actual output | Submission, CPU execution, GPU completion and visible presentation are separate boundaries. Missing FrameTimeline/timer-query data is unavailable, not zero. |
| Unexpected exit | Target package exit record and known process's bounded crash/error logs | OS exit mechanism, V8 heap exhaustion and the responsible business owner require different evidence. |

For Perfetto, resolve the resumed Activity to the actual process; never choose `appbrand0` or `JSRuntimeLooper` by name alone. Bind PID plus process start identity before/after capture and in the trace. Use only supported sources needed for the question. The documented `perfetto --txt -c - -o <owned-trace>` stdin route can resolve a trace-service configuration-file access failure without elevation. Export and parse locally; check actual recording windows, completed scheduled slices and data loss. Requested but absent target data remain unavailable.

Relate separate recordings only through a shared event or bounded clock relationship. Otherwise keep their findings separate. Ordinary preview, development/vConsole enabled, remote debugging, simulator execution and a release build are different conditions. Preserve those conditions when comparing results.

### Memory attribution without the remote-debug channel

**Locate the memory domain first.** Use foreground-bound PSS/RSS/Swap/native/graphics observations and scoped exit logs to distinguish process pressure from an attributable VM/allocator finding. Keep overlapping accounting fields separate. Android `APP CRASH(NATIVE)`/SIGABRT plus a V8 fatal allocation record on the logical thread can establish V8 OOM; the OS category alone does not make it a native-only leak. Exit-info memory is the last recorded sample, not an exact reading at death. Stop input after an unexpected foreground loss and inspect only the relevant process/package evidence. A requested process termination is not product recovery.

**Use MemoryInfra/GC only for its observed provider coverage.** Query public Perfetto producers and bind the target process to `org.chromium.memory_instrumentation`/`track_event`. Registration alone does not establish working detailed dumps. Reuse a valid finite configuration with privacy filtering. Parse actual allocator nodes, capacity/used/external values and GC isolate/thread identities. A Blink renderer isolate does not cover the appservice logical heap. Do not sum hierarchical/suballocation aliases or treat an allocator parent as independent active bytes. Export nested JSON arguments as hexadecimal strings for reliable local decoding when CSV quoting is insufficient.

**Follow selected objects at their real allocation sites.** Reuse source attribution, qualify WeakRef on the phone, and retain only bounded weak witnesses plus scalars. Keep initial and recent samples separate; record selection/eviction, quantity, errors and omitted points. Verify locally that a deliberate strong owner is observable and that the probe itself does not retain released objects. Unsupported liveness is unavailable. Deterministic sampling is not a population estimate; array slots are not heap bytes, and typed views/backings overlap. `deref()` keeps objects alive through its job. A surviving sample alone proves neither a strong retaining path nor a leak; collected JS upload objects do not prove native/GPU release.

**Trace ownership only where it resolves the next explanation.** Match sampled identities at actual cache writes, aggregate membership, request/paint/accepted boundaries and current owner assignments/clears. Distinguish an admitted request, an accepted use and the value currently occupying a slot. Compare survivors with collected objects; acceptance alone need not explain survival. A replaced old entry and its live aggregate raise a specific outer-owner question, without establishing the unknown root. If tracking stops at Pause, label frozen fields last-observed; keep actual slot changes observable through the required drain/retirement when that is the question.

For a framework-owned reference, use only version-verified application/framework objects and known fields. The existing Taro route uses public `eventSource`/`internalInstanceKey` to reach the two owned Sky Canvas Fibers, then bounded descriptor reads of hook/ref/queue fields. Verify this entrance on the target. Do not invoke getters, inspect opaque function closures, enumerate arbitrary properties or serialize product graphs. Keep traversal, depth, sample and export limits; report skipped/capped coverage and scan cost. Host-linked and alternate Fibers do not identify the currently committed tree by themselves. Preserve the original scan timestamp when later packets carry its result forward. No match means only no match in the covered fields.

**Preserve results before the known failure interval.** Reuse the private collector with independent scalar checkpoints, a bounded single-flight queue, bounded attempts, immutable sequence files and exact-byte retries. Acknowledgement requires successful storage; read back new files, binding and hashes during the workload, before its final deadline. Reserve terminal capacity and preserve completed originals before freeing collector slots. Saved host files no longer depend on phone-VM survival; unacknowledged points remain missing after an exit. This is not a guarantee against every network/host failure. Stop new tracking at the relevant lifecycle boundary, retain only weak drain witnesses and release diagnostic resources at the end.

### Collect and qualify a target profile

1. **Reuse and bind.** Locate the existing capture owner and valid evidence. Bind current source, complete compiled candidate, actual target scene, process instance and relevant VM/provider. Confirm nonempty required work and the symptom under the measurement mode; for Sky, preserve the required view, landscape, actual BSC/loaded-SAO work and data/cache state. A visible version or completed command alone is insufficient.
2. **Bound the experiment.** State the competing explanations, decisive fields and stop condition. Set a workload duration through the actual device-side product owner with same-run/lifecycle guards. Allow required idle drain and export early enough to survive the known failure window. Verify earlier profilers have stopped; timeout or a closed menu is not termination proof.
3. **Collect through the existing owner.** Use supported public tools and the project device guard. Add only missing scalar/identity observations at real boundaries; do not change product state or retain frame/payload history to measure it. Keep collector/protocol and complete diagnostic build compatible. Retry an immutable export instead of replaying the workload.
4. **Qualify the data.** Require new parseable local files, matching source/target binding, valid actual windows, useful nonempty coverage, and checked omissions/errors. For stacks, use the captured build's source maps and retain unmapped attribution. Qualify CPU samples, GC events, heap counters and rendering evidence separately. Preserve clock uncertainty, nesting, overlapping units and observer overhead; do not infer missing middle links or call wall time CPU/FPS.
5. **Use the result.** State which explanation it supports or limits and how the next repair changes. A working route needs useful decision-level information, not a particular artifact format. Reuse that route once qualified; tool success is separate from root-cause identification, repair benefit and full product acceptance. If the data cannot distinguish the remaining causes, name the exact missing boundary rather than claiming completion or repeating the same trial.

Current readiness, exact configurations and raw evidence locations remain with the active task owner.

### Capability ceiling and escalation

This combination can deepen business-code timing, asynchronous associations and selected object/resource ownership by adding a justified observation. The added capability still needs validation; it is not already present merely because source code is editable. Larger sample/buffer limits do not supply inaccessible information and can disturb the measured workload. Measure probe cost and choose bounded phases; do not run expensive ownership scans per frame.

Current coverage does not promise an arbitrary logical-VM CPU recording, a complete retained-object graph, JavaScript closure internals, native allocation stacks or complete GPU ownership. Native allocation profiling requires host-process eligibility; Mini Program debug does not grant Android profileability. Missing eligibility produces unavailable evidence, not zero allocations. A finite high-memory success also does not certify unlimited-duration or cross-device stability.

When a remaining decision genuinely needs one of those missing capabilities, select a supported targeted observation or profile that can provide it and qualify only the first unresolved boundary. For an eligible CPU/Memory route, confirm actual execution layer/isolate, useful exported stacks/objects and workload equivalence; a connected badge or phone-like metadata is insufficient. LAN/WAN transport and phone/desktop execution are different facts. Allocation sampling, total churn, heap comparison and retaining paths have different meanings. Official documentation explains semantics, not support in the current WeChat target. Do not re-open the failed high-memory true-debug path without the changed-condition basis above, or withhold independent repairs waiting for a universal profiler.

## Keep the loop economical

Reuse verified sessions, any existing collection path, the source boundary and complete build pipeline. At the next necessary diagnostic edit, consolidate repeated build variants into a finite run-locked mode under the same owner if this reduces work; do not build a general profiler framework first. Archive required evidence before generation refresh, then retire only exact owned obsolete resources.

Reopen a failed tool route only when its relevant version, permission, target or evidence has changed. Once a controlled experiment answers its question, move to its chosen branch. Do not split an effective small product repair into many adjacent low-information variants solely to identify every internal primitive. Conversely, if the removed work is near zero and growth persists, stop attributing that growth to it.

Verify the repair on the full affected product path and explicit obligations. Reuse valid correctness and lifecycle evidence. Durations, sample counts and latency budgets from a research report are proposals, not automatic new gates. Keep diagnosis, repair, target acceptance and tool limitations distinct.

After a useful observation, state the product-facing result before starting another: what is now fixed or located, which explanation the evidence limits, what remains unanswered, and how that changes the next action. Keep raw attempts with their evidence owner. A succession of successful captures or test counts is not a progress explanation; if the proposed next sample cannot change an implementation or completion decision, advance the work instead.

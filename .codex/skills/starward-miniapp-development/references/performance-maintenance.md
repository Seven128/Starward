## Start at the changed owner

Trace input → authoritative state/data → work → accepted result → retirement through real callers. Put a shared rule in its existing owner and migrate affected consumers together. Shared code can have independent per-consumer state; different time validity, source quality, cancellation or trust semantics need explicit adapters. Similar rendering alone does not justify one universal state machine. A file-cache or native-installation repair can benefit every caller; a terrain-source preparation change does not produce cloud or night-light data.

Project choices and exact limits stay with [Map data and raster ownership](../../../../project_context/architecture/runtime-and-domain.md#mini-program-terrain-and-directional-light-evidence), [Sky performance](../../../../project_context/architecture/runtime-and-domain.md#cloud-sky-performance) and [maintenance boundaries](../../../../project_context/architecture/maintenance-boundaries.md). ## Avoid unintended lifetime extension

- A closure is not inherently a leak. Follow the reachable owner that stores it: Query/cache entries, subscriptions, native callbacks and timers can outlive the render that created them. Give stored callbacks only their required identity, service and live-reader handle; do not incidentally retain the complete page, report, frame, image collection or observer. `ref` is a strong reference too. [Reachability and GC](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Memory_management), [closures](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Closures).
- Retire a page reader independently from reusable response data. Hide, replacement and unmount must clear the relevant callback/handle; cleanup for an old reader must not clear its successor. An existing cache TTL does not justify keeping a discarded render alive until expiry. WeakMap/WeakRef are not substitutes for explicit ownership, bounded caches or required cleanup.
- Distinguish retention from stale capture. A held interaction can retain its original authorization/Context token while reading the latest eligible supply from that owner at execution time. Replacing every callback with a fresh closure or indiscriminately using refs can break cancellation or authority checks; preserve both lifetimes explicitly.
- Pair registrations, timers, RAF, subscriptions and native allocations with their actual owner and retirement path. Page hide may leave React mounted; model hide and unmount separately where the product does. Keep cleanup safe after partial setup and repeated replacement. React Effect cleanup mirrors its setup, but does not itself establish a Mini Program native release. [React Effect lifecycle](https://react.dev/reference/react/useEffect).
- When an observed compiler transformation has changed a cached callback's capture scope, preserve and check that boundary through the relevant compressed output or a focused regression using the matching build mechanism. Source-level separation alone then has limited evidence. Project-specific `Object.freeze(function …)` is not a general memory-release API or a blanket rule for functions; keep its reason and supported build conditions with the owning code/Context.

## Bound work by validity and demand

| Changed boundary | Development rule |
| --- | --- |
| Asynchronous/shared work | Bind work and completion to current identity/generation. A superseded result cannot update current state. Cancel only the departing consumer; the shared owner decides when the last reader releases upstream work. Bound pending work and retries through the existing scheduler. For replaceable view input, retain the latest eligible intent rather than an unbounded history; do not discard transactions that require completion. |
| Cache and derived data | Declare the complete reuse key, invalidation, owner and retirement. Use the existing count/byte/time limits and count actual retained data, including failed disposal when relevant. Keep immutable publication work separate from exact-time/view work. Reuse currently valid results; do not add historical-frame caches, pools or copies merely to reduce allocations on paper. |
| Frequent computation/allocation | Avoid rescanning unchanged inputs and recreating large intermediate arrays or whole-result clones. Reuse bounded working storage only while its writer owns it; detach or transfer accepted results so a later write cannot mutate names, picking, source facts or another reader. Check cold construction as well as warm reuse when judging a proposed cache. |
| React/Taro updates | Keep state at its real authority; derive rather than mirror it through extra effects. Avoid unrelated updates rebuilding a large tree or sending large collections through the view bridge. Use supported local update boundaries and the existing drawing writer. `useMemo`/`useCallback` help only with a real reusable calculation or identity-dependent consumer; they do not guarantee correctness or release captures. Preserve effect dependencies and current callback behavior. [React memoization](https://react.dev/reference/react/useMemo), [Taro update costs](https://docs.taro.zone/docs/optimized). |
| Large lists and imagery | Load/render only the content required by the adopted view and navigation semantics. Use existing pagination/LOD/virtualization where applicable, retaining selection, reading position and necessary fallback. Do not shrink required scientific content, precision or quality to make a performance check pass. New prefetch or extra Canvas layers need measured benefit that includes their retained cost. |
| Native/GPU resources | Separate encoded bytes, decoded pixels, textures and auxiliary/backing surfaces; a small file or each local budget does not bound their combined working set. Reuse compatible resources and release obsolete ones through the original owner. Keep current display, replacement overlap and cancellation uncertainties explicit. [WebGL resource guidance](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices). |

Taro's linked guide contains historical 3.x implementation details. Use its update-volume/locality principles; check the installed runtime before adopting a version-specific workaround, configuration or API. Browser APIs and examples do not prove WEAPP support.

Consumer cancellation, underlying work completion, accepted display, logical retirement and physical reclamation are separate events. Completion can end in-flight work while creating a resident image. A native success callback or GL deletion cannot certify immediate physical release; missing confirmation cannot be converted into a free slot by assumption. Preserve the existing bound on uncertainty instead of silently raising limits or adding busy retries.

Distinguish unnecessary retained growth, an oversized steady working set, frequent allocation/GC and temporary overlap before choosing a performance intervention. Their remedies differ and can coexist. [Chrome memory diagnosis](https://developer.chrome.com/docs/devtools/memory-problems). Ownership and cleanup rules apply in ordinary development; new pooling, prefetch, concurrency, worker/WASM or scheduling machinery requires a relevant measured bottleneck and net benefit. Existing rejected choices keep their original reopening conditions.

## Verify and preserve the changed responsibility

- Reuse valid behavior tests and existing target evidence. For a material lifecycle/shared-rule change, check its actual callers and representative distinct failure mechanisms: replacement/cancel, a shared reader surviving another's exit, or old cleanup racing a successor when those paths changed. Do not multiply cases by field, object, duration or light/heavy variants once the shared mechanism is established.
- Assert effects at the responsible boundary: current result identity, legitimate cache reuse, retired reader/resource ownership and preserved content. Source extraction/shape checks supply limited wiring evidence; improve a repeatedly brittle test boundary instead of restoring obsolete production structure. A known compiler-retention regression justifies matching compressed-code behavior, not a whole-product build or heap capture for every edit.
- Check target-runtime effects when the changed platform behavior or claimed benefit needs them. Existing passed evidence remains reusable within its conditions; a local check does not establish visible pixels, physical memory or whole-product capacity. Follow the investigation reference only for an unresolved question that can change the decision; no automatic review agent, profiling bundle or new acceptance gate follows from this reference.
- Put durable ownership, adopted/rejected choices, reasons and material reassessment conditions in the existing Context owner. Keep a short explanation beside a non-obvious code boundary and reuse existing regression protection; new coverage requires explicit user authorization under [the project test-authoring rule](../../../../AGENTS.md#development-execution). Store timings, candidates, raw captures and current status in task evidence. A one-off observation with no future decision value need not become a permanent rule.

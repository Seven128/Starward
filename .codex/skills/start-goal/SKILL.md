# Start Goal

用户主动调用本 Skill，表示要求为当前实际任务开设或续用 Goal，并保存完成任务所需的信息与方案。只是在讨论、编写或评审本 Skill 时，不启动 Goal。若尚未给出实际任务，先询问任务内容，不创建空目标。

目标是使另一段上下文能够依据持久记录准确接续工作；记录完成后继续执行实际任务，不停在计划或建档阶段。不承诺绝对无损记忆，也不把聊天摘要当作唯一记录。

## 建立稳定入口

1. 读取当前任务已有要求、适用的项目规则与相关 Context，确认用户结果、范围和完成条件。先查找本任务已有索引、计划和 Goal，避免建立第二套相互冲突的记录。
2. 选定本任务唯一、稳定、可写的持久索引 `INDEX.md`。优先沿用已有任务目录；没有时使用项目约定的任务记录位置，否则在实际解析的 `$CODEX_HOME/task-notes/<任务唯一标识>/` 下建立，无 `CODEX_HOME` 时使用 `~/.codex/task-notes/`。使用日期、任务用途与必要的短标识区分并发任务；不得覆盖同名任务。不要把记录放在临时目录、可清理缓存或 Skill 安装目录。
3. 先写入并读回最小可恢复索引，再调用当前可用的 Goal 工具。使用 `get_goal` 查已有状态：没有未完成 Goal 时用 `create_goal`；属于同一任务的未完成 Goal 则续用。不覆盖无关的活动 Goal，不通过伪造完成状态腾出位置；遇到此类冲突说明情况并让用户决定 Goal 的归属，独立的资料整理可继续。
4. 新建 Goal 的目标正文同时包含具体结果、关键范围与完成条件、索引的绝对路径，以及“继续执行或上下文压缩后先读该索引；当前细化要求、计划、状态和证据见索引”的恢复指令。只有用户明确指定 token 预算时才传 `token_budget`。
5. 简短告诉用户实际索引位置和当前推进方向，然后继续工作。工具不可用或建档失败时如实说明；不能把普通 Markdown 文件宣称为已创建的 Goal。

Goal 正文示例，使用时填入真实内容与路径：

> 完成【具体用户结果】，范围为【关键边界】，以【完成条件】验收。任务持久索引：【INDEX.md 的绝对路径】。继续执行或上下文压缩后先读该索引，再按其当前需求、计划和状态推进；完成前核对所有必需结果及证据。

若续用的 Goal 未包含索引，使用工具实际支持的目标编辑能力补充。当前只有 `create_goal`、`get_goal`、仅更新状态的 `update_goal` 时，不能修改已有目标正文：保留原 Goal，明确报告这一限制，在回复及现有可恢复记录中写入索引路径，不宣称已写入 Goal，不直接修改内部数据库。新建 Goal 时即放入稳定路径，后续需求变化通过索引更新。

## 保存什么

索引保持精简，但必须能够导航到全部影响执行、判断或验收的必要细节。少量内容可以直接写在索引中；信息增多再拆成需求、计划或证据文件。复用已有文件并链接到准确位置，不强制额外文档层级。

至少覆盖下列实际存在的内容，无内容的栏目不必创建：

- **身份和当前状态**：任务名称、工作区绝对路径、可获得的任务/Goal 标识、更新时间、当前阶段、已完成内容、正在进行的动作、下一步及依赖。区分已计划、已执行、已验证、失败和未验证。
- **当前需求及验收条件**：用户要得到什么、明确不做什么、交付物、细节要求、硬约束、偏好和授权边界。为独立需求给出稳定标识，使其能关联到实现和证据。精确数值、单位、命名、措辞、版本、兼容范围和例外条件不得压缩成模糊概括；关键原话可原样保存。
- **资料与事实索引**：相关代码和文档负责人/入口、设计资源、数据、外部参考、必要工具与运行环境。每个引用说明用途和定位方式，区分用户要求、已证实事实与尚待验证的假设。文件优先使用明确路径，远程资料保留可重取地址及必要版本或日期。
- **当前方案与决策**：实施顺序、模块责任及依赖、实际执行方法、关键风险、验证方法；保留影响后续工作的选择理由、已排除路径及重新评估条件。
- **进度与证据**：需求对应的产物位置、实际检查结果及适用版本/环境、尚未完成的义务、失败或阻塞原因、恢复所需条件。命令执行成功不等于产品行为通过。
- **恢复信息**：足以继续的下一步动作、进行中操作的可查询标识、可能已经产生的外部效果，以及恢复时应重新核实的状态。不要把进程、会话或临时链接写成永久可用事实。

持久来源可靠且可访问时优先索引，不复制整套仓库或日志。仅存在于聊天、即将消失或无法重新取得的必要细节，要及时保存可读内容或合规的本地附件；单有链接或截图文件名不足以恢复时补充必要说明。保存结果、决策依据和可执行步骤，不记录内部思维链。凭证只记录安全存储位置和使用方式，不复制 secret、token、Cookie 或密码。

## 方案随执行演进

按实际复杂度写足够详细的方案：跨模块、长依赖链或高不确定任务需要可独立接续的步骤、接口和验收方法；局部任务用短清单即可。细化近期需要执行的工作，远期保留责任和依赖，获得证据后再展开。已有合用计划时直接维护，不另建竞争版本。

在下列有意义的节点及时更新，不能只等收到压缩提示后补记：

- 收到新增要求、纠正或范围变化；在开展受影响工作前更新当前要求、方案及验收条件。
- 确定关键选择、发现会改变方案的事实、完成一个可验证阶段，或遇到新的阻塞。
- 启动难以安全重复的长时或外部操作前后，记录意图、操作标识与已确认结果，避免恢复后重复提交。
- 即将交接、结束当前轮次、预计发生上下文压缩，或明确收到恢复请求时。

变更要改写当前有效内容，并将必要的旧决策标为“已取代”或移至简短变更记录，写明原因和受影响的工作。不要不断追加彼此矛盾的“下一步”。需求改动使旧证据不再适用时，重新标为待验证；用户没有撤销的原要求仍然有效。

一次更新涉及多个文件时，先落盘细节，再更新索引，使索引只指向已存在的内容。更新后核对关键路径与下一步；不为每次工具调用复制日志。项目稳定事实仍归原 Context 所有，任务进度留在任务记录中。

## 恢复与完成

恢复时先读 Goal 和索引，再按索引读取当前要求、相关方案及所需证据。检查最新用户消息是否尚未入档，并核实相关文件、运行状态和外部操作结果；旧记录不自动证明现状。索引损坏、缺失或来源无法访问时尝试从原始来源恢复，明确仍缺失的内容，不凭空补成事实。

明确当前阶段、已完成结果和最近的未完成依赖，从下一项实际工作继续，不重新规划整个任务，也不因压缩丢失记忆就重复已经有有效证据的操作。耗时任务保留有用的恢复入口；对可能已成功的写入先查询结果，再决定是否重试。

结束前逐项核对当前有效需求与验收证据，修复已知差异，保留未验证项的真实状态。仅在目标确实达成且没有必需工作剩余时，才将 Goal 标记为 complete；预算不足、阶段性完成、已生成计划或记录齐全均不代表完成。暂停、阻塞和预算的处理服从当前 Goal 工具规则，不自创状态或利用完成状态绕过限制。

最终索引保留交付物、验收结论和必要限制；面向用户简短报告实际结果、索引路径和未解决项。若用户明确将任务替换成不兼容的新目标，记录原目标被取代及遗留事项，按工具支持的真实能力处理目标转换，不把被放弃的目标误报为已完成。

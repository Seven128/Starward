# 叠层连续操作与加载中断：已确认交互结论

2026-10-22。用户将叠层完整显示链路性能和无内存泄漏设为第一优先级，云观星六字段点按流畅和无内存泄漏为第二优先级；明确本轮只讨论及更新方案，不实施。以下交互建议经用户“我同意你的看法”确认，规范结论已合入唯一[PLAN](PLAN.md)。本文保调研依据、当前代码观察和适用边界，不形成另一个执行计划；实际进度/下一步归[HANDOFF](HANDOFF.md)。

## 已确认的用户结果

| 场景 | 采用的交互目标 |
| --- | --- |
| 手指未松，正在拖动/缩放 | 原生地图和已有有效叠层持续跟手，不因加载而清空、重挂地图或阻止操作。快速短手势以最终视野为重点；长时间跨新区域时，希望也逐步补出新内容，但以前台手势流畅、可靠视野数据和平台能力为条件。 |
| 松手后新数据未就绪 | 保留仍有效旧覆盖，复用合格缓存/已发布父图，及时补最终所需细节。首个可用覆盖和最终完成分开，不能用永久粗图或掩盖loading宣称变快。 |
| 加载/安装过程中再次拖动或缩放 | 新输入立即接管；取消无用且可取消的旧工作，保其他消费者需要的共享任务。迟到结果须重新满足当前身份、时间、来源、范围与质量条件才可使用，不能覆盖新视野或拉回旧相机。 |
| 加载中跳转“我的”或云观星 | 不把无关网络请求完成作为导航前提。隐藏与卸载分别退休页面任务、回调、计时器和订阅；原生资源沿既有受控清理释放，保安全pin和有界失败恢复。返回恢复用户状态，重新核当前需求。 |

“手势中画面重绘”和“手势中新数据获取/替换”是不同责任。前者保持直接跟手；后者的事件入口、频率、并发及替换方式由微信实际能力和完整链路测量决定。本次没有采用通用固定毫秒数、逐帧轮询、新地图引擎或无限预取。

## 成熟实现的一手依据

- [Leaflet GridLayer](https://leafletjs.com/reference.html#gridlayer-updatewhenidle)明确区分平移期间更新与结束后更新，移动端默认偏向后者以减少请求、保导航流畅；同时提供缩放途中更新、更新间隔和有限周边保留选项。这说明相机跟手与数据调度应分开，并不存在适用于所有负载的单一时机。这里只借鉴机制，不复制默认数值。
- [MapLibre GL JS 的缩放请求选项](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/#cancelpendingtilerequestswhilezooming)说明：缩放中取消来不及完成的旧层级请求可省资源，保留则可能让细节渐进出现但增加短时间工作量。对应本项目应按真实覆盖价值和成本取舍，不无条件全取消或全保留。
- [微信原生 map](https://developers.weixin.qq.com/miniprogram/dev/component/map.html)说明regionchange提供begin/end及触发原因；不能据此假定具备逐帧完整视野事件。持续补图需核实际可用getRegion/事件/安装能力，不从其它SDK直接外推。该官方页面已通过本机HTTPS读取正文。

## 本次只读代码观察

- `apps/wechat-miniapp/src/pages/map/index.tsx`的`onRegionChange`：begin当前取消自动选点聚焦；用户region end发布实际相机，再延迟解析观测Context。现有250 ms属于这条Context更新责任，不能直接叫“所有叠层固定等待”，也不能认定移除它就能变快。
- `pages/map/use-native-map-region.ts`已有实际视野读取、相机/地图身份校验及有限恢复；目前代码不能单凭begin/end证明长时间不松手期间持续获取新视窗。真实端事件节奏、补图成本和画面连续性仍待实施阶段测量。
- 地形/夜光的`use-map-raster-installation.ts`已有新数据未齐时保留target、原生确认后更新呈现身份、map代次和受控退出。云层当前使用`useMapCloudPresentation`及polygon投影，不套用raster文件/纹理的全部机制；不能沿旧研究把当前云层误写成尚无呈现保留责任。
- Map的`useDidHide`会关闭pageVisible并退休页面意图；进入Sky另经`suspendMapRasters`等待原生清理后redirect，并在失败/取消时恢复。两条路径都已有实现入口，但源码存在这些保护不等于“加载中离页”和长期资源回落已通过。

## 测量和验收解释

完整观察对象是用户交互到首个有效覆盖、再到最终正确细节；确认请求/数据就绪前后哪一段占等待，再细分能改变修复方向的责任。第三方服务等待单列且如实保留，不能改供应商内部处理，但本方重复调用、排队、缓存/合并、无关前置依赖、处理、下载、原生安装与呈现仍需优化。阶段可能重叠，不把简单相加当关键路径，不凭HTTP或原生回调成功认定已经显示。

代表机制包括持续不松手跨覆盖、上一轮加载/安装未完时重新拖缩、加载中切“我的”、加载中进Sky及返回。按真实差异选取必要案例，不扩成无依据的全组合矩阵。地形/光害/云量分别保配准/细节、年度值与质量、实际采样位置/所选时刻/有效期；所有场景保有界请求与资源释放。流畅、最终正确和无泄漏各自需要证据。

本次仅确认方案与维护文档；未修改生产代码，未构建/推送/操作手机，也未完成任何新的性能或交互验收。

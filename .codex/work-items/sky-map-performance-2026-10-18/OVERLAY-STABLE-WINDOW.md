# Stable client terrain windows

2026-10-18. This batch implements the existing PLAN's terrain request-identity responsibility. It does not change the PLAN, native camera or map representation. No phone, shared service, database, publication directory, remote storage or production endpoint was changed; no commit/push was made.

## Implemented boundary

`services/terrain-overlay-request.ts` keeps each real request at its actual HTTP precision and uses the shared `displayRasterWindowForBounds`/`displayRasterWindowKey` for supported Map viewport query identities. Small centre/bounds changes inside the same window now share an in-flight metadata read and a still-fresh cached revisit before successful-coverage hysteresis is available. The identity includes the producer-selected LOD, origin, columns and rows. Spot point/radius and legacy Map radius identities keep their original separate meaning and precision.

The pre-existing seven-place outward rectangle normalization moved unchanged from `terrain-request.ts` to `coordinate-system/raster-grid.ts`; the client serializer and planner use the same rule. It preserves the requested rectangle at transport precision rather than replacing it with fixed-window bounds. The native viewport object stays untouched. The offline/exact-grid producer still selects a window from its full-precision bounds; applying decimal normalization again at that boundary was found to add unwanted cells, so that change was removed and the original producer path retained. Existing immutable URL reconstruction and byte identities remain under their owners.

Each cached metadata result carries the request that actually issued it. Coverage admission uses that recorded request, the returned image bounds and its selected level, including when a same-window read started at an earlier camera centre or came from an earlier visit. A later camera input does not relabel the old response. Cross-window cancellation/late-result fencing stays with Query, while the existing download, integrity, native pin and installation owners keep their lifetimes. Finer demand and uncovered edges still request their own data; valid overlapping coverage is not moved, stretched or erased while waiting.

The unchanged domestic technical support rectangle now has one declaration in `miniapp-contracts/terrain-map-coverage.ts`, consumed by the server and client. A rectangle wholly outside that support can share a fixed window with a supported neighbour. Such unavailable/invalid requests retain their individual request identities and cannot populate the supported window's cache. `terrainOverlayRequestWindow` owns the common admission for both identities and coverage: retained coverage cannot suppress an invalid centre/bounds or an actual transition outside support through a transparent fixed-window edge. This is not expanded geographic coverage or a claim of complete source pixels.

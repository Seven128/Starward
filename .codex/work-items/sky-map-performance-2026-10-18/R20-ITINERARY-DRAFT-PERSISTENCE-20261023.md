## Implemented owners and actual behavior

- `apps/api/src/modules/itinerary/itinerary-service.ts` owns validated local-owner draft commands. It reuses `applyItineraryPatch`; that domain helper now constrains only the editable fields it uses and preserves other aggregate fields by its generic input type. Pure draft DTOs live in `packages/domain/src/itinerary/draft.ts`; Node storage stays in the API module.
- `sqlite-itinerary-repository.ts` commits the actual draft, immutable revision snapshot and input-bound receipt in one `BEGIN IMMEDIATE` transaction. Same actor/key/payload replays the historical result; changed payload conflicts. Two connections writing the same base revision cannot both overwrite it. Read ownership is checked in SQL. Current reads do not use historical receipts as current state.
- `runtime.ts` opens the existing `itinerary-and-collaboration.sqlite` file and adds separate draft/version/receipt tables. Existing generic `business_records` rows remain byte-for-byte intact and are not replayed into a fabricated plan. The old fixed 西涌/2026-08-12 template, invented route/weather/astronomy/offline manifest and synthetic friends are retired from the running service.
- `itinerary-routes.ts`, `feature-routes.ts`, `server.ts`, `start.ts` use `/v2/itineraries`, actor-owned detail/history reads and explicit commands. The personal POC composition derives the single `local-owner` only from an actual loopback request. No caller actor/role header establishes identity. An omitted resolver or nonloopback request is denied. This is not authenticated multi-user or production authorization.
- V1 had no actual inputs, revision or stable command key and its renderer required fabricated nonempty route/stage values. Its existing endpoints now return explicit `409 itinerary_client_upgrade_required`; original database records remain recoverable. This is an intentional client migration requirement, **not** a claim of unchanged V1 functionality. The repository's native client and Screen are migrated together to V2; a V1 command URL also accepts the new explicit command body.
- The App starts with real empty state, opens an editable form from the explicitly selected browsing Context and saves only on user action. Existing saved plans are never rewritten by later browsing changes. Inputs include title/date/timezone/origin/people/transport/target/user type/latest return/overnight; collaboration remains disabled. Drafts explicitly have missing route/weather/astronomy and unverified place state. Current UI says saved draft, not executable plan.
- The native client snapshots the complete payload before awaiting storage and stores one pending command per API base URL before HTTP. Lost replies, wrong-identity readback, failed readback and authority loss retain the original payload/key/revision. Retry reads authoritative current state before publishing, so replay of revision 1 cannot replace revision 2. Only command-owner errors that establish no commit permit discarding an attempt; a read failure cannot. Cache publication cancels an obsolete detail read before installing the confirmed current result.
- `tests/acceptance/structured/itinerary-probe.mjs` now calls the real service and SQLite state/history, rather than generic token receipts. Even when that representative path works it returns `passes: false`, `representative_path_passes: true`, an explicit draft-only scope and remaining obligations. Thus whole-family/GLOBAL completion cannot become green from this repair.

## Independent-review repairs — 2026-10-23

The first independent review found two P2 defects in this representative path. Both were reproduced against the pre-repair implementation before changing production code:

- A real client POST with a 66,000-character title exceeded the existing Fastify 64-KiB body limit. It returned the generic `request_body_too_large` without a command rejection outcome, so the durable pending command prevented correction. The focused HTTP regression failed with `rejected: false` instead of a proven pre-execution rejection.
- The creation form copied `DecisionContext.profileId` into `inputs.userType`. With actual identity-shaped fixture values, the form displayed `quick-observing-profile`, `base`, or `missing-profile` instead of observing semantics. All three focused Screen cases failed before the repair.

The itinerary V2 command route and its V1 input-bearing compatibility route now recognize only Fastify's `FST_ERR_CTP_BODY_TOO_LARGE` at the route error boundary. This produces `413 / itinerary_request_body_too_large / outcome: rejected` before the command handler executes. Other errors continue through existing handling; a generic 413 or authority failure is not promoted to proof of no commit. On a new command, the client may retire this proven rejected attempt and preserve the editable form. On a persisted retry, the same parser refusal describes only the latest HTTP request: it cannot establish that an earlier attempt never committed. The original payload/key remain pending, and the UI keeps the uncertain-result message. No request-size limit was invented or changed.

The form now takes the current profile's `observerTypes` and snapshots their existing Chinese labels when the user opens a new draft. `features/preferences/observer-labels.ts` is the small shared wording owner used by both PreferenceWizard and ItineraryScreen. Multiple selected types remain present; a base or missing profile leaves the field empty for explicit user input. Existing drafts continue to use their saved `userType`, and later Context/profile changes do not alter an already opened form or saved draft.

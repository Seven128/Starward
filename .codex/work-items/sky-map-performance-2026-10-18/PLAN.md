## Overlay module boundaries and implementation choices

- **Native viewport and presentation:** `use-native-map-region`, `map-camera`, Map interaction and panel owners retain actual camera, layout and gesture identity. Coverage decisions may reuse an existing bounded working region; a tiny centre change should not automatically discard valid coverage. Gesture scheduling must keep the final view and reject stale results without stealing the camera after user input.
- **Static metadata and request planning:** use the shared coordinate-grid owner for stable window/LOD identities before client reads. Quantize with the same rules as the producer; preserve original requested bounds, actual returned coverage and finer-view requests. Spot radius/location identities retain their distinct meaning. Give Map nightlight its own bounded metadata read backed by NightLightService and the published dataset authority; migrate its current raster/legend/source/loading consumers together, while keeping legacy Scene contracts and weather-dependent marker/filter semantics compatible. A deliberately delayed weather/astronomy read must not delay this static response; a stale layer/account/page must not install it.
- **Terrain and annual-light products:** existing fixed publication/window producers remain the authority for data, hash, level, bounds, licensing and quality. Restore original r6/fixed products before making real-environment claims. Prefer target-area coarse final products plus measured hotspot detail and bounded cold-area processing; raw DEM storage alone is not ready display coverage. Catalogue coverage and bytes first, then prepare useful assets through existing publishers. Terrain and Copernicus horizon remain distinct products; nightlight aggregates numerical/quality fields before fixed colouring, with unchanged spot/filter statistics. Missing/partial data and newly completed areas require compatible immutable identities, not replacement bytes at an old URL.
- **Static distribution:** prepare a map-product adapter at the existing publication/deployment boundary: verify objects first, seal matching inventories, then discover/activate a version. Object/CDN serving should return final bytes without triggering live source reads or image generation. Preserve old URLs, recovery, hash/header/rights semantics and private-data separation. Reuse suitable existing OSS/ESA transport responsibilities, not Sky-only release identities; inspect actual account/domain/quota and select the target before any remote write or purchase. Same-host serving remains a development/compatibility path. Git LFS is versioned development storage, not runtime CDN or database backup.
- **Cloud:** reuse the existing sampled-grid and hourly-series owner, current QWeather v1 adapter and receipt-clock/retention rules. Cache by actual provider-normalized point/configuration/product and complete sequence identity, not the selected hour. If measured camera jitter still changes most points, use a bounded fixed-anchor/spacing plan and only acquire new points. Merge by real source freshness/refresh generation, project exactly the selected hour, and keep old cells only in their original valid footprint. Network prefetch cannot paint unqueried cells or mislabel stale/partial samples. Provider calls and quota remain bounded by existing entitlement/cost constraints; an endpoint reminder does not justify redoing the already completed v1 migration.
- **Download/cache scheduling:** `use-raster-image`, `raster-image-resources` and `map-raster-files` remain responsible for shared downloads, integrity, concurrency, native pins and disposal. Examine request deduplication, foreground-versus-speculative priority, useful retained files and cancellation churn. Prefetch must be bounded, displaceable and cancelable; do not duplicate caches or retain every visited area indefinitely.
- **Native installation:** `use-map-raster-installation` and the ground-overlay coordinator retain installation identity, presented-source meaning and native cleanup. Keep valid overlap until replacement is ready. For a fixed-block trial, start with one 1024² versus four 512² images using the same real data/range/total pixels, then only the object count actually needed by a viewport. Test same-ID update and current add/remove, terrain+light alpha and terrain+cloud order, interior registration, seams and resource return on Android/iOS. Parent/child translucent overlap is not valid fallback without resolving double colouring; use nonoverlapping display units or complete compatible replacement ranges. Public callbacks do not guarantee visibility or group atomicity. Adopt blocks only for measured net benefit without correctness/resource regression; otherwise keep whole windows or a few composed ranges. No WebView/WebGL engine replacement, PMTiles/MBTiles migration, new provider or paid service is adopted.
- **Measurement:** keep non-sensitive durations and counts for lookup/cache hit, queue/source HTTP, CPU/generation, metadata, transfer/bytes, decode, native install and first useful/full required coverage. Separate cold source, local source, published final image and phone-file-hit conditions; correlate with actual visible frames and current candidate/input/version/device. Report valid expected area relative to the full viewport, useful coverage versus target detail, duplicate bytes, blank duration and resource recovery. CPU/event-loop interference justifies bounded worker execution only when measured. Reuse current budgets until actual queue/storage/native-pixel cost supports a change; encoded bytes are not texture memory and DAU is not concurrency. The report's illustrative thresholds, cache sizes and repeat counts are not mandatory gates or claimed p95. Preserve loading/error/partial semantics while shortening the underlying wait.

Mature approaches already identified for investigation include lower-resolution prefetch and parent fallback in [MapLibre Native](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.style.sources/-source/set-prefetch-zoom-delta.html) / [Mapbox RasterSource](https://docs.mapbox.com/ios/maps/api/10.11.1/Structs/RasterSource.html), bounded viewport-related tile caches in [MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/), and versioned HTTP/CDN delivery. These are references for mechanisms, not claims that those SDKs or APIs are available in WEAPP. Detailed current-code/platform evidence belongs in OVERLAY-PERFORMANCE-RESEARCH.md.

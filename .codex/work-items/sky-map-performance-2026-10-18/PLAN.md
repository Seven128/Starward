## Overlay module boundaries and implementation choices

- **Native viewport and presentation:** `use-native-map-region`, `map-camera`, Map interaction and panel owners retain actual camera, layout and gesture identity. Coverage decisions may reuse an existing bounded working region; a tiny centre change should not automatically discard valid coverage. Gesture scheduling must keep the final view and reject stale results without stealing the camera after user input.
- **Terrain and annual light:** existing fixed publication/window producers remain the source of data, hash, level, bounds, licensing and quality. Inspect their current stable keys and level selection before adding tiling or pre-generation. Compare stable spatial partitions, bounded neighbour coverage and a correctly registered coarser covering level as ways to avoid blank edges. Adopt only supported combinations that retain the required ground detail and exact version/quality meaning; do not create a second independent publication owner.
- **Cloud:** reuse the existing sampled-grid and hourly-series owner. Cache by actual location/grid, source/version/validity and time-series identity, and change the rendered hour from already acquired data when possible. Network prefetch cannot paint unqueried cells or mislabel stale/partial samples. Provider calls and quota remain bounded by existing entitlement/cost constraints.
- **Download/cache scheduling:** `use-raster-image`, `raster-image-resources` and `map-raster-files` remain responsible for shared downloads, integrity, concurrency, native pins and disposal. Examine request deduplication, foreground-versus-speculative priority, useful retained files and cancellation churn. Prefetch must be bounded, displaceable and cancelable; do not duplicate caches or retain every visited area indefinitely.
- **Native installation:** `use-map-raster-installation` and the ground-overlay coordinator retain installation identity, presented-source meaning and native cleanup. Keep valid overlap until a replacement is actually ready; avoid remove-then-add holes where the platform supports safe replacement. A tile/multiple-overlay design is conditional on official capabilities plus a small actual native trial, including coordinates, compositing/order, memory and disposal. No renderer replacement or new provider/paid service is adopted by this plan.
- **Measurement:** keep non-sensitive durations and counts for lookup/cache hit, provider/generation, metadata, transfer/bytes, decode, native install and first useful/full required coverage. Bind them to the actual candidate, input/version, device and cache condition. Use the first slow boundary to choose work; a native callback is not automatically a rendered frame. Preserve the current loading/error/partial semantics while shortening the underlying wait.

Mature approaches already identified for investigation include lower-resolution prefetch and parent fallback in [MapLibre Native](https://maplibre.org/maplibre-native/android/api/-map-libre%20-native%20-android/org.maplibre.android.style.sources/-source/set-prefetch-zoom-delta.html) / [Mapbox RasterSource](https://docs.mapbox.com/ios/maps/api/10.11.1/Structs/RasterSource.html), bounded viewport-related tile caches in [MapLibre GL JS](https://maplibre.org/maplibre-gl-js/docs/API/type-aliases/MapOptions/), and versioned HTTP/CDN delivery. These are references for mechanisms, not claims that those SDKs or APIs are available in WEAPP. Detailed current-code/platform evidence belongs in OVERLAY-PERFORMANCE-RESEARCH.md.

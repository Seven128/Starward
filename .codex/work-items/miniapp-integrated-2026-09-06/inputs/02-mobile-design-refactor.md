# 《今晚去观星》移动端设计系统与页面重构开发方案

日期：2026-09-06  
审查仓库：Seven128/Starward  
审查提交：`424c971be1a27b0587c1789ba5e736f1a57aade2`  
主要实施范围：`apps/wechat-miniapp`，以及它直接使用的设计资源、主题生成、相关测试和当前产品说明。  
文档状态：开发建议，尚未实施，也不代表新的设计样板已经得到用户确认。

## 0. 结论与范围

**本次应完成“手机尺度校准、设计系统统一落地、保留产品行为的页面重构”，不重做产品。**

目标视觉定义：正常手机阅读尺度下，文字清楚、控件精巧、层级明确、容器克制、信息排列紧凑，保留今晚去观星自己的色彩与天文识别。

主要结论：

1. 当前“小”已经写入正式设计：小程序正文 12px、辅助文字 10px、部分状态 9.5px，代码对应使用 24/20/19rpx。需要修改当前设计源及其投射链，页面末尾加覆盖样式不能解决长期问题。
2. 全部当前小程序页面需要纳入检查与统一迁移，但复杂状态机、业务模型、接口和已经打磨的地图行为应保留。
3. 已有 Taro、React、TanStack Query、Zustand 和项目公共组件，应该继续复用。主要补强前端组件、样式和交互编排边界，不重做后端或引入新的状态框架。
4. 组件库采用实际收益导向：保留 Taro + Starward 组件层；复杂通用控件可按需引入一个兼容的外部库，地图面板与时间尺不强行换成语义不等价的通用组件。
5. 先做手机上的关键样板并确认，再迁移所有页面；完成证明必须包含当前 WEAPP 构建的实际测量与真机检查。

### 0.1 审查边界

本方案依据当前提交的源代码、设计文档、产品约束、仓库进度说明和用户提供的五张高德截图形成。未在本次审查环境中启动微信开发者工具、连接用户手机或执行该仓库测试，因此不声称当前真机布局、手势或测试已经通过。

所有新增字号、间距、圆角、排期和验收目标均为本方案建议，不是从高德截图精确测量出的数值。

### 0.2 本轮不扩展的范围

不改 React Native App、运营后台的视觉体系，不重做供应商或地图底图，不改变数据库、领域计算、接口语义或产品导航，不新增商业化功能、评分体系、推荐算法，也不借这次改版建设另一套长期任务、审批或视觉验收平台。

后端已有待办继续按原任务处理；若某项缺陷直接阻断本次地图—搜索—地点—星图的验证，则明确合并处理，并与新增视觉问题分开记录。

## 1. 当前实现审查

### 1.1 技术栈与可复用基础

当前小程序 `package.json` 使用 Taro 4.2.1、React 18.3.1、TypeScript 5.9.3、TanStack Query 5.90.21、Zustand 5.0.14。小程序依赖中未引入 NutUI、TDesign、Vant Weapp 或 Taroify 等完整通用 UI 套件。[S2]

项目已经有 `SoftButton`、`CustomNav`、`SemanticIcon`、`SpotCard`、`StatusPanel`、通知和来源组件；也有 `useResourceQuery`、收藏 mutation、地图时间投射与导航安全区封装。上述基础优先演进，不平行复制。[S6][S8]

`config/index.ts` 明确只允许 `weapp`；H5 小程序目标已移除。因此 RN Web、设计 HTML 或普通浏览器预览只能提供局部诊断，不能替代当前小程序的运行验收。[S3]

### 1.2 字号偏小是设计尺度问题

当前 `DESIGN.md` 的独立小程序章节规定：[S4]

| 角色 | 当前逻辑 px，按 375 宽对应 | 当前 rpx |
|---|---:|---:|
| 页面标题 | 17 | 34 |
| 章节标题 | 13.5 | 27 |
| 正文、列表主要值 | 12 | 24 |
| 普通动作 | 11.5 | 23 |
| 紧凑筛选 | 10.5 | 21 |
| 元信息 | 10 | 20 |
| 部分状态文字 | 9.5 | 19 |

`app.scss` 的主要字体类与上述值相符。因此不能把问题简单归为“开发没有遵守设计”；当前设计本身需要纠偏。[S5]

地图样式中还有 `16rpx` 的分段导航文字、`19rpx` 的操作文字，以及多处对字号、内边距和媒体区域的局部覆盖。修改全局 `.type-body` 不会覆盖所有这些声明。[S7]

### 1.3 750 设计宽度不能直接判定为错误

当前 Taro 配置采用 `designWidth: 750`，开启 pxtransform。这个约定本身可以正常使用。[S3][W1]

已有 rpx 的展示关系为：

```text
逻辑 px = rpx × 当前逻辑窗口宽度 / 750
```

因此，24rpx 正文在 375 宽为 12px，在 390 宽约 12.48px，在 320 宽约 10.24px。88rpx 触控区在 320 宽约为 37.55px，并非任何屏幕上都是 44px。

诊断上需要区分三件事：当前选定字号确实偏小；局部 CSS 可能继续覆盖；桌面预览与手机的显示倍率不同。仅凭现在材料，不能断言用户之前全部缩小过程都是某一个转换 bug 引起的。

### 1.4 页面组织存在局部维护负担

地图的 `index.tsx` 约 52KB，`index.scss` 约 48KB。问题不在文件数字本身，而在地图请求、坐标处理、marker 投射、面板协调、拖动进度、主题常量与展示组合集中在一处，样式文件又保留多轮同名选择器覆盖。[S7][S8]

例如当前原生 marker 配色在 TS 内再次写入，WXSS 主题在另一处维护；这有平台必要性，但不应形成两份人工精确色值来源。新的生成链应同时输出 WXSS 与原生控件使用的 TS 值。

### 1.5 已有设计检查不能代替最终外观检查

项目已有设计 profile 校验、selected-design bindings、图标生成和微信验证脚本。部分检查比较资源哈希、manifest、源码标记和文本包含关系。这能发现来源或绑定不一致，但不能单独证明实际字号、点击区域、键盘遮挡和手机阅读体验合格。[S10][S11]

本轮扩展现有检查即可，不创建平行的证据平台。

### 1.6 当前业务仍有未完成验证

仓库 9 月 6 日进度说明明确：五个功能区域、九条主要路由和额外支持页已有大量实现，但尚不能称完整产品完成；正式观星点主旅程、搜索键盘、三处时间尺联动及星图真机指向等仍有未完成验证。[S12]

本轮必须分别记录“既有待办”“本次新增视觉问题”“重构引入的回归”。视觉验收通过不自动把原有业务待办标为完成。

## 2. 产品行为保护范围

### 2.1 当前仓库优先于早期产品稿

用户提供的 2026-08-04 产品/技术文档是历史背景。当前代码与产品约束已经形成更新版本：[S9]

| 项目 | 本次保留的当前行为 |
|---|---|
| 一级导航 | 地图、我的两项 |
| 观星点信息 | 地图中的连续三档面板，无独立四分段详情主流程 |
| 面板章节 | 概览、天文，属于同一个文档的定位导航 |
| 收藏浏览 | 搜索页的“想去”分区 |
| 地点选中 | 地图 marker 或搜索结果都进入同一地点的中档面板 |
| 数据表达 | 客观场地、天气、天文事实与必要风险，不恢复已退休的推荐出发文案 |
| 云观星 | 从当前地点进入全屏星图，继承同一地点和时间 |

因此不得借视觉重构恢复“夜空—地图—我的”三 tab、独立详情四 tabs、额外收藏首页或新的“今晚建议出发”卡。

### 2.2 地图与搜索不变量

- 进入搜索是子路由；原生地图实例、相机、已提交筛选、选中地点、时间和分析图层保留。
- 搜索框转场前后是同一视觉锚点，位置、尺寸、输入起点和文本一致；只改变前导搜索/返回图标。
- 不从高德参考图引入尾部清除按钮、商业入口、历史营销模块等未被当前产品采用的功能。
- 筛选保持即时提交多选，不新增“应用/重置”式暂存编辑，不恢复快速/高级两层结构。
- “想去”“其他观星点”是两个一级结果分区；折叠保持条目身份和有效滚动位置。
- 搜索卡整张是唯一选点动作；有效释放才选中，滚动、拖离、取消不选中。
- 搜索结果返回原地图，并打开所选正式地点的中档面板。

### 2.3 地点面板不变量

```text
visibility = hidden | visible
extent = small | medium | large
bottomPresentation = none | spot-panel | layer-sheet
```

三档是同一份地点文档的不同可见高度；只有大档启用正文纵向滚动。不得用三套 JSX、三个请求对象或重复字段映射模拟三档。

保留首次选点到中档、空地图点击连续关闭、可打断/反向的运动、large 返回 medium、地图与面板并行而非普通模态遮罩的行为。

拖拽只从专用把手热区发起；正文、媒体、整个头部不能变为拖拽区。现有 104×40rpx 把手在本轮属于单独校准的交互几何，不因统一点击规则就扩展到整片头部。需要调整时，只调整专用把手带内的尺寸，并同步当前设计说明与回归测试。

合法媒体保持中档到大档的连续展开及与地图工具显隐的顺序；无合法媒体完全省略节点，不用假星空或空白图片框补位。

“概览/天文”仍是悬浮定位条，不改为 tabs、不拆文档；“想去/分享/云观星”保持一个底部操作栏；外部导航保持基础信息中的安静动作并经过既有安全检查。[S9]

### 2.4 时间、图层与星图不变量

一个共享 Observation Context；同一组真实时间切片；预览、提交、取消和迟到请求的语义不变。

光害保持来源日期对应的静态语义，不伪造逐小时变化。总云量与观测机会按现有真实数据变化，客户端不重算天气或推荐。

星图保持真实目录、现有三维视窗、角度与宽高比关系、传感器权限和生命周期。UI 重构只改变外层布局、标签和控件，不为视觉更好看而增加假星、改天体坐标或把视图偷偷改成平面全天图。

## 3. 视觉方向：精巧清晰的地图工具

### 3.1 对五张高德截图的采用方式

第一张参考地图与浮动控件的主次关系；第二张参考搜索、输入法、结果的连续性；第三至第五张参考地点面板在不同高度下的连续内容与稳定操作栏。

采用的是信息组织和视觉比例，不复制高德的业务入口、营销推荐、评分、Logo、配色或完整页面拓扑。高德截图也不能提供当前手机的 CSS 视口、DPR 和显示倍率，不能把截图原始像素直接转成设计值。

### 3.2 可执行视觉原则

**小巧来自可见控件和容器的克制；可读性由足够的字号、行高和对比度保证。**

- 大面积由白色或中性深色承担；蓝紫用于选中/时间，黄用于天象或已定义的最终提交，绿用于路线，风险色只表达真实异常。
- 地名、操作、主要事实使用清楚的手机字号；低优先级信息用位置和对比区分，不一律缩成小字。
- 相关信息共用行、基线和分隔线；一个地点对象可以有一个容器，但每个指标不单独包卡。
- 减少嵌套容器、空标题、重复提示、粗重边框、大面积填色、阴影和无作用的说明；保留真正改变判断的风险、缺失、来源与时效。
- 图标保持同一线性风格；不引入额外 3D 装饰、随机星空背景、渐变大板或不同粗细的图标拼盘。
- 动效只解释原有状态变化，保留已有可打断交互，不附加装饰循环。

### 3.3 信息密度的判断

高密度不以文字数量或小字号衡量，检查用户是否能在首个视野快速找到当前地点、路程/可达性、关键设施、影响使用的风险，以及下一步动作。

示例：把“距离”“预计驾车时间”从两个大卡片合为一行 `42公里 · 驾车约50分钟`，能减少占用而不损失事实。该示例仅说明结构，不能作为正式地点数据。

当屏幕变窄或文字放大时，允许展示更少行，保留展开/滚动可达性；不能为了维持原截图的行数降低可读性。

## 4. 手机尺度与适配规范

### 4.1 单一单位约定

设计讨论统一使用“逻辑 px”，与截图物理像素、rpx 区分。保留 Taro `designWidth: 750`，本轮不通过修改它修复整站大小。

推荐投射：

| 内容 | 单位策略 |
|---|---|
| 字号、行高、最小点击区、常规图标 | 以逻辑 px 为固定基础，通过生成器输出不会被误转成 rpx 的声明 |
| 文字放大 | 在基础字号上使用当前文字偏好/受支持平台能力，容器随内容重排 |
| 页面宽度、列宽、铺满地图 | flex、百分比、实际可用窗口尺寸 |
| 可以随视口微调的留白/几何 | 有定义的 rpx 或布局 token，不承担文字可读下限 |
| 原生 marker/callout 与系统测量 | 按各 API 的单位直接使用，不再机械乘 2 或乘 DPR |
| Canvas | CSS 展示尺寸与 backing store 分开；DPR 只用于绘制缓冲和相应变换 |

Taro 文档提供 `Px/PX` 逃逸转换的写法。本项目可在生成层使用此方式，但必须用当前锁定的 Taro 4.2.1 实际编译确认结果，不只看源码声明。[W1]

建议增加少量固定探针：15 逻辑 px 正文、20 逻辑 px 图标、44×44 逻辑 px 点击区。在构建产物和真机测量中确认它们未变成一半，也未再次乘 DPR。

### 4.2 字体起始值

以下为第一轮样板建议值。允许用户在手机上确认后整体微调，但不允许每个页面各自重新发明一套。

| Token 角色 | 基础字号 | 行高 | 用途 |
|---|---:|---:|---|
| title-page | 18px | 25px | 普通页面标题 |
| title-spot | 20px | 28px | 地点身份主标题 |
| title-section | 16px | 23px | 概览/天文等主要章节 |
| body | 15px | 22px | 核心事实、列表主值 |
| body-secondary | 14px | 21px | 必要说明、次级内容 |
| action | 14px | 20px | 普通操作和筛选 |
| search-input | 16px | 23px | 搜索输入与 placeholder |
| metadata | 12px | 18px | 更新时间、来源等辅助信息 |
| data-primary | 16–18px | 22–25px | 关键时间/数值，按组件选定固定角色 |
| article-body | 16px | 25–26px | 攻略长文 |
| critical-state | 14px | 20px | 关闭、风险、数据失效等重要状态 |

正文/辅助正文主要使用 400，选中与动作 500，标题 600。数字优先等宽数字特性，避免把整段中文变为等宽字体。核心值、动作和风险不能借用 metadata 角色缩小。

常规业务文字不低于 12px；不向页面开放任意 9/10/11px 的快捷变量。特别密集的非关键图形标注必须单独证明可读并提供同等可达文本，不默认以例外扩散。

### 4.3 留白、几何与点击区

| 项目 | 样板建议 |
|---|---|
| 普通页面水平边距 | 16px；受限地图覆盖区可用 12px |
| 紧密相关项间距 | 4–6px |
| 行内元素间距 | 6–8px |
| 分组间距 | 12px |
| 章节间距 | 16–20px |
| 信息容器内部留白 | 通常 12px，紧凑行 8–10px |
| 常规列表行 | 最小 44px，双行/大字随内容增高 |
| 筛选可见表面 | 约 28–32px 高，独立点击包装至少 44px |
| 搜索可见表面 | 约 40–44px 高，包装至少 44px |
| 普通按钮 | 约 32–36px 可见高，包装至少 44px |
| 最终提交按钮 | 44–48px 高 |
| 常规图标 | 18/20/24px 三档；收藏等已有仪式组件可保留专用尺寸 |
| 常规圆角 | 控件 8–12px，搜索/浮面 12–14px，sheet 顶角 16–20px |
| 分隔线与阴影 | 薄弱分隔线；阴影仅用于需要脱离底图的浮层 |

44 逻辑 px 是本项目建议的点击下限；参考 Apple 的 44pt 命中区原则，但不宣称它与所有平台单位完全等同，也不把它误称为 WCAG 的统一强制值。[W2]

可见小、命中大必须真实成立：不靠互相重叠的透明层、不靠被父级 `overflow:hidden` 裁掉的负 margin，也不让隐藏控件继续截获事件。

专门的拖拽区与精密图表手势区另外校准，并保留可靠的非手势等价操作。

### 4.4 320/375/390/430 与大字

在开发者工具检查四类宽度，至少在一台 iOS 和一台 Android 微信真机验证主流程。320 宽不缩正文，优先换行、减少同列项目、调整局部列布局。

当前 200% 字体能力应覆盖全部语义角色，不只 `.type-body`。大字下标签和值可由横排转纵排，面板锚点、浮动操作栏和表单底部留白重新测量；不能通过全页面 transform/zoom 模拟通过。

文字放大到 200% 不丢失内容和功能是采用的可访问性目标；它需要实际布局与操作检查，不能仅靠样式类存在证明。[W3]

### 4.5 真机校准记录

在已有调试/反馈记录中保留：提交号、构建号、微信/基础库版本、逻辑窗口宽高、DPR、文字设置、截图尺寸、主题、安全区和菜单胶囊实测值。

先确认手机实际阅读，再检查同宽设计稿。浏览器缩放、电脑显示器倍率和聊天缩略图不得作为最终尺寸依据。

## 5. 让设计系统真正生效

### 5.1 唯一当前设计源

继续使用 `DESIGN.md` 的独立小程序 profile，不动顶部属于原生 App 的 YAML 视觉配置。把本次确定的角色值放进一个可解析的结构化 token 段，同一精确值不同时在两张人工表中维护。

现有 Open Design 工程/资源可以继续作为编辑和预览工具；新的版本经手机样板确认后，沿现有选定资源流程切换当前指针。旧 `selected-source` 保持不可变历史，不直接改旧包以绕过哈希验证。[S4]

### 5.2 投射链

```text
当前小程序设计源
  → 轻量解析/生成
  → WXSS/SCSS 主题、排版、间距与控件 token
  → 原生 Map / Canvas / tabBar 所需的 TS token
  → Starward 基础组件与领域组件
  → 路由页面
  → 构建值检查与当前 WEAPP 实测
```

只补齐现有流程缺失的生成能力，不引入大型 token 平台。生成文件标记不可手改；CI 检查重新生成后无差异。

### 5.3 页面样式约束

- 排版、文字颜色、按钮高度、圆角等重复设计值必须通过语义角色使用。
- `app.scss` 保留基础 reset、通用角色和主题入口；不继续承载所有业务组件样式。
- 组件自己的 SCSS 负责组件外观；地图索引只负责舞台与区域定位。
- 同一选择器的重复声明合并；仅删除确认无运行消费者的旧规则。
- 禁止不断向文件末尾追加“最终版”覆盖；`!important` 仅保留有平台原因的具名例外。
- 原生 map 的颜色和标签参数也由同一设计源生成，不能因为无法读取 CSS 变量就手写另一份常量。
- 迁移适配旧类名可以短期存在，但必须是别名、不能有第二套数值，完成该批页面后移除。

无需禁止所有 `<View>` 或所有数字。地图坐标、真实几何、星图绘制和拖动计算有自己的数据含义；禁止的是页面重复手写可复用的视觉决策。

### 5.4 三主题

保留当前白色日间、中性暗色夜间、黑暖红观测主题。先调整结构、字体与层次，不通过整站换色掩盖尺度问题。

每个组件覆盖 default/pressed/selected/disabled/loading/empty/stale/error 等实际状态。观测模式中自有 UI、图标、Canvas 标签、占位、加载和转场不能意外出现白蓝黄绿；不让自动图片预览破坏暗色环境。

原生底图、系统输入法、分享面板等平台拥有的区域单独记录能力边界。不能只加 CSS 滤镜就宣称整部手机全程黑红，也不在本轮悄悄替换地图供应商来规避平台限制。

## 6. UI 组件库与复用策略

### 6.1 当前状态的准确表述

项目已有平台组件和公共组件，但未采用完整第三方 UI 套件。当前设计文档记录了对多个库的调研，并记录 `@taroify/core@1.0.6` 因图标依赖与当前图标约束冲突而未接入；当前选用 Taro primitives 与项目现有 owner。[S4]

统一图标外观不等于依赖树中绝对不能出现图标包。后续准入应检查实际是否打包、能否替换、是否泄露第二套外观，而不能仅凭依赖名自动否决一个库。

### 6.2 主方案

**继续以 Taro 平台能力 + Starward 薄组件层为基础；对复杂通用控件做一次有边界的外部库验证。**

| 类型 | 处理 |
|---|---|
| Button/IconButton/Text/Divider/Cell/Section | 演进现有项目组件，统一 role、状态与点击区 |
| 搜索输入、原生开关、ScrollView | 优先复用 Taro 已有平台能力 |
| 日期选择、复杂通用表单控件 | 单库按需适配，优先验证 NutUI React Taro |
| 地图三档面板、固定搜索锚点、地图/图层协调 | 保留现有交互，整理模块职责 |
| 弧形离散时间尺 | 保留 enhanced ScrollView 与真实切片投射 |
| 星图和传感器 | 保留专业实现，不由 UI 套件接管 |
| 上传传输、草稿、提交幂等和服务端校验 | 保留业务 owner，外部控件只做展示/输入 |

NutUI 有面向 Taro 的 React 组件路线，但这不代表其任意版本都已验证适配当前 Taro 4.2.1 / React 18.3.1。本方案不预先声明兼容，也不要求为了使用它升级全项目。[W4]

### 6.3 1–2 个工作日内完成的验证

仅选择现有页面真正需要的两个复杂通用控件，例如已有时间字段的选择器、一个包含错误状态的表单输入组合。在独立可回退提交中验证：

- 当前 React/Taro peer dependencies、许可和 lockfile；不为它升级主体技术栈。
- 真实 WEAPP 构建、包体变化与实际按需加载。
- 第三方样式自己的设计宽度/pxtransform 约定，避免再发生半尺寸或双倍尺寸。
- 能否通过公开主题 API 或受控包装接入三主题、字号、大字和图标。
- 微信键盘、胶囊、安全区、触控、读屏及原生同层组件关系。
- 是否减少本项目重复实现和后续维护；是否需要大量私有 DOM 选择器或 `!important`。

通过则锁定一个版本、封装在 `ui/adapters` 下、按需迁移；失败则保留现有平台组件，移除试验依赖并记录具体原因。它不阻断其他页面迁移，也不发展成无限期组件库调研。

### 6.4 接入纪律

页面不直接读取第三方内部 class、DOM 结构或默认 token。业务仍使用 Starward 的公开组件契约。已有草稿/请求/提交状态保持一个明确 owner；第三方组件允许合理的临时编辑状态，但不能形成另一份长期业务真相。

不同时引入两套完整 UI 套件，不把 generic Slider 当成弧形时间尺，也不把支持几档展开的通用 FloatingPanel 自动当成当前保留单文档、仅把手拖动的面板替代物。

## 7. 前端架构调整

### 7.1 保留与调整

继续保留 TanStack Query 的服务端数据、Zustand 的跨页面选择/偏好状态、当前 contracts 与 API 客户端。不得引入 Redux/XState 等框架来重写已存在的业务流程，除非后续独立需求证明必要。

本轮将“布局/手势表现”“页面展示”“业务动作”“平台调用”明确分层，逐步移动代码并保持输入输出不变。

建议在现有目录上增补，不要求一次全量改路径：

```text
apps/wechat-miniapp/src/
  styles/                 # 生成的主题、排版、间距、几何
  theme/                  # 已有原生主题、安全区、尺寸适配
  ui/
    primitives/           # Text、IconButton、Button、Cell、Section 等
    adapters/             # 如通过验证，放唯一第三方 UI 适配
  components/             # 继续演进已有公共/领域组件
  features/
    map/
      components/         # SearchEntry、LayerSheet、PanelChrome 等
      use-map-scene.ts
      use-map-presentation.ts
      map-geometry.ts
      marker-projection.ts
    spot/                 # 地点事实展示及动作，沿用现有 feature
    sky/                  # 沿用星图/天文业务边界
    my/                   # 沿用已有 My feature
  hooks/                  # 现有资源与 mutation hooks
  services/               # API 与平台调用适配
  state/                  # 现有跨页面状态
  pages/, spot/, sky/, content/  # 路由入口，主要负责组合
```

上面是职责示意，不要求为凑目录创建空文件。相同责任已有文件时直接改造，不新建同义模块。

### 7.2 地图拆分

1. 提取原生 marker/label 的纯投射；输入地点、选中状态、主题，输出原生 Map 参数。
2. 提取 scene/context 请求与失效规则，继续使用当前 query hooks 和服务方法。
3. 提取唯一 bottom-presentation 协调器，保留 none/spot-panel/layer-sheet、selected spot、extent 的现有关系。
4. 提取面板几何，基于测得的视口、安全区、正文/操作栏尺寸推导锚点；拖动进度使用对应锚点距离，避免另存一份过时的固定像素跨度。
5. 拆出 SearchEntry、LayerSheet、PanelHeader、SectionRail、ActionBar 等展示组件；地点文档保持一次渲染和一次字段映射。

纯移动/提取代码的提交先不改外观；后续视觉提交再调整尺寸。便于区分结构回归与视觉问题。

### 7.3 数据与副作用纪律

Query 返回的数据不为美化 UI 重新计算天气/建议；实体数据与视口临时状态不重复长期存储。保留取消、版本号、上下文指纹、乐观更新回滚和后台停止请求等现有能力。

页面测量只在布局、文字设置、窗口、键盘或 relevant content 改变后执行，不在每个拖动帧全树测量。手势期间优先更新变换与局部表现，不重建地图或整份地点文档。

### 8.1 地图首批样板

必须在全量迁移前完成四个代表状态：地图初始、搜索+键盘、选中地点中档、同地点大档。至少包含一个长地名、一个无图地点、一个状态缺失或关闭的地点。再用设置页作为通用控件密度样板。

样板必须接真实组件和当前 WEAPP；设计静态页可辅助，但不作为“已经可上手机”的证据。

### 8.2 面板密度重排

主体使用身份区、路线/设施事实区、内容入口区、天文区的连续顺序。优先合并共享行，删掉重复容器和无实际帮助的说明。

中档默认尽量完整展示地点身份、主要到达信息和核心设施。若大字或短屏无法同时容纳，允许按现有档位进入大档继续阅读，不把文字缩回去，也不新增另一个摘要副本。

章节定位条保持悬浮，不用永久给所有正文预留整条右侧空列的方式解决碰撞。需要具体检查它与可点击内容、右对齐数值的空间关系，调整局部布局，不能把遮挡当作合理叠层。

### 8.3 表单与支持页

简单字段使用共享 Cell；长文、媒体和多选项目使用上标签。标签有足够宽度，大字条件转为纵向。错误就近出现，不预留大块空白帮助区；提交后滚动/聚焦首个错误。

键盘出现时保持当前输入可见，提交动作只有一份。上传进度、失败、重试和取消在同一媒体项中替换，不把真实异步过程简化成假成功。

## 9. 开发顺序与提交安排

### 阶段 A：现状保留与手机尺度样板（建议 3–5 人日）

读取实施时最新提交并与本方案审查提交比较，确认期间产品行为有无更新。复用现有测试和进度说明记录地图/搜索/面板关键状态；用上述样板确定字号、点击区与视觉密度。

交付：当前行为记录、四个核心手机样板、尺度与问题清单。未取得样板认可，不批量改全部页面。

### 阶段 B：设计源与通用组件（建议 4–6 人日）

更新小程序 profile、选定资源与当前绑定；补齐 token 生成和单位测试；更新基础组件、三主题、图标和文字偏好；完成一次外部库实测决策。

交付：唯一生效的设计值、可重复生成的适配、组件状态样板，外部库通过/不通过结论。

### 阶段 C：地图、搜索与地点面板（建议 7–10 人日）

先提取协调/投射不改变行为，再修改外观、测量锚点和 CSS。完成搜选点、地图返回、三档手势、图层互斥、时间尺与底部动作的完整回归。

交付：主路径完整迁移，保留产品不变量。

### 阶段 D：其余页面（建议 5–8 人日）

迁移我的、设置、计划、链接、导入、投稿、登录、攻略、场地、来源、文章和星图覆盖层。避免各页局部补出不同风格。

交付：14 路由及复用面板的全部实际状态覆盖记录。

### 阶段 E：真机回归、清理与发布（建议 4–6 人日）

检查 iOS/Android、窄屏/大字、三主题、输入法、安全区、数据异常与真实主流程。清除兼容别名和确认失效的旧样式；测量包体和交互性能并回滚无收益依赖。

交付：候选构建、测试记录、未完成项清单和可回退提交。

以上约 23–35 个工程人日，是基于本次静态审查的规划估算，不是承诺工期；既有服务/正式点数据/星图指向待办的额外工作不自动包含。AI 可缩短实现，但不能替代手机观察和平台联调。

### 推荐提交粒度

```text
1. 当前行为/状态测试与尺寸探针
2. 手机样板与当前设计源更新
3. token 生成、基础组件、单位/主题检查
4. 地图代码提取（行为及外观不变）
5. 地图/搜索视觉迁移
6. 同文档地点面板、图层、时间尺视觉迁移
7. 我的、设置与表单页面迁移
8. 星图覆盖层与内容支持页迁移
9. 真机修复、旧规则清理与发布
```

同一批中避免同时更改后端契约、状态语义、库版本和页面样式。单个行为缺陷的修复单列测试与原因，不能以“整理代码”隐藏。

### 10.1 复用现有命令


`test:miniapp:native` 等平台命令需在既有微信开发者工具验证环境运行。手机反馈继续使用项目已有 `miniapp:device` / `miniapp:device:feedback` 流程，不另建入口。

### 10.2 在现有检查中增加四类断言

**生成/源码层：** 当前 profile 与生成结果一致；旧值不会通过另一套 adapter 回流；组件 import 边界和重复样式问题可发现。

**编译层：** 正文、图标、命中区探针得到预期逻辑单位；第三方控件未再次缩半；原生参数和 CSS 使用一致含义；所有主/分包能构建。

**页面几何层：** 用现有 selector 测量获得真实可见范围、字体可用样式、目标矩形和安全区。父级裁切、隐藏交互面、覆盖层与相邻点击目标必须一起检查。

**真机层：** 文字读得清、操作点得到、层次符合目标、键盘/手势/原生地图正确。像素比较之外保留人工检查；不能仅以截图相似度作完成依据。

### 10.3 重点回归矩阵

| 类别 | 必须覆盖 |
|---|---|
| 尺寸 | 320/375/390/430 等效宽度，正常/放大文字，短屏与长地名 |
| 主题 | 日间、夜间、观测；冷启动、切换、返回、弹层、加载和错误 |
| 搜索 | 自动聚焦、外部失焦、键盘收起/再开、候选选择先于 blur、筛选换行 |
| 结果 | 两分区折叠保留条目/滚动；无结果、部分/旧数据、收藏失败回滚 |
| 地图恢复 | 搜索往返、My 往返、星图往返，相机/筛选/时间/地点保持 |
| 三档面板 | 首次 medium，small/medium/large，同一节点；large 单滚动 |
| 手势 | 把手起拖、正文不拖、未越阈值不变档、快速反向、取消与滚动竞争 |
| 面板/图层 | 互斥；图层打开后选新点不闪回旧面板；关闭后按最新意图恢复 |
| 媒体 | 有合法图展开顺序；无图不留区；加载失败/失效的真实处理 |
| 时间 | 三处共享、真实切片、预览/释放/取消、跨午夜、迟到请求 |
| 行动 | 收藏、分享、云观星、导航安全检查，目标/焦点与正常恢复 |
| 表单 | 输入法遮挡、首错定位、草稿保留、上传重试、提交幂等、审核状态 |
| 星图 | 画布展示/缓冲尺寸、标签遮挡、既有投影/传感器测试不回归 |
| 性能 | 地图不重复挂载、拖动不触发整页查询/测量、包体无无意义增长 |

自动化按组件共享能力和风险组合覆盖，人工至少走完整主路径；不要求生成所有状态笛卡尔积截图来制造数量。

### 10.4 数据和视觉证据分别管理

可使用确定性的隔离数据测试长名称、无图、缺失、错误等视觉状态，但须明确属于开发/测试数据。正式主路径另用真实可用正式地点验证，不能把样例截图当作天气、设施、星图指向或导航已经真实可用的证明。

原生地图瓦片等不稳定外部区域可在像素比较中隔离，但这不免除地图交互、覆盖关系和合法标识检查。

## 11. 完成标准

### 11.1 视觉与可读性

在手机正常观看距离下，地点名、正文、筛选和操作无需放大即可使用；整体保持简洁紧凑，不再以 9–12px 的核心文字制造密度。用户已在关键手机样板上确认方向，全页面使用同一套已确认角色。

### 11.2 系统生效

修改一个语义角色能影响其全部实际消费者；WXSS、原生 marker、Canvas 标签和通用控件没有第二份人工同义值。旧设计资源不会被当前生成链重新采用。构建与运行结果与当前选定设计一致。

### 11.3 产品与数据

地图产品不变量没有改变；地点、收藏、时间、筛选、面板、图层、导航、媒体、权限和表单恢复回归通过。不新增错误推荐、假数据或跳过既有安全行为。

### 11.4 平台与覆盖

所有 14 条当前路由和地图内复用区域完成迁移；iOS/Android 主路径验证；窄屏、大字、三模式、键盘、安全区与点击目标达到本次目标。现有尚未完成的业务项仍如实列出，未被本轮视觉验收覆盖就不能标为完成。

### 11.5 工程维护

页面没有继续堆叠同义样式；通用控件有稳定契约、当前主题和状态样例；地图展示与协调职责可单独测试；外部依赖有明确收益和版本，不因接库产生更厚的覆盖层。

代码编译成功、哈希一致、HTML 看起来正确或测试工具能打开页面，都不是上述完成标准的替代品。

## 12. 风险与回退

| 风险 | 处理与回退 |
|---|---|
| 放大文字后中档信息减少 | 合并重复行/容器、调整锚点和可用空间；不缩回正文，不复制第二套摘要 |
| 同时改变 designWidth 导致全站二次缩放 | 本轮保持 750；单位调整只通过受测生成层 |
| 组件库 CSS 单位或 reset 冲突 | 先做两个实际控件验证；隔离 wrapper 样式；失败删除依赖 |
| 地图拆分导致重挂载或状态丢失 | 结构提取独立提交，稳定 identity/key，先通过行为测试 |
| 面板尺寸变化使手势映射失真 | 使用实际锚点几何、保留单一协调器；回归快速反向/取消 |
| 新字级只影响全局类，局部仍很小 | 枚举实际排版消费者，清理局部字号和多轮覆盖 |
| 三主题切换出现白色默认弹层 | 所有自有 overlay 接统一主题；原生边界独立验证与说明 |
| 旧严格检查锁死旧设计 | 新样板确认后更新当前来源指针和期望；不删除检查，不篡改历史包 |
| 既有业务未完成影响发布判断 | 分开记录视觉完成与业务完成；阻断主流程的既有项仍须解决 |

回退以代码提交、当前设计指针、生成适配和对应测试期望成组进行，不只回退截图或某个 CSS 文件。本轮不需要数据库迁移，也不长期保留两套 UI 分支或隐藏主题开关。

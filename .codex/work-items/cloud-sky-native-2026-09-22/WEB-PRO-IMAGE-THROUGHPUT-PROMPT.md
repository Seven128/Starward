请联网做一次有证据、面向落地的专项调研。核心问题按优先级依次是：**社区是否已经有成熟高效的天文显示素材生产方案；Stellarium实际怎样取得、加工和显示这些图像，是采购现成资产、使用公开数据、接受供稿，还是投入人工处理；如果没有适合我们直接复用的方案，现有流程怎样做到约束内最高效。** 请先研究外部成熟实践与素材供给，再评估我们是否还需要逐图加工，最后才优化保留下来的工序。不要把当前技术栈当不可改变的前提，也不要一开始就回答“批处理、并行、缓存、换显卡”。下面是截至2026-10-10的实际情况；你不能访问我们的本地仓库或图像，请勿声称已经看过、运行过或验证过它们。

## 1. 为什么需要这次调研

用户观察到，目前大约每小时只能推进3-4张原图，而且还达不到直接可用。这个速度尚未经过完整阶段计时，但已明显不可接受：按1,000张粗算，仅推进原图就约250-333小时，合格率不足还会增加投入。请以“单位时间新增多少合格、可接入图像”为目标，同时区分原图处理量、文件级通过、实际融合通过和最终采用；不要用模型吞吐量或输出文件数冒充交付效率。

资源侧的条件估算是500-1,000份合格目标/天区成品，约1,000份作为工作量参照，约2,000份作为待进一步核算的扩展规模；不是必须凑数、全部覆盖要求或固定上限。我们需要显著优于几百小时的现实路径，请给不同提效幅度的可验证方案和工时估算，不能凭空承诺某个速度。

- 产品是微信小程序里的原生“云观星”：在可旋转、缩放、随地点/时刻变化的星空中，把真实星云、星系及连续天区图像按天球坐标叠加。现有引擎是WEAPP Canvas/WebGL、TWGL、Astronomy Engine及自有服务。不是生成宣传图，也不是要求每张展示图成为测光科学产品；恒星通常由星表绘制，并非给星表每颗星准备一张照片。

- 最近17个不同原图来源均已加工并复核：3源文件级通过（NGC246、NGC7009、ESO378-1），14源待修。文件通过的三源也未全部满足显示位置、实际融合、权益和采用条件，新Prepared正式采用仍0。9个候选版次产生24个不同图片文件，约51.14MB，不可当24个新目标。先前还有其它试验来源，不能把17当所有历史素材总量。
- 离线加工机实际为Windows、Intel i5-11400F（6核12线程）、RTX 3060、约32GB RAM；本次未核显存容量，不要假设云服务器承担GPU加工。已用Python/NumPy/Astropy/Photutils/Pillow、RC-Astro CLI，以及Photoshop 27.10的COM/JSX批处理。

## 3. 我们目前实际怎么做

1. 来源取得与准入：优先ESO、Hubble、NOIRLab等已处理真实观测成品；现在这批多为已拉伸sRGB JPEG，而非原始线性FITS。保存完整原图、ICC、具体来源/署名/许可、AVM或WCS几何、文件身份。按星云、星系、区域、星团/恒星主体等机制分组；星团、月球行星不能统一去星。可直接使用的原图允许绕过不必要加工。
2. 整图归一化和去星：有共享来源适配器及SXT批处理器。StarXTerminator CLI使用ML11、GPU、RGB8，输出无星层和星层；按像素预算串行调度多文件GPU组，保原网格与完整外围，再生成显示LOD。最新三源批次约2,215万像素，用一次原生多文件调用完成；已支持精确缓存复用、导入既有成品、仅重新复核，不是每张手点运行SXT。当前采用SXT，StarNet暂不考虑；不能把未经本用途核权的模型当替换答案。
3. 集中质量复核：共享工具生成原图/无星/星层/差异的整图和ROI对照，Agent逐幅查看集中材料，检查误删、残环、弱外围、颜色、接缝。每图有文件决定、异常队列和精确输出绑定。自动尺寸/hash/ICC/几何检查不替代内容判断；目前尚没有经过真实反例校准、可放心替代大部分看审的质量分类器。
4. 局部修复：PS主要用于恢复被SXT误删的真实结构。以原图+SXT基底+冻结蒙版批量合成，保可编辑PSD，实际重开PSD并检查核心等于原图、外部等于SXT、羽化符合规则。一个COM批次当前支持1-5项，这只是已有适配器边界。蒙版和结构归属仍经常需要Agent查资料/看ROI；修复后还要集中复核纹理岛、带回的前景星及接缝。不使用生成填充或凭空补细节。
5. 背景和降噪：沿Photutils源检测/排除、稳健网格估计背景，在显示处理链中逆sRGB、扣模型、负残差截零再编码。源排除蒙版只控制背景统计样本，不等于保护天体像素，也不等于显示alpha。NoiseXTerminator按需，试过背景前/后两种顺序，不能无限交替。已拉伸JPEG逆sRGB不会恢复观测线性或科学噪声模型。
6. 分档与出版：共享Prepared发布器从完整工作图生成OVERVIEW/MEDIUM/DETAIL，尽量复用最细原像素、仅编码必要粗档；绑定来源、处理类型、位置、许可、版本及全部文件。仅几何或说明变化时复用像素，不重跑模型。候选、已采用及静态分发库存分开，正常来源发现只能读明确采用项；hash本身不是质量证明。
7. 实际融合：共享Scene批次工具使用真实渲染代码、银河背景、相机及目录星，检查图片off/on、宽/细视角、不同LOD、必要的昼暮/DPR，并集中看输出。当前已有按最大编码RGB通道构造显示贡献的路径，以及显式背景variant的逆sRGB线性光相加路径；不是简单把整张照片不透明盖上。有效黑、数据缺测和显示不贡献各有含义。文件黑底预览通过并不保证放进星空没有方框。
8. 显示位置与接入：名义AVM存在问题时，用独立参考点、Astropy TAN、固定训练/留出样本检查显示位置，保原像素和原AVM，不要求每张都做科研级PSF/测光。来源、缓存、LOD、Back/退出等共享消费者在批次节点选代表验证，现规则已禁止每张图重跑完整页面。原生/手机、整体容量和独立审查保留为相应最终义务，不能因此冻结独立离线批次。

## 4. 真正遇到的失败和已有结论

- 弱背景/矩形残底是关键问题。NGC246经SXT、PS、背景、NXT前/后顺序后仍有可见矩形；固定逐通道黑位会偏色并吞弱外围，统一RGB比例黑位也未保住弱结构。这些已失败，不能再建议无依据扫阈值。RGBA、Screen/Add、减opacity或几何羽化不自动解决真实背景与弱结构分离。
- ESO378-1原始3188x2950图，经PS恢复中心与北侧红壳、一次背景拟合后，主体和弱外围保留，矩形显著减弱但仍有淡颗粒矩形/直边，所以融合仍失败。该图背景拟合约27.9秒、保存结果验证约9.9秒、候选出版约22秒；对应本机进程树采样峰约0.79-0.86GB。这些是局部阶段计时，未覆盖取得、SXT、PS、Agent看审/调研、Scene及返工，不能拿来当端到端速度或云容量结论。
- M104里真实球状星团等紧致成员被SXT当恒星删掉。曾用可信分类表核对85个点、一次PS恢复78个成员；局部改善，但表不完整、其它紧致点归属未知，仍不能把整图判合格。这种逐目标天文身份研究显然可能无法扩展，需要研究如何从来源、类别分流或处理策略上减少这类工作，而不是默认每图都建成员目录。
- Abell33存在压住弱边缘的衍射彩环；Fleming1的喷流附近紧致点归属不清；其它星系有臂结误删、核残环、弱结构和局部恢复连续性问题。某一张有问题不应冻结其它独立批次。
- NGC7009完整原图直接分档，不做SXT/PS/NXT/背景，是目前较顺的一条路径：文件复核、实际多光照/DPR下的观感较好，尚有独立显示位置、最终权益和共享目标运行时资格未闭。它说明“减少不必要加工/优选适用输入”可能比不断加修复步骤重要，但一个样本不证明所有图都能直接用。
- 已查过Stellarium桌面纹理准备/加法合成、Photutils背景、Siril、GraXpert、GIMP Color to Alpha的官方资料。Siril/GraXpert尚未本机试用采用；Color to Alpha不是天体语义分割。请超越工具名列表，解释具体输入、参数机制、输出与实际渲染为什么可能解决问题。不要把我们的失败升格成某工具普遍无效，也不要把官方功能列表当本场景已通过。

## 5. 请按这个顺序研究并回答

1. **社区成熟方案是什么？** 优先查天象仪、星图软件、天文可视化和天文图像社区已有的真实生产实践，覆盖“成品图集/纹理库直接采用”“成熟处理链批量产出”“连续巡天显示”三类。分别指出哪些是完整可复用流程，哪些只是一个算法、GUI工具、插件、论文或少数漂亮示例；给具体数据/代码/脚本/教程入口、自动化程度、人工精修负担、实际适用规模和维护状态。不要把更多工具名当解决方案。
2. **Stellarium到底怎么做？** 分开调查桌面版与Web版，以及目标纹理与连续巡天层，不能把它们混成一条流程。从官方文档、素材仓库/清单、生成脚本、开发者说明及渲染源码追溯至少两种代表对象（如星云、星系；有条件再含密星区域）的“原始来源→素材贡献者/制作者→实际加工→发布文件/几何元数据→渲染与缩放”。重点查去星、背景/纯黑/alpha、弱外围、暗尘带、目录星协调和LOD怎样处理；哪些规则牺牲了结构或依赖人工，哪些真能自动化。起点可用 https://github.com/Stellarium/stellarium 和 https://github.com/Stellarium/stellarium-web-engine ，但结论要引用具体文件/段落和版本，不只看一个blend flag。未公开的环节明确写未知，不凭效果图臆测算法。
3. **他们是高质量数据买来直接用的吗？我们能否复用类似供给？** 分别核实采购、公开科学数据、机构合作、摄影师/社区供稿、项目维护者加工的实际证据；不要预设“买来就能用”或“免费开源就能复用”。区分原始数据质量高、照片后期完成、天球位置准确和显示素材准备完成四件事。列可合法商业使用的具体成品集/供给接口及体量、清晰度、外围、坐标、现成程度；如有付费供给，给公开价格/条款或写需报价，不采购或外联。软件许可证、原图权、派生素材权、加工工具输出用途和自托管分发分别核验，不能把开源引擎许可直接套在所有照片上。必须明确哪些资产真的能省掉我们哪几步，以及仍需做什么。
4. **哪条现成路线最适合我们？** 按来源准入后的合格吞吐、一次性集成成本、每图人工投入、持续维护、商业条件和用户可见质量进行比较。可提出更换来源、直接采用已准备素材、按类别混合不同流程，或调整当前不适合该素材的渲染表示；不要默认继续把任意公开JPEG加工成同一种透明去星贴图。明确哪些沿用现有方案，哪些需要改变方案、质量边界或购买授权；不改变不能生成细节、虚构缺测或隐藏失败的底线。
5. **如果没有足够好的现成方案，现有链如何做到最高效？** 用成熟实践给出具体改造：按输入/结构分流并优选可直接使用的源；避免逐星系建立天文成员目录；背景、噪声和显示贡献分别处理；尽早做廉价真实融合预检；共性问题一次修整组，局部例外有限投入后修复/换源/退出；GPU推理、编码和集中审图合理排程。已有GPU多图调用、缓存、review-only和批次Scene无需重新发明。识别可取消或自动化的重复截图/验证/文档/Agent往返，并保留必要追溯；给每图返工上限和异常隔离策略，不能仅把难图永远搁置来抬高速度。
6. **如何校准质量检查和验收成本？** 明确文件硬检查、素材内容、位置/实际融合、共享消费者、最终产品验收的不同粒度。用少量合格与已知失败样本校准自动告警/集中审图，指出哪些可以整批判断、哪些需Agent/人工、哪些已属于不必要的科研级证明。特别回答矩形残底与弱外围不可兼得时能否换更适用来源/表示，不能只再扫黑位。任何显示级容差或省略检查的建议都要说明用户可见影响、漏检风险与适用范围。
7. **能省多少时间，怎样先证明？** 先区分来源、GPU、I/O、身份绑定、结构研究、蒙版、Agent看审/调研、Scene和返工的实际耗时与假设，给最小计时方案。分别估算500/1,000份合格成品的机器时间、Agent/人工主动时间、总历时、合格率/换源率与不确定区间；比较2倍、5倍、10倍提效需什么条件，不编速度承诺。设计一轮有成本和时间上限的代表批次，优先复用现有17源及其失败结果，明确成功、失败、停止和扩批条件；以新增合格图像/小时判收益，不用模型速度、文件数或“pipeline跑通”替代。

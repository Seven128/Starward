# Tiny Context development contract

Tiny Context preserves durable project facts and this short development contract. It does not manage tasks or certify product completion.

- Understand the user's requirements, default Context and relevant owners. Use clear source material directly; clarify real gaps without manufacturing plans, design documents or handoffs.
- Start with `project_context/global.md` and project-declared defaults. `ty-context context list --default` is optional. Without the CLI, read the manifest directly: default Areas, `read_policy = "default"` nodes and their transitive `default_children`; `default_files` selects files without traversing their children. Pre-schema-5 projects also default to architecture.md. Do not install a CLI over the network merely to read files, or repeat unchanged reads. A failed query is not an empty set: resolve uncertainties material to the current change and report the remainder.
- Identify relevant owners from the affected implementation and follow their dependencies and current controlling sources, without waiting for a trigger keyword. Reading other workspaces does not authorize editing them. Stay within the user's scope, preserve unrelated changes and respect project business, technical and safety constraints. Distinguish requirements from current implementation; do not rewrite requirements to conceal conflicts.
- Choose implementation order, tools, decomposition and parallelism as appropriate. Before adding or materially extending a capability, inspect its owners, consumers, state/data responsibility and dependency direction. Reuse suitable capabilities from the project and target platform. Extract a shared unit when consumers must evolve together in the same responsibility, including a shared role already required on first implementation; migrate affected consumers within scope. Avoid speculative abstraction and unification based only on appearance, size or repetition. Complete the required change.
- Before adopting a new dependency or building substantial custom machinery, consider suitable mature alternatives. Reuse decisions whose conditions still hold; bound investigation to material gaps in target support, behavior, customization, maintenance, license and integration cost. Use a small runtime trial when needed to resolve uncertainty. Suitability, not popularity, decides; justified custom implementation remains valid. Local fixes do not trigger a new selection exercise.
- UI may be implemented and iterated directly from conversation, references and code; an independent design system or formal handoff is not a prerequisite. Reuse confirmed direction and shared components. For affected UI with adopted resources, follow the owner's current reference and scope, actually view current visual references and inspect relevant prototypes or source and behavior descriptions. Adopted resources are requirements within their declared scope. Implement faithfully in the target runtime, compare actual results under relevant comparable conditions and repair deviations. Resolve and report inaccessible inputs, conflicts or platform limits; continue independent work. Do not silently replace confirmed designs. Ordinary repairs reuse current resources without regeneration or renewed adoption; authorized design changes update affected resources and owners.
- Choose checks based on requirements, risk and project rules, including changed boundaries, affected consumers and relevant lifecycle/failure behavior. Reuse existing tests, add meaningful regressions when needed and observe actual outputs. Derive expectations from requirements rather than copying implementation. Repair failures and rerun affected checks after relevant input changes; do not repeatedly broaden checks without a new change, failure or specific concern.
- Update the owning Context only when durable project facts change. Keep project-specific goals, boundaries, confirmed decisions (including adopted/rejected choices), reasons, material reassessment conditions and useful entrypoints; reference exact values rather than duplicating code. Keep current resource references and scope with their owner, resources outside Context, and indices as navigation; repair relevant stale references. Optional cross-session handoff information and temporary investigation records stay task-local, outside durable Context.
- Report implementation, decisive tradeoffs, actual checks and material unresolved items honestly. Explain unverified scope and necessary human action. Installed instructions, structural validation, design adoption, static previews, historical results, tool success and subagent summaries do not establish current product correctness or agent compliance.

This contract applies to authorized implementation, including code, configuration, tests, documents and resources. Reading, discussion and audit do not themselves authorize edits. User scope, host safety requirements and more specific valid project constraints take precedence. No role workflow, mandatory intermediate artifact, model checkpoint or machine acceptance Gate is required.

## Cross-stage Capability Research

This rule applies during requirements research, UI/UX design, writing or revising product logic, technical architecture and implementation logic in Context, and production implementation. It does not depend on invoking a development or design Skill.

- **Investigate before narrowing a complex capability.** For professional rendering, domain calculations, complex interaction, large-scale data or substantial custom machinery, inspect existing project/platform capabilities, credible mature libraries or services, and real working examples before settling the relevant scope or approach. Start from the user's task, not only explicitly named controls; discover material interactions and limitations that the initial description may omit.
- **Bring findings back into product decisions.** Distinguish essential capabilities, useful proposals, explicitly excluded scope and unresolved questions. A reference feature is neither automatically required nor safely ignored because the user did not name it. Explain material omissions or tradeoffs; do not silently expand scope, reduce the intended outcome to fit current code, or treat an attractive demo as a complete solution.
- **Assess feasibility at the stage that needs it.** Use primary documentation and relevant examples to check target-runtime support, behavior/customization, existing ownership and dependency direction, data coverage, licensing, maintenance, performance, delivery size and cost. Prefer a suitable mature capability. If direct reuse does not fit, investigate established interaction/technical logic before proposing bounded adaptation or custom work, and state the decisive reason. Separate verified facts, plausible options and untested assumptions; Context descriptions and browser demos do not establish production readiness.
- **Carry decisions forward rather than restart research.** Save confirmed choices, reasons, scope and material reassessment conditions with the existing Context owner; keep comparison notes and experiments task-local. Reuse findings while their conditions hold. During implementation, verify the actual integration and revisit material changed or unresolved assumptions; do not repeat selection merely because the stage changed. Routine visual/text/local repairs do not trigger broad research.
- **Respect the authorized scope.** Use small runtime trials only within the current authorization. A research/design/Context task does not authorize production implementation, purchases or deployment. Unverified dependencies constrain the affected capability, not unrelated work. This rule adds no mandatory report, workflow phase, approval gate or full-project audit.

## Shared components across design and implementation

- Identify shared product/UI responsibilities while researching requirements and creating or revising UI/UX resources, before production implementation. Reuse existing component families; define a shared unit when current consumers must evolve together or the requirement already establishes that role. Similar appearance alone is insufficient, and a single-page repair does not require cataloguing the whole product.
- Record each affected shared unit with its existing owner: purpose, current consumers, shared content/interaction/state rules, permitted variants and boundaries, and editable resource/reference links with review/adoption status. Keep the shared definition in one place; consumers link to it and record only their differences. Design tools/prototypes should reuse the available component mechanism; when an export only duplicates shapes or markup, record that limitation rather than claiming actual shared implementation.
- Implementation must cover the adopted design/product shared responsibilities and may introduce additional technical units, such as layout primitives, hooks, data access or platform adapters. This is a superset of responsibilities, not a required one-to-one or literal set inclusion between design nodes and source components. Map the design responsibility to actual code owners when implementing; composition/splitting is valid if shared semantics, states, variants and consumer consistency remain intact. Do not independently reinvent the design contract, or force unrelated business logic into a visual material component.
- Carry confirmed changes through the affected shared definition and consumers within the authorized scope. Design-stage sharing does not authorize production code or automatically adopt candidates. Follow [Context resource ownership](project_context/context-maintenance.md#shared-component-continuity) for durable records; no separate handoff document or speculative component framework is required.

## Project-local Implementation Decisions

These rules apply to implementation throughout this repository. They supplement the Tiny Context block above; keep project choices with their existing Context owner. Apply them within the authorized change, without requiring a separate plan, report, approval step or repository-wide refactor for routine work.

- **Preserve the capability before decomposing the work.** For a new or materially changed capability, derive the user's observable result and the governing product rules from the current requirement before splitting work by page, API or data pipeline. Identify the relevant actor/object, valid state transitions, decision inputs and failure/recovery meaning; distinguish requirements, derived decisions and unresolved assumptions where they materially affect behavior. Compare the proposed implementation with that meaning: units, spatial/time coverage, identity and lifecycle can change the capability even when labels match. An existing limitation, demo or convenient provider field is not an approved reduction of scope. Resolve a material mismatch at the owning requirement; record confirmed tradeoffs there and keep implementation gaps distinct. Apply this during product/architecture work as well as coding; a routine local repair reuses the existing contract.
- **Check the affected architecture before extending it.** Before adding a capability or materially changing a shared module, inspect its current implementation, callers, state/data ownership and dependency direction. Assign each material product invariant to the owner that enforces it, and inspect what its consumers need to preserve that invariant across boundaries. Contracts must carry the relevant meaning of results (including identity, validity, missing/partial state and failure), not just a success envelope or matching types; an upstream success cannot establish a downstream effect. Follow `project_context/architecture.md` and only the relevant owning Context. Put behavior with the existing responsible module; do not introduce a second source of truth, circular dependency or lower-level module that imports a feature/page. Read `project_context/architecture/maintenance-boundaries.md` when touching a listed responsibility, and verify its current code before treating historical debt as a required extraction.
- **Search before creating.** Look for matching components, hooks, functions, services and installed/platform capabilities before writing an equivalent. Compare semantics, lifecycle and failure behavior, not just names or appearance. Reuse or extend the appropriate implementation; keep independently evolving responsibilities separate.
- **Extract when there is a real shared responsibility.** Extract the smallest coherent unit when the same rule or interaction has multiple consumers that must evolve together, or the current requirement already defines a shared capability. Duplication count and file length are signals, not automatic thresholds. Use concrete consumer needs to shape the interface; avoid speculative generalization, unrelated boolean variants and wrappers that add no useful boundary. Move affected existing consumers onto the shared implementation and retire their duplicated paths within the change. If that migration would materially exceed scope, make the boundary and remaining duplication explicit rather than claiming unification.
- **Apply the cross-stage research decision to implementation.** Follow [Cross-stage Capability Research](#cross-stage-capability-research), reuse current project decisions, and resolve material remaining target-runtime or integration uncertainties with appropriate checks. Do not add a large dependency for a trivial local operation; verify lifecycle/accessibility and actual dependency/bundle costs where relevant.
- **Close the uncertain path before expanding it.** Trace the smallest useful case from the user's input through the actual state, computation, data/provider and persistence owners to the consumer's visible result or durable side effect. Resolve the material uncertainty on that path before polishing or replicating dependent surfaces. For data-dependent capabilities, check that the target environment has the required fields, entitlement, publication, coverage and current inputs; an adapter or feature flag does not supply them. Reuse the same owners for loading, missing, failure and recovery instead of recreating readiness in each consumer. When replacing a responsibility, verify that affected consumers use the intended owner and the displaced path is retired. This is implementation order within scope, not a new staging workflow or authorization to deploy. Continue independent work when a dependency is blocked, keeping the dependent outcome open.
- **Bind checks to changed responsibilities.** Review dependency direction, state ownership, public interfaces and affected call sites, then check the promised result at the owner that can establish it. A UI check must identify the intended action and its resulting content, not any selected sibling; a persistence check must read the promised durable state. Choose inputs with a known expected relationship (change, invariance or rejection) from the requirement. Ask whether skipping the effect, returning empty data or retaining the previous result would still pass; if so, that check cannot establish the outcome. Validate a useful regression with a failing-before-fix case or bounded mutation when an escaped defect warrants it. Asset presence, source markers, internal fingerprints, mocks and successful commands prove only their declared layer, not the composed product result.
- **Sample by mechanism, expand on evidence.** Group affected consumers by relevant differences in rendering, state/data ownership, platform boundary and lifecycle rather than page count. Include branch changes caused by test doubles, runtime configuration, publication and entitlement: a fixture-only fallback cannot cover a production path that never uses it. Exercise a representative of each affected mechanism and the transitions the change can invalidate; reuse one observation across genuinely shared cases and state why it applies. A different override or execution path breaks that inference. On failure, follow the responsible shared path to its affected consumers; widen further only for a new mechanism, discrepancy or unresolved risk. Stop expanding when changed responsibilities and material differences have suitable evidence; explicit acceptance obligations still apply. Use existing task notes for a short rationale, not a Cartesian scenario matrix or new report. Batch repairs and rerun dependent checks; unchanged evidence does not need repeated collection.
- **Make review change the next action.** Before high-impact shared reuse and large deliveries, obtain independent review from the current requirements, references and actual outputs, without making the author's completion narrative the reviewer's primary input. Inspect missing obligations and visible collateral differences as well as the intended action; successful interaction cannot excuse a visibly wrong frame. Missing observations require observation, known discrepancies require repair, and source conflicts require resolution at the owner. If fixes do not reduce the difference, revisit the mechanism before collecting more passes. For a useful new regression against an escaped defect or high-impact invariant, demonstrate that it detects the wrong behavior with a failing-before-fix case or bounded mutation; prefer the shared failure mechanism over one test per symptom. A second pass by the author is self-review, not independent review. If independent review is unavailable, retain that required gap rather than renaming self-review or silently waiving it. No extra approval stage or mandatory review format is introduced.
- **Bound completion by evidence.** Determine the delivery statement from material requirements and unresolved findings before writing the success narrative. A known in-scope defect remains failed; missing required evidence remains unverified; neither is converted to complete by code presence, aggregate green tests or a limitations appendix. Correct degradation establishes failure handling, not delivery of a capability whose required data or success path never works. Complete the authorized integration and repair work rather than using an honest disclaimer as a stopping rule. Distinguish what works in the tested setup from what is usable in the intended delivery environment; fixtures and isolated provider probes cannot bridge that difference. New contradictory user/runtime evidence reopens dependent conclusions and requires correcting the existing task record and any overstated current owner/resource claims; preserve unrelated valid results. Update Context only for durable decisions and implementation facts, not task pass histories. Keep comparison notes and traces task-local, and reuse existing checks rather than building a universal quality score.

Before closing a material delivery, compare the user's requested outcomes and current owning requirements with the assertions and observations actually obtained, including missing obligations outside the edited files. Existing runner scenarios do not define the scope. Use the existing task notes only where needed to make a gap actionable; no new universal checklist or report is required.

## Project-local UI Implementation Rule

For Starward design-resource creation, revision, packaging or adoption, including requests to use Tiny Context's `design-resource`, read `.agents/skills/starward-design-resource/SKILL.md`. It composes the installed Tiny Context capability with Starward's design methods and existing Context owners. Keep the same project entry for `$starward-design-resource`; ordinary implementation of adopted resources follows the development contract without rerunning generation.

For Starward mobile UI, product-surface, gesture, animation, Bottom Sheet, map/card synchronization, time scrubber, sky manipulation, haptic, or accessibility work, use `.codex/skills/uiux_design/SKILL.md`. Read `DESIGN.md` and the owning Source Plan/Context first. `DESIGN.md`, the Source Plan, and owning Context are upstream authority; the project Skill is an implementation companion and must not override them.

For Mini Program UI work, also follow `project_context/context-maintenance.md#mini-program-page-design-resources`. Read and visually inspect the adopted resources linked from the affected Screen Contract, implement them faithfully and derive verification from the current requirements and actual runtime. Historical candidates are not automatically adopted.

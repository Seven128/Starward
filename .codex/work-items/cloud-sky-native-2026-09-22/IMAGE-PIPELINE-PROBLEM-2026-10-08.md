## 产品究竟要交付什么

这不是一组照片的详情页，也不是视频、离线拼图或 Photoshop 展示稿。用户从某个观星地点进入一个可交互天空，经历“总览 → 转动/缩放 → 搜索或点选目标 → 看局部细节 → 查看出处 → 返回原视角”，还可以调整时间。相机、天球投影、目标标签和点选必须一致；照片不能只是一个随意贴在屏幕上的装饰矩形。

星空还包括真实 BSC/SAO 目录恒星、88 星座、太阳/月亮/行星，以及模拟地景、大气、晨昏、网格和红光模式。**本次只请你解决深空/区域照片、银河背景与目录星的图像供给和合成效率问题**，不要求重做太阳系纹理、整套天文计算或整个产品。历史观测照片也不冒充某个用户时刻的实时摄像画面。

已有产品路线是“广角较低分辨率背景＋有合格素材的目标/区域高清”。允许如实承认某些方向没有高清数据，不要求第一阶段把全天任意位置都做成同等高清。但要区分：能浏览完整天球、照片真实覆盖范围、实际清晰度、对象可识别/可交互范围。这四项不是同一件事。

“自然融入”的具体含义是：正常缩放和平移时不突然冒出一张有硬边的矩形照片，不因细档加载/失败而闪黑或变成明显拼布，不在照片边缘出现突变的星点密度和底色；星云/星系的弱外围不应为了隐藏边界被悄悄裁掉。哪些程度可接受、如何量测，仍需要你提出可执行标准，不能把“绝对无任何缝、全部科学完美”当作未经讨论的无限要求。

前端使用 Taro/React/TypeScript 与原生 WEAPP Canvas/WebGL，复用 TWGL、Astronomy Engine 和自有 API/静态资源服务。我们保留原生路线，不打算通过嵌入一个第三方网页或黑盒引擎回避问题；可以复用许可兼容的成熟算法、标准、库和离线工具。若你认为某个局部边界必须调整，请说明证据和最小修改范围。

## 用户的直觉与需要澄清的问题

用户认为工作应当主要是“找到高清图 → 抠出目标 → 调整颜色 → 放进星空”。实际当前代码没有让大模型逐像素抠图：主要是 Python/NumPy/Pillow/Astropy 处理、按天空坐标取样、生成分辨率层级，以及前端 WebGL 合成；最近也直接复用已有 HiPS 天区瓦片。模型主要在选择输入、编排脚本、调试、看图和判断下一步。

但这不代表当前流程合理。已有记录明确承认：重复试验、逐对象脚本/版本/报告、重复验证，以及把完整连续背景当作局部高清验证的前置条件，拖慢了交付。我们没有完整的下载、解码、重投影、调色、编码、模型交互与人工复核分阶段计时，尚不能断言主要瓶颈是图像计算本身。

请先判断：我们的问题到底适合“目标抠图”，还是更应该采用连续天区影像、分层合成，或按对象类型组合？不要直接以通用去背景工具作为默认答案，也不要默认所有科学加工都必须自己实现。

## 现有输入与能力

- 有带 AVM/WCS 等坐标描述的发布者 JPEG/RGB 图；其坐标精度和适用范围仍需按输入判断。现有一个入口保留完整源图矩形，自动生成三个缩放层级，不做语义分割或去星。
- 有现成的 HiPS 成品：按天空球面分层组织的小瓦片。已有坐标取样、视口选档、加载、缓存、来源标注和实际渲染能力，应当复用。
- 有目录恒星，前端会独立绘制。照片里也包含大量星点，两个层之间如何避免重复、亮度/密度突变仍需要明确策略。
- 有 SDSS 原始科学图像到显示图的实验代码，涉及噪声、有效区域和显示估计；部分结果仍有条带、颗粒和颜色问题。请评估哪些责任对我们的展示用途必要，哪些可以通过成熟成品或工具避免。
- 我们需要可信的展示图，不默认要求把所有照片加工成可做测光的科学产品；同时不能把生成或修补的内容冒充实测，也不能丢掉目标弱外围后声称完整保留。

当前处理链可概括为：

`来源与可用权利 → 缓存原图/坐标元数据 → 确认用途和覆盖 → 必要的取样/分档 → 带哈希的资源清单 → API/静态出口 → 按视口选择资源 → 客户端解码/缓存/GPU → 图像与目录星合成 → 可见来源与返回恢复`

其中“找图”“处理像素”“运行时显示”“检查和交接”是不同成本。不要把开发过程中很长的一次对话，当作某个图像算法运行了同样长时间。

当前两类实际入口也不同：

| 类型 | 已有工作 | 尚不能据此声称解决 |
| --- | --- | --- |
| 发布者完整 RGB 照片（内部称 Prepared） | 读取源图与名义坐标，保留全幅，自动缩放/分档；另一已有路径可做目标平面重采样 | 已经分割出天体、已经去星、已经匹配背景、已经证明绝对坐标精度 |
| 成品 HiPS 天区影像 | 利用 HEALPix 天球分区，从已有层级选瓦片，按实际视口投影绘制，保留原像素/原 alpha | 该 HiPS 必定覆盖全天、所有层级都好看、其来源/色调与另一个供给可直接连续拼接 |

HiPS 是图像组织/取用方式，不是自动调色或消除接缝的算法；把一个有矩形边界的有限照片做成 HiPS，不会凭空得到照片之外的实测背景。AVM/WCS 是把像素映射到天空坐标的元数据，不等于每张图的绝对定位都已经实测合格。LOD 指按视角/屏幕像素选择的细节层级，不是给图片反复做新内容版本。

最近的实际状态：一些 Prepared/HiPS 条件候选已通过部分真实软件消费者、HTTP、缓存、来源页返回与资源释放检查，但普通入口中 Prepared 注册仍为空，相关 HiPS 普通启用仍关闭。当前失败不能靠打开开关包装成已交付。一个 Mellinger 2048×1024 光学银河图已用于低分辨率显示；它的固定低分辨率授权和图质不能自动延伸为付费高清/FITS 权利，也不能代替每个局部照片所缺的外围。

## 已实际观察到的三类问题

1. **照片矩形和星场断边。** NGC6752 的当前实际画面中，密集星点随旋转后的照片矩形突然终止，矩形外是稀疏目录星场。现有亮度相关的合成能减弱暗底，却没有消除星点密度和背景差异。一次线性光合成对照只稍减底色，边界依然明显。这说明“换颜色公式就解决”在该实例中没有成立，不能由此推断所有融合算法无效。
2. **源图自身异常。** 当前检查的 PS1 M8 外围成品原瓦片就有强绿紫结构、硬色块；另外一些 Legacy/ZTF 具体成品配置也发现原生条带/块状问题。它们不是抠图后才出现的，不能靠无限调色碰运气。这些结论只覆盖已检查配置，不代表整个巡天都不可用。
3. **选档/渲染问题曾被混入素材判断。** Rubin M8/M61 的已有原片在修正视口选档后，实际渲染细节明显改善；M61 可见主体旋臂和部分弱外围。局部高清可用，并不等于照片外连续背景已经解决。这个例子没有依赖新的 AI 抠图或重新生成颜色。

为了让你不看截图也能具体理解：

- **NGC6752：** 输入是 4000×3904 的 ESO 成品 JPEG，已有约 512、1024、2048 宽度的三档试验输出。实际约 1.34° 概览中，画面中央是亮而密集的星团，周围大量微小星点铺满一张旋转的矩形；矩形边界之外立刻变为很暗、星点稀少的背景。这既包含底色差异，也包含照片星点与目录星密度差异。该帧银河背景层实际上没有绘制，所以不是“两张足够覆盖同一天区的照片已经对齐、只差颜色匹配”的情况。
- **当前一种 Prepared 合成：** 当 opacity=1 时，它产生近似 `最终RGB = 源RGB + 背景RGB × (1 − max(源R,源G,源B))` 的结果，运算在编码 RGB 上进行。这是亮度相关显示贡献，不是语义抠图，不是逐通道 screen，也不是校准过的辐射亮度相加。曾将源/背景转换到线性光后沿同一责任做对照：底色略减，矩形和星点断边仍在。此失败只否定该小改动足以解决该实例，不排除别的有依据的方法。
- **Rubin：** M8 使用约 2.4° 视场，M61 约 0.4°，实际绘图为 390×844 和 780×1688。原选择器被保守候选格数挤占，选择偏粗层；复用真实可绘投影范围后，M8 用 10 个更细格、M61 用 5 个更细格，分别得到更清晰的星云暗纹与星系旋臂。没有通过提高缓存上限或改颜色得到这个改善。照片外连续背景和独立绝对配准仍未闭合。
- **PS1 M8 外围样本：** 原下载 JPEG 中就能看到目标处强烈绿紫斑块，另一片有硬绿色块。当前配置已停止继续下载同类细档或进行无变化加工。这里首先需要判断来源产品是否适合显示，不能先假设是我们的 alpha 算法抠坏了。

对于“照片星点和目录星重复”：已有渲染顺序会在影像之后绘制目录星，这是需要方案明确处理的结构性风险；目前没有完整全图重复星普查，不能把风险直接写成所有图片都已证实错位/双影。请讨论背景图星点保留、目录星显示权重、目标类型差异以及定位误差各自的责任，避免为消灭重复而把星团本体也去掉。

请把以下三件事分开：源图是否覆盖该位置；显示时使用多少透明度；像素是否是有效科学观测。黑色像素不能一律当作“没有数据”。显示派生可以讨论合理的抠图、去星、色调和融合方法，但需要说明对真实结构的影响，保留原图与处理记录；现有实现的限制不应被自动当作永久产品需求。

## 为什么目前觉得特别慢

已确认的流程问题是：把代表样本验证反复延伸成逐对象、逐批次脚本/版本/长报告；对变化不大的材料重复跑消费者检查；曾将外围背景没解决当作局部高清不能继续的理由；曾根据粗阶边缘诊断瓦片评价整幅母图，后续已纠正。这些是可以纠正的工作方式，不是天文图像天然要求。

还存在一些真实复杂性：可用授权不等于图质好；高清像素数不等于适合当前天区/角尺度；完整照片外围可能根本没有同源数据；不同波段、曝光、后期拉伸的成品不一定能直接匹配；前端选错层级也会让好图显得差。请判断哪些复杂性必须解决、哪些只需保留已知限制、哪些被我们过度工程化了。

过去已经为 SDSS 做过较多科学噪声、掩膜、PSF 相关调查或实验。目前有效要求是：优先成熟真实成品，原始科学加工只补有明确收益的缺口，不继续无必要的同输入参数扫描。停止反复尝试某份失败输入，不等于永久禁止一种成熟算法。请不要因为代码里已经有某个复杂模块，就认定继续投入它是最优路径。

当前缺的是统一的吞吐和复核成本证据：每阶段机器耗时、等待网络时间、复用命中情况、进入人工队列的比例、同一问题被重复调查的次数。我们希望减少的是从原始输入到可采用结果的总成本，而不只是某个 NumPy 函数快一点。请明确区分已有证据、怀疑的瓶颈和下一步需要测量的量。

## 必须保留、可以讨论和暂不处理的边界

**必须保留：** 真实对象身份和适用坐标；原始输入可追溯；缺测与暗像素分开；来源/署名/具体资产许可可交付；有界下载/解码/内存；加载失败可保留适用粗层；不把生成细节冒充实测；不通过只展示漂亮中心隐瞒外围失败。

**可以论证调整：** 目标类型是否分路处理、显示层 alpha 的设计、背景估计、颜色/亮度匹配、去星与目录星融合、不同视角的图层权重、离线和运行时的职责、合理的验收阈值。我们此前停止的是没有新依据的抠黑/羽化/小改色循环，不是请你在不评估的情况下永久排除所有融合方法。若某方法只能牺牲真实外围换好看，需要明确列为产品取舍，不能默默降低要求。

**来源边界：** 当前项目排除了 DSS、指定 Gaia DR3/EDR3 及 ESA 银河产品，不请你把这些重新包装成默认答案。PS1、SkyMapper 并非一概不可商用；要核的是具体输入、成品数据库和加工/分发方式。公开能下载、论文可读或 API 可调用不等于已取得该图像的商业再分发权；反过来也不要假设每张图都必须逐张外联授权。优先明确允许适用用途的公开许可和成熟方案。

1. 比较三条路线：连续巡天/HiPS 背景配局部高清；提取目标透明图叠加目录星空；两者按对象类别组合。说明星系、弥漫星云、疏散/球状星团是否需要不同处理，以及各自的主要失败模式。

3. 说明是否需要 AI；若需要，用在什么有限环节、如何批量运行，哪些结果必须人工复核。目标是规则验证后批量处理，只有异常进入人工队列，而非模型一张张编排整套工作。

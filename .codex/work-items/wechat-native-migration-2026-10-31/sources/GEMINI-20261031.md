## 一、总体推荐路线与主要风险（Executive Summary）

### 1.1 明确推荐的技术路线
不从零手写响应式框架，也不引入新的重型第三方小程序跨端框架或外部 UI 组件库；推荐采用 **“微信原生 Page/Component (WXML/WXSS) + TypeScript 控制器层 (Controller) + `zustand/vanilla` 保持现有单 Store + `@tanstack/query-core` 保持现有查询缓存 + Webpack 5 多入口原生构建链”** 方案：

1. **视图与组件层（WXML / WXSS / Page / Component）**：
   - 21 个注册路由全部改为微信原生 `Page({...})` + `.wxml` + `.wxss`（由现有 `.scss` 经 `sass` + `postcss` 编译）+ `.json`。
   - `src/components/**` 下的 Starward 自有共享组件改为微信原生自定义组件 `Component({...})`。遵守 `architecture.md` 与 `DESIGN.md` 既有决定：**不引入 `@taroify/core`、Vant 或 TDesign**，保持单一 `DESIGN.md` 令牌投影与 `SemanticIcon` 图标权威。
2. **业务控制器层（Page / Feature Controller）**：
   - 针对 `MapPage`（3,407 行）与 `SpotSkyPage`（4,252 行）等复杂页面，采用 **“薄原生 Page 壳（<300 行）+ 纯 TypeScript 业务控制器（`MapPageController` / `SpotSkyPageController`）”** 结构。
   - 原生 `Page` 只负责生命周期挂载/卸载、将 WXML 事件（`bindtap`、`bindtouch*`、`bindregionchange` 等）转发给控制器，以及接收控制器输出的最小视图补丁调用 `safeSetData`。
3. **状态与缓存层（零重写复用核心逻辑）**：
   - **全局状态**：保留 `zustand@5.0.14`，将 `src/state/app-store.ts` 从 React Hook 绑定切换为 `zustand/vanilla`（或直接复用 Zustand v5 Store 实例自带的 `.getState()` / `.subscribe()`），配合约 40 行的原生订阅桥接器 `connectStore`，不引入 `mobx-miniprogram`，不重写 `app-store.ts` 的 40+ 个动作与 `ObservationContext` 事务逻辑。
   - **异步查询与服务端缓存**：将 `@tanstack/react-query@5.90.21` 替换为其底层已安装的同源核心包 **`@tanstack/query-core`**（`QueryClient` + `QueryObserver`）。100% 保留现有 `queryKey`、`queryFn`、`staleTime`、请求合并、作用域失效与 `AbortSignal` 取消语义，无需重写 `src/services/**` 的数据获取逻辑。
   - **不默认引入 `miniprogram-computed`**：`miniprogram-computed` 会拦截每次 `setData` 并全量 diff `this.data`，在 Map（三档面板拖拽、三图层状态）和 Sky（时间播放 tick、六字段调时、罗盘姿态）高频更新场景下会带来额外开销。由 Controller 显式计算差量并通过微任务合并调用 `safeSetData` 更轻量且职责单一。
4. **构建与工程链（保留复杂资产与分包规则）**：
   - 保持 Node + **Webpack 5 原生小程序多入口构建**（移除 `@tarojs/*` 与 `react` 插件，保留 `sass`、`postcss`/`pxtransform`、`contracts-reexports.cjs`、`sharedSourceInclude`、`defineConstants`、`adoptedBIconCopyPatterns` 分包图标去重拷贝及 `release-bundle-location.cjs` 发布目录隔离守卫）。
   - **不裸用微信开发者工具内置 TS/Sass 编译器替代构建脚本**：因为本项目是 pnpm monorepo，直接编译跨包 TS 源码（`@starward/miniapp-contracts`、`@starward/coordinate-system`、`@starward/astronomy-core` 子路径）且依赖构建期常量注入与四分包（`main`/`spot`/`sky`/`content`）图标去重拷贝。

### 1.2 预期收益与客观未知边界
- **已确认的机制收益（事实与必然推断）**：
  - 彻底移除 `react`、`react-reconciler`、`@tarojs/runtime`、`@tarojs/react`、`@tarojs/components` 运行时，消除虚拟 DOM 树（`TaroElement`）构建、`root.cn` 递归序列化及 `base.wxml` 递归模板展开开销。
  - 消除 `SpotSkyPage` 时间播放/六字段调时及 `MapPage` 局部状态变更触发 3,400–4,200 行 React 组件函数整体重跑的 CPU 与 GC 开销，改为针对变化字段的扁平路径 `setData`。
  - 消除 Taro 4.2.1 特有的构建隐患（`config/index.ts` 记录的 prebundle `ConcatSource` 崩溃、跨分包 module id 缓存残留，以及 `HANDOFF.md` 记录的空 Taro wrapper 编译反例）。
- **明确标出的未知边界（不编造百分比）**：
  - 迁移后的具体主包体积缩减字节数（基线：341 文件 / 5,223,531B）、冷启动耗时降幅、Sky 播放帧率提升幅度，须待原生构建产物在真机实测后得出，当前不预设固定百分比。
  - 微信底层的 native `<map>` C++ 内存释放（`physicalMapRelease`）及 WebGL/GPU 物理显存占用在 `HANDOFF.md` 中已明确为平台侧 `UNKNOWN`；去掉 Taro/React 能降低 JS Heap 与 `setData` 跨线程序列化压力，但不会改变微信客户端底层 WebGL 纹理或原生地图图层的物理显存机制。

### 1.3 五大主要风险与应对措施
| 风险项 | 源码/机制根因 | 应对与防呆措施 |
| :--- | :--- | :--- |
| **1. `MapPage` / `SpotSkyPage` 拆解 Hook 时丢失世代号（generation）与迟到回调隔离** | `MapPage`（3,407 行）和 `SpotSkyPage`（4,252 行）含大量 `isCurrent`、`isCurrentRequest`、`skyPageVisibleCurrent`、`skyInteractionCurrent`、`skyTimeIntentCurrent`、`layerFailureActionCurrent` 闭包与 `useRef`。 | 严禁把 `MapPage`/`SpotSkyPage` 平铺进 `Page({...})`；按原闭包边界 1:1 提炼为 `MapPageController` / `SpotSkyPageController` 实例属性，统一由 `DisposerBag` 管理生命周期，在 `onUnload` 单点销毁。 |
| **2. F04 原生 `<map>` 故障替换的前任节点共挂载语义退化** | `HANDOFF.md` 明确：故障恢复时原 `<map>` 节点必须**保同 key/id 挂载在直接后继下**，手势/事件隔离，待真实 `removeGroundOverlay` 完成（`pin=0`）后才卸载。 | 原生 WXML 中必须使用 `<map wx:for="{{mapSessions}}" wx:key="sessionId" ...>`，禁止用简单的 `wx:if` 切换或改变 `wx:key` 导致前任 `<map>` 在 native 栅格未退休前被微信提前销毁。 |
| **3. Sky 双 Canvas（WebGL + 2D Display）及拾取层节点获取时机变化** | `SpotSkyPage` 依赖 `createSkyCanvasSurface`（WebGL Canvas + 2D Display Canvas + 可选 Selection Layer Canvas）。原生组件/页面的 Canvas 节点在 `onReady` 后才可通过 `wx.createSelectorQuery().in(this)` 稳定获取。 | 控制器仅在 `Page.onReady`（或 `wx:if` 挂载的 `setData` 回调后）执行 `SelectorQuery`，并严格校验 `skyPageVisibleCurrent`；严禁改动 `preserveDrawingBuffer` 或 `sky-canvas-surface.ts` 的 `present()` 像素管线。 |
| **4. 原生 `setData` 传入 `undefined` 或大对象引发性能退化/报错** | React `useState(undefined)` 合法，但微信原生 `this.setData({ a: undefined })` 会报错或失效；且误把星表数组/WebGL 对象放入 `this.data` 会导致严重卡顿。 | 封装唯一出口 `safeSetData(pageOrComponent, patch)`：自动将顶层/子路径 `undefined` 转为 `null`、做浅比较过滤无变化字段、合并同一微任务内的多次更新，并在类型层禁止非純视图字段进入 `ViewData`。 |
| **5. 过渡期 Taro 与原生长期双轨并存导致双维护** | 若长期维持 Taro 页面与原生页面混合编译，需同时维护两套构建、两套组件和两套状态桥接。 | 采用**“独立构建输出验证最小闭环 → 分包批量替换 → 一次性切流并卸载 Taro/React”**策略（详见第四节），设硬性退出条件，不在主分支保留混合终态。 |

## 结论与本次约束

用户已明确排除网页嵌入，要求功能可以自主改造。因此比较对象必须能取得所需源码，在我们控制的项目中修改、构建，并适配微信小程序原生 Canvas/WebGL。WebView、直接打开 Stellarium 网站、只提供成品页面或黑盒 SDK 的服务不进入推荐方案。

**目前最值得比较的是：Stellarium 源码商业授权后原生移植、AGPL 原生移植、扩展现有 TWGL/Astronomy Engine 方案。** 前两者最接近参考引擎，但原生小程序兼容性尚未通过试验；第三者更容易控制代码许可边界，完整补齐的工程量更大。“免费引擎”不等于“免费数据、免费接口、无需开源成本”。

用户已选择通过 Agent 扩展现有引擎，商业授权移植仅在 Context 所列重评条件成立时重新比较。这不是已经证明自研总价最低：三条路线的数据费用和 Agent 实际用量仍未知，最终还要满足相同的能力与质量要求。

商业授权没有查到公开价目表，记为未知量 `L`；不能据此说便宜，也不能说昂贵。源码中明确列有商业许可选项，但具体可售范围、修改权、交付物和价格仍需书面确认。[官方源码许可声明](https://github.com/Stellarium/stellarium-web-engine/blob/29870744c470ddc62fa869e153178c82a7824fa4/src/js/pre.js)、[官方商务联系入口](https://stellarium-labs.com/contact-us/)。

## 1. “能力对齐”按什么计算

这里对齐的是 Stellarium Web 的交互星空，而非只有星点、星座线或几张天体照片。工程预算包含以下功能族，以及现有云观星的地点/时间上下文、手机跟随、校准和返回路径。现阶段没有对所有天体、时间范围和设备逐项验收，不能把下面的能力清单理解成性能或数据完整性保证。

## 3. 三条主要路线

### A. Stellarium 源码商业授权 + 原生小程序移植

取得覆盖所用版本/模块的商业授权，沿用我们自己的 Taro 产品界面，将引擎适配到原生 Canvas/WebGL。我们可以自行改造功能的前提，是合同包含源码、可复现构建、修改/移植/分发及持续使用权；不能把“商业许可”自动理解为这些全部包含。

优点是直接复用与目标接近的天文渲染，避免自行重做大量专业逻辑。成本是授权费 `L`、原生适配和数据服务费用；商业许可不会自动解决性能，也不自动包含第三方影像、完整星表、网站搜索 API 和售后。

原生适配不是改几个 import：官方胶水使用浏览器事件/Canvas/动画接口，C 端还有 Emscripten 网络请求，WASM 加载、文件与纹理解码、请求取消、GL 生命周期和内存都需要检查。[Canvas 适配源码](https://github.com/Stellarium/stellarium-web-engine/blob/29870744c470ddc62fa869e153178c82a7824fa4/src/js/canvas.js)、[C 侧网络实现](https://github.com/Stellarium/stellarium-web-engine/blob/29870744c470ddc62fa869e153178c82a7824fa4/src/utils/request_js.c)。

判断：**最接近目标的闭源候选，技术可行性与合同条件都还未闭合。** 没有查到官方提供的现成微信小程序适配包，不能承诺直接安装可用。

### B. Stellarium AGPL + 原生小程序移植

渲染和适配工作与 A 基本相同。按 AGPL 条件使用不需购买引擎商业许可，也允许商业经营；区别主要在必须履行的源码义务和由此产生的商业成本。

直接把引擎与小程序代码组合运行，不能默认只公开引擎改动。需判断组合作品的边界、对应源码以及分发和网络交互义务；分文件夹/分包不自动缩小范围。独立的账号、订单、数据库服务也不因通信就自动全部被覆盖。因此，本路线按“可能需要开放云观星乃至小程序组合前端核心代码”做商业评估，既不承诺只开一个目录，也不认定整个 monorepo 和所有后端必然开源。[AGPL 第 5、6、13 条](https://github.com/Stellarium/stellarium-web-engine/blob/29870744c470ddc62fa869e153178c82a7824fa4/LICENSE-AGPL-3.0.txt)。

判断：**工程并不会显著更省；节省的是购买闭源许可的现金，同时承担开源义务与商业代价。** 用户尚未同意开源，本文不把这条路线视为已授权发布源码。

### C. 继续扩展现有 TWGL + Astronomy Engine + 自有数据服务

沿用已经在小程序使用的渲染表面、姿态校准、天文计算和业务界面，增加专业渲染、深星表分层、全空域巡天、搜索跟踪和动态天体。按成熟算法、数据标准和合适的库实现，不复制受 AGPL 约束的代码后声称自研闭源。

优点是已有平台基础、产品自由度高，所用 MIT 代码本身不要求开放我们的业务源码；数据/图画的署名或派生数据库义务仍独立存在。代价是自行承担渲染质量、天文表现、性能和后续维护；“不用买引擎”不等于这条路线总成本最低。

判断：**闭源且自主控制的可行备选，工程风险主要落在专业能力补齐。** 单纯把现有星点变密或增加数十张天体图片不算能力对齐。

## 4. Agent 开发投入（不折算成钱）

**这是重新按任务拆分的、尚未用原生试验校准的低置信估算；不是实测效率或交付承诺。** 没有把上一版人工人日直接改名，也没有假定“AI 固定快几倍”。已有边界内的代码、接口映射、数据脚本与自动化检查可由 Agent 连续完成；底层运行时、画面正确性、设备性能和数据授权不能按同一比例压缩。

计量口径：

- 默认一条主 Agent 开发工作线，拥有当前代码与工具，Agent 承担阅读、方案细化、编码、构建、自动化测试、调试及修复。不预设多 Agent 并行提速。
- **1 Agent 有效小时**是上述工作实际占用的执行时间；仅为方便理解，8 个有效小时称为 1 个 Agent 开发日。它不是人工人日，也不表示每天一定能运行 8 小时。
- 下载、全量数据离线生成、排队/用量限制、真机可用时间、供应方回函等额外等待不计入有效小时。因此有效投入不能直接当成日历交付时间。
- Agent 输出仍要经过对应层的验证；自动生成代码不代表已经完成天文正确性、画面或真机验收。

共同前提：需求和现有交互方向基本稳定，能取得完整、合法、可部署、格式可用的数据成品或服务，目标设备可用于验证。包括数据接入、索引、缓存和验证，不把仓库示例数据当作完整数据。

| 核心能力可被复用 | 竞争者可能按许可取得并复用我们的相关实现；不能一边按 AGPL 分发，一边额外禁止其商业使用 | **战略成本 `O`，不伪造人民币价格**。如果核心实现的排他性是底线，路线 B 直接不适合 |
| 范围扩大的代价 | 开放范围若从云观星扩展到组合的小程序前端，共享组件和业务逻辑也可能受到影响 | 原生直接组合按高影响评估；不能用“独立分包”当作已经隔离的证明 |

这里的开放是适用的对应源码及其许可义务，**不是要求公开用户数据、账号凭据、生产数据库或所有无关后端**。也不是必然要求公开整个 Git 历史或只能使用 GitHub；具体交付方式与边界要按实际组合作品及协议判断。

## 6. 数据和远端接口：可以自主建设，但没有自动附赠

### 6.1 必须分开的四层

1. 引擎代码：负责投影、天文对象和渲染。
2. 数据成品：星表分片、巡天瓦片、纹理、星座、轨道文件。
3. 在线业务接口：搜索、别名解析、目标说明、轨道更新等。
4. 分发基础设施：存储、CDN、缓存、索引服务和监控。

官方前端源码中的名称查询和搜索调用 `VUE_APP_NOCTUASKY_API_SERVER` 下的 `/api/v1/skysources/...`。这是依赖存在的证据，**不是供第三方商业使用的公开 API 合同或 SLA**。下载引擎仓库不能自动重建这部分。[官方前端查询代码](https://github.com/Stellarium/stellarium-web-engine/blob/29870744c470ddc62fa869e153178c82a7824fa4/apps/web-frontend/src/assets/sw_helpers.js)。

| 数据部署方式 | 购买/经营成本 | 自主改造和可靠性 |
| --- | --- | --- |
| 向供应方取得成品数据及自托管权 | 数据许可 `D` + 我们的存储分发费用；可节省原始加工工时 | 最适合与自主引擎结合，但须包含格式说明、镜像/衍生/更新权和原始数据授权链 |
| 合同使用供应方接口/数据 CDN | `D` 可能按年、MAU、调用或流量计价，暂无可核报价 | 本地功能仍可修改，但覆盖/额度/稳定性受服务合同限制；需要导出与退出方案 |
| 采用独立获权数据，自行加工并托管 | 一些来源无许可费，仍有加工、更新、存储和研发成本 | 最可控，但数据一致性、版权、格式与覆盖由我们承担 |
| 直接沿用官网的公共 URL | 没有得到商业服务和完整数据授权的证据 | 不把它列为可交付的“零成本商用后端” |

### 6.2 已识别的具体数据权益问题

- **DSS 光学影像是主要待报价项。** MAST 当前数据使用政策把 DSS/GSC 列为版权数据，营利商业使用需要权利人的书面许可。不能把“NASA 托管”或“CDS 镜像可下载”等同于免费商用。[现行 MAST Data Use Policy](https://archive.stsci.edu/publishing/data-use)。
- CDS 的 DSS2 彩色 HiPS 登记同时列有自身 ODbL 信息和原始影像版权来源。因此 ODbL 的数据库权利不应被解读为覆盖所有原始影像商用权。[CDS 原始登记](https://alasky.cds.unistra.fr/MocServer/query?ID=CDS%2FP%2FDSS2%2Fcolor&fmt=html&get=record)。更换成其他巡天可作为候选，但需要比较光谱、覆盖和画面；不能默认等价。
- 十亿级 Gaia 访问是引擎能力声明，不是仓库包含完整星表、可免费使用供应方编译数据或 API 的承诺。完整选定目录及加工成品的权利、格式、字段和实际规模仍待落实。
- 官网 credits 混用多个恒星、深空、纹理及说明来源；当前项目已经针对 HIP/Tycho 数值的商业限制做过替换，不能因更换引擎把旧受限文件带回。
- 现有星座定义、图画、OpenNGC、AllWISE 等按各自许可保留归因和派生分发规则；这些内容义务不能笼统说成“项目代码必须开源”。

**数据/API 费用 `D` 与引擎费 `L` 分开询价；即使支付了 `L`，也只有合同明确涵盖的数据和转授权范围才算已取得。**

## 7. 每月存储和分发费用

### 公开单价与模型

以腾讯云中国大陆 CDN、广州标准 COS 的公开示例单价做统一规划。CDN 按月累计阶梯：前 2 TB 为 0.21 元/GB，之后至 10 TB 为 0.20，再至 50 TB 为 0.18；COS 存储参考 0.118 元/GB/月、CDN 回源 0.15 元/GB、标准读请求 0.01 元/万次。HTTPS 请求超出适用免费量部分为 0.05 元/万次。

来源：[CDN 基础计费](https://cloud.tencent.com/document/product/228/75562)、[HTTPS 请求计费](https://cloud.tencent.com/document/product/228/75563)、[COS 计费示例](https://cloud.tencent.com/document/product/436/6241)、[COS 存储参考](https://cloud.tencent.com/document/product/436/50201)。没有使用新客优惠或未知商务折扣。实际地域、产品计费单位与账号资源包需要在采购时复核。

共同假设：

- 计算的是**云观星 DAU**，不是全小程序 DAU；每月 30 天。
- 每人每天新下载 10/30/100 MB，已经扣除客户端缓存复用；包含模块资源、星表和影像，是敏感性假设，不是实测用户行为。
- 500 GB 数据存储，CDN 字节命中率和请求命中率都设为 90%；两种命中率是独立输入。
- 平均一次成功数据响应 64 KB；假设账号当月还有完整的 300 万 HTTPS 免费请求量可供使用。若已被其他模块消耗应相应调低。
- CDN 流量使用十进制 GB/TB；COS 在模型中用十进制等效 GB 做预算预留，实际产品计量换算与请求账单可能不同。因此表中只给约数，不声称逐分账单精度。
- 500 GB **不代表已经证实能装下 Stellarium 的完整数据**。例如 CDS 当前 DSSColor 登记约 419 万张瓦片，但没有据此核实全套字节量；恒星、轨道、纹理、备份还要另统计。

| 云观星日活 | 每人新下载 10 MB/天 | 30 MB/天 | 100 MB/天 |
| --- | ---: | ---: | ---: |
| 100 | 约 66 元/月 | 约 79 元/月 | 约 135 元/月 |
| 500 | 约 93 元/月 | 约 181 元/月 | 约 501 元/月 |
| 1,000 | 约 135 元/月 | **约 318 元/月** | 约 948 元/月 |
| 10,000 | 约 948 元/月 | **约 2,716 元/月** | 约 8,505 元/月 |

1,000 DAU × 30 MB 的算例：月下行约 900 GB；存储 59 元、CDN 189 元、回源 13.50 元、HTTPS 请求约 55.31 元、COS 读请求约 1.41 元，合计约 318 元/月。只算每 GB 而遗漏大量小瓦片的 HTTPS 请求，会低估费用。

同一算例的敏感性：HTTPS 免费量已用完约 333 元/月；两种 CDN 命中率均降到 50% 约 378 元；平均瓦片/响应降至 16 KB 约 533 元；存储从 500 GB 增加到 2,000 GB 约 495 元。它们是分别改变一个条件，不是同时发生的报价。

**这不是云观星的全部现金成本。** 不含 `L`、`D`、Agent 实际新增使用费、搜索/轨道服务的新增计算容量、日志监控、首次批量加工、全量更新写请求、必要备份/容灾，以及境外分发。现有数据包能否覆盖需求要先确认，不能用低月费掩盖数据未获得。开发与维护工作量独立列示，不加入现金总额。

已有资源方面，项目记录已购 4 核/4 GB、3 Mbps、40 GB SSD、300 GB 月流量的轻量主机（109 元/年，2027-08-26 到期）。这是已有投入，不重复列为新采购，也不能把首购价当永久续费价。3 Mbps 理论聚合吞吐仅约 0.375 MB/s、40 GB 磁盘也有限，大量影像应考虑对象存储/CDN；搜索服务是否要扩容以负载验证为准。[当前部署事实](E:/dev/worktrees/Starward/remote-main-20260908/project_context/deployment/current-state.md)。

项目原约 820/1080 元月度规划包含天气等其他能力，不是本模块的新增费用；合并预算时要扣除已计入的重叠存储/分发项，不能将这两个总数机械相加。

## 9. 已采用路线与仍需取得的证据

用户已采用 **C（现有引擎扩展）**。在 Agent 主导、开发投入不折成现金、需要自主改造的口径下，C 无需购买引擎许可，接受更多 Agent 迭代和质量验证，并保持自有业务源码的许可边界。A 的目标能力更接近，但源码/数据合同和原生适配仍未确定，当前不采购。不能用人工工资换算出的差额替用户证明某笔许可费“划算”。

当前采用路线的主要不确定性：

1. **现有引擎的代表链路**：实施时先验证大气/银河/渐进巡天等关键机制与当前姿态、投影、拾取、生命周期的组合；用真实 iOS/Android 设备证据与实际 Agent 投入修正估算，不先扩散尚未成立的实现。

3. **条件性备选资料**：前文 Stellarium 8–16 Agent 小时试验、商业询价草稿及 AGPL 边界审查仅在重评相应路线时使用，不再是当前实施前置任务；没有代用户联系供应方或发送询价。

这些是采购/实现决策所缺的具体证据。公开资料研究可以得出候选、约束和预算模型，但不能产生供应方未提供的价格，也不能替代原生运行试验。

## Confirmed findings (pre-fix lines)

1. **P2: selective invalidation invalidates unrelated in-flight representations.** `response-cache.ts:166-170` increments one global generation even for a prefix/account matcher; `:286` requires that global generation and the same memory object reference. `api-client.ts:317,333,386,399` uses this to accept304, offline fallback and late200 storage. A plans GET can start with a correct If-None-Match, then Settings clears only temporary map/sky caches; the plans body remains identical and its read is not cancelled, yet304 rejects with`bff_http_304`, a transport failure rejects instead of valid stale fallback, and a new200 is not cached. The same issue affects unrelated account reads during removeScope. Separately, evicting a valid memory body and reading the unchanged disk representation changes object identity, causing another false304 failure. Use per-request/key invalidation fences separate from the global native-writer generation, and compare stable representation identity rather than cache-object allocation identity; release request fences on every completion/cancel path.

2. **P2: deletion reports local cleanup success when native pointer replacement and removal both fail.** `response-cache.ts:107-109` suppresses removeStorageSync failures; `:175-181` discards in-memory manifest after failed commit even if durable pointer/chunks could not be removed; `:288` removeScope resolves unconditionally. `api-client.ts:888-904` and Settings consequently claim successful cleanup. Injecting writable-storage failure on both setStorageSync and removeStorageSync leaves the old account manifest/body recoverable by a fresh cache instance after removeScope resolves. Native I/O failure cannot be made into a physical-erasure guarantee: return/surface incomplete local cleanup while preserving the already-successful remote account deletion, clear current in-memory/query state, and fence the revoked stored identity in the current runtime if session removal also fails.

## Repairs completed and verified

- Replaced the transport's global generation check with an exact-key request fence. Only matching invalidation predicates revoke the fence; every success/error/timeout/cancel releases it, so completed requests do not accumulate. The global epoch remains private to async chunk publication. Stable serialized representation plus storedAt determines whether a disk-restored body can satisfy the original conditional request; cache object allocation is irrelevant. The obsolete public generation() transport API was removed.
- Cache removal failures now set an observable incomplete-cleanup result, including failed deletion of a late async orphan chunk. removeScope awaits the writer and returns success/failure; a full explicit retry sweeps owned leftover chunk keys and can recover the cleanup status. Failed storage can still physically retain old bytes; the result no longer claims otherwise.
- Account deletion retains its successful server receipt and returns localCleanupComplete separately. It aggregates response cache, draft enumeration/removal, session and installation cleanup results, always clears the corresponding current Query state, and marks the server-erased stored account unusable in the current runtime even if native removal failed. A late login response for that erased ID cannot rewrite its session; the cached session promise is also cleared on confirmed erasure. A different current account remains usable. This does not promise persistent tombstones when the native store refuses every write/delete, or proof of physical erasure after process restart.
- Settings uses its existing notification/modal components for incomplete cleanup while keeping the remote deletion outcome truthful. The existing app-store.clearLocalCache previously published an immediate success toast and swallowed its own native state write failures: it now still resets map/search/context synchronously, returns the queued persistence result, and leaves final feedback to Settings after both response and state owners finish. resetAfterAccountDeletion reports its state-key deletion result; Settings includes it in the result message. All code callers are the existing Settings handlers. No layout, token, resource, artwork or adopted design was changed.
- The UI companion skill and relevant current DESIGN/Screen shared-state recovery clauses were read for this narrow existing feedback-state correction. No design migration, new component, approval flow, deployment or device operation was added.

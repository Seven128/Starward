### What the available evidence actually explains

1. **Installation compatibility is a weaker check than a live agent connection.** `wechatide-skill/skills/installer/scripts/check-installation.mjs` checks Electron package version against installer helper minimum2.02.2607152, then only spawns the selected wrapper with`-h`. It never proves the GUI service, MCP, client authorization or callback path. The extracted package is2.02.2608070, name微信开发者工具, main`js/electron/main.js`. Thus working help/compatible=true and CONNECT_ERROR are consistent results, not contradictory evidence.
2. **No concrete bootstrap mismatch was found for the recorded auth call.** The official`wechatide.cmd` changes cwd to its directory, preserves the caller cwd in the lowercase cwd environment field, sets ELECTRON_RUN_AS_NODE=1 and launches skill-index.js through the large Electron exe. The probe implements the same argv shape for`auth -c Codex`; its difference is that the official wrapper removes duplicate`--electron`, whereas the probe does not. There is no duplicate flag in that intended call. Static executable inventory found exactly one official-wrapper candidate over50MB after exclusions:微信开发者工具.exe, which is the probe's executable. Encoding/chcp affects console output, not these ASCII client/auth arguments. `wechatidecli.cmd` targets a different, legacy CLI and should not replace the Skill wrapper.
3. **Windows auth bypasses registered URL association for launch.** Public distribution`js/common/cli/skill-index.js` (147,850 bytes, one minified line; auth code around byte offsets15,700–18,950) creates a random local callback task, listens on127.0.0.1 with an OS-assigned port, then directly spawns`process.execPath` with the`wechatide://skill/auth?...`argument and`--cli`, after removing ELECTRON_RUN_AS_NODE from the GUI child's environment. It waits up to30,000ms for a callback; spawn failure OR callback timeout become CONNECT_ERROR/connect_failed. Therefore missing installer/URL registration alone is not an established root cause, and a missing access token should not be inferred from this error.
4. **The pending callback precedes user authorization.** ASAR entry`js/932e6f763ae5066b5462ff169341b870.js` handles the auth URL. When service-port/client permission needs confirmation, it first starts the CLI service and sends pending+taskId, then invokes authorization UI and updates that task. Since the observed failure had no pending taskId, unclicked authorization/unknown credentials are not the demonstrated failure stage. The current evidence points only to startup/URL dispatch/CLI-service/callback establishment, not to an authenticated business-tool failure.
5. **An empty project-list window does not prove all bootstrap steps are finished.** ASAR`js/electron/electron.main.js` registers the URL business handler after async proxy/backend/plugin/static-config initialization and MiniCode service startup. Entrance window creation occurs before the final awaited MiniCode startup.`js/0fe7f92a1cd7a62cd65612f12ca36884.js` queues initial/second-instance wechatide URLs until that handler registers. A slow/failed initialization can therefore leave auth waiting even while a window is visible. This is a supported explanation of the symptom, not a diagnosis that a specific initialization step failed here.
6. **No current environment override mismatch was established.** CLI computes its profile namespace from the base app.asar path and package name; GUI bootstrap`js/c47addee36149e53772b60ab7e158ffe.js` hashes its base app path and on Windows derives its local data root from the parent of the temp directory. The current shell has no ELECTRON_BASE_APP_PATH override; TEMP and TMP agree and their parent matches the CLI's expected Local root. This is a current allowlisted path comparison, not a read of any profile content. Different install roots use different data hashes; however the main process acquires a single-instance lock before bootstrap paths, so side-by-side binaries should not be assumed to mean independently running IDE instances.
7. **The first probe hid the detail needed for the next diagnosis.** It did not output stdout`message`, and its stderr filter dropped every line containing`authorization`, including the official`wait WechatIDE authorization timeout`message. CONNECT_ERROR alone cannot distinguish the concrete cause. Root has now improved the existing redactor to retain safe message/suggestions/error classes and remove URL query values. No further new-IDE command was run as part of this static review.

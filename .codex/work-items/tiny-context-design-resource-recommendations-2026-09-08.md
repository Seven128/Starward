# 给 Tiny Context 的建议：设计资源生成、采用与开发读取

基于 Starward 当前实践及本地安装的 Tiny Context 0.12.0 / schema 5 整理。本文是给公共库的优化建议，不是已实现的 Tiny Context 能力，也不改变本项目现有规则。

核心建议：把“如何形成可继续修改的设计资源”沉淀为按需使用的通用 Skill，把“哪些资源已经成为项目要求、开发如何找到并遵循它们”内化到 Context 与开发契约。资源实体保存在 Context 外；Context 保存其权威引用、适用范围和必要的已确认决定。

## 1. 从 Starward Skill 提取什么

建议提供通用 `design-resource` 能力，只负责资源工作，不承担产品设计方法、项目风格或任务编排。它可作为按需安装或调用的配套 Skill；普通项目初始化不必自动生成设计目录、模板或设计任务。

应保留的逻辑：

1. **读取当前要求。** 从用户输入、默认 Context、相关职责 owner、项目已有设计规范及必要的当前实现中获取约束。区分必须保留的内容、已确认方向、本次修改范围和仍可探索部分。项目未采用某种文档结构时，不要求先补一套设计文档才能工作。
2. **沿用选定方向。** 已有选择时继续修改；根据用户反馈明确修改项与保留项。生成数量、页面和状态范围随当前任务，不固定两方案、多轮迭代或全状态矩阵。没有修改要求时，不为完成流程制造一轮修改。
3. **使用实际可用的工具。** 遵循用户和项目的工具选择，优先复用现成能力；保留可编辑源文件、项目链接及实际支持的导出格式。工具能力或格式转换需要实际验证，不能把截图、HTML 和原生设计节点视为同一种交付物。
4. **保留真实产物。** 保存关键输入、参考来源及用途、原始输出和必要的修改前后版本；实际查看渲染结果。后续人工或 Agent 修订与原始生成结果区分，旧截图不能冒充当前结果。详细记录放资源目录或任务目录。
5. **检查可用性。** 根据当前需求检查完整性、可打开性、可编辑性及实际覆盖范围。只交付截图时如实说明；缺少素材、字体、访问权限或可运行原型时明确缺项。检查器不替用户决定审美偏好。
6. **处理正式采用。** 候选、偏好选择和正式采用的含义要分清。确认采用且在授权范围内时，更新所属 Context 的有效引用，消除受影响规则的冲突，替换旧适用范围；已有明确采用授权时直接执行，不重复询问。
7. **交付可继续开发的入口。** 后续开发者能从采用入口找到源文件、视觉参考、素材、必要的行为说明和比较条件，不需要重新阅读完整探索历史。

不应迁入公共库的内容：Starward 的配色、字号、命中尺寸、密度与排版方法、业务与交互规则、页面/主题清单、平台依赖、指定 Stitch 或 Figma 的默认路线，以及历史 A/B 实验、固定模型档位、盲评量表、强制轮数和旧节点 schema。模型、用量、哈希等运行记录按任务需要保留，不提升为所有设计任务的必填门槛。

## 2. 设计资源存在哪里

建议默认目录为 `docs/design-resources/`，允许项目使用已有等价目录。文件夹名称是推荐约定，不是 Context 成立的前提。

```text
project_context/
  global.md
  context.toml
  areas/<area>/<existing-owner>.md   # 所属页面、组件或功能的现有职责文档

docs/design-resources/
  <surface>/<page-or-component>/
    ADOPTED.md                     # 当前采用入口及各自适用范围
    adopted/<resource>/
      README.md                    # 打开方式、覆盖内容、比较条件及必要说明
      source/                      # 可获得的可编辑源文件或原型
      reference/                   # 视觉、动效等参考
      assets/                      # 所需素材及来源
    candidates/<run>/              # 探索稿和修改记录
```

以上是示例，不要求每种资源都建立所有目录。外部设计文件可以通过稳定链接引用；必要时保留可获得的本地导出，以降低权限、链接和远端内容变化造成的不可用风险。只有截图的任务不应伪造可编辑源文件。

Context 中保存：所属对象、当前采用入口、适用平台/状态/主题/局部范围、必要的已确认决定及相关权威边界。资源目录保存：源文件、图片、视频、素材、资源清单、提示词、生成记录和比较证据。任务进度与生产迁移记录留在任务记录中，不做成长期 Context 状态机。

**唯一性应落在“同一适用范围只有一个当前依据”，而不是“一页只能有一个文件”。** 一页可能部分采用新组件，其余部分继续沿用原有设计；一个入口可以明确映射多个互不冲突的范围。共享组件资源由共享组件 owner 引用，页面链接该 owner，避免各页复制同一套规则。

## 3. 怎样接入现有 Context 机制

沿用现有机制形成读取链：

```text
开发契约 → 默认 Context / 任务相关 owner
         → owner 的当前设计资源引用
         → 采用入口 → 本次相关源文件、视觉参考和说明
```

具体建议：

- `global.md` 只在项目需要时保留很短的导航事实，不全量载入图片清单、页面采用记录和生成历史。
- 所属 Context 按现有 manifest 机制注册并按需读取。开发者修改页面或组件时，应从职责和实现位置定位 owner；不能要求用户必须说出“设计资源”关键词才触发读取。
- 读取 owner 时，继续读取它明确指定的当前设计依据。资源目录不应因被引用就整体注册成默认 Context；历史来源链接也不自动升级为开发要求。
- 不强制项目采用 `Screen Contract`、根 `DESIGN.md` 或新增 `design.md`。这些是 Starward 的组织方式；公共规则应表述为“既有业务/交互 owner”“共享设计规范 owner”和“当前采用资源”。

Tiny Context 0.12.0 已支持如下本地来源声明，可先复用它声明采用入口：

```markdown
<!-- ty-context-controlling-source domain="design" path="docs/design-resources/web/search/ADOPTED.md" -->

搜索结果页的当前设计依据见上述采用入口。
适用范围：桌面端、浅色主题、正常结果状态的结果列表。
其布局与素材是该范围的开发要求；业务和状态含义由本文负责，
共享视觉规则由项目现有设计规范负责。其他状态沿用原有要求。
```

该声明目前请求的是本地 UTF-8 文件校验，不是图片/原型递归加载，也不是设计遵循证明。建议优先补足“开发必须跟进相关权威引用”的契约与文档，再判断是否有必要增加结构化资源字段；不要直接发明一套与 manifest、owner 和既有来源声明并行的设计注册系统。

## 4. 如何让开发严格遵循

建议将下面这段通用义务写入 Tiny Context 管理的开发契约，而非仅留在生成 Skill 中：

> 当改动涉及具有已采用设计资源的界面或组件时，先读取所属 Context 及其明确引用的当前资源，并实际查看相关视觉参考；涉及已确认动效或交互时，检查相应原型或行为说明。在声明的适用范围内，已采用资源属于实现要求。按目标运行时忠实实现，在可比条件下检查实际结果并修正偏差。不得静默替换已确认设计；资源缺失、规则冲突或平台限制须明确处理并报告。普通修复不要求重新生成设计资源；设计采用、结构校验和静态预览均不证明生产实现完成。

这里的“严格”需要具备明确边界：

- **采用阶段解决权威冲突。** 业务含义、共享视觉规则、页面构图各归其 owner。批准的变化同步更新受影响的规范，不能靠一句“图片优先”覆盖业务、可访问性或平台约束，也不能用旧规范无声否定新采用稿。
- **实现阶段实际查看资源。** 只读 README、只扫链接或凭历史印象写代码，都不足以完成视觉资源读取。静态布局看当前图；已采用动态行为按需要运行原型或读其可执行源与行为说明。无法访问必要输入时，明确受影响范围并继续独立工作，不虚构已还原。
- **验证阶段比较真实实现。** 根据当前要求明确视口、字体、数据状态、主题、安全区和动态状态等必要条件。在可比的自有 UI 范围检查布局、字体、颜色、图标、素材和行为。适配规则由项目决定，不默认将不同屏幕整体缩放成同一张图。
- **参考内容与产品事实分开。** 示意数据、地图底图、系统外壳等是否属于还原范围，由采用入口声明；不把原型中的假数据、固定样例或装饰模拟转成生产规则。
- **修改设计与修正偏差分开。** 按现有采用稿修复不需要重新选择设计；若任务已授权改变设计，就更新资源及其 owner。不能为让现有代码“通过”而反向修改设计要求。

这些是 Agent 的行为义务，需要实际运行观察支撑。仅安装一段契约无法保证模型遵循，不应把文件存在或校验通过宣传为像素还原保证。

## 5. 公共库可以校验什么

建议维持 Tiny Context 的轻量边界，分两步落地：

**第一步：复用当前能力。** 更新 managed 开发契约、Context 维护说明与按需资源 Skill，给出上面的引用示例。继续使用现有 manifest 和本地 controlling-source 检查。明确资源是开发输入、候选不是默认权威，以及生成 Skill 不必在每次开发时再次调用。

**第二步：仅在实际需要时增强诊断。** 对显式声明的设计依赖检查路径、安全性、采用入口是否存在，以及明确列出的必需本地文件是否缺失。如果引入可机器读取的适用范围，再检查相同范围的多个当前声明；没有结构化信息时不要声称能从自然语言可靠判定冲突。远端访问与资源包完整性检查应显式触发，不让日常 Context 校验自动联网或运行设计工具。

自动检查不能证明：用户已经批准、截图对应当前代码、模型实际查看过图片、产品交互正确，或设计具有审美质量。不恢复设计前置审批、固定交接文档、历史哈希门禁或任务完成认证。

建议用以下案例验证公共库机制是否有效：

1. 新会话只收到“修改某页面”时，能定位所属 owner 并继续找到相关采用稿。
2. 同目录存在较新的未采用候选时，不以时间或文件名取代当前依据。
3. 只替换某组件或主题时，其他范围保持原有有效引用。
4. 采用入口或必需资源缺失时，报告具体缺项，不伪装为“没有设计约束”。
5. 普通修复沿用现有资源，不触发重生成、重新审批或固定交接流程。
6. 检查输出清楚区分“结构可读取”和“生产已验证”。前者可做确定性回归；后者需要单独的 Agent/运行时实践验证。

## 6. Starward 的依据与可迁移经验

- [原始设计资源 Skill](../../.agents/skills/starward-design-resource/SKILL.md)：已经区分生成、局部修改、交付和采用，并明确开发读取不依赖再次调用 Skill。
- [Context 维护规则](../../project_context/context-maintenance.md#mini-program-page-design-resources)：资源放在 `docs/design-resources/`；Context 保持精简，页面 owner 持有当前入口和适用范围。
- [页面 owner](../../project_context/areas/main/screen-contracts/wechat-miniapp.md)：承接采用资源的强制读取和实现义务。
- [当前地图采用入口](../../docs/design-resources/wechat-miniapp/map/ADOPTED.md)：按范围区分已采用组件、仍适用的旧构图及未覆盖部分。
- [采用资源包](../../docs/design-resources/wechat-miniapp/map/adopted/spot-information/README.md)：提供实际源文件、截图、动态行为、比较条件及示意内容边界。
- 本地 `node_modules/project-tiny-context-harness/README.md`：核对了 0.12.0 / schema 5 的默认读取、按需 owner、来源声明和结构检查边界；未以此判断上游最新版本。

目前 Starward 将读取义务分布在项目入口、维护规则、页面 owner 和实现约定中。公共库可统一承接通用义务，让项目只维护自己的采用关系、范围与设计决定；生成工具与具体设计语言继续由项目选择。

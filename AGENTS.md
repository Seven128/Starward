# Starward engineering rules

These project rules apply throughout authorized research, design and development, whether or not a Skill is loaded. Scale the work to the change: routine fixes need no new plan, architecture document or approval stage. The managed Tiny Context entry below owns Context discovery and maintenance; project choices stay in their existing Context owners.

## Development execution

- **微信开发工具只保留当前有效源码入口和必要窗口。** 操作开发项目、快照或窗口前，读取并遵循 [project source, snapshots and windows](project_context/development-workflow/development-feedback.md#project-source-snapshots-and-windows)。仓库是唯一源码事实源；关闭当前开发项目前完成或核验最新源码同步，不重建废弃快照、不把产物反写源码。默认一个项目窗口；明确隔离需求结束即退役旧入口和窗口。
- 子代理用完立即关闭；需要时新建，不复用旧子代理。
- **不主动做只读的代码审查。** 除非用户明确要求，不安排独立的只读代码审查任务或审查型子代理；实施中的必要源码阅读、调试和结果验证照常进行。
- **Write tests only on explicit request.** Do not create or expand automated tests (unit, integration, E2E) or their support code/infrastructure without explicit user authorization for that scope. Ordinary implementation, fixes, refactoring or "verify this" do not supply it; renaming tests as verification scripts does not bypass it. When the user requests test authoring, read and use [starward-write-tests](.codex/skills/starward-write-tests/SKILL.md). Continue proportionate existing checks and required runtime acceptance. Minimal adaptation of existing tests to confirmed interface/contract changes may preserve their established coverage; do not add cases or weaken assertions to force a pass. Verification requirements do not themselves authorize new test code; report any remaining evidence gap.
- **Native migration test-code restriction (2026-10-31).** The user requires all existing project-authored test code to be removed and forbids adding or restoring any test code during the WeChat native migration, including fixtures, test drivers, and tests renamed as verification scripts. This overrides older test-reuse/adaptation instructions for this migration. Preserve normal business/runtime validation and code-quality rules; use type/build checks and proportionate actual-runtime observations without writing new automated tests. Only a later explicit user change to this restriction can reopen test authoring during migration.
- **Use the smallest useful runtime observation.** For Mini Program development/debugging, use the [development skill](.codex/skills/starward-miniapp-development/SKILL.md) with the matching official DevTools skill. Before choosing latency, frame/rendering or memory measurements or diagnostics, read its [performance investigation method](.codex/skills/starward-miniapp-development/references/performance-investigation.md). Reuse confirmed sessions and valid evidence under the stopping rules below.
- **先共享规则，再批量执行，最后处理例外。** 重复的数据、素材和验证工作先区分公共规则、数据差异与不同机制，复用现有批处理和验证入口。代表路径消除具体机制的不确定性后，转为批量准入、集中复核和异常队列；仅未覆盖机制、质量异常或外部限制支持继续逐项处理。增加同类对象应主要增加声明与批量结果，不复制代码、版本、脚本、测试和交接。批量化不免除完整质量检查和最终验收。
- **Keep one current plan for substantial work.** Define the result, module responsibilities, dependencies, key risks and completion evidence by shared responsibility and distinct mechanisms. Bound representative experiments and their transition to integration, batch use or exceptions. Revise the approach only for changed requirements, ownership, dependencies or decisive evidence; replace superseded directions. Keep status in one short task handoff and results with their evidence owner; resume there after context reset. Routine failures and results do not turn the plan or durable Context into an execution log.
- **Stabilize boundaries, then deliver modules.** Validate uncertain architecture with a small real path through the intended data, state and runtime owners. Develop modules in dependency order, including their normal result, failure/recovery and affected consumers. Adjust architecture when evidence invalidates it; do not design every implementation detail upfront or postpone all integration until the end.
- **Control changes of direction.** Keep findings under their responsible module. Interrupt for invalidated current/dependent work, material data/security risk or necessary replanning; otherwise queue findings, including unrelated defects. Extra defensive machinery must address a supported failure mechanism or material safety/data-integrity risk and justify its complexity; omit speculative robustness rather than silently expanding scope. When blocked, state the dependency and continue independent work. Report module outcomes and remaining obligations.
- **Keep verification proportionate.** Select existing checks and runtime observations sufficient to establish the user's result and material risks, considering impact and setup, maintenance, execution and triage cost. Reuse valid evidence. Prioritize supported inputs, reasonable recovery, known regressions and serious security/data-integrity risks. Select representatives by distinct failure mechanism, not exhaustive input/theme/device/timing combinations. Each additional check must resolve a concrete uncertainty that could change implementation or completion; an imaginable failure alone creates no acceptance requirement. Do not impose mutation or fault injection as a routine gate.
- **Separate development checks from final acceptance.** Run relevant type, contract, behavior and integration checks for changed behavior, explicit unverified obligations or material risks. Batch related repairs before wider integration; perform required visual, interaction, device and performance acceptance at useful milestones. Test architecture-critical platform assumptions before dependent expansion. Preserve product requirements and safety obligations. If a required device/service is unavailable, continue independent work and leave its checks unverified; repeating local checks cannot complete target acceptance. Recoverable local services and missing test data remain preparation work.
- **Stop when the required evidence is sufficient.** Once necessary checks pass and the relevant risks are verified, advance delivery. Expand or repeat checks only for relevant code, input or requirement changes, an actual failure, or a specific unresolved risk that could materially affect the user's result. Do not repeat verification merely for reassurance.
- **Keep tool work bounded.** Reuse a verified tool/session for its supported operation; diagnose the first failed boundary before changing unrelated layers. Read targeted ranges or cursor pages and summarize structured results before printing; truncation is not a complete read. Batch independent reads, serialize stateful operations, and check the prior result before retrying a possible side effect.

## Project-local Implementation Decisions

Apply these quality rules to affected responsibilities and their real consumers:

1. **Preserve product meaning.** Trace the user's result and governing invariants before decomposing work. Contracts must preserve identity, units, time/space coverage, validity, missing/partial data and failure meaning. A convenient provider field or existing limitation does not authorize reducing the requirement; a successful upstream response does not establish the downstream effect.
2. **Keep clear ownership and dependencies.** Inspect implementation and callers before extending them. Give shared data, state and business rules one responsible owner; keep dependency direction explicit and avoid circular imports or competing sources of truth. Follow `project_context/architecture.md`; consult `project_context/architecture/maintenance-boundaries.md` for listed responsibilities and confirm the current code before acting on historical debt.
3. **Reuse coherent responsibilities.** Search existing code and platform capabilities first. Share rules that must evolve together, including on first implementation; migrate real consumers and retire displaced paths. A helper is insufficient if callers still copy its state transitions, recovery or presentation policy. Keep identity, configuration and content in validated declarations; use narrow adapters for distinct behavior. Keep simple single-use logic inline unless extraction names an independent responsibility, isolates a complex boundary or clearly improves readability. Do not merge different domain meanings, lifecycles or trust boundaries based on appearance, size or duplication, or add speculative frameworks or unrelated flags.
4. **Design recovery with the success path.** Handle failure/lifecycle cases required by the affected contract or a concrete material risk: invalid/missing inputs, partial failure, cancellation and stale/out-of-order results where applicable. Keep retries bounded and safe; enforce idempotency, concurrency and transactions where effects require them. Release requests, subscriptions, files and GPU/native resources with their owner. Use defined recovery or degradation semantics; otherwise propagate or surface failure explicitly. Do not conceal failure with broad catches or empty/zero/success-shaped defaults. Preserve valid independent results and distinguish unavailable, stale and genuine zero values. When handoff is needed, retain minimal non-sensitive diagnostics and resumable state; do not introduce a generic recovery framework solely for handoff.
5. **Protect trust and compatibility boundaries.** Validate unknown input at its owning boundary, then pass validated typed values inward without repeating the same checks. Type declarations or casts alone are not runtime validation. New trust boundaries and authorization, ownership or distinct business constraints still require their own checks. Keep secrets and private data out of logs and artifacts. Version persisted/published contracts when compatibility requires it, cover actual old/new consumers, and plan safe migration/recovery for material state changes. Do not silently destroy historical data or strand deployed clients.
6. **Bound performance and operational cost.** For affected hot paths, assess realistic data volume, algorithmic cost, request frequency, concurrency, cache lifetime, memory, package/storage size and external charges. Use existing limits or justified measured budgets, not invented numbers. Measure the relevant bottleneck before optimizing; retain enough non-sensitive diagnostics to locate failures. Do not sacrifice correctness or maintainability for an unmeasured gain.
7. **Verify behavior at its owner.** Before selecting or running checks, read and follow the [verification owner](project_context/areas/main/verification.md#user-journey-verification), including its journey and evidence boundaries. Verify actual rendered results, durable state readback or measured resources when those are the claim. A pass with absent effects, empty data or the previous result does not prove the outcome. Apply the test-authoring authorization, proportionate scope and stopping rules above; required runtime acceptance remains distinct.
8. **Close against scope.** Fix known discrepancies before dependent expansion. Before completion, compare all promised outcomes with current evidence, including obligations outside edited files. Missing evidence remains unverified, known defects remain failed, and successful degradation does not replace a required working capability.

## Cross-stage Capability Research

- 任务涉及“真实天文图像→云观星显示素材”的获取/提取、批量加工、图质异常、处理链恢复或融合接入时，使用 [.codex/skills/starward-astronomical-imagery/SKILL.md](.codex/skills/starward-astronomical-imagery/SKILL.md)，即使请求未提SXT或抠图。执行其主动调研、有限试验和有证据的技能/Context回写；已验证批次复用规则。纯星表/天文计算、普通UI/通用缓存和非云观星美术素材不自动触发。
- Before choosing or narrowing a complex capability, inspect suitable existing project/platform capabilities, mature alternatives and working examples. Bound research to material gaps in target support, behavior, data coverage, rights, maintenance, integration cost and performance. Prefer a suitable mature solution; explain the decisive reason for custom work. A reference feature is neither automatically required nor safely ignored when it changes the intended outcome.
- Carry confirmed choices and reassessment conditions forward with their existing owner. Reopen them only when relevant evidence or requirements change. Verify real inputs, entitlement and publication before building dependent behavior; an adapter or feature flag does not supply data. Keep options, adopted decisions and unresolved assumptions distinct. Research authority does not itself authorize implementation, procurement, external contact or deployment.

## Shared components across design and implementation

Identify shared product/interaction responsibilities during design as well as coding. Before defining or changing them, read and follow [shared component continuity](project_context/context-maintenance.md#shared-component-continuity) for ownership, consumers, variants and resource registration. Implement the shared semantics and migrate affected consumers; keep unrelated business logic out of visual primitives. Design reuse does not establish verified implementation.

## Project-local UI Implementation Rule

- For design-resource creation, revision or adoption, use `.agents/skills/starward-design-resource/SKILL.md`. Ordinary implementation of adopted resources does not restart resource generation.
- For mobile UI, gesture, animation, accessibility or shared interaction work, use `.codex/skills/uiux_design/SKILL.md`. Read `DESIGN.md` and the affected Source Plan/Context first; those owners outrank the implementation Skill.
- For UI implementation/testing, strictly follow current adopted resources within their scope; compare actual target-runtime appearance and behavior under matching conditions, repair discrepancies and rerun affected comparisons before passing. For Mini Program UI, read and follow [page design resources](project_context/context-maintenance.md#mini-program-page-design-resources), including required source reading, comparison methods and evidence limits. Do not silently approximate or substitute the design.

# Tiny Context development contract

Tiny Context preserves durable project facts and this short development contract. It does not manage tasks or certify product completion.

- Understand the user's requirements, default Context and relevant owners. Use clear source material directly; clarify real gaps without manufacturing plans, design documents or handoffs.
- Start with `project_context/global.md` and project-declared defaults. `ty-context context list --default` is optional. Without the CLI, read the manifest directly: default Areas, `read_policy = "default"` nodes and their transitive `default_children`; `default_files` selects files without traversing their children. Pre-schema-5 projects also default to architecture.md. Do not install a CLI over the network merely to read files, or repeat unchanged reads. A failed query is not an empty set: resolve uncertainties material to the current change and report the remainder.
- Identify relevant owners from the affected implementation and follow their dependencies and current controlling sources, without waiting for a trigger keyword. Reading other workspaces does not authorize editing them. Stay within the user's scope, preserve unrelated changes and respect project business, technical and safety constraints. Distinguish requirements from current implementation; do not rewrite requirements to conceal conflicts.
- Choose implementation order, tools, decomposition and parallelism as appropriate. Before adding or materially extending a capability, inspect its owners, consumers, state/data responsibility and dependency direction. Reuse suitable capabilities from the project and target platform. Extract a shared unit when consumers must evolve together in the same responsibility, including a shared role already required on first implementation; migrate affected consumers within scope. Avoid speculative abstraction and unification based only on appearance, size or repetition. Complete the required change.
- Before adopting a new dependency or building substantial custom machinery, consider suitable mature alternatives. Reuse decisions whose conditions still hold; bound investigation to material gaps in target support, behavior, customization, maintenance, license and integration cost. Use a small runtime trial when needed to resolve uncertainty. Suitability, not popularity, decides; justified custom implementation remains valid. Local fixes do not trigger a new selection exercise.
- UI may be implemented and iterated directly from conversation, references and code; an independent design system or formal handoff is not a prerequisite. Reuse confirmed direction and shared components. For affected UI with adopted resources, follow the owner's current reference and scope, actually view current visual references and inspect relevant prototypes or source and behavior descriptions. Adopted resources are requirements within their declared scope. Implement faithfully in the target runtime, compare actual results under relevant comparable conditions and repair deviations. Resolve and report inaccessible inputs, conflicts or platform limits; continue independent work. Do not silently replace confirmed designs. Ordinary repairs reuse current resources without regeneration or renewed adoption; authorized design changes update affected resources and owners.
- Choose checks based on requirements, risk and project rules, including changed boundaries, affected consumers and relevant lifecycle/failure behavior. Reuse existing tests and observe actual outputs. Derive expectations from requirements rather than copying implementation. Repair failures and rerun affected checks after relevant input changes; do not repeatedly broaden checks without a new change, failure or specific concern.
- Update the owning Context only when durable project facts change. Keep project-specific goals, boundaries, confirmed decisions (including adopted/rejected choices), reasons, material reassessment conditions and useful entrypoints; reference exact values rather than duplicating code. Keep current resource references and scope with their owner, resources outside Context, and indices as navigation; repair relevant stale references. Optional cross-session handoff information and temporary investigation records stay task-local, outside durable Context.
- Report implementation, decisive tradeoffs, actual checks and material unresolved items honestly. Explain unverified scope and necessary human action. Installed instructions, structural validation, design adoption, static previews, historical results, tool success and subagent summaries do not establish current product correctness or agent compliance.

This contract applies to authorized implementation, including code, configuration, tests, documents and resources. Reading, discussion and audit do not themselves authorize edits. User scope, host safety requirements and more specific valid project constraints take precedence. No role workflow, mandatory intermediate artifact, model checkpoint or machine acceptance Gate is required.

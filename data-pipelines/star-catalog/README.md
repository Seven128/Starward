# BSC5P Mini Program bright-star acquisition

The Mini Program adopts the specific HEASARC BSC5P publication. NASA's [dataset metadata](https://data.nasa.gov/dataset/bright-star-catalog) identifies the dataset as public and links its license to [government works](https://www.usa.gov/government-works). Preserve the [HEASARC usage policy](https://heasarc.gsfc.nasa.gov/docs/heasarc/data_policy.html), dataset-specific provenance and author/service credit; this decision does not extend to arbitrary NASA-hosted mission material.

Acquire the fixed ADQL query in `build_bsc5p.py` from the official HEASARC TAP endpoint and the current IAU WGSN table. `build_bsc5p.py --catalog <VOTable> --names <IAU HTML> --output-dir packages/astronomy-core/data` uses pinned Astropy to decode binary VOTables, validate units/nulls/query completion and derive the complete -2 ≤ V ≤ 5 subset, excluding the publisher's 14 nonstellar HR identities. Runtime does not fetch either website. Raw bytes and acquisition evidence stay task-local; the runtime JSON and hash-bound manifest are versioned together.

The generator additionally supports `--magnitude-limit 6.5`, producing the separately versioned `bsc5p-bright-stars.v2` data and manifest with 8,404 rows. The acquisition CLI default remains the 1,630-row v1 profile; request 6.5 explicitly to reproduce the current runtime base catalog. Each profile requires the pinned publication's complete row count and rejects upstream query overflow; a smaller response cannot be relabelled as the deeper catalog. Obtain the exact full-column URL from `query_url(magnitude_limit)`. The earlier reduced-column rendering experiment is not sufficient input. `loadBsc5pStarCatalog` explicitly validates and loads either version for the static catalog publication endpoint; the default report/detail loader selects v2. Dynamic reports carry exact observing transforms and a publication reference; the sky client loads the static catalog separately and resolves only the selected instant. This integration does not establish dome projection, constellation artwork, deeper catalog coverage or physical-device performance.

Coordinates are FK5 J2000, epoch J2000. The original [catalog specification](https://cdsarc.cds.unistra.fr/viz-bin/ReadMe/V/50?format=html&tex=true) defines RA proper motion as cos(dec) × dRA/dt, in arcsec/year. Do not treat it as milliseconds of angle, seconds of time or unprojected RA. Preserve magnitude code H/R, uncertainty flags, and nullable B−V. BSC5P's older mixed photometry is not a new measurement or guaranteed Johnson V value.

IAU proper names join by exact, unambiguous HR or HD designation, otherwise exact Bayer identity including component digits or Flamsteed identity. Only the same IAU row supplies a HIP alias; conflicting identities never select the first candidate. Component/ambiguous identities are not guessed, and names/HD/astrometry are not imported from the displaced Hipparcos pack. The independent native App's existing data owners are outside this migration.

For the extended profile, supply `--identity-names <IAU archived naming-stars HTML>` from the [official IAU archive](https://iauarchive.eso.org/public/themes/naming_stars/). When the current designation identifies multiple BSC components, the exact same currently approved name may resolve through one explicitly published archived HR that belongs to that candidate set. Conflicting or out-of-set archived identities remain unresolved, and an explicit current identity is never overridden. The manifest binds this additional source; only identity is read, not archived positions, brightness or retired names. This preserves Alrescha (HR 596) and Marsic (HR 6008) when fainter components enter the catalog, and supplies published names for previously unresolved Alnitak and Alula Australis. A HIP alias can identify a multiple system and must not be used as a one-to-one component merge key.

The pipeline produces data and provenance. Production provider/object-detail/cache migrations and real sky scene verification must additionally establish the delivered capability.

## SAO faint-star supplement candidate

`build_sao.py` prepares the SAO J2000 visual-magnitude subset as a **candidate**, not an automatically published Mini Program layer. NASA's [specific SAO dataset metadata](https://data.nasa.gov/dataset/smithsonian-astrophysical-observatory-star-catalog) links government-works terms; retain the HEASARC use policy and SAO/ADC/USNO attribution. The inspected SAO publication predates the Hipparcos/Tycho releases and does not carry their identified NC statement. This source decision does not resolve the separate Hipparcos constellation geometry boundary below.

Acquire the eight half-open RA partitions returned by `build_sao.query(start)` for starts 0,45,…,315, POSTing to the HEASARC TAP endpoint with MAXREC 100000; save each `visual-to-10-ra-XXX.xml`. A single large query can return `OVERFLOW` despite the requested MAXREC; the builder rejects that response. Also save the BSC query `SELECT hr,sao,hd FROM bsc5p WHERE vmag BETWEEN -2 AND 6.5 ORDER BY hr`. Run the builder with `--source-dir`, `--bsc-base packages/astronomy-core/data/bsc5p-bright-stars.v2.json`, `--cross-identifications <BSC response>`, and an explicit `--output-dir`. The current checked-in server assets live under `workers/miniapp-api/assets/sao`; raw acquisition evidence stays task-local.

The checked source selection contains 254,651 rows with visual magnitude ≤10. Exact BSC SAO aliases suppress 8,369 redundant records; the BSC component rows stay intact. Two records with missing declination motion (SAO 208759/208795) are excluded, leaving 246,280 added identities. An unexpected population/exclusion change fails generation for reassessment. This cutoff does not assert completeness to magnitude 10. HD and spatial proximity never establish identity. Original `ref_vmag`, remarks, HD component and spectral type remain available for truthful details.

**The acquired TAP RA-motion unit label is wrong.** HEASARC's [SAO description](https://heasarc.gsfc.nasa.gov/W3Browse/star-catalog/sao.html) and the original specification define the FK5 RA motion in seconds of time/year; multiply by 15×cos(dec) to obtain tangent arcsec/year. FK5 declination motion already uses arcsec/year. The named source adapter and regressions preserve this distinction from BSC. Coordinates and epoch are FK5 J2000. Visual photometry is heterogeneous; do not call it uniform Johnson V, derive B−V from photographic magnitudes, invent a distance, or treat decimal precision as positional accuracy.

The full generated pack is a server-side acquisition artifact of about 20 MB. It must not be sent as one Mini Program response or bundled into the client. The generator uses the repository's existing Node runtime to produce exact UTF-8 `JSON.stringify` bytes; Python's exponent notation otherwise gives a different hash. Retrieval times were not recorded by the initial acquisition, so they remain null rather than being inferred from file modification times. The BFF publication, existing client cache, current-view loader, observation transform and celestial-details owners now consume this data. Their presence does not establish native rendering, persistent storage or phone performance.

`publish_sao.mts <generated-source-dir> <output-dir>` derives bounded vector tiles and a hash-bound spatial index using the existing Node/tsx tooling. Cells use declination rings with fewer longitude slices toward the poles; actual member directions determine conservative spherical bounds. Magnitude tiers remain disjoint and oversized cells split into stable numeric-SAO chunks. Each tile is capped at 768 rows and 192 KiB. Clients must select in EQJ using the inverse of the validated observation rotation, add the proper-motion angular bound for that exact instant, and preserve the source's magnitude/identity. `sky-stellar-tile-selection.ts` owns that selection; the Sky supplement hook and tile loader connect it to rendering and picking.

`publicationHash` identifies the index and its complete tile layout; `catalogHash` separately identifies the scientific source pack. URLs/cache identities must use the publication hash as well as tile identity, since changing partitioning can change a tile without changing the source catalogue. Each expected tile additionally carries byte length and SHA-256. The explicit output directory is a candidate artifact location, not a deployment command; only files listed by the current index belong to that publication. Never infer readiness from arbitrary leftover files in a reused output directory. HTTP/cache/lifecycle/detail code uses these identities; native composition and device budget checks remain open.

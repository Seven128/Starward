# EOG VIIRS annual night-light publication

This pipeline is the only current publisher for Mini Program satellite night-light estimates. It accepts an operator-acquired EOG Annual VNL V2.2 radiance GeoTIFF and its matching cloud-free-coverage GeoTIFF. It never downloads through a hidden URL, guesses a provider session, or converts radiance directly into Bortle/SQM.

`publish_eog_viirs.py` owns the PostgreSQL transaction and keeps the established CLI/import surface. `eog_raster.py` owns local input validation and legacy relative-AOI preparation. The fixed-method numerical owner is `eog_fixed_method.py`; its versioned thresholds, palette, units, statistics and quality policy are shared with TypeScript in `packages/miniapp-contracts/src/night-light-fixed-scale.json`. These product bins are fixed across regions, not calibrated sky classes. `eog_fixed_raster.py` delegates physical-area intersections to `eog_area_intersection.py`, using bounded vectorized GEOS operations through Shapely. After the existing validity/positive-area checks, a polygon entirely contained within one target pixel contributes its whole physical mass there; crossing polygons still use GEOS clipping. Target branch masks, core/halo exclusions and stable source accumulation apply to both paths; no new geometric tolerance or normalization is introduced. Geometry still comes from `project_display_grid.mts` and the project's coordinate package. Continuous shifted/identity branches are intersected separately and selected by the canonical inverse at each output pixel; a single forward mesh must not fold across the approximate GCJ footprint edge. Numerical arrays and image bytes have separate checksums. Proofs bind the intersection engine, library versions and implementation hash; readers retain historical GDAL proofs. A prepared raster is not a database publication or permission to reinterpret a schema-1 dataset.

The pinned [Shapely dependency](https://pypi.org/project/shapely/2.1.2/) is BSD 3-Clause; its GEOS engine is LGPL 2.1. Retain their distributed notices. It operates locally on existing licensed source pixels and provides no new data entitlement or service.

Preparation explicitly caches only source geometry within its own batch directory. Source arrays are hash-checked and hard-linked into each window; target areas remain independent. Validated per-window checkpoints bind input, geometry and numerical code and can resume an interrupted batch without another warp. Changed code or inputs require a new candidate directory. The sealed inventory remains the sole final marker; checkpoints cannot activate data.

1. Acquire the chosen year's matching V2.2 radiance and `cf_cvg` objects through the [official annual download](https://eogdata.mines.edu/nighttime_light/annual/v22/) account flow and retain their product readme/licence. The [V2.2 readme](https://eogdata.mines.edu/products/vnl/VNL_v22_readme_20230707.pptx) describes version-specific processing; its 2022 satellite combination must not be assumed for other years. A zero radiance pixel alone does not establish valid dark-sky coverage.
2. Copy `manifest.example.json`, fill the exact filenames and SHA-256 digests, and choose the bounded trial AOI.
3. Install `requirements.txt` in an isolated Python environment.
4. Run `python publish_eog_viirs.py --manifest <manifest.json>` with `DATABASE_URL` set.

The [access rules](https://eogdata.mines.edu/products/register/) restrict OpenID programmatic access to paid subscribers from June 1, 2026. Data reuse under CC BY 4.0 does not grant this download entitlement. Use the actual account's authorized acquisition route or lawfully acquired local files; record the exact product/year, acquisition date and hashes in the manifest. Do not treat the example filenames or a successful login as evidence that the selected assets have been obtained.

The command verifies hashes, CRS, grid alignment, AOI coverage and cloud-free counts; derives trial-region relative radiance bands; samples every stored spot; writes at most 512 native-map rectangles; and atomically publishes the dataset. Fully valid blocks retain coarse aggregation. Mixed blocks merge only identical valid horizontal runs on adjacent rows, leaving invalid radiance and insufficient cloud-free coverage unpainted. Each rectangle has its own radiance statistics. Increasing `gridStridePixels` can reduce subdivisions in continuous valid regions, but cannot fill missing coverage or guarantee that fragmented data fits the device budget. Exceeding 512 rectangles rejects publication; choose a smaller declared AOI if necessary. Changed light estimates increment the affected spot revision, so prior publication assessments become stale and the normal server-owned completeness gate must be rerun before a formal spot is visible again.

Published dataset identities are immutable. A publication generated with older processing must use a new `datasetVersion` to be replaced; rerunning the same published manifest reports `already_published` and does not rebuild it.

Schema 2 replaces relative rectangles with an immutable fixed display inventory. Run `prepare_fixed_eog.py --source-manifest <existing-manifest> --dataset-version <new-id> --windows <fixed-window-list.json> --output <release-root>/<new-id>`, then pass its `manifest.json` to the existing publication command. Preparation performs no provider or database operation and does not replace publication's actual source-file hash verification. It explicitly declares whole source pixels covering the requested AOI by outward alignment, retaining the requested bounds in the inventory. The display grid is derived GCJ Mercator, never labelled as WGS84 EPSG:3857. Geometry subpixels integrate the curved coordinate transform while retaining the original pixel's value and quality; they add no source resolution. The shared policy declares the integration step and a floating-point boundary comparison tolerance separately from the radiance bands.

For several declared parts, the same entrypoint can first prepare inputs only: `prepare_fixed_eog.py --source-manifest <existing-manifest> --dataset-version <new-id> --declare-parts <parts.json> --output <input-directory>`. The JSON is an array of `{ "id": "coast-west", "windows": [<fixed-window>] }`; IDs are unique lowercase letters/digits/hyphens/underscores, with a leading letter or digit and at most 64 characters. The request is at most 4 MiB, 4,096 parts and 4,096 requested windows per part; the existing 4,096 expanded assets per part, 1–5 cells per window dimension and 10-degree source AOI limits remain. Composition-implied unit cells count as owned keys: a key cannot belong to two parts, although their source halos may overlap. This declares supplied windows; it does not enumerate a country, choose LODs or create all window shapes.

`project_display_grid.mts --source-footprints` computes each part's envelope over every actual target pixel corner in both continuous inverse branches, using the same traversal as numerical geometry. The Python owner then aligns outward to the actual source grid and adds one original pixel on each edge. Both source headers must agree; out-of-source or oversized footprints fail instead of clipping. The projection subprocess has a 300-second limit, so larger work must remain in finite declarations. `parts/<id>/source-manifest.json` and `windows.json` feed the original numerical preparer explicitly; the final `declaration.json` binds their bytes, original source references/metadata and responsible code. Its `DECLARED_INPUTS_ONLY` status is neither numerical output nor a publication. Immutable replay checks existing bytes, and source/code changes prevent the final marker. Source-file digest verification still belongs to the publisher. Run `python -W ignore -m unittest test_eog_preparation_inputs test_eog_fixed_publication -v` for admission, bounds, replay and existing publication compatibility.

Each composition copies already computed fixed-cell numerical and quality pixels, then applies the common colour policy. It never rewarps the same pixels or averages RGB. The lossless six-band Float64 GeoTIFF companion carries radiance mean, valid area, source-missing area, insufficient-coverage area, published area and quality code under a local GCJ display CRS. PNG, numerical bytes and proofs have independent checksums, and the publication identity binds all of them. Assets and the input manifest are validated before the sealed inventory is written last. Schema-1 datasets retain their original thresholds, cells and histories. `night-light-publication.ts` and `NightLightService` read only the matching PostgreSQL `PUBLISHED` record and sealed files; preparation alone cannot activate Map data. Keep prior `<release-root>/<datasetVersion>` directories to preserve their immutable image URLs.

When a declared part's dense source geometry exceeds the existing `2402²` limit, the same preparer uses `eog_chunk_preparation.py`. It reads source metadata first, then one original-pixel core plus bottom/right halo at a time through the original raster reader. Each projected chunk retains the original dense limit and shared coordinate transform; the full declared source AOI remains at most 10 degrees per dimension. Physical masses accumulate at the existing numerical owner and normalize once. The new explicit contracts are `starward-nightlight-warp-grid-v2` and `starward-fixed-nightlight-raster-v3`: they bind the complete core partition, every chunk geometry descriptor and the adapter/numerical-owner hashes. The former dense grid/proof remains v1/v2. Content-addressed PNG/numerical filenames keep their existing `nightlight-v2-` encoding format; the proof schema determines the admitted preparation variant. The original inventory and schema-2 database dataset are unchanged. Unknown variants, incomplete/overlapping cores, missing halo or unbounded descriptors fail before sealing; source-part, asset, proof and single-chunk limits are not raised.

`eog_sharded_inventory.py` reads only source-grid metadata during preparation admission and reuses the original asset validator and shared TypeScript display producer for either admitted variant. Run `python -W ignore -m unittest test_eog_chunk_preparation -v` for the actual preparer → six-band proof → coordinate shard/display path, independent mask/zero/quality and old dense comparisons, failed preparation and immutable replay. This is offline integration evidence; it does not install the sharded reader in the service, publish a DB row, qualify nationwide display coverage or perform formal static distribution.

Publication requires the canonical revision schema (migration 007 as well as the night-light tables). It locks affected spots in ID order before sampling their coordinates/payloads, then records the actual incremented version's complete immutable spot/detail snapshot and active revision in the same transaction as samples and read models. The preceding baseline remains unchanged for feedback and version comparisons. A missing overview aborts publication instead of leaving a version without its feedback baseline. Recording history does not renew publication assessments; the normal completeness gate still applies. Repeating an already published manifest remains a strict no-op and does not repair older publications implicitly.

Run `python -m unittest test_publish_eog_viirs test_publish_eog_viirs_integration -v` from this directory. Database integration requires a fresh, fully migrated disposable database named `starward_eog_test_*` in `DATABASE_URL`; its caller owns dropping that database after the suite. Fixtures retain their immutable history until database disposal. Do not point these AOI-wide publication tests at a shared development or working database.

The output labels are explicitly satellite-radiance estimates. They are not field measurements, exact sky brightness, Bortle classes, or a promise of naked-eye visibility.

## Spatial discovery and offline display preparation

`eog_sharded_inventory.py --manifest <prepared-part/manifest.json> [--manifest <another-part/manifest.json>] --output <new-index-directory>` validates bounded schema-2 preparations through the existing numerical owner, calls `prepare_display_eog.mts` to produce the final contrast images with the API's shared `projectNightLightDisplay`, and seals `index.json` last. All parts must use the same new dataset, original source digests, numerical/quality policy and source summary. Assign each fixed window to one part; overlapping window keys, even across part boundaries, fail instead of silently selecting one. This does not increase the old AOI, dense-geometry or per-part asset budgets.

The root pins spatial/LOD shards, original inventories, declared source AOIs and source identity. A shard is addressed by `zoom/floor(x/16)/floor(y/16)` from the existing fixed display-window key. `read_window` reads only the pinned root and the selected shard. Each entry carries the original numerical publication, all six numerical bands, original image/proof and the separately identified final display. Missing discovery remains unpublished; corruption of a declared shard fails. No local source paths are copied into the public index. Immutable assets may be hard-linked within the local output; logical file sizes are not physical allocation measurements.

The script does not publish a database record, switch the existing service, upload assets or qualify national coverage. Source-file hash verification remains with the existing publication transaction; a representative batch may also verify the exact originals before preparation. Old schema-2 releases and URLs remain unchanged. The future service must bind this root to its actual `PUBLISHED` record and deliver prepared images through the existing static publisher. An exact window absent from the index is not permission to perform unbounded PNG work inside the API.

Run the focused offline checks with `python -m unittest test_eog_sharded_inventory -v` from this directory. They exercise actual numerical preparation and the shared TypeScript display mapping, exact two-file lookup, unchanged numeric/quality identities, transparent missing pixels, immutable replay and corruption/duplicate rejection. Production capacity, native rendering and end-to-end publication remain separate evidence.

Published source metadata carries the [EOG licence EXHIBIT 1](https://eogdata.mines.edu/files/EOG_products_CC_License.pdf) product notice with the actual manifest product name and Starward's processing description. The small-format map credit is `Source: EOG, Colorado School of Mines.`; full source disclosure retains the notice and modifications. Larger exported graphics must follow the EOG logo requirement and retain the notice; this pipeline does not create or authorize a new export product. An existing immutable publication needs a new dataset version to adopt corrected metadata; changing the publisher does not rewrite stored publications or establish legal acquisition of the inputs.

For reports or publications using Annual VNL V2, retain the applicable EXHIBIT 2 reference: Elvidge, C. D., Zhizhin, M., Ghosh, T., Hsu, F. C., and Taneja, J. (2021), *Annual time series of global VIIRS nighttime lights derived from monthly averages: 2012 to 2019*, Remote Sensing 13(5), 922, [doi:10.3390/rs13050922](https://doi.org/10.3390/rs13050922). This reference does not replace the product notice or authorize a new report/export feature.

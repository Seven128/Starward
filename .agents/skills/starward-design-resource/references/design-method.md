# 从普通描述到设计判断

目标不是字符最多，而是用户最少注意力内能理解最多有效事实。先列每页首要问题、对象身份、关键事实、行动与可深入证据，再决定是否需要容器。当前已有采用资源，用于理解具体设计选择的目的和适用范围，不作为完成度标尺。具体视觉基准由 DESIGN.md §1.3、产品 Context 与页面采用包维护，不默认沿用已退役 A/B 实验。

## 从迭代反馈中更新设计判断

每次明确反馈、修订或采用后，按 `project_context/context-maintenance.md` 的“持续校准设计系统与用户偏好”判断是否需要更新现有owner。先从具体差异理解用户追求的效果，再区分跨页原则、组件规则与页面特例；未确认推断不当成用户定论。同步改写冲突旧规则，让下一次生成依据更准确的风格和UIUX逻辑，而非仅多一个参考截图。先按 product-profile.md 的设计概念分类，区分UIUX原则、偏好、风格、系统规则与页面决定；采用页是局部选择的证据，不提供统一完成度基线。

## 首次交付前的设计推敲

### 设计阶段就建立公共组件

遵循 [跨阶段公共组件规则](../../../../AGENTS.md#shared-components-across-design-and-implementation)。在本次受影响页面中识别共同的产品/交互职责、组件族和材质，不等开发时再从相似截图猜测复用关系。复用已有定义；有明确共同职责时才新增，不为普通修图先造全产品组件库。

向 Stitch 输入共享职责、实际消费者、保留的不变量与允许的变体；生成后检查同一组件在不同页面的真实内容、状态、主题和交互差异。将可编辑公共定义放在资源包的共享位置，具体业务/状态规则与消费者归属按 [Context 连续性规则](../../../../project_context/context-maintenance.md#shared-component-continuity)记录。静态复制、相似外观或同名图层不等于已建立可复用组件；导出能力不足时明确标注映射与限制。本地资源适配与 Stitch 原稿分开保留。

交付时让后续开发能找到共享定义和各消费者差异；不要预先规定一个设计节点必须对应一个源码组件。实现可以组合、拆分并增加技术单元，但不能丢失既定公共语义、状态或变体。候选状态与采用状态继续分开。

### 复杂能力在设计阶段先做有界调研

遵循项目 [跨阶段能力调研规则](../../../../AGENTS.md#cross-stage-capability-research)。本节只补设计侧用法，不另建调研触发条件或技术选型规则。

从用户任务出发操作或观察成熟示例，关注缩放后的信息增益、分级加载、对象点选、输入方式、缺失覆盖和恢复等会改变体验的能力。将发现映射到本页的信息结构、手势竞争、状态与返回路径，区分核心任务必需、值得提议与本期不做；影响产品含义的结论回写所属 Screen Contract。

生成输入注明已确认能力、仍依赖技术验证的部分及需要保留的降级状态，避免先画定大量自定义能力再倒推实现。已有效的调研结论直接复用；视觉修订不重新发起技术选型。

### 视觉推敲

1. 先看最接近当前职责的采用页真实画面和适用交互，选择有明确用途的参考区域。简要指出当前任务适合借鉴的比例/密度/材质/图标/动效及原因，以及新页面需要独立解决的阅读重心。只有token文字不能替代看参考。
2. 把这些正向目标带入生成输入：什么应最先被看到、对象如何辨识、哪类卡片或信息组适合、哪些状态需要连续变化。只传与任务有关的限制，不把全部历史“禁止项”铺满提示词；不预设所有内容都是素灰行，也不硬规定每页必须有某种装饰。
3. 生成后实际渲染，并排对照参考。分别检查业务是否成立、视觉与交互是否符合当前明确要求。若仍有线框感、无重心、控件默认感、比例失衡或生硬状态变化，在原授权范围内先修订这些具体问题，再交付用户。保留首个原稿，说明本地修订，不能冒充一次生成即达标。
4. 主动修订不是无限重抽。优先同一方向的具体改进，遵守本次数量/预算，额外工具调用如实记录；遇到偏好未确定或工具不能实现的部分，带着具体方案说明已实现内容和未决部分。用户无需再说一次“太丑了”来授权原请求已经包含的精修。

将“精致、小巧、简约、高级感、密度高、字别太小”解释为可修正的判断：

- 先删重复标题、说明和不成立的模块；关联短事实共享轴/矩阵，长原因回正文。层级通过位置、对齐、字重和组间距离共同表达，不能所有事实都加粗。
- 用当前可读字级起步。缩窄屏幕后减少列数、允许容器增高；关键值/单位/风险不省略，不靠降字号守住一行。将可见面与 44 logical-px hit 分开，邻近扩展区不相交。
- 分组以真实任务和对象为依据：连续事实用共享表面，完整对象可以成为有层次的卡片。按采用稿和职责运用材质、图标及轻高程；My已采用的渐变/玻璃是有效设计依据，不用概括性禁令抹掉，也不机械推广到所有页面。
- 两页共享字体/图标/间距语言，但地图工具与账户中心不机械同构。颜色表达当前语义，状态有文字/形状替代；观测模式使用自身黑/暖红 token。

先区分页面身份、组标题、对象内容、状态说明和操作，决定用户应先看哪一层。标题不是所有可点击内容的默认样式：列表里的地点、日期、计数通常不应与页面身份争夺最大字号/最重字重。字号、字重、行距与组间距一起形成主次；不要只改灰色深浅。用一个真实内容较长的单元推敲这套关系，再沿用到另一页，不以看起来规整的空壳组件决定内容尺寸。

密度按“有用信息占用多少空间”判断。先合并同义说明，关联的短状态和值共用一行或紧邻排列；多个未知字段可以用明确覆盖各字段的简短说明表达，不能删掉风险或把未知改成可用。容器由真实内容撑开，避免只有日期/地点/状态却占据大半张卡；也不要把剩余空白用假功能填满。可视图标/底板与完整点击区域分别设计，44px目标不意味着每个图形、色块或文字行都要显得44px高。

方向数量与页面范围遵从当前任务；已选方向就延续，不重新制造多个假设。新探索让生成工具补全阅读重心和信息组织，再检查方向间是否有实质变化，不能只有换色。不要预设容器模板，也不要为差异改掉业务顺序和页面职责。扩展到另一页时共享强调关系，而非只共享颜色和圆角。

每轮先看完整1×真导出：不读说明能否分清标题、内容与状态，最大的块是否承载最重要的信息，几种方向是否真的有不同阅读体验。若整体普通、字像同一级、内容占高失衡，正式修订应处理这些问题；只修黑点、箭头或几像素间距不能证明整体成立。再并排检查跨页组件、长中文/单位、小屏/命中/风险，最后回完整画面。评论定位到节点/区域和预期变化；技术修复不充作新的设计样本。

用户明确认为整体偏大、层级弱时，重新分配各文字角色和容器高度，不能只把画板整体缩放。若调整超出现行精确token，把候选值及原因放入拟议差异，并继续使用真实逻辑像素、对比度和独立点击区域；不先改生产真源来消除差异。用户拒绝全部方向时，记录无可采用项，修设计假设后再开新版本；不从被拒结果里强选最佳项。

默认用具体实物问题和用户普通反馈评价，不要求评分表。旧 Codex A/B 试验量表仅在明确复做该试验时使用，见 delivery-and-review.md；历史评分与失败记录保持原样，不据此代填新路线的用户偏好。

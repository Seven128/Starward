# Stitch 设计生成与交付

默认由 Stitch 生成和修改视觉稿，Codex 整理需求、操作工具、检查实物与交付。工具选择不代表某一稿已成为生产视觉规范；继续已有任务时读取任务内的选中方向与原始文件。

## 输入与连接

输入先给出正向设计目标与有用途的采用参考：首屏重心、比例/密度、对象卡片、图标质感和适用交互。说明当前任务适用的原则、已确认偏好及参考的具体用途，不给“达到旧稿完成度”的模糊要求，也不能只传“白底、蓝灰、极简、不要装饰”。再简短分清：必须保留的业务信息/操作；用户明确喜欢的局部及图中位置；明确不喜欢的问题；仍可探索部分。推测单列，不把整张未认可候选当风格规范。现有页面图主要保留业务，参考图与获认可局部主要表达视觉意图。保留文字可读性和点击区域，不能用删信息、截断状态或整体缩小制造密度优势。

优先发现可用的官方 Stitch 工具/MCP；其次利用已登录的官方网页。只连接本次必需能力，不创建通用平台。工具与登录能力以实际探测为准；不购买、使用付费额度或公开分享。若缺外部登录/授权，说明必要动作，不索取密码。正常网页上传或图片粘贴可用时由 Agent 完成；自动操作确实受阻再提供可直接提交的提示词、图片和用途。不给 Stitch 塞 Figma 命令或全部历史治理记录。

参考入口：[官方 MCP 设置](https://stitch.withgoogle.com/docs/mcp/setup)、[Google 官方扩展](https://github.com/gemini-cli-extensions/stitch)。实际调用时核对现行方式，不假设工具名称或登录状态。服务可见模式与实际底层模型分开记录，未知模型写 unknown。

## 生成与修改

数量、范围和预算按当前用户要求；选中方向后不重开抽卡。每次保存实际提交的输入、参考用途和完整输出，包括额外生成的候选。遇到失败先确认是否已产出/消耗，再决定必要的技术重试；一次重试仍失败就停止生成并说明，不持续消耗额度。

首稿按统一手机内容视口实际渲染，旧候选直接复用，不用设备外壳、装饰背景或不同缩放美化比较。服务生成尺寸若与要求不同，保留原导出并明确说明查看方式；不暗改原稿。按 DESIGN.md §1.3 和 design-method.md，首稿按当前需求检查阅读重心、比例、可读性和状态连续性，相关参考仅用于理解适用的设计手法；原请求要求精致页面时，明显基础/粗糙的结果应在同一方向内主动修订，而不是等用户重复要求美化。保留原始导出并区分生成与本地修订，次数/预算规则仍适用。再检查业务完整性、文字截断、地图点位/素材对应、可读性、点击目标和实际交互支持。用户判断偏好，不用机械自评分替代。

修改提示包含用户原话、具体变化和明确保留项；将 Agent 发现的技术问题标为检查发现，不冒充用户偏好。保存修改前后，验证所要求的改善及原有优点是否保留。Codex 后续做的代码修复必须单列，不能归功于 Stitch。用户只选方向但没要求修改时先保存选择，不为了流程凑一次修改。

## 资源与记录

任务目录保留实际提示词、参考原文件/来源/用途、各次原始输出、可打开项目链接、同视口真实比较及简短检查记录。记录生成提交数、成功初稿数、技术重试、视觉修改、额外候选、人工介入和可见用量；未知为 null 并解释。日额度前后差仅代表观察区间总量，不能推算失败请求或每张图的独立收费。

仅有截图就明确只交付截图。有 HTML 和项目链接就如实交付，并检查其文字/布局是否可继续编辑；不据此声称具备 Figma 原生组件或已经完成开发交接。视觉值得继续且需要 Figma 时才验证转换，另计成本，保留 Stitch 原稿。旧 Figma schema、匿名比较脚本、三次 A/B 量表与全状态测试不自动成为此路线的必经流程。

结论区分用户偏好、产品缺陷、资源可编辑性和生产采用。小样本可支持当前路线选择，不能证明长期审美下限。生产页面及 DESIGN.md 的修改需要对应任务范围，选中方向本身不等于授权迁移生产。

# Management credentials and migration

The server derives the audit actor and allowed operations from the presented credential. `x-admin-token` remains the transport field for existing clients. `x-admin-actor` is optional and, when present, must exactly match the authenticated principal; it never selects roles. `GET /v2/admin/session` returns only that principal's actor, roles and allowed operations. It returns neither credentials nor their hashes.

Management routes that accept a body require a non-null JSON object. After authentication and operation authorization, the shared admission in `admin-operations-support.ts` rejects absent, scalar and array bodies before field access or business calls. Its text/revision validators return structured HTTP 400 `INVALID_INPUT`, with `retryable: false`; field names such as `provider` or `revision` cannot turn invalid input into a supplier outage or concurrency conflict. Existing domain validators, actual repository conflicts, provider failures and unknown prior-command recovery retain their own meaning. This object admission is not a replacement for each operation's nested data validation.

Configure distinct credentials with `MINIAPP_ADMIN_CREDENTIALS`, a JSON array:

```json
[{"actorId":"admin:owner","tokenSha256":"<64 lowercase hexadecimal SHA-256 characters>","roles":["OWNER"]}]
```

Generate strong independent credentials through the existing secret-management process, hash their exact UTF-8 bytes using SHA-256, and distribute each plaintext credential only to its intended operator. The array is server configuration. Treat its digests as confidential operational material; do not log them. Valid roles remain `OWNER`, `MODERATOR`, `MEDIA_REVIEWER`, `PUBLISHER` and `AUDITOR`. Duplicate credential digests, invalid identities, empty roles and malformed configuration fail closed. A configured array takes precedence over the legacy variables and never falls back if invalid.

For a bounded transition, the existing single `MINIAPP_ADMIN_TOKEN` remains supported only with both `MINIAPP_ADMIN_ACTOR` and `MINIAPP_ADMIN_RBAC`. The server-side actor must have a nonempty role assignment in that mapping. For example, a fixed `admin:owner` actor may map to `["OWNER"]`. Other entries do not create usable identities for that token. Missing configuration now fails in every environment; there is no development default OWNER. An old multi-actor shared-token configuration must migrate to separate credentials. Do not change live credentials implicitly or let a client header choose the fixed actor.

Deployment validation uses the same parser as the API and accepts either complete scheme. The example environment retains the explicit single-owner transition. Existing isolated launchers configure their own fixed actor; the infrastructure check gives its auditor a distinct credential. These source changes do not reconfigure a running environment or certify deployed behavior. A deployment changing credential ownership needs a planned secret update and a check using the intended operators before it can expose management writes.

Admin-web authenticates against `/session`, shows that returned identity, and retires all old reads/commands on logout or replacement. Credentials remain in memory; the page removes only the two obsolete admin session-storage keys and does not import them or reconnect automatically. Refresh or close requires authentication again. The command journal uses IndexedDB transactions to reserve an encrypted unresolved command before its first HTTP dispatch. Its scope and encryption key bind the origin, API audience, server-confirmed actor and exact credential through the origin's random salt; neither raw credentials nor private command/receipt plaintext are persisted. Another credential or principal cannot inherit the command.

Reauthentication restores the original serialized body, revision, idempotency key and any known commit/cache-failure fact without sending a mutation. “重试原操作” explicitly reuses those bytes and the same declared readback check. A later rejection does not erase earlier uncertainty or a matched commit receipt; only matching receipt, durable readback and required cache completion retire the recovery row. Failed or unsupported journal storage preserves the confirmed identity and independent reads, while blocking journal-owned writes and command retries. “重试读取操作记录” explicitly retries restoration without dispatching. Unreadable material is retained; there is no plaintext fallback. Clearing/evicting origin storage or losing/changing the originating credential still requires durable server receipts/current-state reconciliation, and cannot be treated as cancellation. Event-catalog operations retain their separate content/version reconciliation and never retry a mutation automatically.

The cache effects following a completed transaction use one `committedEnvelope` owner. It attempts all affected prefixes and preserves the committed data/receipt if Redis fails; a Redis permission error cannot turn that committed write into an authorization rejection. Responses explicitly report `postCommit.cacheInvalidation` as `COMPLETE` or `FAILED`, with a human-readable warning on failure. API and admin-web must migrate together: the UI verifies receipt actor/key/status and durable readback, then keeps the operation unverified if public cache refresh failed. It retains the same command/key for an explicit retry, which replays the existing receipt and retries invalidation. It does not claim that public Map/search data refreshed. The CLI reports the saved result plus the cache warning, and never automatically reissues a legacy non-idempotent write. This is explicit recovery, not a new durable cache-retry worker or proof that a live Redis fault has been repaired.

The command owner preserves unresolved history and any matched commit receipt across retries and same-credential reauthentication. A later retry returning 401/403/409 cannot prove that an earlier submission did not commit, and cannot discard that earlier command. Only a first definite rejection without prior uncertainty can release an uncommitted attempt; an existing unknown or committed-but-incomplete result remains available for same-key recovery until receipt/readback and cache completion establish the outcome.

The operator CLI accepts `session` to inspect the server-derived identity. `MINIAPP_ADMIN_ACTOR` / `--actor` is only an optional expected-identity assertion. `resolve` requires `--revision` and `--idempotency-key`; `merge` requires `--submission-revision`, `--spot-revision` and `--idempotency-key`. `candidate-create` also requires `--idempotency-key`; `spot-patch` requires both `--revision` and `--idempotency-key`. Preserve the original input file, all flags and the same key after a lost or unverified response, and retry only explicitly. Same actor/key with changed parsed input or operation is rejected. Keys are not secrets, and the CLI does not persist or reconstruct the original input for the operator.

Deploy the API before the updated spot CLI. Its session preflight requires the exact version **1**, method and path in `commandContracts`: `POST /v2/admin/spots/candidate-commands` for `spot.candidate.create`, and `PATCH /v2/admin/spots/:spotId/commands` for `spot.patch`. Both entries require a valid key, and PATCH requires a numeric `expectedRevision`. The receipt and business result commit atomically; the CLI verifies the returned actor, operation, key, revision and matching result/readback before reporting the effect. A mixed-generation request reaching an older route catalog returns 404 at the new path before an effect; the CLI never falls back to a legacy write. Advertised contracts do not replace write-side authentication or RBAC.

Original no-key `POST /v2/admin/spots` and `PATCH /v2/admin/spots/:spotId` remain compatible and non-idempotent. Their unknown outcomes require durable-state reconciliation before another write. A key opts those old paths into receipts on the new server, but an older server may ignore it, so they are not the rolling-version recovery entrance. Receipt/readback describes the committed snapshot, not a promise that no later edit occurred. Cache FAILED remains a committed effect awaiting explicit same-key cache recovery. The client performs no automatic mutation retry, production/database migration or credential rotation.

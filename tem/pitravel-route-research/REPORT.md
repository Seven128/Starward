# 圆周旅迹路线实现定向调查

调查日期：2026年9月14日（北京时间）。目标：[指定行程网页](https://www.pitravel.cn/plan/journey/7685320728933093603?source=miniapp)。成功取证的路线请求时间为18:09和18:11。用户手动登录后完成网页观察，并查看了电脑端正在运行的同一小程序页面。证据等级：**已证实**表示直接网络、代码或官方材料支持；**推断**表示依据充分但仍有其他解释；**未知**表示当前看不到或未安全触发。

## 1. 结论摘要

**已证实：网页底图是高德，小程序底图是腾讯。** 网页加载高德 JavaScript SDK（网页地图开发工具包）并创建高德地图；小程序当前窗口显示腾讯版权信息。两端底图不同，不能由其中一端推断另一端的路线数据来源。[E01、E02、E04、E07]

**已证实：这条网页路线的距离、时长和坐标来自圆周旅迹自有后端 `/api/slytherin/v1/web/route`。未知：该后端上游是谁。** 请求带起终点的地点编号、交通方式和 `realTime:1`，响应带 `distance`、`duration`、`paths`。没有供应商声明或足以确认上游的执行证据。自有域名不代表自建路网，高德底图也不代表当前这条路线由高德计算。[E05—E07]

**已证实：网页展开交通方式面板，会在一个请求中取齐步行、骑行、驾车、公交四组结果。** 当前已选驾车；没有切换，因为代码显示选择另一方式会调用行程事件更新。小程序也实际展示四种方式，但未取得它的网络或代码，是否共用后端仍未知；原生 App 未调查。[E02、E04、E05、E07]

**已证实：蓝线使用返回坐标，并在首尾补上地点连接段；缺少可用坐标时会直接连接地点。** 本次公交返回的 `paths` 就只有起终点两点。驾车路线末坐标与公园地点标记相距约1.14千米，所以蓝线不能整体等同于可通行道路。[E05—E08]

**未知：这些时长是否使用实时路况、是否指定时间预测，以及服务器是否缓存。** `realTime:1`、小程序“出发”时间文字和多次相同数值都不足以证明这些语义。[E04、E05、E08]

**没有确认到符合 Starward 费用约束、可直接投入商业生产的方案。** 独立路线接口的技术形态适合继续验证，但高德公开基础许可为五万元/年，按你的约束排除；腾讯同样要求商业授权，本次公开价格页没有给出固定许可价，不能把流量单价当作全部成本。圆周旅迹合同、账单及扶持资格全部未知。[E09、E10]

### 实际响应与页面数值

起点为顺宝花园，终点为顺峰山公园。下表网页与接口均已验证；小程序列只验证显示，不能与网页响应建立直接对应关系。[E02、E04—E07]

|方式|`travelType`|`distance`，米|`duration`，秒|网页显示|小程序显示|
|---|---:|---:|---:|---|---|
|驾车|0|14424|2937|14.4千米，48分钟|14千米，48分钟|
|步行|1|16208|12965|16.2千米，3小时36分钟|16千米，3小时36分钟|
|骑行|2|16215|5243|16.2千米，1小时27分钟|16千米，1小时27分钟|
|公共交通|3|17271|4457|17.3千米，1小时14分钟|17千米，1小时14分钟|

**已证实：网页距离默认按0.1千米四舍五入；时间丢弃剩余秒数。** 因此2937秒虽是48分57秒，显示48分钟。地图“Day1 14km”是把当天距离加总后按整千米四舍五入；并不是另一次道路测量。小程序整数距离的算法未读取，不据外观断言其取整规则。[E07、E08]

### 关键请求与字段

两类请求均为圆周旅迹域名上的 POST（带请求体提交数据的请求方法）。这里只记录观察到的正常页面调用，不提供生产接入方式。[E05、E06]

1. 行程详情：`/api/slytherin/v1/pcweb/journey/detail`，参数 `journey_id`、`is_map_view:false`。选定日期内两个地点事件带 `start_poi_info.inner_poi_id`、`location`、`coordinate_type:GCJ02`，首事件保存 `route_transportation_type:0`。GCJ02是国内地图常用的偏移坐标体系。已摘录的事件没有距离、耗时或折线路径字段。
2. 加载后路线：`/api/slytherin/v1/web/route`，`routeRequest` 内每项为 `originPoiId`、`destinationPoiId`、`travelType`，并有 `realTime:1`。本次先请求已选驾车；展开面板后一次提交 `[1,2,0,3]` 四种方式。请求中没有起终点经纬度，也没有显式出发日期/时间参数。
3. 路线响应：`code:0`、`success:true`，`data.routeData` 各项含起终点编号、方式、米制距离、秒制时长、`paths`。公交另有 `public_transit_info`，包括票价、文字描述和步骤。本次摘录未见供应商声明、路线更新时间或拥堵明细字段。

**已证实：打开行程会另外发出路线获取请求，而不是只展示行程详情中的已有距离数值。未知：后端收到请求后现算还是读取以前的结果。** 前端新发请求、服务器新计算和使用实时交通数据是三个不同问题。[E05—E07]

## 3. 实际数据流程

```text
打开已获权查看的行程
  → 圆周旅迹行程详情：地点编号、坐标、顺序、已选方式
  → 网页按相邻地点组合 routeRequest
  → 圆周旅迹 /web/route
       → [看不到：上游数据服务、路网、缓存、计算与交通数据]
  ← routeData：distance + duration + paths
  → 卡片换算米/秒，显示距离和时间
  → 地图解析 paths、补地点首尾坐标，再交给高德折线组件绘制

展开交通方式面板 → 同一个 /web/route 请求取齐四模式 → 面板显示
选择另一方式 → 代码将调用事件更新；本轮没有执行
```

这条流程由实际请求、字段、组件读取逻辑和页面数值共同支持；未给压缩代码中的请求辅助函数补写未找到的内部实现。[E05—E07]

**已证实：驾车、步行、骑行返回多点折线；公交本次只返回地点连线。** 驾车为15个路径字符串、共203个坐标项（包含重复点）；步行为41段、629项；骑行为46段、617项。解析方式是先以分号拆点，再以逗号拆经纬度。公交仅一个字符串、两个点。后端是否抽稀过坐标未知；不能因为点少就认定某种简化算法。[E05、E07]

**已证实：地图还会人为补齐路线首尾到地点标记的连线。** 驾车末点到公园标记约1141米，步行约33米，骑行约110米。**推断：**驾车末点可能是某个可驾车入口，也可能是点位选择或路径数据问题；没有入口资料，无法判定。公交若进入同一绘制分支，会按两点直连，这是代码推导，未通过切换公交做动态验证。[E05—E08]

**已证实：相关卡片存在直线距离兜底。** 匹配到路线但 `duration` 不大于0时，代码用球面距离并标“直线距离”；地图缺少有效路径也会直连。在本次成功显示的四组耗时路径中，没有看到前端按固定速度计算预计用时的证据；不作全站不存在这种逻辑的声明。[E07]

**未知：实时和缓存。** 本次传 `realTime:1`，小程序面板有“18:12出发”，但不能单独证明实时拥堵估时或未来出发预测。初始HTML未匹配关键路线字段/数值，主要证据仍是路线响应。网络事件存在缓冲截断；浏览器缓存禁用不排除服务器缓存，也不据缺少第三方请求断言没有第三方服务。[E05、E08]

## 5. 对 Starward 的意义

**可借鉴的前端做法：**把“距离/时长的数据获取”和“地图绘制”分别处理；按交通方式保存独立结果；打开方式面板时按需取齐；统一米和秒的单位换算。这里借鉴的是已观察到的交互与数据组织方式，不是复制其代码或接口。[E05—E07]

**需要改善的展示细节：**道路末点、观星点标记、停车入口可能不一致。若补上步行/连接段，应明确区分；只有两个点时不能展示成已经获得道路路线。路径失败可以显示明确标注的直线距离，不应把它当成道路距离并按固定速度生成看似精确的预计用时。[E05—E08；这是针对Starward的建议]

**需要自行取得的数据服务：**用自己的主体、合同和凭证取得路线接口授权。当前证据只支持“独立路线数据接口适合这个需求”的技术判断，尚未支持任何满足成本约束的生产供应商选择。圆周旅迹的私有接口不应作为 Starward 的生产数据源；其一请求返回四模式也不能拿来推算供应商侧只有一次计费。

**仍需验证：**观星点的真实可达入口、夜间步行/骑行覆盖、公交发车时间语义、路线缺失处理，以及自有卡片、腾讯底图混用和计划回看许可。圆周旅迹这个城市公园案例不能证明偏远观星点或夜间场景可用。本轮未修改 Starward 代码或持久项目决策。

# WeChat Mini Program Physical-Device Testing

## Owner and boundary

This on-demand verification Context owns repeatable physical-phone diagnostic operations under `tools/miniapp/device-*`. `project_context/development-workflow.md` remains the sole owner of environment isolation, candidate promotion and formal acceptance; `project_context/deployment.md` owns the operator-preview IP backend and formal releases. This is a supplemental diagnostic entry, not a replacement native acceptance runner or a production feature.

- For initial physical development feedback, use the imported, version-matched official `wechatide-skill` against the exact prepared project. Its automator `automation_viewport_action(action=remote)` owns the true-debug request and official QR/automatic path; its initializer and debugger tools then read actual runtime identity and scoped Console/Network where supported. Use the visible DevTools QR action only after the registered official tool reports a concrete unsupported boundary. USB/ADB is independent and optional for machine capture/input. Project `miniprogram-automator` adapters remain bounded compatibility diagnostics for an already owned automation endpoint; they are not the primary official control plane and must not be retried after `device_test_official_sdk_unavailable` as though that were a phone result.
- Treat the IDE command/MCP service and its page automator as separate subchannels. Compile and Console/Network success does not prove runtime/page/screenshot/remote readiness. On the exact failure `timeout waiting for automator response`, first establish one owned official `cli auto` connection for the unchanged prepared project and verify a read-only automator call; preserve the project window and candidate. If `remote` then moves the window into a waiting true-debug scene and simulator automator reads pause, verify the phone/QR scene rather than closing the IDE or regenerating the candidate.
- Verify that `cli auto` returns the requested MCP-visible `autoPort`; a stale closed-window utility can retain the old port while the new project is assigned another. Retire only the verified owned stale automation process, then rebind the unchanged candidate. Classify readiness per operation because page-data access may succeed while runtime or viewport actions time out.
- Interpret `已连接` only as true-debug transport attachment. Establish runtime state with fresh device identity, current page and scoped Console/Network, and establish visible phone behavior through a separately identified phone-display channel or the operator. The official `simulator_screenshot` remains a desktop-simulator capture during true-debug and cannot override the phone observation. Classify the phone content separately: an absent/empty page root is a render failure, while a visible recovery card is a rendered degradation state. A phone request to host loopback (`127.0.0.1`/`localhost`) normally reaches the phone itself; status `0` is a network/configuration finding, but does not alone explain a blank content layer, and neither USB nor true-debug tunnels it.
- Keep every `simulator_*`/`get_simulator_*` result scoped to the desktop simulator unless its registered contract explicitly states otherwise. Do not merge simulator Console/Network/base-library/pixels with a phone `systemInfo` into one device trace.
- Host-side device diagnosis is an agent-owned development operation: select one current Android Platform Tools ADB, resolve competing daemon/client versions, inspect or restart the bounded Windows Android USB interface, reconnect the transport, start the official true-debug attachment, and collect scoped screenshots/runtime diagnostics through the project commands. Do not hand these repair steps to the phone operator merely because the first transport probe fails. The operator owns only actions that physically cannot be performed from the host, such as reconnecting the cable, selecting the USB mode, accepting the phone's trust/debug prompt, scanning an official QR, rotating the device, or completing MFA. Preserve the open DevTools/compile scene while repairing an observation channel unless its owning command requires a controlled restart.
- Some OEM Android builds expose the literal ADB identity `(no serial number)`. This does not make a single authorized USB transport unusable: prove uniqueness with `adb -d`, bind the current host USB `get-devpath` to its `transport_id`, and issue commands through `adb -t`. Recheck that binding before capture/input; a reconnect or path change invalidates prior screenshot authority. `adb get-state=device` proves only host transport registration—if `adb shell` stalls or the device becomes `offline`, repair/re-authorize the USB session before claiming phone screenshot or input capability.
- Selecting a USB role such as file transfer can re-enumerate the composite USB functions. Complete that selection and any debug authorization first, wait for one stable authorized transport, then return the target Mini Program to the foreground before capture. A capture attempted while the system USB settings surface is foreground must fail closed; do not diagnose that refusal as a Mini Program rendering or ADB identity defect.
- Reuse the settled external phone project prepared through the existing build/deployment owners. Do not rebuild, change AppID, inject location, mutate generated files, fetch credentials or deploy as a side effect of device diagnostics. Reuse `fingerprintBundle` for local bundle freshness. A local hash does not prove that the phone is running those bytes: ADB-only observations require operator confirmation of the opened candidate; SDK checks add runtime AppID/platform verification, not byte-level identity proof.
- The owner-only IP lane remains available without a domain under deployment's existing conditions. ADB is a control/observation channel, not a network tunnel or a way to bypass platform origin/TLS rules. Owner-authorized Android TLS wireless pairing is supported as the connection choice below. Do not enable `adb reverse` or legacy `adb tcpip 5555`, install trust certificates, disable VPN/TLS checks, or retry a policy-blocked SSH/browser operation through another channel.
- Automatic delivery follows the desktop account/device association. Choose between [same-account automatic delivery and cross-account QR](wechat-device/development-feedback.md#account-routing-and-automatic-delivery): use automatic preview only after verifying matching current accounts; use QR when they differ or the relationship is unknown, without switching accounts for convenience. Preview and true-debug use their respective official channels. After DevTools updates, verify the running binary/version, exported Skill version and exact project window together; stale processes or duplicate installations can otherwise look like an authorization or product failure.
- Treat QR true-debug LAN and WAN as alternative transports, not product variants. After a fresh scan, a phone overlay with `连接断开`, `服务器忙`, zero confirmed/sent/received messages and `cmdId 1002, errCode -1` means the phone never attached to the debugging session; do not attribute the blank content root to page code or bind the candidate. WAN can fail at the WeChat relay even when the phone has ordinary Internet access. For LAN recovery, preserve a required VPN/TUN configuration: first verify that the physical WLAN subnet still has a more-specific direct route, then inspect the DevTools all-interface listener and Windows network category. A Private-only firewall exception does not cover a WLAN categorized Public. Use one enabled inbound TCP rule scoped to the exact DevTools executable and the explicit physical WLAN subnet across the active profile; do not expose random ports broadly, disable the VPN, or add a route/proxy bypass when the existing WLAN subnet route is already direct. Android Toybox netcat has no `-z`; prove the phone-to-host path with a bounded real TCP handshake. If every DevTools listener is reachable but the LAN QR still reports local-network failure, stop changing firewall rules: the IDE may have advertised the TUN adapter address, so use its explicit physical-adapter selection when available or the WAN path. End the failed phone debug session before scanning a newly generated QR.
- A green WAN `已连接` is still not a runnable page when its expanded overlay shows `服务器正常`, confirmed/sent/received all zero, and repeated `cmdId 1005, errCode 1`. In that state the WeChat shell and custom TabBar can change selection while every Taro page body remains empty, official runtime automation times out, and application Console/Network cannot yet diagnose page code because no application message was delivered. Compare the phone WeChat build with the active DevTools build and update the phone client through its trusted current distribution before rebuilding product code or changing the candidate. Bind only after nonzero transport activity plus current phone runtime/page evidence.

## Android transport choice and reconnect

For the owner's NIO Phone, prefer the authorized Android 11+ TLS wireless-debugging route over further repeated USB repair when phone display/input is needed. The phone exposes pairing and has executed bounded shell probes over this route; that establishes feasibility, not durable connectivity or working project capture/input. USB remains an alternative. Missing an OEM “always allow” checkbox, MTP availability, or a transient `device` entry does not establish either a broken authorization flow or a phone `adbd` root cause. Do not repeat unchanged cable/trust/driver resets without new evidence.

- **Pair once, reconnect separately.** Use the existing official Platform Tools installation and a reachable local Wi-Fi network. Open the phone's Wireless debugging details by tapping the row, not merely its switch, then its pairing-code control; verify the actual OEM interface before assuming an entry is absent. Android 11+ TLS pairing needs no initial USB connection or USB RSA checkbox. Use `adb mdns services` to discover the intended phone's `_adb-tls-pairing._tcp` endpoint, or the address displayed by that phone when discovery is unavailable. If the target is ambiguous, obtain its displayed address rather than guessing. Run `adb pair <pairing-address>` and supply the short-lived code privately at its prompt. Never persist or echo the code, device identifiers or raw discovery output to Context/run logs.
- **Select the connection endpoint.** Pairing and connection use separate ports. Use the same target's current `_adb-tls-connect._tcp` endpoint (or its Wireless debugging details address) with `adb connect <connection-address>` when automatic connection has not occurred. Addresses/ports can change after a network change, reboot or wireless-debugging toggle. Reuse the pairing while valid; rediscover the connection endpoint before asking for a new code. Request phone action only when the network/debug switch, revoked or missing pairing, expired code, or unavailable address actually requires it.
- **Verify each layer.** Explicitly select the authorized transport; prove `device`, then a bounded shell command, then the scoped foreground/focus and screenshot checks, and finally the reviewed input. ADB and WeChat's LAN/WAN true-debug transports are independent: a working WAN attachment can coexist with local wireless ADB and does not prove or disprove local ADB reachability. Preserve that attachment and the candidate while diagnosing ADB. A successful pair or shell probe is not a screenshot, input, restart/reconnect or sustained-stability result. Require those observations separately before reporting the relevant capability as working; Android 17 Wi-Fi 2.0 reconnection guarantees must not be attributed to Android 14.
- **Use the explicit project selector.** `tools/miniapp/device-adb.mjs` owns transport selection. Project commands default to USB `-d`; pass `--transport wireless` only for the operator-authorized target after pairing/reconnection. The wireless path accepts exactly one connected TLS transport, binds its current transport plus a private identity fingerprint, and rechecks both before scoped commands. It never emits or persists the endpoint. Keep the session's device binding, foreground/focus guards, private screenshots and fresh-input requirements. Endpoint reuse or reconnection must not silently follow another phone; invalidate prior input authority and prove the target again.
- **Keep recovery bounded.** Discover and probe the current target before changing host state. If mDNS is absent, try the phone-displayed connection endpoint; if connection or shell fails, identify the local reachability, authorization or transport boundary before retrying. Drain subprocess output concurrently with timeouts (reuse `runTool`); a blocked diagnostic wrapper is not proof of a phone failure. Stop repeating a failing repair that adds no evidence. On pause, preserve valid pairing and the candidate, record the first unresolved boundary task-locally, and close only owned command sessions; do not revoke all ADB trust as routine cleanup. The owner may turn off wireless debugging when finished.

Protocol references: [Android wireless debugging](https://developer.android.com/tools/adb#connect-to-a-device-over-wi-fi) and [AOSP ADB Wi-Fi architecture](https://android.googlesource.com/platform/packages/modules/adb/+/HEAD/docs/dev/adb_wifi.md). These define the protocol; actual OEM UI and observed target behavior govern readiness.

## Alternatives and verification

Allowed channels are official `wechatide-skill` MCP true-debug/runtime tools, direct official GUI plus user-visible confirmation when the registered tool is unavailable, Android Platform Tools ADB for scoped display/input, and optional official scrcpy for continuous display/control. Select official MCP first for DevTools/runtime state and ADB only for its independent OS/display boundary. scrcpy is optional; if adopted later disable audio and clipboard synchronization, scope it to the authorized device and own its process lifecycle. Appium/Android Studio are unnecessary dependencies for the present bounded route. Rooting, hidden super-app APIs and browser-policy workarounds are not alternatives.

`npm run test:miniapp:device-tools` checks selection, failure/redaction, freshness, bounded input, session cleanup and SDK adapter boundaries with injected drivers. Run `doctor` against the actual host, then `capture`/input/remote/inspect against the actual connected phone before claiming functioning physical integrations. Driver tests are not device evidence. Finish with Context validation and touched-source modularity. Product changes still run their existing owning checks and final-candidate journey.

Primary references: [Android ADB](https://developer.android.com/tools/adb), [Platform Tools](https://developer.android.com/tools/releases/platform-tools), [official scrcpy](https://github.com/Genymobile/scrcpy). The installed locked `miniprogram-automator` public declarations/implementation define the usable SDK adapter. SDK availability is not a claim that the connected phone supports every method.

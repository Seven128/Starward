# WeChat Mini Program Physical-Device Testing

## Owner and boundary

This on-demand verification Context owns repeatable physical-phone diagnostic operations under `tools/miniapp/device-*`. `project_context/development-workflow.md` remains the sole owner of environment isolation, candidate promotion and formal acceptance; `project_context/deployment.md` owns the operator-preview IP backend and formal releases. This is a supplemental diagnostic entry, not a replacement native acceptance runner or a production feature.

- Primary low-cost route: an owner-authorized Android connected by USB, official Android Platform Tools ADB, and the installed official `miniprogram-automator` SDK attached to WeChat DevTools. ADB observes the actual display and injects deliberate taps/swipes; SDK remote debugging is a separate, capability-checked channel for public runtime observation when the target supports it. A remote connection alone does not establish successful runtime reads, and neither connection implies the other is ready.
- Reuse the settled external phone project prepared through the existing build/deployment owners. Do not rebuild, change AppID, inject location, mutate generated files, fetch credentials or deploy as a side effect of device diagnostics. Reuse `fingerprintBundle` for local bundle freshness. A local hash does not prove that the phone is running those bytes: ADB-only observations require operator confirmation of the opened candidate; SDK checks add runtime AppID/platform verification, not byte-level identity proof.
- The owner-only IP lane remains available without a domain under deployment's existing conditions. USB is a control/observation channel, not a network tunnel or a way to bypass platform origin/TLS rules. Do not enable `adb reverse`, Wi-Fi ADB, install trust certificates, disable VPN/TLS checks, or retry a policy-blocked SSH/browser operation through another channel.

## 1. Development Device Feedback

Enter this channel only after the changed physical invariant has a first runnable WEAPP slice or a coherent edit batch is locally stable. Typical triggers are capsule/safe-area geometry, native map/tiles/gestures, permission prompts and recovery, GPS/coordinate centering, compass/physical rotation, foreground/background/restart/subpackage lifecycle, real device network/TLS/domain-list behavior, or an Android/iPhone difference. Ordinary domain, copy and state work stays in deterministic and warm DevTools feedback unless a physical boundary is actually at risk.

- The project entry is `npm run miniapp:device:feedback`. It reuses the existing Taro WEAPP output and `release-bundle-artifact.mjs` fingerprint owner, waits for stable bytes, snapshots one external private project, and invokes only the installed official DevTools `auto-preview` and ordinary `preview` capabilities. The command becomes a current capability only when its package-script registration and project tests exist.
- `start` creates the first feedback run; `refresh` creates a new generation and invalidates the prior generation's ADB session, screenshot and input authority before binding the new fingerprint; `preview` creates an official ordinary-preview QR for the exact current generation when automatic delivery did not reach the intended phone/account; `bind` is reserved for the exact operator-confirmed official update; `stop` removes only the run, snapshot, QR and device session it created. `doctor` is read-only capability/readiness feedback.
- Automatic preview is permitted because this is development feedback. It is not state-preserving Fast Refresh: the phone may reopen/restart the Mini Program and lose route-stack or in-memory state. Coalesce edits before `refresh`; never make every source save trigger a phone push.
- If the installed official CLI lacks the public command, login/service-port state blocks it, or the command fails, stop at the official boundary. Keep the prepared private project and offer the smallest supported handoff: generate the public ordinary-preview QR, or open that exact project and let the user choose the version-visible official Preview action (for example `预览` or `使用当前页进行真机预览`). Never depend on one historical menu label, and do not call private HTTP endpoints, SDK internals, raw CDP or hidden WeChat APIs.
- A zero exit from public `auto-preview` proves only that the official command completed for whichever account/device the tool selected; it does not prove that the intended USB phone or a different authorized developer account received the generation. On a first private snapshot, DevTools may still require the visible local-project `信任并运行` decision before compilation or phone update. Always return the prepared project path. If automatic delivery reaches the wrong account/device or the intended phone does not visibly show the generation, create one ordinary-preview QR for the unchanged generation and have the user scan it from the intended authorized WeChat account. Phone visibility remains separately unverified until observed; do not add or use an undocumented trust-bypass flag.
- Ordinary-preview generation rechecks the recorded bundle and canonical JSON configuration before and after the official command. A byte-only DevTools rewrite of `project.config.json` is tolerable only when canonical JSON equality proves every value is unchanged; a semantic config or bundle change fails closed. QR bytes remain repository-external and run-owned, are never logged or copied to Context, and are removed after confirmed binding. Refresh and stop own any remaining QR/generation cleanup; a DevTools file lock may defer that exact owned deletion, which must stay visibly pending until stop rather than masking the new generation.
- The user owns login, first/recovery scan, USB trust and any phone action the official flow requires. The operator may use the existing scoped ADB capture/input commands only after a fresh screenshot. Phone not foreground, disconnect, scan timeout, build/source drift and official-tool timeout are visible development-feedback failures, never product acceptance results.
- Official GUI 真机调试 or the existing public `miniprogram-automator` remote adapter may be selected for a targeted development observation after binding the exact generation. Its QR, connection and runtime inspection remain separate from ADB readiness and ordinary preview; every result stays explicitly debug-attributed and cannot prove debug-off behavior or fixed-candidate acceptance.
- Every output is labelled `development_feedback` and reports only candidate/generation identity, official invocation disposition, observed product behavior, verified/unverified/invalidated scope and cleanup. It must not emit `passed` or `accepted`, and it must not preserve QR content, device serial, precise location, WeChat logs or user data.
- A successful official invocation means only that the supported update command completed for the prepared bundle. A visible phone observation is separate; debug/remote/vConsole/domain-relaxed results stay attributable to those conditions. No result from this channel crosses into the fixed-candidate channel.

## 2. Settled-Candidate Device Verification

Enter only after cheap checks, warm WEAPP/DevTools feedback and relevant targeted device feedback are stable. Use one clean ordinary preview or applicable experience build, record its complete candidate identity, keep all candidate inputs fixed and, where practical, turn off phone development/debug state. The existing `npm run miniapp:device -- start/capture/capture-permissions/capture-location/tap/swipe/back/remote/inspect/stop` path remains the evidence-level diagnostic mechanism.

- Automatic refresh is forbidden while results are being collected. Bundle/source/config/AppID/API-origin/base-library/build-input drift invalidates the session and all dependent observations; create a new candidate and rerun the complete applicable journey rather than relabelling the old evidence.
- Every input requires a new screenshot from the same device, foreground activity and display. Ordinary preview, phone debug state and desktop remote attachment are independent conditions and must be reported separately. Debug or remote results cannot become debug-off ordinary-preview results.
- The human performs scan/login/USB trust/physical rotation and reviews every permission or location requester before input. Run the applicable cold-start, navigation, permissions, GPS/map, Observation Context, weather/astronomy, network failure/recovery, background/return and persistent-state journeys without using simulation to prove GPS or physical direction.
- A single Android proves only the declared owner-device sample. iPhone safe area, device/OS/WeChat-version population, physical direction and unobserved conditions remain explicitly unverified.
- Failure returns to development: repair through cheap checks and relevant targeted device feedback, then generate a new settled package and rerun the complete applicable device verification. `stop` deletes only the validated tool-created session; the existing phone-bundle owner separately retires its external project and QR material.

The remaining sections define the detailed settled-candidate commands, privacy scopes, remote/ordinary-preview interpretation and journey rules. They also constrain any shared ADB operation used during development feedback; development use never inherits their evidence meaning.

## Preparation and repeatable commands

- Install official standalone Platform Tools; Android Studio is unnecessary for this route. Discover ADB through `STARWARD_ADB_PATH`, the existing Android SDK, the private StarwardTools installation, or PATH. Do not download tools on every test or change global package/proxy settings.
- The user connects a data-capable cable, enables USB debugging, personally accepts the computer's RSA authorization and opens the target Mini Program. WeChat login, identity verification, remote-debug QR scan and physical phone rotation remain user actions. With explicit owner authorization, the test operator handles this Mini Program's privacy/location and other feature-required permission prompts, including deny, recover and grant cases; these are test actions, not product permission bypasses. Do not operate chats, payment, unrelated permissions or account-security settings.
- `npm run miniapp:device -- doctor` checks tool/device readiness without recording device serial numbers. Zero, unauthorized, offline or ambiguous USB devices block phone operations. The default route uses exactly one USB device; disconnect additional USB devices instead of guessing.
- `npm run miniapp:device -- start --project <absolute-external-phone-project>` binds a disposable session to a settled local bundle. Commands `capture`, `tap`, `swipe` and `back` take `--session <absolute-session-directory>`; `tap`/`swipe` take normalized screen coordinates in `[0,1]`. Operations require the Android foreground activity to be a WeChat AppBrand activity, and input requires a recent screenshot from the same connected device and unchanged foreground activity/display. This is an operator-assisted boundary, not proof of the target AppID: inspect the screenshot before issuing input.
- For an explicitly authorized permission-recovery test, open the target Mini Program's visible WeChat permission-settings control, then use `capture-permissions --session <directory>`. This separately admits only WeChat's exact `AppBrandAuthorizeUI` and its `AppBrandAuthorizeDetailUI` child, with activity metadata proving the current page was launched by WeChat and shares the same Android user/task with the underlying AppBrand activity; the detail page additionally requires its authorization-settings parent in that same user/task. The primary focused window must match. Review the visible Mini Program name and permission before a fresh `tap` or `back`. The permission scope is carried by that single-use capture; ordinary `capture` still rejects these activities, and permission-scoped swipes, other WeChat pages and Android system settings remain blocked. Return to ordinary `capture` after leaving the page. This metadata plus operator review is not runtime AppID verification.
- If that deliberate location request opens Android's runtime permission prompt, `capture-location --session <directory>` admits only an explicitly supported PermissionController activity. It requires the WeChat launcher, same-user/task AppBrand return owner, matching primary focus, and a system-installed PermissionController package. Inspect the visible requester and location purpose before choosing the least privilege sufficient for the case; no background location or unrelated permission is implied. This scope allows only fresh tap/back actions and never Android Settings, USB trust, login, global permission resets or app-ops changes. Unknown OEM components fail closed until inspected and covered by the existing adapter's checks.
- Open the intended external project through official DevTools automation before `start`: initial import may normalize project config bytes. If this changes the fingerprint of an already started session, discard that session and bind the now-settled bundle; never ignore drift or silently relabel an earlier phone observation.
- `npm run miniapp:device -- remote --session <directory> --endpoint ws://127.0.0.1:<automation-port>` uses public `miniProgram.remote()` on that already explicitly opened, automation-enabled project. Its public terminal QR output is not logged: the bounded adapter renders only the recognized QR block matrix to a private session PNG, preserving the code and adding a quiet border for scanning. The user scans that image or the official DevTools QR; no SDK internals, hidden super-app APIs or private CDP are called. Unsupported QR output formats fail rather than being guessed. The QR file is deleted after connection/failure; raw text/content never goes into Context, logs or source. Only fixed connection-stage labels are emitted. If the official remote protocol is unavailable, use the official GUI or report the limitation.
- `inspect` uses the same session/endpoint after remote attachment and returns only a bounded allowlist: runtime platform/AppID match, OS/WeChat/base-library versions, safe-area/window/capsule dimensions, known route and map-control geometry/location-state labels. Simulator (`devtools`) is rejected as phone evidence. SDK commands have bounded deadlines; disconnect only their own SDK client, not the user's IDE or global ADB server. Inspect does not install API mocks, collect storage, request payloads, exact location, WXML or console text.
- The remote worker resets its stage deadline when the QR becomes available, so compilation cannot consume the user's scan window. Connection, QR generation, user scan and connected inspection have separate bounded waits; the parent retains a final process watchdog and removes QR material even if the worker fails. A timed-out command is terminal only after its process handle confirms exit. Reobserve that handle before retrying; never create concurrent remote sessions because a progress poll was quiet.
- `stop --session <directory>` deletes only the validated tool-created session directory, including screenshots. It does not erase WeChat data, revoke app permissions, close unrelated processes or remove the externally prepared phone bundle. The user closes remote debugging and can disable USB debugging/revoke computer trust when finished; the existing bundle owner separately cleans its sensitive temporary project.

## Privacy, failures and lifecycle

- Screenshots may contain precise map locations or notifications. They are private, repository-external, short-lived artifacts. Use a quiet test phone/suppress notifications manually; never commit screenshots, QR codes, device identifiers, credentials or private locations. Context contains only stable workflow meaning, not run output. No raw logcat, chat access, clipboard synchronization, microphone/audio capture, blanket UI dumps, rooting, bootloader changes or device-wide process killing.
- Tool subprocesses use argument arrays without a shell, bounded output and timeouts; failures emit fixed error categories, not raw stderr. USB identity is held only in process memory for commands; a session-local random salted device binding prevents sending input after switching phones without retaining its serial. A disconnected device, changed bundle, missing foreground proof, stale screenshot, different focused window or unsupported SDK call fails visibly. Activity/window checks do not detect every dialog within an AppBrand activity: the operator must inspect each fresh screenshot, identify the test case, requester, permission and button before acting. Owner-authorized Mini Program permission prompts can be operated; login/payment/security dialogs cannot. A system permission window outside the recognized foreground scope remains unsupported until its requester and return boundary can be verified by the adapter; never relax the guard to every system window or use `pm grant`, `appops`, settings/database edits or a blanket UI dump as a substitute. Readiness and diagnostic success never set product acceptance to passed.
- Local bundle fingerprints are checked before and after observations. Partial observations after drift/failure are not fresh evidence. Only owned external files are cleaned; unknown directories, symlinks/junction aliases and concurrent sessions on the same state directory are rejected.
- Test-only location/compass simulation stays in the existing `platform-simulation` runner. Physical tests use real platform APIs; turning a phone, magnetometer calibration and sensor quality still need actual hardware observations. ADB screenshot/input cannot simulate truthful physical orientation.

## Required journey and evidence interpretation

### Explicitly instrumented request-failure comparison

When the public SDK cannot expose the physical runtime and product feedback has generalized the error, an explicit `MINIAPP_DEVICE_REQUEST_DIAGNOSTICS=1` test build may observe failures at the existing Mini Program `services/api-client.ts` transport owner. It must not issue substitute requests or change authentication, retries, cancellation, TLS or response semantics. The dedicated diagnostic formatter emits only fixed stage/category labels and bounded integer platform/HTTP codes; it never emits request keys, URLs, headers, bodies, account/location data or raw error text. Unknown errors remain unknown, and a category inferred from platform text is a diagnostic hint, not proof of root cause.

The test build presents only the first terminal failure per JavaScript runtime using an explicitly labelled native test modal. Notification failures cannot change request results. There is no diagnostic persistence, console logging or background polling. This dialog is instrumentation, so it cannot establish uninstrumented layout, interaction, timing or acceptance. It does not enable the broader acceptance reset/inspection hooks or fixture mode. A new instrumented candidate requires the existing build owner, separate external bundle/session binding and explicit new-preview confirmation; never patch a previously scanned bundle.

Formal `releaseBuildEnvironment` forces this flag off even when inherited from the shell. Verify both enabled and disabled builds: the enabled bundle must contain the diagnostic marker and the formal/ordinary bundle must not contain it. Unit checks cover output redaction, unknown input, first-failure concurrency and presentation failure; actual phone observation is still required. Once the failure is localized, repeat the affected product journey with the instrumentation disabled.

### Keep the test path separate from product findings

This Context owns the reusable device connection/debugging path, commands, authorization boundaries, recovery and cleanup. A run's diagnostic-path status records which USB capture/input, official remote connection, runtime reads and ordinary-preview transitions actually worked. Product findings are a separate issue list with entry, action, observed feedback, impact and unresolved cause. Neither list is a second Context authority; screenshots, run status and private environment details remain external/task-local.

A successful screenshot/input followed by a visible product network error establishes an operable observation/control path and a product/environment symptom; it does not establish backend success or an ADB failure. Conversely, SDK inspection timeout or a foreground guard rejection is a diagnostic limitation, not evidence of a product defect. Keep candidate identity, invocation success, visible product behavior and end-to-end acceptance distinct in every report.

### Remote-to-ordinary-preview comparison

Record the DevTools remote attachment and the phone's own Mini Program development/debug switch separately. They are different states: disconnecting the desktop remote session, scanning an ordinary preview, or observing no remote overlay does not establish the phone debug switch's value. Inspect the target Mini Program's official menu (where available, `…` → `开发调试`) without changing it; the visible `打开调试`/`关闭调试` action is evidence of that setting, not of successful network access. Do not open heap snapshots, unrestricted console/network payloads or unrelated account menus for this check.

An authorized debug toggle can leave the supported AppBrand foreground and require reopening the Mini Program. Stop input/capture at that boundary and ask the user only to reopen the same preview; a new QR is not required solely because of this transition. After reopening, obtain a fresh capture and inspect the official menu again before claiming the switch changed. A sent tap is not confirmation. A failed capture invalidates input authorization even if the previous PNG remains on disk; display it only as historical evidence, never as the new result.

The IP-preview deployment route uses a publicly trusted IP certificate but still depends on an explicitly authorized development-only phone domain-list exception; it is not ordinary experience or public-release traffic. Do not disable TLS verification or install a private CA to repair a phone TLS failure. Record domain-list failures separately from certificate/transport failures and use the deployment-owned public-trust check before retrying the phone. If the current task disallows the phone domain-list exception, generic testing authority does not resolve that conflict: obtain an explicit owner decision before toggling the exception. Do not silently enable it to make a failing network case pass. Keep debug-disabled and explicitly authorized debug-enabled results distinct, record the original switch state, and restore it after a bounded comparison unless the owner asks to keep it for the trial. Never infer public network readiness from either remote connection or debug-enabled request success. Deployment remains the owner of the permitted IP lane and its security prerequisites.

1. Preserve the settled external candidate. Generate an ordinary preview through the existing official preview/build owner with its lock and before/after fingerprint checks; do not regenerate product code merely to switch observation modes.
2. End the current official remote session and have the user scan the ordinary-preview QR. Record that user confirmation separately from the screenshot observation that the remote-debug overlay is gone. An overlay disappearing alone does not identify the newly opened candidate or prove a process cold start.
3. Capture and inspect the current Mini Program before any input. If the user navigates or scans while the operator acts, a changed foreground invalidates the previous input credential; recapture rather than replaying the old coordinates or treating the rejected input as a product failure. Do not inspect the WeChat scanner/chat while it is outside the AppBrand boundary.
4. Repeat the affected actual entry, permission, location, network-retry and map/astronomy cases in ordinary preview. Keep the official runtime-read channel's availability independent from the ADB screen channel. User-confirmed preview plus matching local hash still does not provide byte-level phone attestation.
5. After the QR is consumed and the run is recorded without private data, clean the tool's disposable session using `stop`. It does not close or clear the phone app. To continue observing that same approved app, `start` a fresh session bound to the same settled external project and obtain a new `capture`; do not reuse the old screenshot credential or require another scan solely because local diagnostic files were renewed. The separate phone-bundle owner controls eventual sensitive bundle cleanup.

On the final candidate, record the declared phone/OS/WeChat/base-library and network conditions without unique identifiers. Exercise real entry/cold start and return, safe-area/capsule clearance, visible location/retry controls, location allow/deny/recovery, visible map tiles, truthful zero-spots/error/loading states, current-context weather/astronomy, and foreground/background/return. Authorized permission tests use the actual Mini Program prompt or its scoped official permission page, record the before/action/after outcome without private data, and restore the agreed usable state. App-level WeChat OS permissions may affect other Mini Programs: do not reset them globally to manufacture a prompt. Do not wipe all WeChat data to simulate cold start. A `reLaunch` within remote debugging is a route restart, not a process cold start.

Distinguish GPS acquisition, map centering and coordinate conversion, backend Observation Context resolution, map tiles, formal spots and provider results. Tiles alone prove none of the others. For compass behavior compare real physical rotation with visible heading changes, then verify sensor lifecycle after leaving/returning. Public-place/date simulation is supplemental and cannot prove GPS or real sensors. No exact personal coordinates are copied into reports.

Remote debugging can change network routing, execution timing and runtime behavior. Repeat the affected journey in ordinary preview after disconnecting debugging; do not promote debug-mode measurements to normal-use performance. Android is the initial operator-assisted sample, not iPhone/representative-population acceptance. iPhone-specific safe-area repairs require an iPhone recheck. Public domain, filing, formal authentication and public release remain separate external gates.

## Alternatives and verification

Allowed alternatives are direct official GUI + user screenshots, ADB + official SDK, and optional official scrcpy for continuous display/control. Select ADB + SDK for scoped machine observations and reuse of installed tools. scrcpy is optional; if adopted later disable audio and clipboard synchronization, scope it to the authorized device and own its process lifecycle. Appium/Android Studio are unnecessary dependencies for the present bounded route. Rooting, hidden super-app APIs and browser-policy workarounds are not alternatives.

`npm run test:miniapp:device-tools` checks selection, failure/redaction, freshness, bounded input, session cleanup and SDK adapter boundaries with injected drivers. Run `doctor` against the actual host, then `capture`/input/remote/inspect against the actual connected phone before claiming functioning physical integrations. Driver tests are not device evidence. Finish with Context validation and touched-source modularity. Product changes still run their existing owning checks and final-candidate journey.

Primary references: [Android ADB](https://developer.android.com/tools/adb), [Platform Tools](https://developer.android.com/tools/releases/platform-tools), [official scrcpy](https://github.com/Genymobile/scrcpy). The installed locked `miniprogram-automator` public declarations/implementation define the usable SDK adapter. SDK availability is not a claim that the connected phone supports every method.

# WeChat Settled-Candidate Device Verification

This on-demand verification node owns fixed-candidate physical-device verification plus its repeatable preparation and command surface.

Screenshot artifacts are immutable within their disposable session: ordinary/scoped captures and recording final frames each return a distinct image path, capture ID, capture-completion time, SHA-256 and private JSON receipt. Consumers use the returned `screenshot` path; `screen.png` is not a current-capture alias. Identical hashes identify identical bytes across distinct observations, not identical capture times or reusable input authority. Only the latest successful capture can supply the existing expiring, single-use input grant. Session cleanup still removes these private artifacts; archive required evidence through its existing owner before cleanup. Earlier overwritten images cannot be reconstructed from a later file or timestamp.

For a visibly focused Mini Program field, `miniapp:device -- text --session <directory> --value <public-query>` supports bounded non-secret ASCII queries (letters, digits, spaces, colon, dot, underscore and hyphen; at most 80 characters). It consumes the same fresh screenshot authority as tap, preserves device/bundle/display guards, and rechecks foreground/focus between paced characters. Shell syntax, Unicode and permission-scope text are rejected; a partial failure requires a fresh capture and inspection rather than replay. Text is neither retained in the session nor emitted in the command result. Inspect actual field contents and results: command success alone does not establish correct entry. This is a narrow search-testing aid, not a credential or arbitrary-shell input lane.

### Guarded Android recording

An explicit `swipe --ms` can cover one sustained single-finger movement within the finite bound owned by `screenGestureArguments` and CLI help. It consumes one fresh input grant and keeps the existing foreground, display, transport and permission guards; it does not admit pinch, another pointer or another input. For `record-swipe`, select a clip that leaves time for preflight and the complete gesture: the recorder refuses dispatch when its remaining window is too short. Requested gesture duration and encoded video coverage remain separate observations.

For a named dynamic visual question, `record-tap` and `record-swipe` take the same arguments as `tap`/`swipe` and combine that one reviewed input with a bounded Android MP4 capture. For passive motion/stability observation, `record --session <directory> [--transport usb|wireless]` uses the same recorder without sending any input or adding a dummy tap; its result explicitly reports `inputSent: false`. All three default to six seconds; an explicit `--seconds` accepts 6–15 seconds when delayed resources need a longer observation window. A longer recording does not extend screenshot input authority or permit a second input. All three use the same current bundle, session lock, device binding and single-use screenshot grant. Only ordinary Mini Program scope is admitted; permission/system windows gain no recording permission. `tools/miniapp/device-test.mjs` and `device-record.mjs` remain the single recording owners; `device-record.mjs` handles encoding, periodic foreground checks, a unique private device temporary path, signal/exit cleanup and unlink before binary transfer. `AdbDevice.input` checks recorder cancellation after its screenshot and transport checks, synchronously before actual dispatch; a slow preflight cannot send a gesture whose recording has already ended. An unchanged final scope and display are required before media is returned. `exec-out` receives the script as its own argument, without an extra shell quoting layer. The 16 MiB transfer bound, native time limit, failed-start/replay rules and private nested-session storage stay with those owners. Native support, encoded coverage and disconnect cleanup still require actual observation. A recording can contain fewer updates than its requested wall duration; encoded timestamps and cropped inspection do not establish physical application FPS, whole-scene performance or runtime AppID. Inspect the actual sequence against the named requirement and keep partial or failed conclusions with the run evidence.

## 2. Settled-Candidate Device Verification

Enter only after cheap checks, warm WEAPP/DevTools feedback and relevant targeted device feedback are stable. Use one clean ordinary preview or applicable experience build, record its complete candidate identity, keep all candidate inputs fixed and, where practical, turn off phone development/debug state. The existing `npm run miniapp:device -- start/capture/capture-permissions/capture-location/tap/swipe/back/remote/inspect/stop` path remains the evidence-level diagnostic mechanism.

- Automatic refresh is forbidden while results are being collected. Bundle/source/config/AppID/API-origin/base-library/build-input drift invalidates the session and all dependent observations; create a new candidate and rerun the complete applicable journey rather than relabelling the old evidence.
- Every input requires a new screenshot from the same device, foreground activity and display. Ordinary preview, phone debug state and desktop remote attachment are independent conditions and must be reported separately. Debug or remote results cannot become debug-off ordinary-preview results.
- The human performs scan/login/USB trust/physical rotation and reviews every permission or location requester before input. Run the applicable cold-start, navigation, permissions, GPS/map, Observation Context, weather/astronomy, network failure/recovery, background/return and persistent-state journeys without using simulation to prove GPS or physical direction.
- A single Android proves only the declared owner-device sample. iPhone safe area, device/OS/WeChat-version population, physical direction and unobserved conditions remain explicitly unverified.
- Failure returns to development: repair through cheap checks and relevant targeted device feedback, then generate a new settled package and rerun the complete applicable device verification. `stop` deletes only the validated tool-created session; the existing phone-bundle owner separately retires its external project and QR material.

The remaining sections define the detailed settled-candidate commands, privacy scopes, remote/ordinary-preview interpretation and journey rules. They also constrain any shared ADB operation used during development feedback; development use never inherits their evidence meaning.

## Preparation and repeatable commands

- Install official standalone Platform Tools; Android Studio is unnecessary for this route. Discover ADB through `STARWARD_ADB_PATH`, the existing Android SDK, the private StarwardTools installation, or PATH. Do not download tools on every test or change global package/proxy settings.
- Select the authorized transport through the owner's [USB/TLS wireless preparation](../wechat-device.md#android-transport-choice-and-reconnect), then return the target Mini Program to the foreground. Only the USB route requires a data-capable cable, USB debugging and its RSA authorization; TLS wireless pairing uses its own phone control. WeChat login, identity verification, remote-debug QR scan and physical phone rotation remain user actions. With explicit owner authorization, the test operator handles this Mini Program's privacy/location and other feature-required permission prompts, including deny, recover and grant cases; these are test actions, not product permission bypasses. Do not operate chats, payment, unrelated permissions or account-security settings.
- `npm run miniapp:device -- doctor` checks tool/device readiness without recording device serial numbers. Its current adapter selects exactly one authorized USB device; zero, unauthorized, offline or ambiguous USB transports block that adapter's phone operations. This does not diagnose a separate wireless or WeChat true-debug channel. Wireless pairing does not remove the need to implement and verify explicit wireless selection in that same adapter before using these capture/input commands over it.
- `npm run miniapp:device -- start --project <absolute-external-phone-project>` binds a disposable session to a settled local bundle. Commands `capture`, `tap`, `swipe` and `back` take `--session <absolute-session-directory>`; `tap`/`swipe` take normalized screen coordinates in `[0,1]`. Operations require the Android foreground activity to be a WeChat AppBrand activity, and input requires a recent screenshot from the same connected device and unchanged foreground activity/display. This is an operator-assisted boundary, not proof of the target AppID: inspect the screenshot before issuing input.
- For an explicitly authorized permission-recovery test, open the target Mini Program's visible WeChat permission-settings control, then use `capture-permissions --session <directory>`. This separately admits only WeChat's exact `AppBrandAuthorizeUI` and its `AppBrandAuthorizeDetailUI` child, with activity metadata proving the current page was launched by WeChat and shares the same Android user/task with the underlying AppBrand activity; the detail page additionally requires its authorization-settings parent in that same user/task. The primary focused window must match. Review the visible Mini Program name and permission before a fresh `tap` or `back`. The permission scope is carried by that single-use capture; ordinary `capture` still rejects these activities, and permission-scoped swipes, other WeChat pages and Android system settings remain blocked. Return to ordinary `capture` after leaving the page. This metadata plus operator review is not runtime AppID verification.
- If that deliberate location request opens Android's runtime permission prompt, `capture-location --session <directory>` admits only an explicitly supported PermissionController activity. It requires the WeChat launcher, same-user/task AppBrand return owner, matching primary focus, and a system-installed PermissionController package. Inspect the visible requester and location purpose before choosing the least privilege sufficient for the case; no background location or unrelated permission is implied. This scope allows only fresh tap/back actions and never Android Settings, USB trust, login, global permission resets or app-ops changes. Unknown OEM components fail closed until inspected and covered by the existing adapter's checks.
- Open the intended external project through official DevTools automation before `start`: initial import may normalize project config bytes. If this changes the fingerprint of an already started session, discard that session and bind the now-settled bundle; never ignore drift or silently relabel an earlier phone observation.
- `npm run miniapp:device -- remote --session <directory> --endpoint ws://127.0.0.1:<automation-port>` uses public `miniProgram.remote()` on that already explicitly opened, automation-enabled project. Its public terminal QR output is not logged: the bounded adapter renders only the recognized QR block matrix to a private session PNG, preserving the code and adding a quiet border for scanning. The user scans that image or the official DevTools QR; no SDK internals, hidden super-app APIs or private CDP are called. Unsupported QR output formats fail rather than being guessed. The QR file is deleted after connection/failure; raw text/content never goes into Context, logs or source. Only fixed connection-stage labels are emitted. If the official remote protocol is unavailable, use the official GUI or report the limitation.
- `inspect` uses the same session/endpoint after remote attachment and returns only a bounded allowlist: runtime platform/AppID match, OS/WeChat/base-library versions, safe-area/window/capsule dimensions, known route and map-control geometry/location-state labels. Simulator (`devtools`) is rejected as phone evidence. SDK commands have bounded deadlines; disconnect only their own SDK client, not the user's IDE or global ADB server. Inspect does not install API mocks, collect storage, request payloads, exact location, WXML or console text.
- The remote worker resets its stage deadline when the QR becomes available, so compilation cannot consume the user's scan window. Connection, QR generation, user scan and connected inspection have separate bounded waits; the parent retains a final process watchdog and removes QR material even if the worker fails. A timed-out command is terminal only after its process handle confirms exit. Reobserve that handle before retrying; never create concurrent remote sessions because a progress poll was quiet.
- `capture-location-picker --session <directory>` admits only the observed WeChat `SoSoProxyUI` native location picker, with the same launcher, same-user/task AppBrand return owner, focus, identity and display checks. Its fresh capture permits only `back` to cancel/return; tap, text, swipe and arbitrary WeChat pages stay blocked. It does not establish successful location selection, GPS or browsing Context commit. Do not tap a transient Info close control after its visible lifetime: wait for expiry, capture the stable page again and inspect the intended target.
- `stop --session <directory>` deletes only the validated tool-created session directory, including screenshots. It does not erase WeChat data, revoke app permissions, close unrelated processes or remove the externally prepared phone bundle. The user closes remote debugging and can disable USB debugging/revoke computer trust when finished; the existing bundle owner separately cleans its sensitive temporary project.
- For explicitly authorized USB hotspot recovery, `open-tethering-settings --session <directory> --confirm authorized_network_setup [--page more|wifi]` owns a separate fixed Settings navigation. It consumes the fresh Mini Program capture; `--page wifi` may also start from a freshly captured owned More page. `capture-tethering-settings [--page more|wifi]` admits only the adapter's exact system component with its navigation receipt, system-package provenance, focused BASE_APPLICATION window and explicit unlocked state. The two scopes permit fresh tap/back only; text, swipe, recording, credentials, unrelated Settings/permission dialogs and unrecognized OEM child pages remain blocked. Unknown dispatch is inspected through its retained owner, never automatically replayed; a successful ordinary Mini Program capture retires this temporary scope. SSID/credentials and network identities stay private, and a Settings action does not establish actual connectivity. This is separate preparation for an authorized environment repair, not a settled-candidate product result.

# WeChat Device Development Feedback

This on-demand verification node owns targeted physical-phone development feedback. It is diagnostic only and cannot qualify a settled candidate.

## 1. Development Device Feedback

Enter this channel only after the changed physical invariant has a first runnable WEAPP slice or a coherent edit batch is locally stable. Typical triggers are capsule/safe-area geometry, native map/tiles/gestures, permission prompts and recovery, GPS/coordinate centering, compass/physical rotation, foreground/background/restart/subpackage lifecycle, real device network/TLS/domain-list behavior, or an Android/iPhone difference. Ordinary domain, copy and state work stays in deterministic and warm DevTools feedback unless a physical boundary is actually at risk.

- The project entry is `npm run miniapp:device:feedback`. It reuses the existing Taro WEAPP output and `release-bundle-artifact.mjs` fingerprint owner, waits for stable bytes, snapshots one external private project, and invokes only the installed official DevTools `auto-preview` and ordinary `preview` capabilities. The command becomes a current capability only when its package-script registration and project tests exist.
- `start` creates the first feedback run; `refresh` creates a new generation and invalidates the prior generation's ADB session, screenshot and input authority before binding the new fingerprint; `preview` creates an official ordinary-preview QR for the exact current generation when automatic delivery did not reach the intended phone/account; `bind` is reserved for the exact operator-confirmed official update; `stop` removes only the run, snapshot, QR and device session it created. `doctor` is read-only capability/readiness feedback.
- Automatic preview is permitted because this is development feedback. It is not state-preserving Fast Refresh: the phone may reopen/restart the Mini Program and lose route-stack or in-memory state. Coalesce edits before `refresh`; never make every source save trigger a phone push.
- If the installed official CLI lacks the public command, login/service-port state blocks it, or the command fails, stop at the official boundary. Keep the prepared private project and offer the smallest supported handoff: generate the public ordinary-preview QR, or open that exact project and let the user choose the version-visible official Preview action (for example `预览` or `使用当前页进行真机预览`). Never depend on one historical menu label, and do not call private HTTP endpoints, SDK internals, raw CDP or hidden WeChat APIs.
- A zero exit from public `auto-preview` proves only that the official command completed for whichever account/device the tool selected; it does not prove that the intended USB phone or a different authorized developer account received the generation. On a first private snapshot, DevTools may still require the visible local-project `信任并运行` decision before compilation or phone update. Always return the prepared project path. If automatic delivery reaches the wrong account/device or the intended phone does not visibly show the generation, create one ordinary-preview QR for the unchanged generation and have the user scan it from the intended authorized WeChat account. Phone visibility remains separately unverified until observed; do not add or use an undocumented trust-bypass flag.
- Ordinary-preview generation rechecks the recorded bundle and canonical JSON configuration before and after the official command. A byte-only DevTools rewrite of `project.config.json` is tolerable only when canonical JSON equality proves every value is unchanged; a semantic config or bundle change fails closed. QR bytes remain repository-external and run-owned, are never logged or copied to Context, and are removed after confirmed binding. Refresh and stop own any remaining QR/generation cleanup; a DevTools file lock may defer that exact owned deletion, which must stay visibly pending until stop rather than masking the new generation.
- The user owns login, first/recovery scan, USB trust and any phone action the official flow requires. The operator may use the existing scoped ADB capture/input commands only after a fresh screenshot. Phone not foreground, disconnect, scan timeout, build/source drift and official-tool timeout are visible development-feedback failures, never product acceptance results.
- Official GUI 真机调试 or the existing public `miniprogram-automator` remote adapter may be selected for a targeted development observation after binding the exact generation. Its QR, connection and runtime inspection remain separate from ADB readiness and ordinary preview; every result stays explicitly debug-attributed and cannot prove debug-off behavior or fixed-candidate acceptance.
- Prefer official GUI 真机调试 for the first targeted physical observation. QR-based debug does not require an ADB-authorized USB cable; use USB/ADB only when scoped screenshot/input or device-side state observation is actually needed. A USB file-transfer prompt is not the Android RSA `允许 USB 调试` trust dialog, and absence of the RSA dialog is irrelevant to a GUI QR path. Do not spend the remote-debug diagnosis budget repeatedly resetting USB trust unless an ADB-owned operation is the boundary that failed.
- Before scanning a LAN-mode QR, verify the phone's current Wi-Fi has no stale manual proxy, the phone and host are on the same reachable subnet, the selected host address belongs to the physical adapter rather than a VPN/TUN adapter, and the required host port is reachable through firewall/access-point policy. If the local WebSocket attachment fails and DevTools falls back to WAN, record the local transport failure separately even when the remote overlay later says connected. PC-side Codex/VPN access may coexist through split routing; disabling the whole VPN is not the default repair.
- Treat authorization as two scoped identities: the desktop DevTools account must be an owner/authorized developer for the AppID, and the scanning phone WeChat account must independently be authorized for that Mini Program. They need not be the same account. A phone-side “login successful” notification without a completed desktop session is only server-side authorization feedback; if the desktop remains at `登录中`, first isolate DevTools version/profile/network compatibility rather than rescanning indefinitely.
- Use a known-good official DevTools version as a recoverable compatibility baseline and preserve the previous user profile before resetting or rolling back. On this Windows host, `2.01.2510280` restored login and GUI QR generation after the `2.02.2607xxx/2.02.2608050` line exhibited a stuck post-scan login and an internal missing SWC helper; this is a host-observed compatibility fact, not a permanent global pin. Re-evaluate against a newer official stable release only through login, exact-project package generation and one bounded connection probe. A generated-bundle missing asset such as an `iconPath` is project/snapshot ownership; an `ENOENT` under DevTools `resources/app.asar` is tool-install/version ownership. Do not repair one by mutating the other.
- After connection, grant only the scoped WeChat/OS permissions required by the journey and confirm their recovery path. Location permission, Android nearby/local-network policy and Mini Program authorization are separate boundaries; a rendered Tencent map proves tile rendering but not GPS, coordinate conversion, backend Observation Context or API success. The reusable success ladder is: package and QR generated; authorized scan launches the exact Mini Program; local or explicitly recorded WAN debug transport connects; the target permission state is observable; the affected real journey succeeds or yields a correctly classified product/environment failure. Only the last row is product feedback, and all rows remain non-acceptance development evidence.
- Every output is labelled `development_feedback` and reports only candidate/generation identity, official invocation disposition, observed product behavior, verified/unverified/invalidated scope and cleanup. It must not emit `passed` or `accepted`, and it must not preserve QR content, device serial, precise location, WeChat logs or user data.
- A successful official invocation means only that the supported update command completed for the prepared bundle. A visible phone observation is separate; debug/remote/vConsole/domain-relaxed results stay attributable to those conditions. No result from this channel crosses into the fixed-candidate channel.

# WeChat Device Development Feedback

This on-demand verification node owns targeted physical-phone development feedback. It is diagnostic only and cannot qualify a settled candidate.

## 1. Development Device Feedback

Enter this channel only after the changed physical invariant has a first runnable WEAPP slice or a coherent edit batch is locally stable. Typical triggers are capsule/safe-area geometry, native map/tiles/gestures, permission prompts and recovery, GPS/coordinate centering, compass/physical rotation, foreground/background/restart/subpackage lifecycle, real device network/TLS/domain-list behavior, or an Android/iPhone difference. Ordinary domain, copy and state work stays in deterministic and warm DevTools feedback unless a physical boundary is actually at risk.

- The project entry is `npm run miniapp:device:feedback`. It reuses the existing Taro WEAPP output and `release-bundle-artifact.mjs` fingerprint owner, waits for stable bytes, rejects a detected malformed/non-HTTP(S) compiled API base, a phone loopback API origin, and Taro experimental CompileMode `*-templates.wxml` artifacts before any phone delivery, snapshots one external private project, and invokes only the installed official DevTools `auto-preview` and ordinary `preview` capabilities. The command becomes a current capability only when its package-script registration and project tests exist. A DevTools recompile of an already prepared project cannot repair a build-time API origin or a mismatched Taro template/JavaScript pair; rebuild the tracked Taro output from a clean generated root and create a new generation.
- `start` creates the first feedback run; `refresh` creates a new generation and invalidates the prior generation's ADB session, screenshot and input authority before binding the new fingerprint; `preview` creates an official ordinary-preview QR for the exact current generation when automatic delivery did not reach the intended phone/account; `bind` is reserved for the exact operator-confirmed official update; `stop` removes only the run, snapshot, QR and device session it created. `doctor` is read-only capability/readiness feedback.
- `preview` and true debug are separate channels. Ordinary preview is the frozen-generation delivery lane for phone UI and interaction feedback, but it has no attached phone Console, Network or runtime inspector. It must not be described as 真机调试 or as proof that true-debug attachment works. Use the version-matched official true-debug flow separately when runtime diagnosis is required; an unavailable true-debug transport remains an explicit limitation rather than being relabelled as preview success.
- Automatic preview is permitted because this is development feedback. It is not state-preserving Fast Refresh: the phone may reopen/restart the Mini Program and lose route-stack or in-memory state. Coalesce edits before `refresh`; never make every source save trigger a phone push.
- If the installed official CLI lacks the public command, login/service-port state blocks it, or the command fails, stop at the official boundary. Keep the prepared private project and offer the smallest supported handoff: generate the public ordinary-preview QR, or open that exact project and let the user choose the version-visible official Preview action (for example `预览` or `使用当前页进行真机预览`). Never depend on one historical menu label, and do not call private HTTP endpoints, SDK internals, raw CDP or hidden WeChat APIs.
- A zero exit from public `auto-preview` proves only that the official command completed for whichever account/device the tool selected; it does not prove that the intended USB phone or a different authorized developer account received the generation. On a first private snapshot, DevTools may still require the visible local-project `信任并运行` decision before compilation or phone update. Always return the prepared project path. If automatic delivery reaches the wrong account/device or the intended phone does not visibly show the generation, create one ordinary-preview QR for the unchanged generation and have the user scan it from the intended authorized WeChat account. Phone visibility remains separately unverified until observed; do not add or use an undocumented trust-bypass flag.
- Ordinary-preview generation rechecks the recorded bundle and canonical JSON configuration before and after the official command. A byte-only DevTools rewrite of `project.config.json` is tolerable only when canonical JSON equality proves every value is unchanged; a semantic config or bundle change fails closed. QR bytes remain repository-external and run-owned, are never logged or copied to Context, and are removed after confirmed binding. Refresh and stop own any remaining QR/generation cleanup; a DevTools file lock may defer that exact owned deletion, which must stay visibly pending until stop rather than masking the new generation.
- DevTools' visible true-debug `重试` may officially recompile and upload the unchanged prepared project while regenerating an expired or failed QR. This is expected packaging work, not a Taro source rebuild or a new feedback generation, and it cannot repair or alter a build-time API origin. Do not prohibit that operator action. Preserve the generation identity, then recheck its bundle/config bytes before binding; any actual semantic drift still fails closed and requires a new generation.
- A bundle fingerprint identifies exact bytes; it does not establish that those bytes can render. Taro 4.2.1 experimental CompileMode assigns generated template prefixes through process-wide loader order, and a later build can pair incompatible `common`/subpackage template and JavaScript outputs while still completing and hashing successfully. Starward does not use that experimental mode. Build from a clean generated root, reject its `*-templates.wxml` artifacts at the feedback snapshot boundary, and open each decisive rebuilt candidate under a fresh prepared-project path. When two adjacent generations differ only in generated template/JavaScript groups, a bounded file-level A/B may localize the compiler regression, but copied generated files are diagnostic evidence rather than a shippable repair.
- A newly opened prepared project can display only the Mini Program shell or a compile indicator while DevTools finishes its first compile. Wait for compilation to settle before judging the page. The first page-automator read can time out during that interval; a later complete simulator frame and successful read close only the desktop boundary. Require current route/DOM plus a visible page capture; one blank `simulator_screenshot` is insufficient for a native `Map`, whose compositor can yield an isolated empty capture despite a mounted page. Conversely, a TabBar-only phone observation remains a phone failure even when the desktop simulator is healthy.
- The user owns login, first/recovery scan and phone-only USB trust or wireless-pairing controls. The operator uses the existing scoped ADB capture and fresh-screenshot input boundary. Phone not foreground, disconnect, scan timeout, build/source drift and official-tool timeout are visible development-feedback failures, never product acceptance results.
- Prefer the version-matched official `wechatide-skill` true-debug flow for the exact generation, then bind only after operator-confirmed phone visibility. Official GUI is a fallback for a concrete unsupported tool boundary; the public `miniprogram-automator` adapter remains a bounded compatibility diagnostic. QR, connection and runtime inspection remain separate from ADB readiness and ordinary preview. On DevTools 2.02.2609102/Skill 0.3.10, QR attachment can suspend `automation_runtime_info` while the phone still shows `已连接`; keep the session, record the runtime read as unavailable, and obtain phone pixels through the guarded ADB lane rather than restarting the project. Every result stays explicitly debug-attributed and cannot prove debug-off behavior or fixed-candidate acceptance.
- Treat the phone scanner as a separate, observable transition. Before input, show one current official QR at a crisp, stable size and capture the phone in WeChat's scanner; after input, check the resumed activity and phone pixels. A scanner-opening helper can report that the scanner is no longer foreground because the QR was recognized immediately; the resulting Mini Program foreground is success, not a scanner failure. End a failed phone debug session before scanning a replacement QR, and never use pixels from the old session to identify the new generation.
- A QR file or viewer process existing on the host does not prove that the phone camera can see it. Bring the current QR window into the actual foreground before opening the scanner. Returning from the scanner to WeChat Launcher without the Mini Program activity is an incomplete scan. `bind --confirm official_update_completed` is an operator assertion, not phone-foreground evidence; if the next guarded Mini Program capture fails, that session cannot support product evidence until a fresh capture succeeds on the Mini Program.
- Keep true-debug attachment and remote page automation as separate subchannels. A current phone page plus a green server state, nonzero received-message count and no pending messages proves that the debug runtime exchanged traffic; it does not prove that `automation_runtime_info` or other structured commands work. On Nightly 2.02.2609102 with Android WeChat 8.0.78, a session can render correctly and receive traffic while each structured command times out and the phone overlay records `cmdId 1006, errCode -50011`. Record that result as true-debug runtime attached with structured remote automation unavailable, retain ADB/vConsole or the desktop debugger for bounded diagnosis, and do not restart the package/QR/USB layers unless their own evidence fails.
- When the operator has explicitly authorized host-side phone control and positioned the phone to scan the current QR, the agent may complete this handoff through the existing guarded ADB lane. Render only the current QR at its native readable size, require WeChat Launcher or scanner foreground before known input, and verify that the result is the Mini Program activity plus current product pixels. Returning from the scanner to WeChat Launcher without a Mini Program launch is an uncompleted scan; one bounded retry of the same still-current QR is allowed after rechecking the foreground. Do not inspect chat content, infer success from input delivery, or carry screenshot authority across the launch.
- For an unattended authorized handoff, check Android display readiness, keyguard state and current input focus separately before opening the scanner. An online wireless ADB transport, a lit display or the expected resumed Activity alone does not prove that guarded taps will reach WeChat. Some OEM power dumps omit `mInteractive`; absence is unknown rather than `false`. Combine wakefulness/display state, `mHalInteractiveModeEnabled` when present, keyguard state and the focused window/application. Use the one-way `KEYCODE_WAKEUP` only when wake evidence is needed; never use toggling `KEYCODE_POWER`, which can lock an already usable phone. A supported wake or dismiss request may be attempted once, but never enter, infer or bypass a device credential. If the keyguard remains, preserve the prepared generation and continue independent checks; after an ordinary unlock, regenerate only an expired QR for the unchanged generation, explicitly focus the verified WeChat Launcher, then repeat the guarded Launcher → scanner → Mini Program transition. A keep-awake setting may be used only through an owned reversible helper that records and restores the exact prior value.
- ADB input coordinates belong to the active captured display, not the hardware panel declaration. Android may expose both `Physical size` and a smaller `Override size`; using the former can report a successful tap while missing the visible control. Use the guarded project input command after generation binding. For the authorized pre-binding scanner transition, prefer the active override when present and otherwise the fresh screenshot size, then recapture and inspect every intermediate WeChat surface before the next input.
- Image viewers can scale a captured phone image. Derive a normalized input from one coordinate system only: either the original capture dimensions or the displayed image dimensions divided by that displayed image's dimensions. Never read a pixel position from a resized view and divide it by the original capture height; that can move a panel gesture onto the native Map and create misleading behavior.
- When repeated true-debug attempts for an unchanged, locally healthy generation reach only the relay shell (including `已连接` with zero runtime exchange or a TabBar-only page), one official ordinary-preview QR for those exact prepared bytes may isolate delivery from relay attachment. A rendered ordinary preview is product/runtime development evidence under ordinary-preview conditions; it does not prove true-debug attachment, runtime identity, debug-off behavior or settled-candidate acceptance. Bind only after the exact ordinary preview is visibly running, and keep the relay failure as a separate tool/transport finding.
- Official Console/Network grep selects complete buffered records and does not redact their fields. Do not use broad network filters during authenticated or location-bearing journeys: a matching record can include Authorization headers, disposable tokens, request bodies, exact coordinates or response identities. Prefer page/runtime assertions and endpoint-specific status probes; if a buffered record is indispensable, select a non-sensitive event and reduce it in memory to an allowlisted status summary before output. Simulator buffers remain desktop evidence even while a phone true-debug session exists.
- QR-based debug does not require an ADB-authorized USB cable. Use ADB only when scoped screenshot/input or device-side observation is actually needed, following the owner's [USB/TLS wireless selection and reconnect](../wechat-device.md#android-transport-choice-and-reconnect). A file-transfer prompt is not USB RSA authorization; neither prompt is required for Android TLS wireless pairing or WeChat QR debug. Do not repeatedly reset USB trust when another channel is the failed boundary.
- Before scanning a LAN-mode QR, verify the phone's current Wi-Fi has no stale manual proxy and the phone and host have a mutually reachable route. When VPN/TUN or virtual adapters exist, use the official LAN-mode help popover's `切换IP` action to select the physical WLAN address and scan only the regenerated QR; Nightly 2.02.2609102 otherwise defaults to its first enumerated non-loopback IPv4 and can advertise the TUN adapter. Recheck the choice after every new project window or DevTools process because it is not reliably retained across that boundary. Verify an all-interface DevTools listener and admit the minimum inbound TCP range on the WLAN's actual firewall profile. Wireless ADB/mDNS does not prove this debug socket or an existing API firewall scope admits the phone's current source; recheck both bounded paths after WLAN, DHCP, hotspot or adapter changes. For an HTTP API, prefer a bounded request that reads the response status or first response bytes: a bare Toybox `nc` connection can reach the listener yet exit nonzero when the caller times out an intentionally open HTTP socket, so that exit alone is not an unreachable verdict. A required VPN/TUN may remain enabled and route metrics should stay unchanged. If LAN falls back to WAN, record that failure separately. A green WAN overlay with zero confirmed/sent/received counters and repeated protocol errors remains pre-runtime; require message exchange and visible page startup before treating true debug as attached. Do not reopen a solved USB path or rebuild product code for these transport failures.
- Treat authorization as two scoped identities: the desktop DevTools account must be an owner/authorized developer for the AppID, and the scanning phone WeChat account must independently be authorized for that Mini Program. They need not be the same account. A phone-side “login successful” notification without a completed desktop session is only server-side authorization feedback; if the desktop remains at `登录中`, first isolate DevTools version/profile/network compatibility rather than rescanning indefinitely.
- Use a known-good official DevTools version as a recoverable compatibility baseline and preserve the previous user profile before resetting or rolling back. On this Windows host, `2.01.2510280` restored login and GUI QR generation after the `2.02.2607xxx/2.02.2608050` line exhibited a stuck post-scan login and an internal missing SWC helper; this is a host-observed compatibility fact, not a permanent global pin. Re-evaluate against a newer official stable release only through login, exact-project package generation and one bounded connection probe. A generated-bundle missing asset such as an `iconPath` is project/snapshot ownership; an `ENOENT` under DevTools `resources/app.asar` is tool-install/version ownership. Do not repair one by mutating the other.
- After connection, grant only the scoped WeChat/OS permissions required by the journey and confirm their recovery path. Location permission, Android nearby/local-network policy and Mini Program authorization are separate boundaries; a rendered Tencent map proves tile rendering but not GPS, coordinate conversion, backend Observation Context or API success. The reusable success ladder is: package and QR generated; authorized scan launches the exact Mini Program; local or explicitly recorded WAN debug transport connects; the target permission state is observable; the affected real journey succeeds or yields a correctly classified product/environment failure. Only the last row is product feedback, and all rows remain non-acceptance development evidence.
- Treat native API declarations and native-control constraints as part of the physical boundary. `requiredPrivateInfos` must enumerate every location API the compiled product actually invokes; declaring `getLocation` does not authorize or describe `chooseLocation`, even when both flows share one permission explanation. Native `showModal` action labels must each stay within WeChat's four-character limit. Centralize repeated consent-modal copy, cover these invariants deterministically, and still exercise the native launch/cancel return on a phone because desktop mocks can accept configuration that the phone runtime rejects.
- Every output is labelled `development_feedback` and reports only candidate/generation identity, official invocation disposition, observed product behavior, verified/unverified/invalidated scope and cleanup. It must not emit `passed` or `accepted`, and it must not preserve QR content, device serial, precise location, WeChat logs or user data.
- A successful official invocation means only that the supported update command completed for the prepared bundle. A visible phone observation is separate; debug/remote/vConsole/domain-relaxed results stay attributable to those conditions. No result from this channel crosses into the fixed-candidate channel.

For structured DevTools acceptance, preserve one authenticated product identity across journeys that share server data. A journey-local reset may cancel requests, clear response/query caches and restore the canonical product store, but it must not remove the session or installation identity; reserve the identity-clearing reset for the beginning of an isolated session. When a later journey reviews or resumes a record created through production UI, read it back immediately through the current product session, retain its raw identifier only in process memory, and persist only hashes/state evidence. Do not re-login from an installation identifier or search for a loosely matching record later. Likewise, an existing Map information panel satisfies a prepared formal-spot journey only after its Observation Context spot identity matches the prepared spot; otherwise close it and select the named target through production UI. Record anonymous account continuity after intervening journeys so a client-reset bug cannot appear as an empty-list or missing-record product failure.

Android native Back behavior is presentation-owner specific. In the current Taro/WEAPP stack, `enableAlertBeforeUnload` protects dirty editors reached through `navigateTo` but does not prompt for the same editor embedded in the Map Tab root. A hidden `PageContainer` did not intercept that root Back; making `PageContainer` own the complex embedded form added a native Back entry but repeatedly rendered the form blank or cropped across valid layout variants. The adopted Map overlay therefore remains page-owned: its explicit close, tab switch, marker/target switch and other product exits must call the editor's confirmation owner. Android system Back from the dirty embedded root editor remains a platform/runtime limitation unless the adopted product flow is changed to a real page route. Do not generalize standalone-editor Back evidence to this root overlay or silently replace its adopted presentation.

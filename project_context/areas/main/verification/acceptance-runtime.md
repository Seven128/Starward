# Acceptance / Runtime Verification Context: main

This on-demand verification Context owns repeatable authority checks and formal product-runtime evidence boundaries. It states what the listed paths can falsify; passing prose, static shape, or a command alone never establishes product acceptance.

## Owner

- Owning area: main.

## Authority And Runtime Verification Paths

- npm run design:lint invokes the official Google design.md CLI through its Windows-safe `designmd` binary alias and checks the authored visual-system document structure.
- npm run design:system:verify checks both independently scoped system adoptions. For the native App it checks the exact DESIGN→runtime color/type/spacing/radius projection, role equality, six-value observation palette, and rollback classification of older page/control targets. For the WeChat Mini Program it checks the selected source/index/reference digests, canonical DESIGN table equality, all eighteen roles across day/night/observation, warm-red closure, required contrast pairs and explicit non-inheritance from the App profile; it does not claim a Mini Program runtime projection exists.
- npm run design:targets:verify checks the unchanged rollback-target hashes, 14 Surface Keys, 95 Control Keys, page/control set equality, Source Plan equality, and their continued DESIGN index presence. It protects integrity and semantics only; it is not a current visual-fidelity check.
- npm run test:acceptance:mobile runs the full mobile browser suite with its isolated server lifecycle when a warm development session is not appropriate.
- python C:/Users/777/.codex/skills/.system/skill-creator/scripts/quick_validate.py .codex/skills/uiux_design checks the project interaction Skill structure and metadata.
- npx --yes impeccable detect docs/design-system/brand.html performs an auxiliary scan of the retained legacy export only; it cannot evaluate or constrain the active system.

## Required Preparation

- Network access may be required the first time the Google design.md or Impeccable CLIs are resolved through npx. On Windows, use the `designmd` alias exposed by `npm run design:lint`; invoking `design.md` from the repository root collides with the `DESIGN.md` file association.

## Runtime Acceptance Boundaries

- Primary-navigation acceptance must cold-start the production activity, press all five tabs, and observe canonical route/screen identities `/tonight`, `/map`, `/trips`, `/sky`, and `/me`. It must give at least two tabs distinguishable nested-route and scroll/canvas positions, switch away and back, and prove independent restoration; a shared root `ScrollView`, anchor jump, conditional destination swap, detached deep link, or selected-tab styling alone cannot pass.
- The same navigation check exercises a nested deep link that activates its owning tab, invalid/stale-link recovery to that tab root, route-owned overlay closure, owning-tab stack pop, and native Android Back behavior without synthetic cross-tab history. iOS retains the same contract while its current live runtime evidence remains deferred.
- Formal browser/API acceptance must use a run-unique data root or an explicit deterministic reset and must keep idempotency identity stable when non-semantic freshness fields change. A prior interrupted or completed run must neither conflict with a later isolated run nor silently reuse its domain result.

## Expected Signals

- Design lint completes without schema/structure errors.
- System verification confirms DESIGN.md is the sole exact-value authority for two independent profiles. Native App runtime tokens match only the App profile and retain its role-isomorphic six-value observation system. The selected Mini Program source and eight references retain their registered digests; the canonical Mini Program section exposes the same eighteen roles in day/night/observation, satisfies its registered contrast pairs, stays inside black/warm-red observation closure, and contains no App token-source or target dependency.
- Project interaction Skill validation completes without frontmatter, naming, or resource errors; its authority statement keeps DESIGN.md/Source Plan/Context upstream.
- Retained legacy brand, light-kit, and dark-kit HTML files can resolve their local font and supporting artifact paths, but remain inactive visual inputs.
- Every repo-local rollback target retains its registered SHA-256 identity; the mobile 12/83 and operations 2/12 sets remain unique and equal between page coverage and control contracts without becoming current style baselines.
- Every Outcome acceptance run uses at least two materially different inputs through production entry points and proves the result changes with those inputs.
- Stateful and artifact-producing flows prove the applicable database/file/object/native sink write and read it back from a fresh service instance, process, or app restart; in-memory continuity is insufficient.
- Native and external boundaries expose an invocation/result seam so automated tests can substitute an isolated adapter, while the production runtime either invokes the real adapter or presents an explicit unavailable/degraded state.
- Success, failure/timeout/permission denial, duplicate/idempotent retry, and conflict behavior are observed where applicable. Removing the write, adapter call, restart readback, or input dependency must make the owning Outcome Check fail.

## Acceptable Warnings

- Impeccable findings are review signals, not a Tiny Context gate.
- Google design.md may report authored mode/material color roles as unused because its component frontmatter supports only a small single-mode sub-token vocabulary. These warnings are acceptable only when there are zero lint errors and `npm run design:system:verify` proves the native App projection plus the selected Mini Program authority tables, role closure, contrast contract and profile isolation. The check intentionally does not call the Mini Program profile a runtime projection while no runtime exists.
- Static Open Design kits are reference surfaces and cannot by themselves prove production application behavior.
- Until production UI exists, prose and Skill validation cannot prove interruption, velocity handoff, haptics, system-gesture competition, reduced motion, frame pacing, or red-light luminance; those require automated state checks and representative real-device evidence.
- Representative outdoor/device validation and China production promotion may remain future external gates for the current owner-only personal trial. This postpones only the external evidence; it does not waive production-path integration, local persistence, adapter invocation, honest degradation, emulator tests, or counterfactual machine evidence.
- The current target profile requires Android native runtime evidence. iOS application code, native-project integration, platform adapters, interaction/accessibility behavior, and build readiness remain implementation obligations, while macOS/Xcode/iOS Simulator execution and iOS build/runtime evidence are deferred. This deferral is an explicit unverified state, never a passing result; Android, browser, static, or historical evidence cannot substitute, and a future profile must re-enable the iOS runtime Checks before claiming iOS usability.

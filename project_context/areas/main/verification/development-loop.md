# Development-Loop Verification Context: main

This on-demand verification Context owns fast development feedback, bounded warm-session reuse, change-class routing, and the cadence for promoting a settled candidate to stronger checks. Formal acceptance meaning and Android Release execution remain in their owning sibling verification Context.

## Owner

- Owning area: main.

## Development Verification Paths

- npm run test:mobile:fast runs the mobile TypeScript check and current mobile Vitest suite without starting Metro, an emulator, or an APK build.
- npm run test:verification:fast checks Web session identity/reuse, native population/filter/shard/checkpoint semantics, installed-APK parsing, build fingerprint/cache invalidation, ABI scoping, stable CMake staging, and bounded Gradle reuse without compiling an APK.
- npm run dev:acceptance:mobile starts one foreground API-watch + Expo Web/Fast Refresh development session on the stable local port; while it remains owned by that terminal, npm run test:acceptance:mobile:warm may rerun the existing Playwright journeys without another server startup. Formal Playwright startup remains non-watch; the warm path is repair feedback, not a replacement for Contract or Final-Gate commands.
- npm run dev:inspect:mobile:web runs a diagnostic-only selected-design comparison against that owned warm React Native Web session. Outcome, Control, Mode and canonical mobile Condition filters narrow repair feedback; the command never emits Long-Task Check evidence and never substitutes for Android.

## Development Feedback Ladder

- Use the cheapest faithful feedback surface first and promote the same settled change through progressively stronger checks. The normal inner loop is changed-module type/unit/contract tests, then Expo Web or an installed Expo Dev Client with Metro Fast Refresh for React Native JavaScript, TypeScript, layout, styling, copy, and ordinary interaction work.
- Mini Program work follows the separate root-owned ladder in `project_context/development-workflow.md`: deterministic and warm WEAPP/DevTools feedback first, then risk-triggered `device development feedback` at a runnable physical boundary, and finally fixed-candidate device verification. The physical development channel is batched rather than save-triggered and cannot promote its observations into acceptance.
- Use Contract `input_paths`, Binding carriers, and reported stale Progress as the change-to-Check authority; do not maintain a second hand-authored impact map. During rolling repair, run only the affected package/Outcome checks plus dependency regressions, then widen to Stage checks and the complete Live Final Gate at their declared boundaries.
- Watch mode, warm Metro, and a long-lived development client are suitable for the bounded edit loop. Gate evidence uses deterministic non-watch commands against a settled snapshot; a watch process or green overlay is never itself a passing Check.
- Fast Refresh and browser rendering are development feedback only. They cannot prove a packaged native release, cold start, deep-link delivery, native permission/bridge behavior, system navigation, offline restart, or operation without Metro.
- React Native Web renders the same production component and route sources for fast layout, token, copy, ordinary state and interaction feedback; a separately maintained Web imitation of the mobile UI is forbidden. Selected-design diagnostics read the canonical handoff and its frozen mobile page/control targets directly, label every output diagnostic-only, and preserve Outcome/Control/Mode/Condition attribution.
- Coalesce related edits before target-runtime verification. Run the Contract-declared Android release install/check at the earliest stable owning-Outcome boundary, rerun it only after an applicable native input or declared carrier makes its evidence stale, and run it again when required by the Live Final Gate. Do not invoke a release APK build after every small edit or merely because another lightweight Check ran.
- A JavaScript/TypeScript/style/copy change normally does not require rebuilding an already installed development client. Rebuild Android when an applicable native dependency, Expo config/plugin output, AndroidManifest/resource, Gradle setting, Java/Kotlin/C/C++ source, ABI, signing/package identity, or bundled-release behavior changes. API/domain-only changes first use their service, contract, persistence, and browser/native-client integration checks; they require a new APK only when the packaged client or native boundary also changed.
- Before the expensive native gate, make the affected typecheck, unit/contract tests, structured boundary checks, browser journeys, API availability, route/action identifiers, and required emulator/device state pass. A failed prerequisite blocks the release build instead of triggering speculative rebuilds.
- Do not rerun an unchanged failed command merely to see whether it passes. First inspect the first causal assertion, trace/log, server health, port/process ownership, and current input fingerprint; retry only after a repair or when the runner explicitly classifies the failure as transient and retry-safe.

## Development / Test Execution Contract

- The canonical cadence is one explicit loop: keep a bounded Metro + development-client session alive → implement one coherent repair/feature batch with Fast Refresh and cheap checks → make the batch locally stable → freeze that snapshot and run one Stage-level packaged Release acceptance pass → collect all findings from that pass → return to the same fast development loop and repair the findings as one batch → package again only when that batch is stable. Never place Release assembly between individual edits or individual hypotheses.
- A failed packaged acceptance pass is a collection point, not a per-finding rebuild trigger. Inspect its complete logs, observations, screenshots and prerequisite state; reproduce each repairable issue with the development client, Web, unit/contract or structured checks where faithful; coalesce the fixes; then rerun the packaged Gate once. An immediate second Release build requires a settled snapshot or an explicit reason that the defect exists only in packaged/native behavior.
- Configuration is not runtime readiness. Do not report native Fast Refresh as enabled merely because `expo-dev-client`, a package script, or a generated native project exists. A bounded native development session is ready only after the selected app is installed as a debuggable development client, Metro reports healthy, and the running app requests its current JavaScript bundle from Metro. These are session-local feedback signals, never acceptance evidence.
- `progress_stale` is an acceptance-freshness condition, not an instruction to run its Check immediately. Queue the affected re-verification, coalesce related repairs, and run it at the earliest stable owning-Outcome boundary before dependent work grows and again where the Live Final Gate requires it. A stale flag by itself never authorizes an APK build.
- Before invoking a targeted Check, expand its complete cost path: Main run, every Counterfactual, server startup/teardown, native assembly, install, cold start, and scenario exercise. Any command that can reach `assembleRelease` is an expensive target Gate and stays outside the per-edit loop, even when the top-level command is named `verify` or targets only one Outcome.
- Select the first feedback path by the changed boundary:

  | Change class | First feedback | Native rebuild rule |
  | --- | --- | --- |
  | React Native JS/TS, layout, style, copy, ordinary interaction | affected unit/type/contract tests, then Metro Fast Refresh or Expo Web | no development-client or Release rebuild |
  | API/domain/persistence logic | owning package and structured boundary checks, then warm client/browser integration | no APK rebuild unless packaged client/native behavior changed |
  | Browser-only owner operations UI | affected unit checks and the owned warm Playwright session | no APK rebuild |
  | Native dependency, Expo plugin/config output, manifest/resource, Gradle, Java/Kotlin/C/C++, ABI or package identity | cheap native preflight, then one development-client rebuild for the settled native fingerprint | Release build only at the stable target Gate |
  | Stage or Final acceptance snapshot | declared deterministic Gate against the exact settled snapshot | one content-addressed Release APK may serve all same-snapshot scenarios |

- Contract `input_paths` must follow the owning Claim, carrier, and real shared dependencies. An earlier Stage Gate must not use an app-wide glob when an unrelated later feature cannot affect its assertion; shared shell/navigation/state paths are listed separately from Outcome feature paths. Evidence freshness scope and APK artifact scope are distinct: broad evidence inputs may require a scenario rerun, but the APK build fingerprint includes only production bundle/native inputs and excludes test-only files, docs, logs, screenshots, and verifier outputs.
- Before an expensive native Counterfactual, verify that its declared carrier is reachable from the target root or otherwise participates in the exercised runtime boundary. An unreachable or obsolete barrel/route is Contract drift, not a reason to compile a mutated APK. A mutation that removes a required entrypoint/import, or a missing API/device/tool prerequisite, must produce a deterministic fail-fast result before Gradle starts when the same falsification can be established without packaging.
- Native Gate prerequisites are mandatory and precede assembly: the explicitly bounded set of selected device serials/ABIs, expected package identity, Java/Android toolchain, API health and deterministic data state, declared route/action identifiers, port ownership, and sufficient disk headroom. Repair all failing prerequisites and exercise the hypothesis through the development client or cheaper surface before spending another Release build.
- On Windows, the native verifier resolves Java deterministically from an explicit valid `JAVA_HOME`, then Android Studio's bundled JBR, then a valid `java` on `PATH`; the resolved Java identity remains part of the Android build fingerprint. A missing or invalid toolchain fails before Gradle rather than depending on an interactive shell profile.
- One bounded session has one owner for each Metro/API/browser server, port, emulator/device, and build process. Silent output is not evidence that a process stopped and is not permission to launch a duplicate; inspect its child process, port and health instead. Cancellation or tool interruption must terminate the complete task-owned process tree, including Gradle daemons created for that bounded run, and clean only explicitly identified task-owned temporary snapshots.
- A warm server returning HTTP 200 is insufficient identity. Development reuse must confirm a session descriptor served by that same origin against the task-owned local registry, owner PID, repository identity and restart-sensitive startup-configuration fingerprint; a dead owner, mismatched descriptor, changed configuration or unrelated listener fails closed. Formal evidence additionally requires the declared source/config fingerprint and deterministic state isolation. Never run warm tests against an unknown or stale process merely because it occupies the expected port.
- Expensive runners must expose phase and elapsed-time diagnostics on a non-evidence channel so build, install, exercise, Counterfactual and cache-hit time remain distinguishable. Lack of progress output triggers inspection, not a duplicate run or an unchanged retry.

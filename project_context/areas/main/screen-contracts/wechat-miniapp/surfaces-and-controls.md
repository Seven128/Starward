# WeChat Mini Program Surfaces And Controls

This on-demand subdomain node normatively continues the Mini Program Screen Contract and owns its stable Surface responsibility list and complete material Control inventory.

## Stable Product Surfaces

### `miniapp-map-discovery`

- Primary question: Which formal stargazing spot should I find, evaluate and act on without losing the map or current observing context?
- Main surface owns: the one physical map; one fixed floating Search entry; the dedicated `spot/search` child; the one formal-spot selection; the three-extent `map-spot-information-panel`; and the current layer/time, route, favorite, contribution and evidence actions. The Map Search entry contains only Search affordance and current query summary when applicable. Search owns one visual field shared with the entry, anchored query suggestions, a single-line horizontally scrollable filter strip with a fixed trigger for its two-level category sheet, and `想去`/`其他观星点` result partitions. Strip choices commit immediately; the sheet's local draft confirms or cancels against the same committed store under [Map and Search](map-and-finder.md). Visible/system/edge Back closes the sheet first, then returns to Map through one reversible child transition; neither field state carries a trailing clear/close action. Filter choices use a semantic prefix icon, stable text and a non-layout selected ornament. Partition disclosure retains item identity, focus, scroll anchor and live geometry without flicker. Whole result cards commit selection, return to the same Map, recenter it and restore medium even for a repeated spot; there is no trailing selection button. The adopted daytime media card has no border/shadow and follows its leading readability treatment with first-line address alignment.
  Search activation preserves the field and its rendered query/placeholder as a stationary visual anchor while child content reveals below it; compact suggestions and a titleless filter group follow without oversized vertical gaps. A marker or returned result opens the same panel at `medium`. The three visible extents retain one continuous objective document and differ only by viewport clipping; `large` alone enables its vertical scroll, and valid media is the sole presentation exception, pulled into the document top during medium-to-large progress. The compact full-width white header band follows any valid site gallery in the document and scrolls out with the name; without media it is the first region. Only that actual visible band may manipulate extent, while press/tap without drag changes nothing and panel content never starts that gesture. Media reveals before the Search, location and layer controls fade near the screen top. The compact sticky `基本信息/天文` text navigation follows the sole section-navigation contract in [Spot and sky](spot-and-sky.md); the lower action region retains `想去/云观星/分享`. Ordinary unavailable values render the common visible copy `暂无数据` while their distinct domain/recovery states remain intact. Map uses one `none | spot-panel | layer-sheet` bottom-presentation owner, so opening layers clears the panel's presentation/active state, and a marker selected from an open layer sheet retargets directly to a new medium panel without restoring an intermediate old panel.
- It forbids: the retired Finder Bottom Sheet, map-embedded filters/results, a “筛选条件” title/divider, oversized suggestions/filter gaps, changed Search text, quick-versus-more filters, Search trailing `x`, standalone detail/night pages, per-extent content trees, a second map, whole-panel drag, tap-to-cycle handle, missing real document-header band, a fixed/sticky drag area above scrolled content, no-image placeholders, visible scrollbar chrome, gapped/shadowed panel rails, oversized action chrome, ruler arrows or non-draggable fake tracks, independent panel/layer active flags, deep-blue active surfaces, an independent observing-condition card, layer close/off actions, duplicated action bars, framed time rulers, TripDecision/recommended-window copy, `尚未核实` as ordinary missing copy, duplicated time truth, fake live facts, generic tutorial/implementation/data-state explanations, visible sample/version/reviewer copy and third-party brand imitation.

### `miniapp-sky-orientation`

- Primary question: Where are the currently observable objects as the device and selected observing time change?
- Main surface owns: `sky/detail` as a full-viewport sensor-following sky canvas; one quiet leading Back action without a boxed title/spot-time header; Source-backed in-canvas object labels; the raised, arrowless, horizontally draggable curved center-emphasis time ruler; material sensor recovery only when it changes use; and screen-reader/degraded object equivalence. Ordinary following remains programmatic state rather than visible explanatory chrome. It inherits the valid formal spot and Observation Context from Map and stops its sensor lifecycle whenever no longer foregrounded.
- It forbids: an independently seeded/global route; a boxed “方位天空 / 地点 · 时间” header or top target/location action; persistent “方向跟随中”/gesture/tutorial/data-mode copy; manual heading controls; decorative stars presented as targets; a framed or generic linear slider; persistent object tables; large non-canvas content; fabricated pose; persisted orientation tracks; or a standalone astronomy/professional/target page.

### `miniapp-my-library`

- Primary question: What is my account state, and how do I reach my plan or settings without turning the root into a second content browser?
- Account export and deletion require a fresh identity check bound to the initiating account, in addition to its authenticated session; confirmation dialogs alone are not reauthentication. The client supplies a fresh native WeChat login code, the API verifies the same identity before either operation, and failures retain the existing session/data. Local fixture identity checks are not real WeChat verification. Transport entrypoints: `services/api-client.ts`, API `auth-service.ts` and `controller.ts`; codes stay transient and must not enter logs or durable storage.
- Main surface owns: editable avatar/nickname, one Settings gear, near-term 观星计划 card and 观星点创建与反馈 records under [My account and plans](map-and-finder.md#my-account-and-plans), plus recoverable child routes. Settings owns the single day | night | observation mode control.
- It forbids: peer My/Favorites/Plan/Settings tabs; the subtitle “收藏、计划与显示偏好”; any Favorite count, row, list or duplicate browsing route on My; separate day/night tabs plus an observation CTA, a binary Switch pretending to own three modes, copied commerce/membership/promotion modules, remote/second-family icons, fake statistics, banner walls, page horizontal scrolling, sample content cards, duplicate spot information, and dynamic-provider failure deleting the static favorite relation retained by Search/Map.

### `miniapp-profile-content`

Retained implementation responsibilities only: profile links are retired from the current Mini Program topology and Import has no My entry; do not revive the old root during migration.

- Primary question: How can the user manage external profile links and import their own stargazing post while preserving rights, lineage, moderation and point identity?
- Main surface owns: neutral external link records, URL validation and copy-first fallback; `SOURCE → EDIT_DRAFT → ASSOCIATE_SPOT → PREVIEW → SUBMIT`; rights attestation; manual import; parser/license gates; editable draft protection; formal `spot_id` association or independent `spot_proposal_id`; moderation and EXIF/location sanitization.
- It forbids: platform affiliation claims, dangerous schemes, automatic parsing without allowlist/license/SSRF controls, parser retry overwriting edited fields, a proposal creating a formal `spot_id`, and unreviewed public UGC.

### `miniapp-contribution-intake`

- Primary question: How can an authenticated user submit a field report, correction or proposed place without publishing an unreviewed fact or leaking private location/media metadata?
- Main surface owns: an existing formal-spot context when supplied by the information panel; a full prefilled editable site document and immutable baseline/version; field/media differences and a frozen pending receipt; explicit rights and precise-location consent; bounded media selection/upload; multiple manual remote new-place drafts (feedback has no drafts) and upload state; idempotent submit/retry; and the current user's pending/approved/rejected history. Its presentation is one keyboard-safe scroll owner with quiet Back/title chrome, compact divider-backed rows for simple fields, top-label groups for multiline/topic/media controls, conditional new-place location, inline validation, upload progress/recovery and exactly one final submit. Map/new-place and panel/existing-spot entries converge on the same form owner. My opens creation and feedback records including private drafts; rejected records can be edited and resubmitted through the same owner, under the Map/My record contract.
- It forbids: automatically confirming a submitted claim, automatically collecting the contributor’s current device location for existing-spot feedback, retaining raw EXIF, accepting unsupported MIME or oversized files, submitting without explicit rights for media, disclosing another contributor's data, creating a formal spot or changing published facts before owner review plus canonical completeness reassessment, a separate wizard state invented only for layout, per-field cards, reserved empty helper gaps, duplicate sticky/document submits, or controls hidden behind the keyboard.

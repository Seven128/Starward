## Development Feedback Ladder

- Use the cheapest faithful feedback surface first and promote the same settled change through progressively stronger checks. The normal inner loop is changed-module type/unit/contract tests, then Expo Web or an installed Expo Dev Client with Metro Fast Refresh for React Native JavaScript, TypeScript, layout, styling, copy, and ordinary interaction work.
- Use Contract `input_paths`, Binding carriers, and reported stale Progress as the change-to-Check authority; do not maintain a second hand-authored impact map. During rolling repair, run only the affected package/Outcome checks plus dependency regressions, then widen to Stage checks and the complete Live Final Gate at their declared boundaries.
- Watch mode, warm Metro, and a long-lived development client are suitable for the bounded edit loop. Gate evidence uses deterministic non-watch commands against a settled snapshot; a watch process or green overlay is never itself a passing Check.
- Fast Refresh and browser rendering are development feedback only. They cannot prove a packaged native release, cold start, deep-link delivery, native permission/bridge behavior, system navigation, offline restart, or operation without Metro.
- React Native Web renders the same production component and route sources for fast layout, token, copy, ordinary state and interaction feedback; a separately maintained Web imitation of the mobile UI is forbidden. Selected-design diagnostics read the canonical handoff and its frozen mobile page/control targets directly, label every output diagnostic-only, and preserve Outcome/Control/Mode/Condition attribution.
- Coalesce related edits before target-runtime verification. Run the Contract-declared Android release install/check at the earliest stable owning-Outcome boundary, rerun it only after an applicable native input or declared carrier makes its evidence stale, and run it again when required by the Live Final Gate. Do not invoke a release APK build after every small edit or merely because another lightweight Check ran.
- A JavaScript/TypeScript/style/copy change normally does not require rebuilding an already installed development client. Rebuild Android when an applicable native dependency, Expo config/plugin output, AndroidManifest/resource, Gradle setting, Java/Kotlin/C/C++ source, ABI, signing/package identity, or bundled-release behavior changes. API/domain-only changes first use their service, contract, persistence, and browser/native-client integration checks; they require a new APK only when the packaged client or native boundary also changed.
- Before the expensive native gate, make the affected typecheck, unit/contract tests, structured boundary checks, browser journeys, API availability, route/action identifiers, and required emulator/device state pass. A failed prerequisite blocks the release build instead of triggering speculative rebuilds.
- Do not rerun an unchanged failed command merely to see whether it passes. First inspect the first causal assertion, trace/log, server health, port/process ownership, and current input fingerprint; retry only after a repair or when the runner explicitly classifies the failure as transient and retry-safe.

## Development / Test Execution Contract

- The canonical cadence is one explicit loop: keep a bounded Metro + development-client session alive → implement one coherent repair/feature batch with Fast Refresh and cheap checks → make the batch locally stable → freeze that snapshot and run one Stage-level packaged Release acceptance pass → collect all findings from that pass → return to the same fast development loop and repair the findings as one batch → package again only when that batch is stable. Never place Release assembly between individual edits or individual hypotheses.
- A failed packaged acceptance pass is a collection point, not a per-finding rebuild trigger. Inspect its complete logs, observations, screenshots and prerequisite state; reproduce each repairable issue with the development client, Web, unit/contract or structured checks where faithful; coalesce the fixes; then rerun the packaged Gate once. An immediate second Release build requires a settled snapshot or an explicit reason that the defect exists only in packaged/native behavior.
- Configuration is not runtime readiness. Do not report native Fast Refresh as enabled merely because `expo-dev-client`, a package script, or a generated native project exists. A bounded native development session is ready only after the selected app is installed as a debuggable development client, Metro reports healthy, and the running app requests its current JavaScript bundle from Metro. These are session-local feedback signals, never acceptance evidence.
- `progress_stale` is an acceptance-freshness condition, not an instruction to run its Check immediately. Queue the affected re-verification, coalesce related repairs, and run it at the earliest stable owning-Outcome boundary before dependent work grows and again where the Live Final Gate requires it. A stale flag by itself never authorizes an APK build.
- Before invoking a targeted Check, expand its complete cost path: Main run, every Counterfactual, server startup/teardown, native assembly, install, cold start, and scenario exercise. Any command that can reach `assembleRelease` is an expensive target Gate and stays outside the per-edit loop, even when the top-level command is named `verify` or targets only one Outcome.
- Select the first feedback path by the changed boundary:

  | Change class | First feedback | Native rebuild rule |
  | --- | --- | --- |
  | React Native JS/TS, layout, style, copy, ordinary interaction | affected unit/type/contract tests, then Metro Fast Refresh or Expo Web | no development-client or Release rebuild |
  | API/domain/persistence logic | owning package and structured boundary checks, then warm client/browser integration | no APK rebuild unless packaged client/native behavior changed |
  | Browser-only owner operations UI | affected unit checks and the owned warm Playwright session | no APK rebuild |
  | Native dependency, Expo plugin/config output, manifest/resource, Gradle, Java/Kotlin/C/C++, ABI or package identity | cheap native preflight, then one development-client rebuild for the settled native fingerprint | Release build only at the stable target Gate |
  | Stage or Final acceptance snapshot | declared deterministic Gate against the exact settled snapshot | one content-addressed Release APK may serve all same-snapshot scenarios |

- Contract `input_paths` must follow the owning Claim, carrier, and real shared dependencies. An earlier Stage Gate must not use an app-wide glob when an unrelated later feature cannot affect its assertion; shared shell/navigation/state paths are listed separately from Outcome feature paths. Evidence freshness scope and APK artifact scope are distinct: broad evidence inputs may require a scenario rerun, but the APK build fingerprint includes only production bundle/native inputs and excludes test-only files, docs, logs, screenshots, and verifier outputs.
- Before an expensive native Counterfactual, verify that its declared carrier is reachable from the target root or otherwise participates in the exercised runtime boundary. An unreachable or obsolete barrel/route is Contract drift, not a reason to compile a mutated APK. A mutation that removes a required entrypoint/import, or a missing API/device/tool prerequisite, must produce a deterministic fail-fast result before Gradle starts when the same falsification can be established without packaging.
- Native Gate prerequisites are mandatory and precede assembly: the explicitly bounded set of selected device serials/ABIs, expected package identity, Java/Android toolchain, API health and deterministic data state, declared route/action identifiers, port ownership, and sufficient disk headroom. Repair all failing prerequisites and exercise the hypothesis through the development client or cheaper surface before spending another Release build.
- On Windows, the native verifier resolves Java deterministically from an explicit valid `JAVA_HOME`, then Android Studio's bundled JBR, then a valid `java` on `PATH`; the resolved Java identity remains part of the Android build fingerprint. A missing or invalid toolchain fails before Gradle rather than depending on an interactive shell profile.
- One bounded session has one owner for each Metro/API/browser server, port, emulator/device, and build process. Silent output is not evidence that a process stopped and is not permission to launch a duplicate; inspect its child process, port and health instead. Cancellation or tool interruption must terminate the complete task-owned process tree, including Gradle daemons created for that bounded run, and clean only explicitly identified task-owned temporary snapshots.
- A warm server returning HTTP 200 is insufficient identity. Development reuse must confirm a session descriptor served by that same origin against the task-owned local registry, owner PID, repository identity and restart-sensitive startup-configuration fingerprint; a dead owner, mismatched descriptor, changed configuration or unrelated listener fails closed. Formal evidence additionally requires the declared source/config fingerprint and deterministic state isolation. Never run warm tests against an unknown or stale process merely because it occupies the expected port.
- Expensive runners must expose phase and elapsed-time diagnostics on a non-evidence channel so build, install, exercise, Counterfactual and cache-hit time remain distinguishable. Lack of progress output triggers inspection, not a duplicate run or an unchanged retry.

## Expensive Runtime Reuse

- One bounded native verification session may keep the selected emulator/device, ADB connection, Gradle daemon, API, and other verified prerequisites warm. Reuse ends when the relevant source/config/toolchain fingerprint changes or the session ends; process warmth cannot be used as evidence.
- Building and exercising are separate costs. Within one exact repository snapshot, build type, ABI, lockfile/native configuration, toolchain, and environment fingerprint, a verifier may assemble one Release APK and reuse that exact content-addressed artifact for multiple declared Android scenarios. Each device verifies the installed artifact hash once for the bounded shard, and every Scenario still forces an attributable known state within its Condition/Mode unit, exercises its own route/action, and emits its own fresh observation.
- The Live Final Gate must produce or verify at least one Release APK from its captured snapshot. Sharing that APK across same-snapshot Checks is permitted only when the verifier binds the APK hash and complete native-input fingerprint into every consuming result; a cached filename, historical installation, timestamp, or prior Progress record is insufficient.
- A browser/API server may be shared across same-snapshot development checks. Formal Check reuse additionally requires an exact source/config fingerprint, health verification, unique test namespace or deterministic state reset, and teardown ownership. Until those guarantees exist, warm-server results remain repair feedback and formal checks retain isolated startup.
- Cheap stateless checks may run concurrently only when they have disjoint ports, files, databases, devices, and other mutable resources. Native design work may also run in parallel only after one complete canonical population is deterministically partitioned across distinct selected Android serials: one worker owns one device, log buffer, display override, app state and artifact directory at a time; workers never share an emulator or mutable evidence file. APK assembly remains serialized per ABI and every consuming shard binds the verified production-input and APK hashes.
- A native repair session may atomically checkpoint an attributable Condition/Mode production-root prelude, each Control observation and each acceptance Scenario. A partially resumed unit performs at most one new cold-start/root prelude before collecting all of that unit's missing fragments. Resume is allowed only when the checkpoint manifest exactly matches the production-input, APK, canonical design, Contract/verifier, selected population and device-environment fingerprints; missing, duplicate, malformed or mismatched fragments are rerun or fail closed and incomplete aggregation cannot emit a passing Check result.
- Resume is a repair/Stage-candidate cost optimization, not historical acceptance. Diagnostic filters cannot be resumed into full evidence, changing any declared input invalidates the checkpoint, and the Live Final Gate always starts a fresh evidence session without consuming prior repair checkpoints. Full acceptance still requires exact expected-population equality and independently attributable positive observations.

## Android Build And Cache Hygiene

- Preserve Gradle dependency/build caches and scoped Android intermediates during active development; incremental reuse is an optimization, not acceptance evidence. Do not run `gradlew clean`, delete the whole Android build tree, or purge the global Gradle cache as a routine retry. Use scoped cleanup only after a diagnosed stale/corrupt artifact and rerun the affected checks afterward.
- The project Android verifier resolves a stable dependency-repository identity even when it runs inside a disposable verification snapshot. It keys persistent short-path CMake staging by that repository identity and ABI, computes a content fingerprint over mobile/native/shared-package inputs plus the public build environment and Java/Node identity, and verifies both that fingerprint and the Release APK SHA-256 before a cache hit. A miss assembles once, fails if inputs change during the build, then atomically publishes only the generated Release APK and manifest to a repository-scoped temporary cache outside the disposable snapshot; the cache is non-authoritative, may be deleted between sessions, and never stores scenario results.
- Before native execution, each selected device must contain the exact Release APK: the verifier validates the installed package's safe `base.apk` path and SHA-256, skips transfer only on an exact content match, and otherwise installs then rechecks the hash. Every fresh Condition/Mode unit force-stops and cold-starts the production activity, completes its root journey, and records that shared prelude. Its Control and Scenario fragments may then reuse only that same live process through exact-session context switching and deterministic surface/state reset; each fragment still performs and records its own interaction. Artifact/device reuse removes duplicate compilation, transfer, launch and page traversal, but never turns a diagnostic checkpoint or shared prelude into an independent positive result.
- Reinstalling the same application ID replaces the installed app and the stable `app-debug.apk` / `app-release.apk` output paths replace prior files; the workflow must not create per-attempt APK archives unless a declared evidence or release artifact requires one.
- Inspect build/cache size before cleanup. Clean only explicit project build outputs or verified cache targets, retain files needed by an active Check, and perform broad cache maintenance after the active delivery rather than inside the edit-test loop.
- Stop task-owned Metro, API, browser-test, emulator helper, and build processes when their bounded development/verification session ends. A Long-Task must not accumulate orphan servers or mistake a warm process, cached APK, or historical install for fresh Final-Gate evidence.

## Session Preflight And Cost Feedback

- Before a bounded expensive session, verify every selected Android serial/ABI, its independent device/environment identity, package identity, required Java/Android toolchain, API health and emulator reachability, free disk headroom, ports, and ownership of any reusable process. Fail before compiling when one of these prerequisites is missing.
- Capture per-Check setup/build/install/exercise durations and cache-hit reasons in disposable test/CI output rather than Context. Use repeated critical-path measurements to justify optimization; do not preserve one-off timing logs or machine-specific paths as durable truth.
- The repository-root `npm test` currently validates Context only. Product code uses the owning workspace tests and Contract-declared Checks; neither the root alias nor a single workspace test substitutes for Stage or Final-Gate coverage.
- Prefer improving an observed repeated critical path over adding another orchestrator, remote cache, task graph, or persistent state plane. TypeScript incremental builds, a new monorepo runner, and remote build caching are deferred until measured local type/test time—not native packaging or server startup—is a material bottleneck.

## Expected Signals

- Tiny Context validation completes without structural errors.
- Doctor reports the installed package and managed surfaces as healthy; advisory findings must be reviewed rather than silently ignored.
- Design lint completes without schema/structure errors.
- Project interaction Skill validation completes without frontmatter, naming, or resource errors; its authority statement keeps DESIGN.md/Source Plan/Context upstream.
- Imported brand, light-kit, and dark-kit HTML files can resolve their local font and supporting artifact paths.
- Every repo-local selected target retains its registered SHA-256 identity; the mobile 12/83 and operations 2/12 sets remain unique and equal between page coverage and control contracts.
- Every Outcome acceptance run uses at least two materially different inputs through production entry points and proves the result changes with those inputs.
- Stateful and artifact-producing flows prove the applicable database/file/object/native sink write and read it back from a fresh service instance, process, or app restart; in-memory continuity is insufficient.
- Native and external boundaries expose an invocation/result seam so automated tests can substitute an isolated adapter, while the production runtime either invokes the real adapter or presents an explicit unavailable/degraded state.
- Success, failure/timeout/permission denial, duplicate/idempotent retry, and conflict behavior are observed where applicable. Removing the write, adapter call, restart readback, or input dependency must make the owning Outcome Check fail.

## Acceptable Warnings

- Impeccable findings are review signals, not a Tiny Context gate.
- Static Open Design kits are reference surfaces and cannot by themselves prove production application behavior.
- Until production UI exists, prose and Skill validation cannot prove interruption, velocity handoff, haptics, system-gesture competition, reduced motion, frame pacing, or red-light luminance; those require automated state checks and representative real-device evidence.
- Representative outdoor/device validation and China production promotion may remain future external gates for the current owner-only personal trial. This postpones only the external evidence; it does not waive production-path integration, local persistence, adapter invocation, honest degradation, emulator tests, or counterfactual machine evidence.
- The current target profile requires Android native runtime evidence. iOS application code, native-project integration, platform adapters, interaction/accessibility behavior, and build readiness remain implementation obligations, while macOS/Xcode/iOS Simulator execution and iOS build/runtime evidence are deferred. This deferral is an explicit unverified state, never a passing result; Android, browser, static, or historical evidence cannot substitute, and a future profile must re-enable the iOS runtime Checks before claiming iOS usability.

## Excluded Dead Ends

- Do not treat static preview appearance, Context prose, or a command exit code as proof of live weather, routing, deployment, or human acceptance.
- Do not treat a fixed user/time/place/result, process-local repository, success label/evidence card, metadata-only upload, manifest-only offline pack, declaration-only native adapter, or prewritten trace/restore report as proof that a business loop ran.
- Fixtures may isolate uncontrollable providers or device APIs in automated tests, but they must be injected behind the same production adapter and cannot replace the production route, state transition, sink write, restart readback, or failure behavior.

# Mini Program Candidate Acceptance

This on-demand verification node owns deterministic test, WeChat DevTools acceptance, representative-device acceptance and candidate promotion/freshness boundaries.

## Candidate Verification Lanes

### 2. Deterministic Test

- Generated semantic SVGs under `apps/wechat-miniapp/src/assets/semantic/` retain LF bytes on every Git checkout, including Windows with `core.autocrlf=true`; the scoped `.gitattributes` rule owns that transport constraint. `generate-semantic-assets.mjs --check` and the workflow conformance test compare exact generated bytes and manifest hashes without newline normalization. Repair an affected existing checkout through the same generator, never by changing manifest digests or weakening byte checks. This rule does not rewrite immutable design sources or impose a repository-wide SVG normalization policy.
- The active Field Signal system `selected-source/**` package and the older Sky Canvas page-constraint `selected-source/**` package are byte-frozen inputs, so their scoped Git attributes disable text conversion and preserve the committed blob bytes for declared resources and frozen inspectors/oracles. An existing checkout may restore a resource only after its committed bytes match the unchanged manifest/handoff digest and the working difference is proven to be checkout newline conversion; actual source changes require the applicable immutable-version update route. Neither restoration nor a matching digest proves production conformance.

- Unit, domain, contract, adapter, state-machine, and component tests use deterministic fixtures and a run-unique writable root. Uncontrollable platform or Provider behavior is injected behind the same future production boundary rather than replaced with a second implementation.
- The explicit `MINIAPP_DEVELOPMENT_FIXTURE_MODE=1` lane composes the in-memory formal-spot repository and deterministic weather adapter only at the existing BFF Port/Adapter boundary, and the client must compile the persistent user-visible “开发验收数据 · 不用于现实判断” marker. Merely selecting `MEMORY_TEST` or running an acceptance command does not authorize fixture data in an unmarked client. Every non-fixture startup keeps the real Provider adapter and reports unavailable/partial/expired truthfully instead of falling back to deterministic data.
- Real paid Providers, production accounts/data, irreversible external side effects, shared mutable services, and nondeterministic clock/network/location dependencies are forbidden. Success, error, timeout, permission denial, network failure, retry/idempotency, recovery, cancellation, and cleanup are exercised where applicable.
- These checks can establish deterministic semantics and failure behavior inside their declared harness. They cannot prove a WeChat renderer, DevTools runtime, permission prompt, map/location integration, device lifecycle, or packaged build.

### 3. WeChat Tool Acceptance

- After deterministic checks pass, cleanly regenerate `apps/wechat-miniapp/dist/weapp/**` and open the current `apps/wechat-miniapp/project.config.json` through one exclusive project-owned invocation at `E:\Dev\Starward`. Aliases, junctions, `SUBST`, canonical-checkout substitution and copied production roots are forbidden. DevTools children use their own physical user temporary directory. Tiny Context no longer materializes runtime snapshots or owns verification.
- Infrastructure runners must work with a minimal declared environment, independent of interactive shell variables. `tools/miniapp/docker-compose-runtime.mjs` owns invocation: Windows uses installed standalone Compose v2; other platforms use `docker compose`. Infrastructure startup and backup/restore reuse it. Keep the existing minimal-environment regression; no Harness snapshot is required.
- WeChat DevTools caches projects by AppID/project identity and may initially open a new physical snapshot with an empty project-state AppID even when the tracked config is correct. The runner overlays only ignored `project.private.config.json` with a deterministic project name unique to normalized snapshot root plus candidate fingerprint and pins base library `3.17.1`. For a newly materialized snapshot it first runs a non-product registration session: require at least one native project watcher on the exact physical candidate, rewrite `project.config.json` with the exact same bytes to trigger DevTools' supported dynamic config reload, require `Tool.getInfo.SDKVersion === 3.17.1`, close through `App.exit`/`Tool.close`, then prove complete process/port/watcher teardown. Watcher observation uses explicit UTF-8 transport. Every watcher must parse and target either that exact candidate or a physically resolved, existing `WeappLocalData` directory directly under a 32-hex profile of the installed user's DevTools `User Data` root. Internal watchers are counted separately, never establish candidate presence, and are not exempt from teardown; unknown paths, other projects, nested lookalikes and redirected internal directories fail closed. That session makes no journey or product-acceptance claim. Canonical interactive development does not need this isolated registration step.
- Formal setup and evidence sessions then run from clean tool processes. Setup moves to the network-neutral auth route, exactly resets/reads back the canonical empty DAY/MY seed, proves the production Settings DAY control and live `theme-day` class, records diagnostics, waits for runtime-event quiescence and closes; its state is discarded. Evidence independently resets again before journeys. Degradation keeps the BFF healthy until the named fault window. Runtime observers detach only after quiescence; unhandled rejections fail the run. The Windows launcher preserves installed `cli.bat` semantics by reusing `device-feedback-official.mjs`'s physical CLI resolver for both launch and quit, rather than assuming the GUI executable is an Electron Node host. The resolver supports the bundled `node.exe` + `cli.js` layout and the admitted Electron layout; an unavailable invocation fails closed. The formal runner retains exclusive lifecycle ownership, pins IDE HTTP port `23977` and automation port `9420`, observes callback ports, and closes every exact `--cli` root process plus every watcher and declared/observed port for a stable window. A future installation-layout change must be handled at that existing resolver and tested without relaxing candidate binding, port closure or evidence checks.
- The collector bounds connection establishment and every automator protocol request, including version negotiation and page/element queries. A request deadline poisons and disposes that session, rejects all pending and subsequent requests, and retains the original tool/process/port/configuration cleanup obligations. It never treats late responses or a timeout as an empty selector, successful interaction or retryable mutation. A late connection is disposed rather than adopted. The installed automator connection seam is shape-checked; dependency drift fails closed rather than skipping version negotiation or deadlines.
- The DevTools runner owns exactly one `complete-current` journey set. It has no proposal-version/profile switch and no legacy route set: Detail and Night must be entered from the selected formal Map point, while My, Plan and Settings must be entered through the current Map/My tab and child controls. Source filename versions remain provenance only and cannot select a different native test product.
- DevTools may rewrite tracked `project.config.json` into byte-different but JSON-semantically identical formatting. Restoration is allowed only after the evidence IDE/watchers are fully closed and only when canonical JSON equality proves that no value changed; otherwise ownership is lost and the run fails without overwriting. The runner then restores the exact original public bytes and exact prior private bytes/absence, and only afterward computes the candidate after-fingerprint. Complete generated-bundle and candidate fingerprints must equal their pre-session values. Final evidence is written only after these restorations and all teardown pass. Historical JSON/screenshots, CLI success, a live socket, hand-edited generated output or a retry against another checkout cannot be promoted to evidence.
- A settled weapp build plus WeChat DevTools can prove only the exact tool-side WeChat runtime behavior actually observed for the bound candidate, tool version, project configuration, fixtures, and environment. It cannot inherit claims from a removed Web proxy or prove representative-device behavior.

### 4. Representative-Device Acceptance

- The supplemental owner-assisted Android USB/ADB + official WeChat remote-debug route is owned by `project_context/areas/main/verification/wechat-device.md`. Its registered diagnostic commands reuse settled phone bundles and preserve this file's promotion/isolation rules; they do not constitute the full representative-device acceptance runner. That Context owns physical operations, privacy, cleanup and diagnostic limitations without duplicating environment topology.

- Produce a device-acceptance preview or experience build from one settled candidate in the dedicated device environment. Every selected representative device must use the same exact device-lane build identity; this does not permit reuse of the DevTools lane's AppID/key, writable state, secrets, or project directory.
- Verify the selected permissions and denial paths, network profiles and recovery, location behavior and privacy, map behavior, cold start, warm start, foreground/background and termination/relaunch lifecycle, storage/readback where applicable, cleanup, and measured performance on the declared device population.
- Device model/OS, WeChat version, base-library version, network/location conditions, sample population, workload, metrics, budgets, comparators, and tolerances remain decision-required. No performance or capacity claim exists until a project-owned measurement binds all of them.
- Device-specific conclusions cannot be inferred from DevTools results. Results from one device, OS, WeChat version, permission state, or network profile cannot be generalized to an undeclared population.

## Candidate Promotion, Freshness, And Cost Control

1. Develop and repair with deterministic checks plus the warm WEAPP/WeChat DevTools renderer whenever a rendered or platform-owned invariant changes. Coalesce one coherent change batch before promotion; never substitute a cheaper browser renderer that cannot observe that invariant.
2. Freeze one candidate identity covering all acceptance-relevant Taro source, dependency lock, project/build/base-library configuration, fixture/data contract, selected assets, API contracts, acceptance scenarios, native runner closure and tool environment. Recheck the identity before and after every evidence-producing WeChat session; a changed input invalidates dependent results rather than inheriting a historical pass.
3. Generate/import weapp once and run the complete applicable WeChat DevTools acceptance pass. A failed tool pass is a collection point for batched repair, not a rebuild trigger per finding.
4. After DevTools obligations are fresh, generate the dedicated device preview/experience build and run the declared representative-device matrix with the same exact device-lane build.
5. A relevant candidate, environment, fixture, API, toolchain, AppID/config, or build-input change invalidates every dependent downstream result; DevTools and device obligations remain mandatory for their own boundaries.
6. Test-only reports, screenshots, logs, and other excluded non-production outputs must not force a package rebuild, but they also never make evidence fresh. Exact production/build and evidence-freshness input sets must be declared separately when commands are implemented.
7. Do not package after each edit, after each hypothesis, or merely because another cheap check ran. Package only at a stable promotion boundary or when a defect can be reproduced only in the packaged/tool/device boundary.
8. Record build, import, startup, exercise, and teardown durations only in disposable run output. The topology is cost-ordered, but it makes no claim that weapp packaging, DevTools, or device verification currently takes any particular time or is globally optimal without measurement.

The stable command ladder is `npm run dev:miniapp` for the warm native inner loop, `npm run check:miniapp:fast` for deterministic changed-candidate feedback, `npm run test:miniapp:infrastructure` for isolated persistence/provider-boundary checks, `npm run test:miniapp:native` for an isolated fresh WeChat DevTools collection, and `npm run test:miniapp:current` for their ordered conjunction. `npm run test:miniapp:native -- --scope platform-simulation` is a supplemental test-only DevTools diagnostic: the runner may install fixed, session-scoped location and compass API mocks, must exercise the real production controls and state transitions, must restore or discard those mocks with the isolated session, and must label the output so it cannot establish real permission, map-tile, provider, device-sensor, device-orientation, device-matrix, preview, review or release evidence. A historical report, manual QR scan, DevTools GUI state or removed Web/H5 proxy is never proof.

Formal acceptance is the conjunction of fresh, applicable observations from their own layers on the bound candidate. Missing journeys, commands, environments, tools, devices or external confirmation remain `unverified` or `decision-required`; no weaker layer upgrades the claim.

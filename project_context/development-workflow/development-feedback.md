# Mini Program Development Feedback

This on-demand verification node owns the three-tier feedback structure, native-first invariant and development feedback lane. It cannot produce formal candidate or device acceptance.

For agent observations, the version-matched official `wechatide-skill` is the primary WeChat DevTools control plane. The DevTools menu action `导出 SKILL` and terminal-reported `wechatide-skill` path are equivalent acquisition routes: copy the whole official directory one way from the installation into the agent's skills directory, replace an older same-named copy, then reload skill discovery. Export/import does not configure authorization. The separate MCP configuration copied from DevTools `设置 → 安全` must be installed in the client; its MCP token is distinct from the optional CLI access token and never belongs in the repository, Context, run logs or shell history. Keep one stable client name for the authorization session.

Client MCP registration and an ad-hoc `wechatide` CLI process do not automatically share credentials. A help command or token-free readiness check can succeed while a later page/runtime operation returns `mcp_token_required`. When the current session is already authorized, invoke the CLI through a local private wrapper that reads the existing client MCP configuration at runtime and passes the token without printing it or embedding it in repository files, command text, shell history or durable logs. Do not ask the user to recopy a still-valid token merely because the shell process did not inherit client configuration.

Use the official initializer/compiler/automator/debugger/previewer scenes for project windows, runtime reads, element/page actions, screenshots, filtered Console/Network and preview. [The development observer](../../tools/miniapp/development-observer.md) remains an optional low-latency adapter for an already owned 9420 automation connection and existing project journeys; it is not a second DevTools authority or a substitute for missing official MCP authorization. Page/Element commands depend on the actual current runtime capability; unsupported queries must not become fabricated input or repeated cold launches. Do not use Computer Use for Mini Program development or testing unless the user explicitly requests it. Physical-device feedback remains required for device-owned behavior.

Every DevTools development run binds an exact, newly built WEAPP project path and its source/build identity before importing or opening it. Never select a same-name historical import merely because it appears in the IDE list. At completion, inspect the official imported-project list and remove task-owned transient or superseded Starward WEAPP entries through the official project-list owner; removal concerns IDE list entries only and must not delete source, generated build bytes, other applications, or an unverified path. Keep at most the explicitly current canonical project entry when ongoing work needs it, and record any list entries that could not be identified or removed. A failed authorization/list operation leaves cleanup unverified; it does not license private IDE database edits or an unqualified clean-list claim.

The imported project is generated output, not a second source repository. After the last relevant source, contract, asset or build-configuration edit, rebuild the WEAPP output, rebind its fingerprint and exact import path, and refresh or reopen that project before final simulator observation. Compare the compiled route/API/configuration identity with the current repository candidate; a previously open window, successful earlier compile or same-named import cannot prove synchronization. Keep generated output out of the source commit unless an existing project owner explicitly tracks it. If the IDE cannot refresh the current bytes, mark simulator evidence stale and repair the import/build boundary before claiming the final candidate was observed.

For visual review, inspect the screenshot's actual pixel dimensions and the runtime's logical viewport before comparing typography, spacing, or state composition. A project window can reopen at a tiny simulator scale and produce a 149×321 capture for a 390×844 logical device; maximize or resize the verified project window and recapture at a readable physical size instead of enlarging the small bitmap. Read representative WEAPP element geometry/computed text sizes alongside the image when values matter. A successful build plus `simulator_refresh` can still display cached old WXSS: compare a changed runtime value with the just-built output, then reopen the exact project if they differ. Only current, readable, source-synchronized WEAPP observations can support visual conclusions.

The IDE command service, simulator capture and page automator are separate readiness boundaries. If official project opening, compilation and screenshot work while runtime/page/element or `remote` consistently waits for an automator response, preserve the exact open project and inspect the installed `cli auto --help` before recovery. Use an owned explicit automation port only when that DevTools version supports it, then verify the actual listener and a read-only runtime operation. Stable 2.02.2608070 does not advertise or retain `--auto-port`; its `cli auto` exit alone cannot establish a 9420 owner. This does not rebuild or identify a phone bundle. Record and clean up the automation owner independently. A fresh prepared project can time out on its first runtime read while compilation settles; one complete simulator frame followed by a successful read establishes that boundary without a rebuild. After `remote`, a temporary loss of page-automator responses may mean the IDE is switching to, waiting in or attached to the true-debug scene; check the device/scene boundary before restarting, refreshing or closing the project.

Verify the `auto` command's returned `autoPort`, not only its requested port or exit code. A stale project owner can retain the default port and make a new request silently bind another port that the MCP route does not select. Close the stale project and stop only its verified owned automation process, then bind the unchanged current project to the MCP-visible port. Tool readiness is also operation-specific: a successful page-data query does not make a timing-out runtime or viewport action successful. Record the smallest failing operation rather than declaring the entire automator connected or disconnected.

Treat DevTools labels and transport indicators as boundary-local facts. A visible `已连接` establishes that the phone true-debug session attached; it does not establish that the current page mounted, the expected candidate is foreground, APIs are reachable, or the product journey succeeded. After attachment, attempt fresh official runtime identity, current page and scoped Console/Network, then obtain a separately identified phone-display observation before diagnosing the product. DevTools 2.02.2609102 with Skill 0.3.10 can leave `automation_runtime_info` timing out after a QR session is visibly attached; preserve the session, label runtime identity unverified, and use an identity-guarded wireless/USB ADB capture for actual phone pixels plus narrowly scoped debugger output when available. `simulator_screenshot` is explicitly a DevTools-simulator capture even when a true-debug runtime is attached; never label it as phone pixels or use it to override the operator's current phone observation. Conversely, an automator timeout before attachment is a tooling-channel failure rather than a blank-page observation. Distinguish an empty content root/native-render failure from an intentionally rendered loading, empty or recovery state before changing UI code.

For a fresh prepared-project path, allow the first DevTools compile to settle before reading the initial blank shell. With native `Map`, an isolated blank simulator screenshot can be a compositor capture miss even when the route, DOM and later frame are complete; combine runtime/DOM with repeated visual capture. A fingerprint proves byte identity rather than renderability. Starward keeps Taro experimental CompileMode disabled and rejects `*-templates.wxml` at the physical-feedback snapshot boundary because Taro 4.2.1 can produce a successful, stable-hash bundle whose generated template prefixes disagree with its JavaScript chunks. Always rebuild from a clean generated root and a fresh prepared path; cross-generation generated-file copying remains a localization experiment only.

Tools whose registered names start with `get_simulator_` or `simulator_` remain simulator-scoped unless their own contract explicitly says otherwise. Their base-library version, Console, Network and pixels may differ from the attached phone. Use `automation_runtime_info` and page-data queries for the runtime they actually report, and label mixed evidence per operation; never combine a phone `systemInfo` with simulator Console/Network/screenshot into one alleged phone trace.

The phone resolves loopback independently from the host. A development API origin such as `127.0.0.1` can work in the desktop simulator yet fail on a physical phone, where it targets the phone itself; USB/ADB and a true-debug attachment do not tunnel that traffic. A truncated or otherwise malformed build-time origin can instead become a relative request and must be rejected before phone delivery. Network entries with status `0` establish a phone-network/configuration finding only after the compiled absolute HTTP(S) origin is verified; they do not by themselves explain or disprove a concurrently observed blank content layer. Use the already owned LAN or remote-IP development lane when the journey needs host services, and keep its candidate/config identity explicit.

## Four-Layer Environment Topology

### Three-tier feedback and physical-device acceptance structure

The four environment layers below remain the isolation model. Across those layers, development and device work use exactly three cost-ordered feedback strengths:

1. **Fast development self-check** combines changed-module type/unit/contract/state/component checks, the Taro WEAPP watch compiler and the real route in WeChat DevTools. Isolated location, compass, time, permission and Provider substitutes may prove only their declared deterministic or tool-side behavior.
2. **Device development feedback** is a risk-triggered development channel for physical behavior that DevTools cannot faithfully establish: menu-capsule/safe-area geometry, native map and gestures, permission allow/deny/recovery, GPS/coordinate centering, compass/physical rotation, foreground/background/restart and subpackage lifecycle, real device network/TLS/domain-list behavior, and Android/iPhone differences. It creates no new Gate and never produces acceptance evidence.
3. **Settled-candidate device verification** binds one clean, fixed candidate and runs the complete applicable cold-start, navigation, permission, GPS/map, Observation Context, weather/astronomy, network-failure recovery, background/return and state-recovery journeys. Candidate inputs remain unchanged for the run; relevant source, configuration, AppID, API origin, base-library or build-input drift invalidates dependent results.

Use device development feedback at the first independently runnable slice for a device-owned invariant, and again after a coherent repair/feature batch when the expected localization value exceeds the refresh cost. Do not package and push for every saved file. An official automatic preview/debug path may reduce repeated scanning, but its command completion does not prove delivery to the intended phone/account; an unchanged-generation ordinary-preview QR is the public fallback for a different authorized developer account or device. Every refresh is a new bundle generation that may restart the Mini Program and lose its page stack or in-memory state. Debug injection, vConsole, URL-check relaxation, remote debugging and automatic preview remain development conditions and cannot be promoted into settled-candidate evidence.

For a device-owned invariant, start the official `真机调试` flow for the exact prepared project through `wechatide-skill` automator's `automation_viewport_action` with `action=remote`; use its returned async/QR state and the official polling rules. The visible GUI action is the fallback when that registered tool reports a concrete unsupported capability, not the default control path. `auto_preview` and `create_preview_qrcode` deliver preview builds and do not establish a true-debug attachment. USB/ADB is an optional independent capture/control channel, not a prerequisite for QR-based remote debugging and not the first explanation for a failed QR, login, package upload or remote connection. Diagnose the path in owner order: exact project and generated bundle -> imported Skill/version/login/MCP authorization -> successful true-debug request/QR -> authorized phone account scan and launch -> remote connection transport -> runtime identity and scoped Console/Network -> scoped WeChat/OS permission -> product journey. Stop at the first failed boundary instead of changing later layers speculatively. A tool login, generated QR, scanned QR, connected overlay, visible map tiles and successful API/product journey are distinct observations; none implies the next.

The agent owns host-reachable recovery within that order, including official-tool invocation, ADB/client version selection, bounded USB-interface repair, authorized TLS wireless pairing/reconnection, true-debug attachment and scoped log/screenshot collection. Follow the device owner's [transport choice and reconnect](../areas/main/verification/wechat-device.md#android-transport-choice-and-reconnect) for repeated USB failure and paired-wireless readiness; a working WeChat WAN attachment and local wireless ADB are independent. Preserve the current candidate and open compile/debug scene while repairing an independent observation channel. Ask the phone operator only for a physical or account action the host cannot perform: cable/USB-mode changes, a phone-only trust/pairing control, official QR scan, device rotation, MFA or remote approval.

On DevTools 2.02.2609102, an already MCP-opened project can make a subsequent `cli auto` stall at AppID permission fetching while holding the IDE RPC queue. For a clean true-debug startup, let `cli auto --project <exact prepared project> --auto-port 9420 --trust-project` open the candidate itself. If the version-specific stall is observed, stop the pending calls and retire only the verified owned DevTools processes before retrying the unchanged candidate; do not rebuild or refresh it. A returned `autoPort=9420` is necessary but page operations remain a separate readiness boundary.

When a required VPN/TUN makes LAN true-debug advertise the wrong interface, retain the VPN and use the DevTools QR panel's official LAN-address selector: enable LAN mode, open its adjacent help control, and switch to the physical WLAN IPv4 before scanning the regenerated QR. On Nightly 2.02.2609102, leaving this selection empty can advertise the first non-loopback IPv4 enumerated by the runtime, which may be a TUN or Hyper-V adapter. A new project window or DevTools process may lose the explicit choice, so recheck the selector before each newly created true-debug session while virtual adapters remain. This explicit selection restored phone runtime attachment while the required TUN remained active. WAN true-debug, the host fixture API over physical WLAN and paired wireless ADB remain independent transports. Do not alter route metrics, reopen USB trust or edit the candidate to repair this address-selection boundary.

The DevTools desktop account and scanning phone account may differ when both are authorized for the same Mini Program; use the project owner/developer account for the desktop session and an explicitly authorized developer account on the phone. The GUI can generate a debug QR without ADB and may do so without the CLI service port; the service port is required only by the repository's CLI/automation path. When more than one DevTools window exists, select the one whose title and project root match the prepared snapshot rather than relying on recency or avatar state.

Automatic true-debug targets the currently logged-in desktop WeChat account and may therefore select the wrong device when the intended phone uses another authorized developer account. Use the QR true-debug route for that phone without changing the desktop project owner. Keep DevTools version, exported Skill version and active executable path aligned after an update; duplicate installations or an already-open older process can make a successful Skill call target a different binary than the visible window. Verify the running version and exact project window before changing configuration or reinstalling.

After a device-feedback finding, return to the cheap owning checks, repair one coherent batch, and use targeted device feedback again only when that physical boundary is relevant. Once the earlier layers are stable, create a new settled candidate and rerun the complete applicable device verification; targeted feedback never substitutes for it.

On a deliberate cross-session pause, retain the current feedback run, prepared generation and fingerprint while closing its owned project/automation processes. The next session resumes the exact generation from the recovery index and `feedback.json`, establishes one project window and MCP-visible 9420 owner, invokes `remote` once, and waits at the physical QR boundary. Do not repeat installation, Skill export, build, preview generation, token collection or ADB repair unless a fresh check at that specific boundary fails.

### Native-first implementation and feedback invariant

- The first runnable carrier for every Mini Program product surface is the tracked Taro source compiled to WEAPP and observed through the repository-native project in WeChat DevTools. Do not first implement, tune, or approve the surface in Web/H5 and then port it to WEAPP, even as a temporary development shortcut. Web DOM/CSS layout, browser navigation/storage/lifecycle and browser substitutes for map, Canvas, permission, sensor, safe-area, capsule, package and native-component behavior are not predictive enough to authorize Mini Program implementation decisions.
- Platform-neutral work may still take the cheaper path before the renderer: pure domain functions, state machines, schemas/contracts, BFF services, Provider adapters and serialization may use deterministic unit, contract or process tests when the exercised code is exactly the code consumed by the Mini Program. Those tests establish only their declared portable semantics; they cannot approve WXML/WXSS projection, component behavior or any WeChat platform boundary.
- Browser tooling remains valid for a separately owned Web product surface or an API/tooling diagnostic that does not render or mirror Mini Program UI. It must not host a Mini Program clone, supply a visual baseline, originate layout fixes, stand in for a WeChat journey, or become an intermediate product implementation.
- The normal feedback order is: selected-resource and Source mapping -> changed-module deterministic checks -> warm WEAPP compilation and the real route in WeChat DevTools -> clean current-candidate DevTools collection -> representative-device verification for device-owned claims. Later layers do not make earlier platform substitutions valid, and DevTools observations do not inherit representative-device authority.
- Any change involving WXML/WXSS projection, responsive geometry, native map/Canvas, route or subpackage behavior, permission, location, sensor, storage, lifecycle, safe-area/menu-capsule geometry, accessibility or platform interaction must remain continuously runnable in the warm WEAPP loop while it is developed. A code review, unit test or browser rendering may supplement that loop but cannot replace it.

### 1. Development

- `npm run dev:miniapp` is the primary interactive Mini Program entry: it health-starts the pinned PostGIS/Redis development services, then starts the modular-monolith API, Outbox/BullMQ worker and Taro weapp watch compiler against one development-only loopback binding, waits for the API and initial bundle, opens the repository-native project in WeChat DevTools, and owns teardown of the API/worker/compiler process trees. Infrastructure containers remain warm for the next inner-loop session. `--no-open` keeps the same source/watch loop without opening the GUI; `--api-port <port>` selects an otherwise free development port; `--memory` is an explicit unit/debug fallback that cannot supply persistence or acceptance evidence. Test identity stays in the data and internal evidence; it does not add a product banner, badge, source card or diagnostic popup. Follow the current [test-data presentation contract](../areas/main/screen-contracts/wechat-miniapp/shared-state-and-recovery.md#测试数据不增加产品说明). Product edits remain in tracked source even while DevTools is open.
- The isolated `LOCAL` + `MEMORY_TEST` + `LOCAL_TEST` service has a test-only plan-share signing key when no `MINIAPP_SESSION_SECRET` is supplied, so simulator share creation and receipt can be exercised. An explicit secret takes precedence; `POSTGRES` and non-local profiles never receive that fallback. Memory service restarts discard its plans, so re-create and read back the test plan before claiming a share regression. This fallback does not supply release credentials or durable share links.
- Use the cheapest faithful feedback path first: changed-module checks through `npm run check:miniapp:fast`, then the warm WEAPP compiler/WeChat DevTools loop. “Cheapest” means the lowest layer that can actually observe the changed invariant; it never authorizes a browser imitation or Taro H5 projection for platform-owned behavior.
- For UI work, the feedback loop starts from the active DESIGN target, Screen Contract and the complete currently selected I21 handoff/canonical dependency closure rather than the current screen. Observe the real WEAPP route at declared logical widths/modes/states in WeChat DevTools; current runtime appearance, a sampled frame or resource integrity inspection never overrides active authority or proves production conformance.
- Edit only tracked Taro source, shared contracts and owned configuration. `dist/weapp/**` and files opened inside WeChat DevTools are generated consumers, never an authoring surface or a second implementation truth; `dev:weapp` watch mode may regenerate them for feedback.
- Use weapp/WeChat DevTools development feedback for WeChat components and APIs, routing, permissions, storage, lifecycle, package configuration, responsive layout and accessibility. This is still development feedback, not acceptance.
- WEAPP production code may use only JavaScript capabilities supported by the bound Mini Program base library or an app-owned, tested compatibility helper. A Node host global such as `structuredClone` cannot be assumed from unit-test success; `packages/miniapp-contracts/**` owns the explicit `UserPreferences` snapshot copy used by the Mini Program synchronization path.
- Every development session uses disposable API, data, file, outbox, Provider-ledger, session, and output roots plus one bounded process/port owner. A warm process is reusable only inside its identified session and never becomes acceptance evidence.
- Development can prove only fast local feedback for the exercised renderer and inputs. It cannot produce a DevTools, device, release, or product-acceptance conclusion.
- The separately scoped owner-only remote IP trial remains a development session, not the formal DevTools or representative-device acceptance lane. Its deployment, token and SSH boundaries are owned by `project_context/deployment.md`. The installed official CLI must report a usable service port and login state before importing the exact generated project; a missing accessibility tree, a window title or CLI exit code alone is insufficient. Reuse permitted local login sessions and the needed local CLI/service capability within the conversation authorization. Keep credential/account values out of output; request human action for an actual unavailable capability, physical phone scan, MFA or remote approval. Preserve the settled bundle and fingerprint during QR generation, keep QR/login/credential material outside Git, and distinguish successful CLI preview from successful phone cold-start, session/API, persistence and real-data journeys. A documentation-only correction does not justify overwriting an unchanged pending preview bundle.
- For LAN-mode remote debugging, the phone and host must share a mutually reachable LAN path. Select the physical WLAN address through the DevTools LAN-mode help popover's `切换IP` action; do not rely on the default when VPN/TUN or virtual adapters exist. Confirm an all-interface DevTools listener, the WLAN's actual firewall profile, the minimum inbound TCP range and access-point client isolation before blaming product code. Keep the phone Wi-Fi proxy disabled unless that proxy is the test subject. Failure of the local WebSocket attachment followed by WAN fallback is a transport finding, not a product failure or proof that LAN works. A green overlay whose confirmed/sent/received counters remain zero is also insufficient: require nonzero runtime exchange and visible page startup. Leave LAN mode off when these reachability preconditions are not intentionally established.
- Keep the DevTools-bundled Node/runtime private to DevTools. On Windows, installation or launch may prepend an old Node under the DevTools installation to `PATH`; project `npm`, Harness and test commands must resolve the repository-supported Node version explicitly or through a command-scoped `PATH`. A failure such as an unsupported `--import` option or missing modern `node:` builtin is a host-runtime selection failure until the effective `node` path/version is checked, not an infrastructure or product-test failure. Do not rewrite project checks or global proxy/runtime configuration to accommodate the bundled runtime.

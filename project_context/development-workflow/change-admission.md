# Mini Program Workflow Change Admission

This on-demand verification node owns unresolved decisions/external inputs, capability/environment change admission, design rationale and repository-check boundaries.

## Remaining Decisions And External Inputs

- Exact package/dependency/base-library versions, commands, fingerprints and failure contracts are pinned by the active Contract and lockfile during bootstrap, then recorded from code truth in the implementation index and verification Context.
- Web/H5 is not a Mini Program product or acceptance carrier. WeChat map/canvas/sensor/permission/lifecycle/package and responsive behavior require WEAPP + DevTools and declared physical-device observations.
- The local WeChat DevTools CLI is `C:\Program Files (x86)\Tencent\微信web开发者工具\cli.bat`; its current tool version/login state and observed project-path identity must be captured by the runner. Formal acceptance pins and verifies base library `3.17.1`; no previously imported GUI project, socket, watcher, private config or historical tool result is a passing fact.
- Environment-specific AppID/key values, upload identity, preview/experience channel, fixed-egress runner/IP allow-list, rotation/revocation and real platform reconciliation remain external inputs. The implemented secret mechanism, bundle identity checks and redaction policy do not authorize one lane to reuse another lane's AppID/key.
- Exact endpoint compatibility, fixture catalogue and adapter reuse are implementation obligations under the declared shared owners; no current API behavior may redefine the current accepted semantics or leak native-App-only platform semantics.
- Exact DevTools and device journey matrices, negative cases, observation/comparator policy and machine/external split are frozen by the active workflow before acceptance.
- Representative device/OS/WeChat-version population, selection rationale, network and location profiles, performance/capacity workload, metrics, sample count, baseline/budget, comparator/tolerance, and owner of any required human confirmation.
- The implemented Ubuntu release-product CI lane performs no DevTools login, platform upload, design-resource conformance, Context/Harness validation or external side effect; it builds only a structurally nondeployable WEAPP candidate and tests upload validation with an injected fake driver. A separate disabled workflow owns environment-bound preview/upload on a protected dedicated runner, with exact bundle fingerprinting, short-lived redacted artifacts and fail-closed reconciliation intent. Real credentials, fixed egress/IP allow-list, tool access, mutable-resource allocation and platform results remain unresolved external inputs.

## Capability And Environment Change Admission

The current Mini Program owners and command ladder are implemented. Any future workflow that adds or materially changes a workspace, runner, environment lane, command, selected-resource binding or evidence boundary must preserve the following order; no workflow type by itself proves that the capability exists or passed:

1. Define and update the owning product/surface Context for the selected Mini Program responsibilities, consume `target.system.wechat-miniapp-sky-canvas-field-signal-2026-09-02` plus `target-miniapp-sky-canvas-current-constraint`, and map every affected production surface to the owning Screen Contract and current complete page-resource closure before implementation; do not borrow App/Admin artifacts, sample only screenshots, reactivate superseded styling or invent another visual authority.
2. Create or change the real package/configuration owner intentionally, pin dependency locks, versions and commands, and then update the implementation index from current code truth.
3. Install exact ignore rules before generating `dist/**`, `project.private.config.json`, QR/secret material, temporary projects, or reports. Confirm all secret and sensitive-artifact paths resolve outside the repository where required.
4. Implement the isolated runner, health/fingerprint protocol, deterministic reset, failure/recovery seams, teardown, and scoped cleanup before registering a CI or acceptance lane.
5. Bind every environment to distinct mutable resources and credentials, then prove the promotion/staleness rules with project-owned checks. Only actual runnable commands may be added to verification Context.
6. Update this Context and its triggers whenever a reservation becomes current, a command/version/path/owner changes, or a new evidence boundary is adopted. Do not create a ghost Area merely because the source directory was bootstrapped.

## Design Rationale And Alternatives

- A root, on-demand Context keeps the absent cross-workspace capability discoverable without inflating the default Area or pretending a workspace exists. Placing these facts in the current Mobile development loop would wrongly inherit Expo/Android commands and evidence; scattering them across architecture and verification files would create duplicate truth.
- The cost-ordered ladder preserves fast feedback while retaining platform-specific proof. Always packaging after each edit wastes an unmeasured expensive boundary; browser-only acceptance misses WeChat semantics; DevTools-only acceptance slows portable repairs and still misses real-device behavior; shared mutable environments destroy attribution and recovery confidence.
- A plausible future challenge is adding a second miniapp target or CI-hosted DevTools lane. It lands as another isolated environment binding and promotion obligation here, with workspace-local detail only if durable facts warrant it; it must not duplicate product truth or reverse the dependency into current App/Admin owners.
- No numeric speed, reliability, capacity, or compatibility improvement is claimed. Future optimization requires measured workload, environment, baseline/budget, comparator/tolerance, and a project-owned measurement.

## Repository Verification Boundary

- `npm run context:validate`, `make validate-context`, `make validate-harness`, `npm run context:doctor`, and the package-managed source-parity check can validate Context structure, routing, installation health, and applicable source-workspace parity.
- Repository review must confirm any current Mini Program workspace, acceptance and tool paths match their owners; generated/private artifacts remain ignored; the implementation index matches code truth; the selected visual target remains rooted only in `DESIGN.md`; and no historical output is promoted into Context.
- Context checks do not build, test, run or accept the Mini Program. Only the active Contract's current-candidate checks and sole Final Gate may do so.

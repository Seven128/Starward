## Selected Environment Topology

### Staging

- Staging is a remote, non-public-release environment for real deployment, migration, provider-sandbox or explicitly authorized trial integration, production-shaped smoke checks, Mini Program preview/experience builds, and operator acceptance. It may be provisioned on demand for a release and deprovisioned after its attributable receipts and required short-lived artifacts are retained; absence of a currently provisioned staging instance disables remote staging deployment and therefore blocks production promotion rather than silently substituting CI or production.
- Staging has its own compute/runtime identity, database, Redis namespace or instance, object bucket/prefix, queue, cache prefix, session secret, provider credentials and quota ledger, DNS origin, Mini Program credential/channel, logs and backups. It never reads or writes production user data and cannot receive production webhook or payment traffic.
- Staging may be stopped when idle to control cost. Suspension cannot turn its last run into current evidence; wake-up must re-establish health, migration level, candidate digest and secret bindings.

### Production

- Production is the only public-user environment. It accepts only provider-backed, licence-compatible composition and truthfully disables or degrades a capability whose production adapter, credential, source right or external approval is absent.
- Production has a separate always-on compute/runtime and separate mutable resources from staging. It does not share a host process tree, writable volume, database, Redis, bucket, session secret, provider credential, queue, cache namespace, backup target or deploy credential with staging.
- Only the HTTPS reverse proxy is internet-addressable. PostgreSQL, Redis, worker control, administrative operations and internal health dependencies remain on private/container networks; administration uses authenticated, least-privilege paths and is not exposed by opening database or Redis ports.

### Runtime Shape

- The selected initial runtime is one provider-neutral Linux OCI/Compose stack per environment: automatic-HTTPS reverse proxy -> `workers/miniapp-api` BFF, plus the independently supervised Outbox/BullMQ worker, PostgreSQL/PostGIS and Redis. A managed object store becomes a separate adapter boundary when contribution media is enabled.
- API, worker and one-shot migration processes use the Docker/Compose runtime's built-in init process for PID 1 signal forwarding and orphan reaping. The release image starts Node directly and performs no runtime-stage operating-system package fetch. This preserves bounded shutdown semantics while keeping image construction dependent only on digest-pinned OCI inputs and the locked application dependency closure; an unfrozen APT fetch, an unverified copied init binary or running Node as an unreaped PID 1 are forbidden shortcuts.
- The BFF and worker consume `packages/miniapp-contracts/**` and the same release image/source revision. The client calls only its environment's BFF origin; it never receives provider secrets or calls weather, map, media or content providers directly.
- Kubernetes is not selected for the current modular monolith and initial load. Managed containers, managed PostgreSQL/Redis, or horizontal API replicas remain allowed future substitutions when measured reliability, capacity or operational cost justifies them; they must preserve the same contracts, state owners and promotion rules.

## Configuration And Secret Boundary

- Tracked configuration contains schemas, names and non-secret defaults only. Secret values are resolved at deployment from an approved cloud/repository environment secret mechanism and are injected into the exact process that needs them; unresolved `secret-ref:` strings must fail closed.
- Staging and production use distinct database URLs, Redis URLs, cache/queue prefixes, Mini Program AppID/key material, WeChat AppSecret/session secret, admin token, weather/map/provider credentials, object-store credentials and deploy credentials. A credential may not be copied between environments merely to make a check pass.
- Production uses `MINIAPP_AUTO_MIGRATE=0`; schema migration is a separately logged, one-shot release operation. The existing ordered SQL files and `schema_migrations` table remain the sole schema source of truth: the migration owner holds one PostgreSQL advisory lock for the run, reads the applied-version set, skips exact known versions, executes each pending file in its own transaction, and verifies that the file registered its own version before commit. Lock contention, an unknown applied version, a missing registration or any SQL failure rolls back and fails the release. Runtime startup verifies the expected schema version and refuses incompatible state.
- Reverse-proxy TLS renewal is automated and monitored. Production CORS/origin, request-size and timeout rules are explicit and testable; development loopback allowances do not leak into production. The single-host edge network has an explicit private subnet and fixed Caddy address, and the API trusts only that exact `/32` proxy address rather than a hop count, wildcard private range or forwarded header from any direct peer. The Fastify startup boundary owns one global public-request limiter backed by the environment's existing Redis, keyed from Fastify's trusted-proxy-resolved normalized client IP with IPv6 `/64` aggregation and an environment-isolated namespace. Remote startup requires an explicit bounded request count/window and Redis URL, storage failure fails closed, only exact internal liveness/readiness probes are exempt, and a 429 uses the API's stable retryable error shape. The tracked initial example is 120 requests per 60 seconds per normalized client key; it is an availability/cost guardrail rather than measured capacity or a final launch traffic budget.
- SSH, registry and cloud API access use least privilege, key/token rotation and an attributable operator. Database/Redis ports are never opened to the public internet, and secrets, precise location, identity tokens, raw contribution metadata and upload keys are redacted from logs and reports.
- The initial single-host profile is x86-64 Ubuntu 24.04 with at least 4 online CPUs and 4 GB advertised memory. It applies Compose-native hard memory and PID ceilings to every service and uses bounded per-container local log rotation. These values protect host availability and disk capacity but are not throughput or sizing proof; measured workload, memory pressure, queue depth, latency and restart evidence own any later adjustment. Redis keeps an explicit data-memory ceiling below its container ceiling, and PostgreSQL/Redis remain backend-network-only.

## Data Lifecycle, Failure, And Recovery

- Before a migration that can change durable data, create an encrypted, environment-owned PostgreSQL backup plus manifest and verify that it is readable. Production backup retention, recovery-point target, recovery-time target and restore-drill cadence remain decision-required before public launch; a backup command or unit-tested recovery state machine without a successful representative remote restore drill does not establish recoverability.
- The initial backup owner uses an externally provisioned 256-bit encryption key file and writes only an authenticated encrypted dump plus a non-secret integrity/restore manifest to an absolute environment-owned backup directory. It restores into a run-unique temporary database on the same isolated PostgreSQL owner, verifies the current schema-migration identity, and drops that database before issuing the receipt. The in-memory implementation has an explicit configured size ceiling; exceeding it fails closed and requires a streamed/off-host backup implementation rather than silently exhausting the host. A local or mounted-directory receipt does not prove off-host durability until the selected provider target and retention policy are configured and exercised.
- Application rollback selects the retained prior image digest and configuration only when schema compatibility is established. Database recovery requires exact environment, target database and encrypted-backup SHA-256 confirmations; it restores and schema-checks a new database before stopping writers, retains the original database through cutover, and switches the original back if new-state readiness fails. It never automatically deletes the retained original. An incompatible data migration uses an explicitly tested down migration or a forward repair; it must not restore an old database over newer accepted writes without an operator-owned recovery decision.
- API and worker shutdown are bounded and drain or safely requeue owned work. Health distinguishes process liveness from readiness of schema, database, Redis and required composition. A provider outage may yield attributable partial/stale/unavailable state under existing product rules but never fixture-backed success.
- A failed staging or production deployment stops promotion, preserves diagnostic evidence without secrets, and leaves the previous healthy production revision serving when possible. Unknown listeners, mutable-tag drift, missing secrets, migration mismatch, failed backup, failed readiness, worker failure or candidate mismatch fail closed.

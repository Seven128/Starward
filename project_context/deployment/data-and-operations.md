# Deployment Data And Operations

This on-demand deployment node owns configuration and secret separation, database migration, backup/restore, rollback, lifecycle failure handling and production observability.

## Configuration And Secret Boundary

- Tracked configuration contains schemas, names and non-secret defaults only. Secret values are resolved at deployment from an approved cloud/repository environment secret mechanism and are injected into the exact process that needs them; unresolved `secret-ref:` strings must fail closed.
- `infrastructure/deployment/provision-internal-secrets.sh` is the tracked one-time owner for environment-local generated PostgreSQL, Redis, backup and QWeather Ed25519 material. It runs only through an attributable root channel against an already bootstrapped environment directory, refuses every existing or symlink target before generation, stages all output privately, installs each root-owned/deploy-group-readable file by same-filesystem rename, removes its newly created targets if the sequence fails, and emits only non-secret status plus the QWeather public-key fingerprint. It does not collect provider account values, render the API lane, rotate credentials, start Compose or run from CI/CD. A later managed secret store may replace this external provisioning boundary without changing the lane or release-candidate contract.
- Staging and production use distinct database URLs, Redis URLs, cache/queue prefixes, Mini Program AppID/key material, WeChat AppSecret/session secret, admin token, weather/map/provider credentials, object-store credentials and deploy credentials. A credential may not be copied between environments merely to make a check pass.
- Production uses `MINIAPP_AUTO_MIGRATE=0`; schema migration is a separately logged, one-shot release operation. The existing ordered SQL files and `schema_migrations` table remain the sole schema source of truth: the migration owner holds one PostgreSQL advisory lock for the run, reads the applied-version set, skips exact known versions, executes each pending file in its own transaction, and verifies that the file registered its own version before commit. Lock contention, an unknown applied version, a missing registration or any SQL failure rolls back and fails the release. Runtime startup verifies the expected schema version and refuses incompatible state.
- Reverse-proxy TLS renewal is automated and monitored. Production CORS/origin, request-size and timeout rules are explicit and testable; development loopback allowances do not leak into production. The single-host edge network has an explicit private subnet and fixed Caddy address, and the API trusts only that exact `/32` proxy address rather than a hop count, wildcard private range or forwarded header from any direct peer. The Fastify startup boundary owns one global public-request limiter backed by the environment's existing Redis, keyed from Fastify's trusted-proxy-resolved normalized client IP with IPv6 `/64` aggregation and an environment-isolated namespace.
  Remote startup requires an explicit bounded request count/window and Redis URL, storage failure fails closed, only exact internal liveness/readiness probes are exempt, and a 429 uses the API's stable retryable error shape. The tracked initial example is 120 requests per 60 seconds per normalized client key; it is an availability/cost guardrail rather than measured capacity or a final launch traffic budget.
- SSH, registry and cloud API access use least privilege, key/token rotation and an attributable operator. Database/Redis ports are never opened to the public internet, and secrets, precise location, identity tokens, raw contribution metadata and upload keys are redacted from logs and reports.
- The initial single-host profile is x86-64 Ubuntu 24.04 with at least 4 online CPUs and 4 GB advertised memory. It applies Compose-native hard memory and PID ceilings to every service and uses bounded per-container local log rotation. These values protect host availability and disk capacity but are not throughput or sizing proof; measured workload, memory pressure, queue depth, latency and restart evidence own any later adjustment. Redis keeps an explicit data-memory ceiling below its container ceiling, and PostgreSQL/Redis remain backend-network-only.

## Data Lifecycle, Failure, And Recovery

- The selected staging deploy user has no sudo capability. Its existing user crontab and running cron daemon own the hourly maintenance schedule; do not escalate through Docker, install privileged system services or depend on an SSH session. The installer preserves unrelated crontab entries and dispatches through the successful preview deployment pointer. A failed run remains observable through nonzero exit and private status/operation receipts; delivered external notifications require separate runtime evidence.
- Operator-preview backup maintenance reuses its existing operation lock and verified-backup owner. `inspect-backups` is read-only; explicitly selected `maintain-backups` preflights the scoped encrypted files, removes expired personal-trial backups and creates a verified replacement when the newest remaining backup is at least 24 hours old or absent. Cleanup precedes database health checks so a failed backup does not silently extend retention. Only manifests carrying the personal-trial policy and matching environment, Compose project, database, exact generated filename, file type, size and digest qualify; unknown legacy backups remain visible for operator reconciliation, never guessed from modification time. Maintenance failures surface through the existing failed operation receipt. The deploy-user cron schedule invokes this operation hourly;
  the seven-day expiry target therefore has up to one scheduled interval of cleanup lag under healthy operation, and stopped/missed/failed jobs require operator intervention. Schedule installation, runtime, alerts and legacy cleanup remain unverified until exercised on the selected host.
- The owner-selected personal-trial encrypted PostgreSQL backup retention target is seven days (168 hours from dump start), not a retention period for live accounts, contributions, logs or retained-original recovery databases. `tools/deployment/verified-backup.mjs` records this policy and an absolute UTC expiry only for the separately validated staging operator-preview lane; formal staging/production backups do not inherit it. Expiry metadata is not deletion evidence. Existing backup files remain untouched, and daily backup scheduling plus at-least-daily expiry cleanup, failure alerting and restore-after-account-erasure reconciliation must be implemented and exercised on the host before claiming an enforced seven-day lifecycle. A missed or failed backup must be visible; it must not silently extend personal-data retention. Do not prune another environment, the encryption key, a retained-original database or an unclassified legacy backup under this policy.
- Before a migration that can change durable data, create an encrypted, environment-owned PostgreSQL backup plus manifest and verify that it is readable. Production backup retention, recovery-point target, recovery-time target and restore-drill cadence remain decision-required before public launch; a backup command or unit-tested recovery state machine without a successful representative remote restore drill does not establish recoverability.
- The initial backup owner uses an externally provisioned 256-bit encryption key file and writes only an authenticated encrypted dump plus a non-secret integrity/restore manifest to an absolute environment-owned backup directory. It restores into a run-unique temporary database on the same isolated PostgreSQL owner, verifies the current schema-migration identity, and drops that database before issuing the receipt. The in-memory implementation has an explicit configured size ceiling; exceeding it fails closed and requires a streamed/off-host backup implementation rather than silently exhausting the host. A local or mounted-directory receipt does not prove off-host durability until the selected provider target and retention policy are configured and exercised.
- Application rollback selects the retained prior image digest and configuration only when schema compatibility is established. Database recovery requires exact environment, target database and encrypted-backup SHA-256 confirmations; it restores and schema-checks a new database before stopping writers, retains the original database through cutover, and switches the original back if new-state readiness fails. It never automatically deletes the retained original. An incompatible data migration uses an explicitly tested down migration or a forward repair; it must not restore an old database over newer accepted writes without an operator-owned recovery decision.
- API and worker shutdown are bounded and drain or safely requeue owned work. Health distinguishes process liveness from readiness of schema, database, Redis and required composition. A provider outage may yield attributable partial/stale/unavailable state under existing product rules but never fixture-backed success.
- A failed staging or production deployment stops promotion, preserves diagnostic evidence without secrets, and leaves the previous healthy production revision serving when possible. The protected remote-promotion boundary may surface only the receipt-owned, allowlisted failed-step and error-code identifiers to CI so an operator can localize a failed run without host access; it must not surface request bodies, tokens, credentials, context identities, precise locations or provider responses. Unknown listeners, mutable-tag drift, missing secrets, migration mismatch, failed backup, failed readiness, worker failure or candidate mismatch fail closed.

## Observability And Operations

- Both public-domain and operator-preview Caddy profiles filter the complete request object and response headers from both access and default/error log encoders. This prevents URLs, search strings, viewport coordinates, context identifiers, request headers and future nested request fields from entering those logs; timing, status, byte counts and attributable error classes remain available. Do not replace this with a finite sensitive-query denylist or change forwarded product requests. The filter applies to newly emitted logs only: existing log copies require separately approved retention/cleanup. Capacity-based container rotation is not a time-retention guarantee; public-release backup retention, log retention and restore-after-erasure reconciliation remain explicit launch decisions, never invented fixed-day promises.

- API and worker emit structured logs with release identity, environment, request/trace identity, provider run and attributable error class; they exclude secrets, session tokens, precise user location and raw uploaded metadata.
- Required production signals include API liveness/readiness, request latency/error rate, database and Redis connectivity, worker heartbeat/queue backlog/dead letters, provider health/quota/cost, disk and memory pressure, certificate expiry/renewal, backup completion and restore-drill status. Exact alert thresholds require measured workload or an explicit initial operator budget.
- Each environment exposes only the minimum authenticated operational view needed to diagnose it. `infrastructure/monitoring/quality-signals.json` remains the cross-product signal vocabulary; deployment wiring must project those signals without making the JSON declaration proof that monitoring runs.

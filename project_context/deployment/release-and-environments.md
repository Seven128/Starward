# Deployment Release Identity And Environments

This on-demand deployment node owns public-IP certificate handling, release identity/external gates and the selected staging/production/runtime topology. Delivery mechanics, secrets and recovery remain in sibling nodes routed by `project_context/deployment.md`.

## Public IP certificate lifecycle

The IP issuer deliberately omits the optional ACME contact email; it must not send the old internal-preview placeholder or infer a personal contact. Formal deployment still owns its separate `CADDY_EMAIL` descriptor contract. Expiry checks and Caddy renewal, not email notifications, own certificate health.

The owner has authorized free public IP certificate issuance and automatic renewal for the existing owner-only trial. The sole IP edge policy uses the pinned Caddy ACME implementation with the Let’s Encrypt `shortlived` profile; no parallel internal-CA fallback is active. Caddy owns account/certificate private keys, renewal scheduling (including ARI), retries and atomic certificate replacement in the existing persistent `caddy-data` volume. Keep its restart policy and do not delete its storage to force renewal. A normal deployment may briefly interrupt the trial, but never recreates data volumes. Old internal-CA files may remain as inactive migration residue until the public path is verified; no client trusts them for the current path.

Certificates last about six days, so manual periodic issuance is not an acceptable lifecycle. Validate the loaded automation policy, system-trusted IP certificate and expiry, persistent storage across edge restart and explicit failure handling. A first issuance/restart does not prove a later natural renewal; retain that distinction in operation evidence. Failed issuance or renewal must not switch to plaintext, an internal CA or skipped verification. Existing `deployment:preview --operation check` is the bounded public-trust/readiness check; it fails for invalid or imminently expiring certificates. The public CA certificate exposes its IP identifier in certificate-transparency logs; this is not permission to expose authenticated API data or credentials. Public trust alone does not satisfy WeChat domain-list/filing or public-release requirements.

## Selected Environment Topology

### Staging

- Staging is a remote, non-public-release environment for real deployment, migration, provider-sandbox or explicitly authorized trial integration, production-shaped smoke checks, Mini Program preview/experience builds, and operator acceptance. It may be provisioned on demand for a release and deprovisioned after its attributable receipts and required short-lived artifacts are retained; absence of a currently provisioned staging instance disables remote staging deployment and therefore blocks production promotion rather than silently substituting CI or production.
- Before the filed HTTPS origin exists, the owner may run one explicitly non-qualifying operator preview on the staging host. It reuses the exact Compose API/worker/PostgreSQL/Redis/migration owners. DevTools reaches the fixed internal API address through an authenticated SSH local-forward bound to loopback. Owner-phone debugging may additionally use the tracked IP-preview Caddy overlay: only Caddy publishes 443, obtains a Let’s Encrypt shortlived certificate for the host IP through TLS-ALPN on 443 (HTTP challenges are disabled), requires a run-random preview header before proxying, removes that header before the API, filters it from access logs, and leaves 80/API/database/cache unbound. Every lifecycle command that includes Caddy must retain both Compose files; omitting the overlay would restore the normal public-domain edge mappings.
  The corresponding WEAPP build embeds that preview header and `https://<host-ip>` only for the development preview; development URL checking is disabled and the owner must enable phone debugging for the IP domain-list exception; TLS certificate validation must remain intact. Compatibility remains unverified until that exact phone succeeds. This preview may use `LOCAL_TEST` authentication only with the explicit acceptance-mode guard, real trial providers and the staging database namespace; local-test session success does not prove WeChat OpenID/AppSecret authentication. It never creates a staging release receipt, proves ICP/Mini Program filing, satisfies production promotion, or permits ordinary experience/public traffic.
  Raw public `http://<IP>`, an unguarded public test API, token-bearing plaintext traffic, fixture substitution, existing-volume overwrite, production-bundle token retention and weakening the formal release validator are forbidden. The preview descriptor and generated secrets remain outside Git; after the filed HTTPS staging lane exists, remove the overlay, internal certificate state, preview token/header and tunnel instructions, then requalify the exact candidate through the normal backup, migration, public-readiness and receipt path.
- Staging has its own compute/runtime identity, database, Redis namespace or instance, object bucket/prefix, queue, cache prefix, session secret, provider credentials and quota ledger, DNS origin, Mini Program credential/channel, logs and backups. It never reads or writes production user data and cannot receive production webhook or payment traffic.
- The current owner-only `TRIAL` staging lane binds QWeather JWT credentials for the primary timeline/official-alert roles, explicitly selects the free-entitlement-compatible 24-hour Weather API v1 hourly window, and uses Open-Meteo's qualifying non-commercial endpoint for layered-cloud/model evidence. The QWeather hourly owner calls `/weather/v1/hourly/{latitude}/{longitude}` at the provider-documented 1 km resolution; the retired-path v7 grid API is not an allowed release dependency. It carries no QWeather paid-plan assumption and no Open-Meteo commercial API key. The 24-hour selection is an explicit environment capability boundary: the source/model identity and available horizon remain visible, missing hours stay unavailable, and the adapter never retries a rejected 72-hour request as a hidden downgrade.
  This is also an environment/licence boundary rather than fixture permission: real provider failure remains attributable partial, fallback or unavailable state, and a later commercial/public lane cannot inherit this selection.
- Staging may be stopped when idle to control cost. Suspension cannot turn its last run into current evidence; wake-up must re-establish health, migration level, candidate digest and secret bindings.

### Production

- Production is the only public-user environment. It accepts only provider-backed, licence-compatible composition and truthfully disables or degrades a capability whose production adapter, credential, source right or external approval is absent.
- The `COMMERCIAL` production lane requires the 72-hour QWeather Weather API v1 hourly window and forbids Open-Meteo's non-commercial endpoint. The current layered-cloud/model-evidence composition therefore requires a separately approved QWeather entitlement and Open-Meteo commercial credential in addition to production QWeather JWT credentials; absence of either commercial binding blocks a full-capability production release rather than silently borrowing staging credentials, selecting a fixture, downgrading the requested horizon or treating the QWeather primary timeline as proof of the missing evidence source.
- Production has a separate always-on compute/runtime and separate mutable resources from staging. It does not share a host process tree, writable volume, database, Redis, bucket, session secret, provider credential, queue, cache namespace, backup target or deploy credential with staging.
- Only the HTTPS reverse proxy is internet-addressable. PostgreSQL, Redis, worker control, administrative operations and internal health dependencies remain on private/container networks; administration uses authenticated, least-privilege paths and is not exposed by opening database or Redis ports.

### Runtime Shape

- The selected initial runtime is one provider-neutral Linux OCI/Compose stack per environment: automatic-HTTPS reverse proxy -> `workers/miniapp-api` BFF, plus the independently supervised Outbox/BullMQ worker, PostgreSQL/PostGIS and Redis. A managed object store becomes a separate adapter boundary when contribution media is enabled.
- API, worker and one-shot migration processes use the Docker/Compose runtime's built-in init process for PID 1 signal forwarding and orphan reaping. The release image starts Node directly and performs no runtime-stage operating-system package fetch. This preserves bounded shutdown semantics while keeping image construction dependent only on digest-pinned OCI inputs and the locked application dependency closure; an unfrozen APT fetch, an unverified copied init binary or running Node as an unreaped PID 1 are forbidden shortcuts.
- The BFF and worker consume `packages/miniapp-contracts/**` and the same release image/source revision. The client calls only its environment's BFF origin; it never receives provider secrets or calls weather, map, media or content providers directly.
- Kubernetes is not selected for the current modular monolith and initial load. Managed containers, managed PostgreSQL/Redis, or horizontal API replicas remain allowed future substitutions when measured reliability, capacity or operational cost justifies them; they must preserve the same contracts, state owners and promotion rules.

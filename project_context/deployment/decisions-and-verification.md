# Deployment Decisions And Verification

This on-demand deployment node owns unresolved blockers/debt disposition, provider and capacity selection, external inputs and the limits of deployment verification.

## Implementation Blockers And Debt Disposition

- Complete full release-environment validation with an allocated domain and real protected lane configuration, then verify Caddy, public hostname-valid TLS, external readiness and release identity through the real edge entry point. The operator IP preview uses a separate public-IP-certificate edge and local-test authentication; it cannot satisfy these public-domain release gates.
- Exercise the implemented typed-confirmation database recovery command in a Docker-capable disposable environment and then the selected remote topology, including retained-original cleanup policy, interrupted cutover, disk exhaustion, connection drain, failed switchback escalation and measured recovery time/data-loss boundaries. The current remote dump/encryption/isolated-restore run proves the backup mechanism against real PostgreSQL but does not exercise recovery cutover, accepted-write behavior or disaster recovery. Add a tested application-image rollback path only after schema compatibility and accepted-write behavior are explicit.
- Select and exercise an off-host encrypted-backup target, retention policy, recovery point/time objectives and restore-drill cadence before public launch. Local or mounted-directory bytes do not prove durability.
- Implement an object-store adapter and lifecycle/authorization checks before enabling contribution media outside local development. Until then the capability remains disabled in staging/production.
- Configure the implemented environment-bound WEAPP preview/upload workflow with distinct protected staging/production AppIDs, upload keys, approved HTTPS domains, a fixed-egress dedicated runner and required production reviewers. The owner, local checks and disabled workflow exist, but no real platform credential, preview/upload receipt, review submission or public release does.
- Distinguish the currently enabled trusted-main staging scheduling gate and selected operator-preview lane from formal staging/production qualification. Inspect the actual workflow job/receipt and current runtime identity before claiming that a successful workflow promoted its head revision; a skipped qualification or historical registry round trip does not establish that result. Formal staging/production still require their own protected descriptors, application/provider secrets and promotion evidence. No registry allocation, login, image round trip, workflow definition or unit test is a remote deployment receipt. A deployment Skill remains optional and cannot replace these repository-owned commands.

## Provider And Capacity Selection

### Current capacity target: 200 DAU (2026-10-02)

- The user-selected planning target is **200 DAU for the Mini Program as a whole**. Cloud-sky usage is a subset; use all 200 users in a stated conservative scenario, not as measured adoption or concurrency. Earlier 500/1000-DAU cost examples are historical scenarios, not current targets or tested capacities.
- Expected production resources are **one 4-vCPU / 16-GB Linux host, 12-Mbps peak public bandwidth, 2000-GB monthly outbound allowance and 180-GB SSD**, with Tencent Cloud Lighthouse as the expected provider. Mainland locations including Beijing, Shanghai, Guangzhou, Chengdu and Nanjing are candidates, not a multi-region deployment. The final region, actual order, eligibility, renewal price and provisioned resources remain action-time facts. This records an intended capacity, not a purchase, deployment, SLA or load-test receipt.
- **Sky imagery storage planning (2026-10-04):** 180 GB is the whole-host disk, not an imagery allocation. The publisher estimate of roughly 6.34 TB for one SkyMapper color HiPS cannot fit in full; progressive loading and client caching save transfer but cannot remove that inventory gap. Plan a lower-resolution wide background plus qualified high-resolution targets/regions, recording actual coverage and maximum useful detail. This is not a claim that every alternative requires 6 TB, nor a certification of the smaller plan. Before adopting quantities, account for current/retained products, staging copies, images, database, logs, backups and headroom; keep source frames and processing intermediates in the offline publication environment. Do not invent a fixed imagery quota, delete old URLs or assume external hosting is free. The [source direction](../external-capabilities.md) and [research reconciliation](../../.codex/work-items/cloud-sky-native-2026-09-22/evidence/galaxy-imagery-direction-reconciliation-2026-10-04.md) preserve source restrictions and unresolved capacity.
- **Staging remains 4 GB** and retains its own environment/data/secrets. It can verify the same protocols, lifecycle, failures and recovery with bounded representative data. It cannot certify production throughput or 16-GB memory headroom; qualify capacity on the production shape or a materially equivalent isolated environment. Larger offline imagery acquisition/mosaicing/encoding belongs outside the live application host. The old assumption that the existing 4-GB host must become production is superseded; no host migration or purchase is performed by this decision.
- Optimize client and server together for full-quality interactive performance. Initially prefer a single business host with versioned static sky resources served directly by its HTTPS edge, plus bounded persistent client file caching and view/resolution-driven loading. Static delivery must preserve publication integrity, attribution, prior-version compatibility and applicable access boundaries. This remains the adopted direction. Optional `STARWARD_SKY_STATIC_DIRECTORY` now selects the implemented image-bound static lane in the existing release/preview owners; an unconfigured environment retains its API lane. The shared producer enumerates approved publication owners at image build, and `tools/deployment/sky-static-bundle.mjs`/`sky-static-release.mjs` own canonical integrity, exact-image extraction, a leased retained history union and full HTTP byte/header verification. Generated readonly mounts preserve protected-preview authorization and API fallback; configured v2 staging qualification binds the current image publication separately from each host’s history union. A prepared inventory is not a successful release receipt, and unbound pre-static image/control rollback is not certified. Local filesystem, controlled release chains, actual support-image extraction and adapted local HTTPS evidence are development checks; no configured cloud deployment, full clean candidate, storage-growth lifecycle or capacity acceptance follows. API, worker, database and Redis remain bounded and isolated by responsibility.
- An object store/CDN is **not a prerequisite for initial cloud-sky delivery at 200 DAU**. Preserve an environment-owned resource-origin adapter so measured peak egress, regional latency, asset growth or cost can justify it later without changing product semantics. This does not waive the separate object-store requirement for user contribution media. CDN/object-store egress, requests and origin traffic have their own charges; the VM allowance does not cover them automatically.
- The resource allowance counts public **outbound** traffic, resets monthly and does not roll unused traffic forward. Excess traffic is metered; sufficient account balance is required to avoid overdue suspension. Fetching raw inputs into the host is inbound; serving them to clients or exporting backups is outbound. Verify actual billing against the [official billing rules](https://cloud.tencent.cn/document/product/1207/44368) and [package listing](https://cloud.tencent.com.cn/document/product/1207/73452), not an old promotional screenshot.
- For planning only, 200 daily users × 30 days × 10/30/50/100 MB of newly transferred content gives approximately 60/180/300/600 GB per month (decimal units, before other traffic/protocol overhead). Peak 12 Mbps is approximately 1.5 MB/s shared by the host, not per user or guaranteed throughput. Monthly volume alone does not establish acceptable cold-start latency.
- Acceptance must include ordinary mixed business traffic and **10 and 20 simultaneous cold-cache cloud-sky entries as initial burst scenarios**, then warm revisits, continuous pan/zoom, time/tracking and recovery. These are test cases, not a concurrency ceiling. Record first usable frame and detail completion, tail API latency, frame time, client decoded/native/GPU memory, server CPU/RSS/DB/worker backlog, disk, cache hit rate and actual outgoing bytes. Establish justified budgets from the candidate and product experience before claiming capacity; no fixed frame rate, latency or operating bill is established by this planning update.

- The owner selected the current Mini Program commercial-capable composition: WeChat's native base map/place picker, project-owned formal-spot search and external navigation; QWeather as the sole forecast source plus independent official alerts, air quality and recent one-to-two-day history; GLO-30-F terrain, licensed EOG annual night-light radiance, offline BSC5P/OpenNGC catalogs, self-hosted AllWISE W3 products, Astronomy Engine calculations and reviewed GMN meteor material. Layered cloud, multi-model weather, Open-Meteo fallback, Amap route/POI calls, basemap themes and automatic road ETA/range are retired from this product. This is authorization to complete integration and verification, not evidence of account entitlement, host reachability, published data or product acceptance. Do not add subscriptions, purchases or annual commitments on this decision alone. Reassess only when verified entitlement, target-network access, required data quality/coverage, licensing or measured cost makes a selected source unsuitable. Product budgets and release scope remain owned by `project_context/global.md`; credential storage and retrieval remain owned by `deployment/data-and-operations.md`.
- The viable initial provider set included a mainland lightweight Linux VM with provider registry/DNS/object storage, a general cloud VM with the same boundaries, or managed container/data services that support the current Node, PostGIS, Redis and background-worker lifecycle. The first-host selection is now a Tencent Cloud Lighthouse Linux VM in Shanghai using the paid shape above, with TCR Personal Edition as its initial repository-owned image registry. Off-host storage tier, renewal choice and any later staging-host procurement remain external decisions.
- The initial selection uses a low-cost mainland Linux VM/Compose deployment because it reuses the existing modular monolith and local service topology with the least operational surface. A promotional price or static instance shape is procurement evidence only, not capacity, availability or performance proof.
- Before public traffic, measure the declared cold start, representative API/provider workload, worker backlog and PostGIS query set against explicit latency, memory, CPU, disk and cost budgets. Scale up, split managed data services or add replicas only from current measurements; no SLA, high-availability or capacity claim is currently made.

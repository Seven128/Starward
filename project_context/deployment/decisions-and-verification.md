This on-demand deployment node owns unresolved blockers/debt disposition, provider and capacity selection, external inputs and the limits of deployment verification.

- Complete full release-environment validation with an allocated domain and real protected lane configuration, then verify Caddy, public hostname-valid TLS, external readiness and release identity through the real edge entry point. The operator IP preview uses a separate public-IP-certificate edge and local-test authentication; it cannot satisfy these public-domain release gates.
- Exercise the implemented typed-confirmation database recovery command in a Docker-capable disposable environment and then the selected remote topology, including retained-original cleanup policy, interrupted cutover, disk exhaustion, connection drain, failed switchback escalation and measured recovery time/data-loss boundaries. The current remote dump/encryption/isolated-restore run proves the backup mechanism against real PostgreSQL but does not exercise recovery cutover, accepted-write behavior or disaster recovery. Add a tested application-image rollback path only after schema compatibility and accepted-write behavior are explicit.
- Select and exercise an off-host encrypted-backup target, retention policy, recovery point/time objectives and restore-drill cadence before public launch. Local or mounted-directory bytes do not prove durability.
- Implement an object-store adapter and lifecycle/authorization checks before enabling contribution media outside local development. Until then the capability remains disabled in staging/production.
- Configure the implemented environment-bound WEAPP preview/upload workflow with distinct protected staging/production AppIDs, upload keys, approved HTTPS domains, a fixed-egress dedicated runner and required production reviewers. The owner, local checks and disabled workflow exist, but no real platform credential, preview/upload receipt, review submission or public release does.
- Exercise the configured trusted-main GitHub publication into the approved TCR repository and its complete Shanghai staging promotion after the remaining protected staging descriptors and application/provider secrets exist. The manually operated TCR push/digest-resolution/host-pull round trip establishes registry reachability but cannot substitute for that workflow run. Trusted-main staging CD and environment-protected production manual promotion remain disabled and runtime-unverified until those descriptors exist; no registry allocation, login, image round trip, workflow definition or unit test is a remote deployment receipt. A deployment Skill remains optional and cannot replace these repository-owned commands.

## Provider And Capacity Selection

- The viable initial provider set included a mainland lightweight Linux VM with provider registry/DNS/object storage, a general cloud VM with the same boundaries, or managed container/data services that support the current Node, PostGIS, Redis and background-worker lifecycle. The first-host selection is now a Tencent Cloud Lighthouse Linux VM in Shanghai using the paid shape above, with TCR Personal Edition as its initial repository-owned image registry. Off-host storage tier, renewal choice and any later staging-host procurement remain external decisions.
- The initial selection uses a low-cost mainland Linux VM/Compose deployment because it reuses the existing modular monolith and local service topology with the least operational surface. A promotional price or static instance shape is procurement evidence only, not capacity, availability or performance proof.
- Before public traffic, measure the declared cold start, representative API/provider workload, worker backlog and PostGIS query set against explicit latency, memory, CPU, disk and cost budgets. Scale up, split managed data services or add replicas only from current measurements; no SLA, high-availability or capacity claim is currently made.

## Verification Boundary

- Current Context-only changes are checked with `npm run context:validate`, `make validate-context`, `make validate-harness`, `npm run context:doctor`, and the package-managed source-parity check where applicable.
- Release-product CI covers the Mini Program API production-workspace dependency audit, release-code SDK/type/unit checks, deployment/uploader tests, backend and nondeployable WEAPP builds, isolated PostgreSQL/Redis integration and OCI construction. It runs no design-resource or Context/Harness gate and alone creates no remote evidence. The enabled trusted-main IP-preview workflow separately exercised image publication, exact-digest pull, host preflight, encrypted backup with isolated restore, one-shot migration, API/worker/edge startup and guarded IP readiness. An independent post-run check confirmed actual container image/revision identity and healthy private data services; same-image recovery also preserved the checked four core persistence tables. The preview's operation receipt cannot qualify a formal staging release.
  Formal domain/WeChat credentials, provider degradation, public-domain system-trusted TLS, qualified staging/production promotion, recovery cutover, off-host disaster recovery, application rollback and representative-device acceptance remain unverified or explicitly deferred. Manual workflow dispatch retains full product checks but has not separately been exercised; host-side check/backup/deploy operations and the automatic workflow path have been exercised.
- Context, a workflow file, a cloud console screenshot, an image push or a successful SSH command does not prove deployment or product acceptance. Handoff reports remote environments, filings, checks and public release as completed only from attributable current evidence.

# Deployment Mini Program Delivery And Promotion

This on-demand deployment node owns environment-bound WEAPP bundle identity, protected preview/upload, receipts, promotion and explicit rollback boundaries.

## Mini Program Delivery, Receipts, And Promotion

- The WEAPP bundle is environment-bound because AppID, API origin and platform configuration affect its bytes. The tracked `apps/wechat-miniapp/project.config.json` is the current source/DevTools AppID identity; a deployable staging or production build must require its protected lane AppID to equal that tracked identity instead of silently rewriting an old-account source candidate. `tools/miniapp/wechat-app-id-migration.mjs` owns the guarded source/local-config transition after a new platform account exists, but never owns account registration, subject/admin membership, AppSecret, upload key, request-domain/privacy approval or OpenID migration. Staging preview/experience and production upload therefore have separate fingerprints and credentials even when they use the same source revision. The exact production bundle must be exercised through its production/experience channel before review submission; platform review and final public release remain explicit human actions.
- `tools/miniapp/**` owns the one repository command that may create a release-class WEAPP bundle identity. It accepts an explicit `ci`, `staging`, or `production` lane and API origin, exclusively owns the generated-output root for that invocation, performs a clean production-mode WEAPP build, rejects loopback/insecure/reserved origins for deployable lanes, and emits a disposable content fingerprint manifest. The `ci` lane must use a reserved `.invalid` origin, accepts no platform credential, and is structurally non-deployable; a successful CI bundle therefore cannot be promoted or uploaded. Staging and production require their own explicit AppID identity and real HTTPS origin, and neither may be reconstructed from the CI bundle.
- `tools/miniapp/upload-release-bundle.mjs` owns preview/upload validation and consumes, but never rebuilds, the exact environment-bound bundle manifest. It uses an isolated, exactly locked platform-supported uploader runtime under `tools/miniapp-uploader/**`; that dependency tree has known critical transitive audit findings and is therefore confined to a protected, fixed-purpose self-hosted Linux runner with no backend/cloud credentials. The runner receives a repository-external upload key only for the external operation, verifies the bundle before and after it, redacts AppID/key material, and retains only short-lived QR/receipt/reconciliation artifacts. Production preview may establish the QR and bundle digest; production upload additionally requires exact typed confirmation of operation, lane, version and digest. Platform review and public release remain manual.
- Every deployment emits a disposable, attributable receipt containing environment, source revision, backend image digest, WEAPP fingerprint where applicable, migration version, start/end time, operator/workflow identity and check outcomes. Receipts are operational evidence and never durable Context.
- The repository-owned promotion command combines one stable environment base descriptor with one non-secret immutable candidate identity and executes the fixed boundary `prepare -> validate -> required backup/isolated-restore -> Compose render -> immutable-image pull -> one-shot migration -> converged startup -> worker checks -> public HTTPS/TLS/release-identity checks -> redacted receipt`. Release identity is injected once by Compose and is forbidden from the API/worker/migration secret-bearing lane files.
  The public check uses the configured domain without redirect following, accepts only a bounded JSON readiness response with the expected security headers and exact environment/revision/image digest, requires a system-trusted hostname-valid TLS 1.2+ certificate with at least seven days remaining, and records only non-secret protocol/certificate metadata. Production additionally requires an exact typed digest confirmation, a complete successful staging receipt for the same revision/digest, and a fresh successful production backup/isolated-restore receipt; staging cannot reuse that production receipt. The command never resolves a mutable tag, accepts another image repository, rebuilds a candidate, purchases infrastructure, submits a filing, publishes a Mini Program, or logs a secret.
  Because this probe runs from the selected host, it is release evidence for that vantage point rather than proof of independent internet reachability or continuous monitoring.
- A failed release does not automatically replace durable data or claim a safe application rollback. The operator may explicitly select a retained prior image digest only after the migration compatibility boundary is known; a data repair or restore remains a separate, attributable recovery decision.

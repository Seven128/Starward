# Deployment Mini Program Delivery And Promotion

This on-demand deployment node owns environment-bound WEAPP bundle identity, protected preview/upload, receipts, promotion and explicit rollback boundaries.

## Mini Program Delivery, Receipts, And Promotion

The protected WeChat workflow passes `vars.STARWARD_WECHAT_SKY_RESOURCE_ORIGIN` to that bundle owner, falling back explicitly to its API origin when the variable is empty. A selected environment must configure its qualified resource domain before an off-host candidate is claimed; ambient build variables do not supply this binding.

Sky-only static catalog admission and source-link consumers import `services/sky-catalog-api.ts` directly; the common API client retains their shared transport and cache. Package ownership must follow those real consumers without a reverse reexport. Keep room for official DevTools packaging: fitting the raw local 2 MiB limit alone does not establish that ordinary preview or true debug can package the same candidate.

The WEAPP compiler keeps sky-only contract implementations with their actual subpackage consumers by allowing webpack to skip the contract forwarding entry, rather than marking the whole library or frontend as side-effect-free. `apps/wechat-miniapp/config/contracts-reexports.cjs` validates that entry and its local dependency initialization before applying the single-entry rule. Only the real contracts entry may also resolve the already declared coordinate-system dependency to this repository's fixed source entry; that dependency and its local imports undergo the same recursive audit within their own root. Unknown external imports, root escapes and uncertain initialization still fail. The existing filter-map/schema exceptions belong only to contracts/filters.ts and do not transfer to the coordinate workspace. An unused reexport dependency's initialization can disappear, so global setup, CSS, new dependencies or new initialization mechanisms must not be smuggled into this contract graph; unknown forms fail and require reassessing its responsibility. The check is a conservative project syntax boundary, not a general JavaScript purity proof. Existing CSS/assets stay with their original owners. Run the real candidate's package inspection after relevant compiler/dependency/configuration changes: pure compiled address checks and ordinary local byte budgets do not certify native loading or the platform upload package. See [scoped package evidence](../../.codex/work-items/cloud-sky-native-2026-09-22/evidence/package-ownership-2026-10-10.md).

The release owner also binds `--sky-resource-origin` (defaulting to the requested API origin) and overrides any ambient `MINIAPP_SKY_RESOURCE_BASE`. Current v3 and earlier v2 manifests record both origins. `tools/miniapp/compiled-sky-origin.mjs` reuses the candidate's webpack runtime/common bytes to execute only the pure address owner: real API discovery, immutable resource/legacy W3 routing, environment cache identity and absent formal preview credentials must match. Expected strings in comments or unrelated files supply no binding. Missing/duplicate/dependency-bearing owners or unexpected common entry callbacks fail rather than launching App/pages or falling back to text presence. Compiler/runtime shape changes require reassessment of this bounded adapter; compiled pure behavior is not native/network acceptance. Build manifests record byte pins/roles, and v2/v3 platform consumption freshly derives them, checks a supplied record and retains the derived result in receipts. Earlier v2 without that extra record still undergoes the same fresh semantic check; historical v1 remains same-origin and rejects an injected different resource origin. This version boundary is implemented in `tools/miniapp/release-bundle-request.mjs`, `release-bundle-artifact.mjs` and `wechat-platform-operation.mjs`; a configured origin or fake-driver pass does not qualify an OSS/CDN endpoint, request-domain approval or target device. Resource/data semantics remain with the [runtime owner](../architecture/runtime-and-domain.md#微信小程序影像平台边界), with [scoped compiled evidence](../../.codex/work-items/cloud-sky-native-2026-09-22/evidence/compiled-origin-binding-2026-10-10.md).

Release v3 binds one freshly allocated `artifacts/miniapp/release/bundles/<UUID>/weapp` directory and the measured package budget, leaving development `dist/weapp` and earlier candidates intact. `tools/miniapp/release-bundle-location.cjs` is the single compiler/consumer path grammar; the artifact owner checks directory ancestors for reparse points, refuses a reused manifest, rechecks source project identity and candidate bytes, then exclusively writes the manifest. An existing manifest needs a fresh `--output-manifest` path under the release root, rather than replacement. Taro refuses an already existing release output, including a dangling directory entry. V3 platform consumption resolves this bound directory, freshly checks its fingerprint, origins and budget, and passes the same directory to the driver/post-operation readback; legacy v1/v2 still use the legacy root and reject an injected directory field. The v2 receipt remains compatible and records the selected directory/budget for v3. `built-candidate.test.mjs` consumes the explicit `MINIAPP_BUILT_CANDIDATE_MANIFEST` (default CI manifest), and the protected WeChat job supplies its own lane manifest before platform operations. These local guards do not certify platform upload-package size, domain approval, native loading or off-host deployment.

- The WEAPP bundle is environment-bound because AppID, API origin and platform configuration affect its bytes. The tracked `apps/wechat-miniapp/project.config.json` is the current source/DevTools AppID identity; a deployable staging or production build must require its protected lane AppID to equal that tracked identity instead of silently rewriting an old-account source candidate. `tools/miniapp/wechat-app-id-migration.mjs` owns the guarded source/local-config transition after a new platform account exists, but never owns account registration, subject/admin membership, AppSecret, upload key, request-domain/privacy approval or OpenID migration. Staging preview/experience and production upload therefore have separate fingerprints and credentials even when they use the same source revision. The exact production bundle must be exercised through its production/experience channel before review submission; platform review and final public release remain explicit human actions.
- `tools/miniapp/**` owns the one repository command that may create a release-class WEAPP bundle identity. It accepts an explicit `ci`, `staging`, or `production` lane and API origin, exclusively owns the generated-output root for that invocation, performs a clean production-mode WEAPP build, rejects loopback/insecure/reserved origins for deployable lanes, and emits a disposable content fingerprint manifest. The `ci` lane must use a reserved `.invalid` origin, accepts no platform credential, and is structurally non-deployable; a successful CI bundle therefore cannot be promoted or uploaded. Staging and production require their own explicit AppID identity and real HTTPS origin, and neither may be reconstructed from the CI bundle.
- `tools/miniapp/upload-release-bundle.mjs` owns preview/upload validation and consumes, but never rebuilds, the exact environment-bound bundle manifest. It uses an isolated, exactly locked platform-supported uploader runtime under `tools/miniapp-uploader/**`; that dependency tree has known critical transitive audit findings and is therefore confined to a protected, fixed-purpose self-hosted Linux runner with no backend/cloud credentials. The runner receives a repository-external upload key only for the external operation, verifies the bundle before and after it, redacts AppID/key material, and retains only short-lived QR/receipt/reconciliation artifacts. Production preview may establish the QR and bundle digest; production upload additionally requires exact typed confirmation of operation, lane, version and digest. Platform review and public release remain manual.
- Every deployment emits a disposable, attributable receipt containing environment, source revision, backend image digest, WEAPP fingerprint where applicable, migration version, start/end time, operator/workflow identity and check outcomes. Receipts are operational evidence and never durable Context.
- The repository-owned promotion command combines one stable environment base descriptor with one non-secret immutable candidate identity and executes the fixed boundary `prepare -> validate -> required backup/isolated-restore -> Compose render -> immutable-image pull -> one-shot migration -> converged startup -> worker checks -> public HTTPS/TLS/release-identity checks -> redacted receipt`. Release identity is injected once by Compose and is forbidden from the API/worker/migration secret-bearing lane files.
  The public check uses the configured domain without redirect following, accepts only a bounded JSON readiness response with the expected security headers and exact environment/revision/image digest, requires a system-trusted hostname-valid TLS 1.2+ certificate with at least seven days remaining, and records only non-secret protocol/certificate metadata. Production additionally requires an exact typed digest confirmation, a complete successful staging receipt for the same revision/digest, and a fresh successful production backup/isolated-restore receipt; staging cannot reuse that production receipt. The command never resolves a mutable tag, accepts another image repository, rebuilds a candidate, purchases infrastructure, submits a filing, publishes a Mini Program, or logs a secret.
  Because this probe runs from the selected host, it is release evidence for that vantage point rather than proof of independent internet reachability or continuous monitoring.
- A failed release does not automatically replace durable data or claim a safe application rollback. The operator may explicitly select a retained prior image digest only after the migration compatibility boundary is known; a data repair or restore remains a separate, attributable recovery decision.

# Deployment Operator Preview Lane

This on-demand deployment node owns the temporary guarded public-IP/operator-preview delivery path. It is neither formal staging qualification nor production release.

## Operator Preview Delivery

- The current delivery scope is deployment engineering only: second-account enrollment, phone automation and full device acceptance are deferred at the owner's request. Completing a repeatable deployment loop does not assert device compatibility or complete product acceptance. Business registration, domain/filing and public production remain paused.
- IP-preview CORS retains the API runtime owner's HTTPS-only policy and permits only the selected HTTPS IP origin. Native WEAPP requests, including the authenticated SSH-forward development lane, do not require adding a browser Origin. HTTP loopback, public HTTP and arbitrary external origins are rejected before deployment; the preview validator must not admit configuration that the unchanged API startup owner rejects.
- The shared Compose executor strips inherited `STARWARD_*`, `COMPOSE_*` and `CADDY_EMAIL` variables before invocation so the explicitly selected private descriptor is the interpolation source of truth; registry/SSH process credentials remain external. Commands have a bounded process timeout and never echo raw command stderr or rendered secret-bearing configuration.
- The temporary IP lane has a repository-owned `deployment:preview` command, separate from formal promotion. It shares the environment validator's database/provider/security rules, Compose executor, immutable candidate preparation and verified-backup engine, but accepts only the explicitly guarded staging/local-test/IP profile and produces `starward-operator-preview-operation-v1` receipts with production qualification false. Formal validation and staging qualification never accept that profile or receipt. The staging workflow selects exactly one `domain` or `operator-preview` lane through protected environment configuration; manual dispatch may exercise the selected lane after the same release-product checks, while automatic publication still requires successful trusted-main Product CI.
- Every IP-lane operation holds one environment-wide host lock. Deployment first validates the rendered two-file Compose configuration, existing healthy data services, exact image digest/revision and private ports; pulls only the application image; stops edge/API/worker; executes the existing encrypted backup with isolated restore; runs the existing one-shot migration; and starts API/worker then edge without recreating PostgreSQL or Redis. A failed operation records the failed step and whether writers were stopped; rerunning the same candidate is the supported forward-recovery route after the fault is repaired. There is no automatic old-image selection or database restore. An interrupted lock is removed only after the operator verifies no owning process remains.
  Health checks use only system public trust roots, retain TLS/IP SAN verification, and verify unauthenticated 404 plus authenticated exact release identity. A bounded certificate-acquisition wait may precede readiness after edge startup; it cannot accept an internal/staging CA or bypass TLS. Public IP trust is reported separately from formal domain/platform qualification. This temporary adapter is removed with the existing IP overlay when the domain lane is adopted.
- Operator-preview readiness also owns one bounded real-provider smoke through that same authenticated HTTPS edge after exact release identity succeeds. It resolves a short-lived Observation Context for a fixed public Guangzhou reference point inside the declared Greater Bay Area trial boundary and first loads the production map-scene cloud path. When the database contains a non-fixture formal population, the check fails unless that real product path exposes available `QWEATHER` policy/和风天气 evidence and `Astronomy Engine` calculation evidence. When the formal population is empty, the deployment control plane may instead pass an isolated test program over stdin to the already deployed API container;
  that program reuses the production QWeather composition and `AstronomyService` with the contracts-owned explicit `TEST_FIXTURE` spot, has no database/cache write path and reports the result only as `ISOLATED_TEST_SIMULATION` with `FORMAL_POPULATION_MISSING`. This fallback verifies provider credentials/transport/normalization and local astronomy composition without fabricating product data; it never establishes the map/spot product journey or formal population. The receipt retains only scope/provider/state/count summaries; it never retains the preview token, precise user location, context identity, raw response or provider credential. Database fixture insertion, a public diagnostic endpoint, accepting fallback weather as QWeather success, or relabeling simulation as product evidence are forbidden.
  This single trial-provider read proves only the stated scope for that scenario; it does not prove forecast correctness, provider-wide availability, user-location permission, map tiles, capacity, public trust or production qualification. A future provider replacement must update this exact expectation rather than pass through fallback or unlabelled fixture evidence.
- The non-secret `STARWARD_STAGING_CD_ENABLED` scheduling gate is repository-scoped because GitHub evaluates the job condition before environment-level variables are available. It has no duplicate environment-level value. The lane, target paths, image repository and credentials remain owned by the `staging` environment restricted to the `main` branch. Enabling scheduling never bypasses trusted-source, product-check, environment or host-lock checks.

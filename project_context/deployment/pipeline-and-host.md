# Deployment Pipeline And Host Provisioning

This on-demand deployment node owns release-product CI, immutable backend image publication/promotion and explicit host provisioning/hardening boundaries. Mini Program bundle upload is routed separately.

## Product CI, Image Promotion, And Host Lifecycle

- A Skill may explain or invoke repository-owned release commands after they exist, but it is never the release executor, secret store, environment owner, receipt, approval boundary or source of deployed state. CI/CD and tracked deployment definitions are required for repeatability and auditability.
- Pull requests run deterministic release-product CI before merge: clean dependency installation from the lockfile, a Mini Program API production-workspace dependency audit at high severity, deployment-owner tests, release-code SDK/type/unit checks, backend release builds, a structurally nondeployable WEAPP CI bundle, infrastructure checks, and production-image construction. Design resources, Context/Harness validation and other repository-governance checks are not release products or release gates and remain outside these deployment workflows. No secret-bearing or irreversible external step runs on an untrusted pull request.
- The selected personal-developer control plane is GitHub Actions plus repository-owned workflows. Docker Compose and Caddy own each host runtime; no Jenkins, Coolify, Dokploy, Portainer, mutable-tag updater or other persistent deployment control plane is installed on the initial 4-GB host. GitHub's job/step/log/retry/environment UI is the initial visual operations surface, while workflow YAML remains the editable pipeline source of truth. Coolify or Dokploy remains an allowed future substitution when multiple applications or hosts make its operational savings exceed its persistent memory, disk, update and recovery cost; adopting one must reuse immutable images and environment separation rather than create a second release owner.
- After secret-free Product CI succeeds for a trusted repository `main` push, the selected release workflow builds the exact revision once as the release OCI image, records its registry digest, publishes it to the configured TCR Personal Edition repository above, and may automatically deploy that exact digest to staging. TCR Personal Edition is selected for the initial mainland-host profile because it has no subscription charge and provides the required basic OCI storage/distribution path, but it has shared-service quotas and no service-level agreement. The allocated namespace/repository, both GitHub/Shanghai-host login bindings and one manually operated immutable-image registry round trip are complete; trusted-main GitHub publication remains unexercised.
  Staging deployment resolves only staging secrets, applies the declared migration job, starts API/worker, and runs current health and smoke checks. Product CI's earlier local image construction is validation evidence and is never promoted.
- The workflow accepts one environment-owned registry host, image repository and username plus one protected password; it does not hard-code a cloud-account identity. TCR is the sole initial release-image source of truth: simultaneous GHCR dual publication and automatic cross-registry fallback are forbidden because they introduce ambiguous provenance. Registry authentication, push, digest resolution or host pull failure stops deployment. A later registry change updates the one approved repository binding and affected Context/workflow configuration before release; an immutable digest is still mandatory.
- Before either remote workflow transfers a control package or invokes promotion, the repository-owned read-only host preflight verifies the selected Linux host architecture, minimum CPU/memory/disk envelope, Node 24 runtime, Docker Engine/Compose reachability, required base descriptor and environment-owned directory ownership/mode. It performs no package installation, firewall change, directory creation or remediation; any mismatch fails before deployment mutation and must be corrected through the explicit host provisioning path.
- `infrastructure/deployment/bootstrap-fresh-host.sh` is the explicit one-time provisioning owner for a newly purchased, otherwise unused Ubuntu 24.04 x86-64 host. It requires root plus an exact fresh-host/environment confirmation, rejects an existing Docker installation or unsupported OS/architecture, installs Docker only through Docker's official APT repository, installs the exact Node 24 release from a checksum-pinned official archive, and applies bounded retries only to those authenticated official artifact downloads without weakening their fingerprint/digest checks. It creates the fixed deployment user and isolated environment directories, and enables a host firewall only after allowing the operator-supplied SSH port plus HTTP/HTTPS. It is never invoked by CI/CD, never generates credentials or base descriptors, and its existence is not evidence that a host was provisioned.
- `infrastructure/deployment/harden-ssh-after-key.sh` is the separate post-enrolment SSH-hardening owner. A root operator may invoke it only after the fixed deployment user's non-empty, correctly owned and permissioned `authorized_keys` exists. It installs one project-owned OpenSSH drop-in that keeps public-key login enabled while disabling password and keyboard-interactive authentication and direct root SSH login, validates both syntax and effective daemon policy before reload, and fails without changing the active daemon when prerequisites or policy checks fail. CI/CD never invokes it and the deployment user receives no general sudo access. The operator must prove a fresh deployment-user key session after reload and retain a separately verified provider management/recovery path; the script does not create, rotate or delete keys and does not by itself prove lockout recovery.
- Provider-specific container-registry reachability is an operator-owned host concern outside the provider-neutral bootstrap. When direct Docker Hub access is unavailable, a host may use only its cloud provider's current officially documented Docker registry mirror or an explicitly selected project registry; all repository-owned release and third-party images remain digest-bound, and the operator must verify the configured mirror and daemon state before relying on it. Unknown public mirrors, removing digest pins, mutable release tags and silently changing image provenance are forbidden shortcuts. A later provider or network change requires re-evaluating and removing or replacing this host-local setting.
- Production is a manual promotion of an already staging-qualified backend image digest. It does not rebuild from a branch or mutable tag. Promotion requires external release gates, a current production backup, migration preflight, approved operator identity, explicit target digest, bounded rollout, post-deploy smoke checks and a retained prior image digest.

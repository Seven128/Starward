Starward owns 《今晚去观星》. Current delivery is the WeChat Mini Program: trustworthy place, weather, astronomy, arrival and safety facts support users choosing places, arranging travel and observing; users decide whether to go. It does not present a combined departure recommendation. Existing native App material is retained as inactive product history, with its distinct meaning and design preserved.

- There is one current implementation per product responsibility. Native App, WeChat Mini Program and owner operations have distinct surfaces; do not infer one product's behavior or visual values from another.
- The Mini Program has Map and My as its primary destinations. Its sky route belongs to a selected formal spot or the current account’s submitted pending proposal, as defined by the Map Screen Contract. Read the owning Screen Contract before changing those flows.
- Current distribution remains owner-only personal trial; source adoption is not purchase or public-release authorization. Native App retains its CNY 200/month trial ceiling. Mini Program now adopts the [external-capability selection and cost baseline](external-capabilities.md): its former CNY 350 trial ceiling and CNY 0.25/DAU/month selection cap no longer constrain this scheme.
- Mini Program source and product changes follow that adopted owner, including actual coverage, provenance, commercial terms and costs. The current initial scale is 200 DAU; expected production capacity and unchanged 4-GB staging are owned by [deployment capacity](deployment/decisions-and-verification.md#current-capacity-target-200-dau-2026-10-02). The roughly CNY 820 / CNY 1080 monthly scenarios are historical assumptions, not the updated operating budget. Preserve the independent native App decisions.
- Product logic that uses external data, services or capabilities must fit their applicable commercial-use conditions. **Before adopting or integrating any new external data, service or capability, check commercial compliance; also recheck when extending an existing use.** Consult the [commercial compliance summary](external-capabilities.md#商业化合规速查), including permitted commercial uses, attribution, reuse/distribution, access entitlements and platform conditions. Record the decision, material conditions and official lookup links with the existing owner; unresolved permission is not approval to use. Supplier fields do not authorize new product content or changes to adopted design resources; keep detailed evidence in manifests and task records.
- Continuously calibrate Mini Program design style and UIUX principles from new resources and explicit user feedback. Update the existing design/Context owners as part of iteration and adoption; distinguish general preferences from page-specific choices. Read [design quality expectations](product-profile.md#mini-program-design-quality-expectation) and [calibration rules](context-maintenance.md#持续校准设计系统与用户偏好).
- Current Mini Program development scope includes the adopted terrain/icons/event-modal changes and whole-product UI/UX verification, Context alignment and missing implementation repairs; follow the [owning Screen Contract](areas/main/screen-contracts/wechat-miniapp.md#整体uiux与context对齐补开发). Design adoption does not establish implementation completion.
- Context owns intended product meaning and boundaries; code owns current implementation. Root DESIGN.md owns the existing confirmed visual profiles. User requirements and confirmed decisions remain applicable after workflow-tool retirement.
- Design resources are persistent: maintain one adopted version per scope through incremental changes, and clean up non-adopted alternatives in both Stitch and local resources when a requirement's pre-development work concludes. Follow [design-resource lifecycle](context-maintenance.md#design-resource-lifecycle); pending review is not adoption, and current editable sources/variants/dependencies must remain complete.
- Follow [cross-stage capability research](../AGENTS.md#cross-stage-capability-research) during requirements, UI/UX, product/technical Context work and implementation. Confirmed capability choices remain with their existing Context owners.
- Follow the user's [local preservation, explicit data uploads and batched commit policy](development-workflow/resources-and-artifacts.md#each-commit-binds-the-required-development-inputs): preserve necessary raw inputs locally, upload data only on the user's explicit upload request, and commit less frequently after coherent material repairs. Keep code/Context/Harness/input identities compatible and label deferred remote preservation honestly. Uploads, commit preparation and unrelated minor findings must not displace the current product priority; Git/CI success does not establish external-data delivery.
- After pulling or synchronizing code, [synchronize the current consumers' required data](development-workflow/resources-and-artifacts.md#receive-required-data-with-code-and-recover-missing-inputs) through the existing commands and authorized transfer tools. If local use later exposes missing data, locate, obtain and verify it before retrying. Context and the development skill direct this agent workflow; no additional synchronization script or custom Git/npm hook is adopted.
- Keep durable facts with their existing owner; reference exact sources rather than copying implementation. Task progress, logs and optional handoffs stay outside Context. Tiny Context does not manage task state or certify completion.

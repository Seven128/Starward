# Architecture Context

## System Boundary

- This repository owns the Starward product contract, visual design system, React Native application, modular API/workers/admin implementation, data-processing code, and verification harness for 《今晚去观星》.
- Weather, astronomy ephemerides, light-pollution data, maps, routing, location, push channels, and object storage remain replaceable boundaries. The current personal-trial profile may use qualifying free/non-commercial sources or isolated adapters; it must not imply purchased rights, production traffic, or external validation.
- Existing files under docs/design-system/ are retained static Open Design rollback/reference exports. They are not current visual inputs, runtime architecture, or a competing authority.

Model comparison changes confidence and explanation, never selects the clearest model. Active material official alerts remain independent hard blockers; an unavailable/expired alert feed makes a positive trip recommendation data-insufficient even when forecast fields exist. Every fused hour retains its contributing source identities, while source/model run, validity, interpolation and limitations remain visible through the shared BFF contract. Provider failure never selects a fixture, and production/trial startup fails closed unless the selected provider use and credentials are licensed/configured.
- Mini Program development has exactly one current implementation, evolved in place from the existing owners. Proposal labels such as V1/V2/V2.1.1 establish Source precedence, migration history, or a wire-contract identifier only; they never authorize parallel services, repositories, state stores, UI trees, test suites, feature branches, or compatibility product paths. Product UI and ordinary operator copy describe the current capability directly and never expose those internal proposal/version labels. The current accepted proposal replaces superseded product behavior in the same owner. Any temporarily retained old-schema adapter must be isolated at an external boundary, have no default route or product semantics, and cannot become a second source of truth.
- `data-pipelines/dark-sky/**` owns offline acquisition validation and publication of operator-acquired EOG VIIRS night-light rasters. It accepts only digest-bound, licensed, EPSG:4326 source objects plus declared cloud-free coverage, publishes immutable dataset identity, relative product bands, source-linked spot samples and bounded PostGIS map-grid cells in one transaction, and never labels those relative bands as Bortle or SQM. A missing real publication yields unavailable/partial product state rather than a generated geographic pattern or fixture fallback.
- `workers/miniapp-api/src/meteor-event-catalog.ts` owns the reviewed, versioned IAU/IMO meteor-event facts shipped with the current implementation; `AstronomyService` owns location/time projection from those facts. Runtime scraping is forbidden, and a peak/activity value may be shown only when the catalog carries an attributable reviewed model for that value. Dataset and algorithm versions are traceability identities inside this one implementation, not product variants.
- `workers/miniapp-api` owns two current, composable decision boundaries rather than one blended score: `SkyOpportunityEngine` evaluates normalized per-time-slice celestial, weather, darkness, moon, light-pollution and optional horizon evidence, keeps confidence separate from score, and owns the hysteresis/minimum-duration continuous-window segmenter; `TripDecisionEngine` accepts only a complete formal-spot evidence snapshot, references the resulting `SkyOpportunity`, and applies access, openness, road, legal and safety blockers before any suitability explanation. PostgreSQL persists digest-bound, immutable SkyOpportunity and TripDecision replay snapshots separately so a rule can be re-evaluated without overwriting its historical input or conflating the two conclusions. Client surfaces consume these server results and never recreate either rule set. The MapScene boundary projects a viewport-bounded, compact loaded timeline from those same hourly SkyReport rows: each frame carries only per-spot dynamic signals plus polygons for the one requested dynamic layer, while source-dated light pollution and other static layer metadata remain single-copy. The client may preview those frames locally, but release commits the sole Observation Context before refresh; neither preview nor callout may substitute the whole-night TripDecision for the selected-time SkyOpportunity. Rule/dataset identities are replay and traceability metadata inside the same implementation, not product variants.
- PostgreSQL/PostGIS is the sole current formal-spot truth. A server-owned, fail-closed publication policy evaluates the proposed final record—not only the requested status patch—and returns an attributable missing/invalid evidence list for identity, coordinate source, access/last road, parking, the eight facility states, openness/legal entry, night safety and hard blockers, horizon/open directions, site-media claim, source provenance, verification freshness, visibility policy and operator review. Production reads cannot project a spot as `PUBLISHED` unless this gate passes; source-code fixtures and all-`UNKNOWN` evidence never satisfy it.
- The same PostgreSQL owner accepts new operator-supplied locations only as `DATA_INSUFFICIENT` candidate records with explicit provenance. Authenticated admin application services and the project-owned CLI expose current completeness issues and edit the single evidence-backed record, including the route owner fields required by the publication policy (`lastRoad`, `parkingGuidance`, route state and source); the removed Mini Program demo Web console is not an owner. Candidate enrichment registers every newly referenced source in the same transaction and cannot bypass the completeness policy through direct database mutation. Only a freshly complete server assessment enables publication. Candidate intake never seeds production startup, never appears through formal-spot read ports, and never fabricates unavailable route, light-pollution, facility, safety, horizon or media facts.
- `workers/miniapp-api` also owns the authenticated contribution intake and moderation boundary. PostgreSQL stores user/admin reports, corrections, proposed places, upload-session identity and review history; a replaceable `MediaObjectStorePort` stores only MIME/size-validated, metadata-sanitized derivatives while raw client paths, EXIF and precise contributor coordinates are excluded from ordinary read models and logs. User submission, admin review, canonical fact merge and formal publication are distinct state transitions: neither approval nor an uploaded object may update the formal spot projection until operations explicitly merges attributable evidence and the existing completeness policy passes on the resulting record. Abandoned upload sessions expire and their objects are deleted; idempotency and contributor identity scope prevent duplicate or cross-user writes.
- The same identity boundary owns Settings account-data operations. A data export is a server-generated, identity-scoped, versioned JSON snapshot assembled from current durable records; it excludes session credentials, WeChat identity digests, internal object keys and raw media bytes, and the Mini Program never reconstructs the authoritative export from local cache. Account deletion is an idempotent server command with explicit confirmation: it removes the WeChat identity mapping, revokes every session, deletes mutable account preferences/library/plans/profile/import/media records, de-identifies retained moderation/publication evidence, and returns a deletion receipt before the client clears local state. Append-only review, merge, publication and audit evidence may remain only under the resulting unlinkable pseudonymous subject required for integrity; the UI must disclose that retention and cannot call local cache clearing an account deletion.
- Mobile navigation truth lives in one Expo Router route tree: a persistent five-tab navigator maps Tonight, Map, Trips, Sky, and Me to `/tonight`, `/map`, `/trips`, `/sky`, and `/me`, with a route-owned nested stack under each tab. A persisted destination preference may assist restoration, but it cannot become a second router or screen-identity source.
- Mobile development feedback uses that same React Native component/route tree through Expo Web or an installed development client. `tests/acceptance/start-mobile-web.mjs` and its session helper own the bounded Web/API process and restart-sensitive session identity. Browser diagnostics remain a support renderer, not a native runtime or visual authority; the archived page/control visuals cannot be used as current comparison baselines.
- `tools/long-task/verify-native-target.mjs` remains the single project Android Check executor and result aggregator. Its native verification-session module owns deterministic population planning, independent-device shard assignment, exact-input checkpoint identity and atomic fragment recovery; neither cached fragments nor diagnostic filters create another verifier, Authority, Check or completion state.
- The Android design-evidence module is a session-gated observation transport inside the same production React Native tree. One session-qualified launch establishes the current evidence session; bounded context switches may then retarget Control/Scenario attribution only when they present that exact session identity. Exact context/state acknowledgements expose only transport readiness: the verifier must still observe the production owner carrier, interaction and result in the same committed UI tree, and a missing carrier fails immediately after its acknowledged render context instead of triggering blind whole-page polling. These acknowledgements cannot activate in an ordinary user run, reset product authority, create evidence by declaration, or replace the unit's production-root journey.

Acceptance invokes that carrier with variable inputs, verifies committed database/file/native/external receipts, recreates the runtime against the same isolated data directory, reads state back, checks idempotent replay, and verifies invalid/failing operations cannot report success.

## Data / Control Flow

- The existing native App durable user flow remains conclusion → place selection → departure/observing window → route and risk → professional evidence → preparation → field use.
- The independent Mini Program durable flow is Map discovery and Finder `想去` favorite browsing → formal Spot Detail → hard-blocker-aware Tonight decision → Guides/Site/Spot Night → external navigation/favorite/plan → observation mode, with a separate My account-center branch for identity summary, Plan, Contribution and Settings. Detail and My converge on the same contribution child route; submissions remain provisional through owner moderation and never bypass the canonical spot publication gate. My does not duplicate favorite browsing, and Settings owns the sole observation-mode entry. Settings also owns identity-scoped departure-condition and contribution-status reminder intent in the existing revisioned `UserPreferences` record; intent never claims that a platform subscription was granted or delivered. Nearby-location preference maps to the same `ASK_ONCE | MANUAL_ONLY` truth, while orientation and precise contribution coordinates remain per-use platform/form consent rather than durable global grants. Settings data export is read-only and server-generated; account deletion is confirmed, idempotent, server-owned, revokes the active identity/session before the client clears local state, and discloses any de-identified integrity evidence that must be retained. Feature-disabled profile-link/import surfaces are absent from the current route tree rather than retained as an old product path. Only a formal `spot_id` can establish Spot Night context.
- Selected place, time window, route, arrival estimate, and risk are one coordinated state. Changes propagate to every surface that presents those facts.
- A Mini Program observation plan is saved against the caller's current server-resolved Observation Context. The BFF derives the plan's formal-spot context from that owner, preserves any validated map/user route origin in the versioned plan context snapshot, and restores it before estimating plan route nodes. Snapshot v1 remains read-compatible but cannot invent a missing route origin; new writes use v2. The client never submits route coordinates as independent plan truth, and a plan without a recoverable origin exposes route-unavailable state rather than fabricated distance or drive time.
- Visual mode is orthogonal to task state: planning, night, and red-light modes retain the same current place and workflow position.
- Mini Program day/night/observation modes are likewise orthogonal to route/domain state. Observation mode uses the closed Mini Program warm-red system and exits to the exact prior presentation context; it does not inherit native App token values.
- Selecting a primary tab changes the active route and rendered screen. Each tab owns its primary scroll or immersive canvas plus its nested navigation state; switching tabs never scrolls a shared page, jumps to a section anchor, or conditionally swaps pseudo-pages inside one root `ScrollView`. Tab-local route/scroll state is preserved independently while the versioned decision context remains shared across tabs.

## Design Rationale

- Authority is intentionally split by concern: Context defines what the product and surfaces must do; DESIGN.md defines how the visual system should look and feel; exported assets demonstrate or implement that system.
- This prevents generated CSS, JSON, or static kits from silently redefining the product contract.

## Constraints And Tradeoffs

- Mobile-first behavior and outdoor/low-light use make safe-area handling, reduced motion, contrast, and low-luminance field behavior architectural UI constraints. The native App profile requires `44px` touch targets; the selected Mini Program profile independently requires `88rpx` targets.
- Direct-manipulation state is split from committed domain state: gesture presentation may move continuously and be interrupted, while place/time/route/itinerary changes commit only to valid coordinated states and recover cleanly on cancellation or provider failure.
- Deep links activate the owning tab and nested route, while native Back first closes route-owned overlays and then pops only that tab's stack. Tab selection itself does not synthesize cross-tab Back history.
- Forecast and astronomy data are uncertain; provider data must not be presented as guaranteed truth.
- A Mini Program hard safety blocker is evaluated before score aggregation and forces the effective conclusion to “不建议”. The selected design resource's retained “推荐” heading under a blocker is a resolved Source conflict and is not production semantics.
- Sky-opportunity score and confidence are independent: missing critical inputs cannot be treated as zero or converted into a confident result, and a favorable sky window cannot override a formal spot's access, openness, legal, road or safety blocker. The primary result is a continuous observation window derived from the time grid, not an all-night average or a single instant.
- Shared `platform-boundary` code currently models only one native-App primary product and a limited auxiliary Mini Program. This is acknowledged technical debt: implementation must introduce a per-product carrier boundary or an independent Mini Program boundary without overwriting native-App semantics or duplicating provider/license truth.
- Professional density must use aligned matrices and progressive disclosure without overwhelming the primary decision.

## Verification Implications

- Context integrity is checked through the Tiny Context commands in project_context/areas/main/verification.md; specialized checks are routed from that default index to its on-demand verification nodes.
- DESIGN.md structure is linted separately from exported asset integrity.
- Active authority integrity is checked by `npm run design:system:verify`: it preserves the native App DESIGN→runtime projection and six-value observation palette while separately validating the selected Sky Canvas source digests, exact mode-role table, closed warm-red observation palette, contrast and accessibility contracts, provider lineage and App-profile non-inheritance. `npm run design:targets:verify` separately protects unchanged legacy archives; passing it does not reactivate their visual styling.
- Production UI verification must eventually cover representative mobile viewport, visual mode, key state, and long-content combinations; static kits alone cannot prove product behavior.
- Web/Fast Refresh and filtered native diagnostics shorten the repair loop, while only complete current-snapshot target-runtime aggregation can satisfy the Android Assertions. Parallel native execution is valid only across disjoint selected serials with one attributed worker lifecycle per device. Within a shard, one Condition/Mode unit may share its root-proved cold-start prelude while every Control and Scenario retains a separately reset, attributed observation; Final Gate does not consume repair-session checkpoints.
- A service class, endpoint, adapter declaration, generated report, or screen is not completion evidence by existence. Machine acceptance must execute the production path and its counterfactual must fail when the carrier, write, adapter invocation, or restart readback is removed.
- Mini Program acceptance additionally requires the same production candidate's deterministic checks, Taro builds, current WeChat DevTools observations, declared multi-size/mode/state/accessibility checks, and platform/device observations required by the current accepted Source and `target-miniapp-sky-canvas-current-constraint`. Its formal handoff preflight proves only selected input identity, declared Fact closure and implementation-feasibility Source consistency; it does not prove runtime conformance.

## Open Risks

- Official-source research and the current personal-trial profile establish qualifying free-first choices and a CNY 200/month ceiling, but purchases, commercial contracts, public redistribution, production accounts/traffic, representative devices, outdoor validation, legal/store approval, and production provider promotion remain future gates.
- A corrective audit found fixed responses, process-local repositories, metadata-only side effects, and declaration-only native boundaries in existing scaffolding. They must be replaced by durable production loops before any Outcome can be accepted.
- Windows-hosted delivery may not by itself establish the physical WeChat observations required by the current acceptance matrix, nor real provider, coordinate-authorization or real WeChat-identity facts. Those rows remain explicit blocking External Confirmations; they cannot be omitted or replaced by project pass/verdict rows, and the Goal cannot close while any required confirmation is pending.

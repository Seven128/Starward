# Architecture Detail: Runtime And Domain Components

This on-demand foundation node continues `project_context/architecture.md#component-map`. It owns the detailed cross-workspace runtime, provider, data, decision, publication, contribution and identity component boundaries; the parent remains the architecture entry and routing owner.

## Runtime And Domain Components

- Remote release keeps development/test/acceptance state separate from two distinct cloud environments. Staging and production use separate compute/runtime identities, mutable data, credentials, queues, caches, buckets, backups and Mini Program bindings; the same immutable backend image digest is promoted after staging, while each environment-bound WEAPP bundle retains its own fingerprint and platform credential.
- Mini Program production code is owned by `apps/wechat-miniapp/**`; its production journeys are the real WEAPP routes and `tools/miniapp/**` owns isolated build, WeChat DevTools observation and platform lifecycle. No browser/H5 Mini Program implementation or acceptance proxy exists. The package consumes a generated projection of only the Mini Program DESIGN profile and calls shared contracts/BFF through explicit client ports. It never directly calls external weather/map/media/content providers or imports the native App token module.
- `workers/miniapp-api/**` owns the Mini Program modular-monolith BFF and server-side Port/Adapter composition; `packages/miniapp-contracts/**` owns its shared typed API/domain boundary. It remains independent from the native App API composition, and any later consolidation must preserve these domain identities, capability gates and failure semantics instead of making the client call providers directly. Explicit `SAMPLE_DATA` fixture adapters are permitted only for deterministic tests or an explicitly identified development/acceptance scenario; every current non-test startup and commercial startup rejects that composition. A real-provider failure may expose attributable cache, partial, expired or unavailable state, but it never selects a fixture as the product success path.
- The generated public Mini Program transport manifest is limited to the HTTP methods accepted by WeChat `wx.request`: `GET`, `POST`, `PUT` and `DELETE`. `tools/miniapp/generate-miniapp-sdk.mjs` rejects another method such as `PATCH` before client generation; API routes serving this public manifest use the corresponding supported method so browser or Node-only tests cannot mask a WEAPP dispatch failure.
- Inside that BFF, one server-owned weather-composition boundary—not the client and not the separate native-App API—owns the current observing-night weather truth. For the China trial path it combines the QWeather coordinate-grid primary timeline and official alert feed with Open-Meteo Best Match layered-cloud evidence plus explicit ICON, GFS, ECMWF IFS and AIFS model runs. QWeather total cloud and operational fields remain primary when available; Open-Meteo may fill only the declared layered-cloud/model-evidence roles, and may become the timeline only through an explicit `PRIMARY_FALLBACK` state. Model comparison changes confidence and explanation, never selects the clearest model. Active material official alerts remain independent hard blockers;
  an unavailable/expired alert feed makes a positive trip recommendation data-insufficient even when forecast fields exist. Every fused hour retains its contributing source identities, while source/model run, validity, interpolation and limitations remain visible through the shared BFF contract. Provider failure never selects a fixture, and production/trial startup fails closed unless the selected provider use and credentials are licensed/configured.
- Mini Program development has exactly one current implementation, evolved in place from the existing owners. Proposal labels such as V1/V2/V2.1.1 establish Source precedence, migration history, or a wire-contract identifier only; they never authorize parallel services, repositories, state stores, UI trees, test suites, feature branches, or compatibility product paths. Product UI and ordinary operator copy describe the current capability directly and never expose those internal proposal/version labels. The current accepted proposal replaces superseded product behavior in the same owner. Any temporarily retained old-schema adapter must be isolated at an external boundary, have no default route or product semantics, and cannot become a second source of truth.
- Search filter state contains the current 16 enabled conditions plus one validated driving-range parameter with time/distance mode and separately remembered minute/kilometre limits. The Mini Program store owns committed, draft and opening-snapshot copies; the BFF evaluates only the active mode against attributable route evidence. Hidden account ranking preferences do not control this filter, and straight-line distance never satisfies it.
- `data-pipelines/dark-sky/**` owns offline acquisition validation and publication of operator-acquired EOG VIIRS night-light rasters. It accepts only digest-bound, licensed, EPSG:4326 source objects plus declared cloud-free coverage, publishes immutable dataset identity, relative product bands, source-linked spot samples and bounded PostGIS map-grid cells in one transaction, and never labels those relative bands as Bortle or SQM. A missing real publication yields unavailable/partial product state rather than a generated geographic pattern or fixture fallback.
- `workers/miniapp-api/src/astronomical-event-catalog.ts` composes the reviewed, versioned IAU/IMO meteor facts from `meteor-event-catalog.ts` with the 2026 solar/lunar eclipse occurrences deterministically calculated by the pinned Astronomy Engine adapter. The same server astronomy boundary owns location/time projection; consumer code never calculates an ephemeris or scrapes providers. A peak/activity value may be shown only when the catalog carries an attributable reviewed model for that value. Dataset and algorithm versions are traceability identities inside this one implementation, not product variants.
- `packages/astronomy-core/**` is the shared astronomy calculation and static-catalog extension point. A reproducible `data-pipelines/star-catalog/**` acquisition step may derive a magnitude-limited Gaia DR3 bright-star pack only from the declared official query, release, fields and credit/license terms; the committed pack and manifest are immutable checksum-bound inputs and are never refreshed during a user request. `workers/miniapp-api/AstronomyService` projects that pack for the authorized WGS84 observing location and every returned SkyReport time slice, preserves catalog/algorithm/source identity, and emits a compact scene through `packages/miniapp-contracts/**`. The Mini Program may transform returned azimuth/altitude into canvas and sensor-relative pixels, but it does not own equatorial calculation, fetch Gaia directly, invent stars or use a rendered image as sky data. A missing or invalid pack fails closed at build/startup; a missing scene remains explicitly unavailable without deleting independently valid targets or weather evidence.
- `workers/miniapp-api` owns two current, composable decision boundaries rather than one blended score: `SkyOpportunityEngine` evaluates normalized per-time-slice celestial, weather, darkness, moon, light-pollution and optional horizon evidence, keeps confidence separate from score, and owns the hysteresis/minimum-duration continuous-window segmenter; `TripDecisionEngine` accepts only a complete formal-spot evidence snapshot, references the resulting `SkyOpportunity`, and applies access, openness, road, legal and safety blockers before any suitability explanation for consumers that still expose those outputs. Mini Program discovery and its information panel do not display combined recommendations or the retired recommendation filters; underlying safety facts and navigation restrictions remain effective. PostgreSQL persists digest-bound, immutable SkyOpportunity and TripDecision replay snapshots separately so a rule can be re-evaluated without overwriting its historical input or conflating the two conclusions. Client surfaces consume these server results and never recreate either rule set.
  The MapScene boundary projects a viewport-bounded, compact loaded timeline from those same hourly SkyReport rows: each frame carries only per-spot dynamic signals plus polygons for the one requested dynamic layer, while source-dated light pollution and other static layer metadata remain single-copy. The client may preview those frames locally, but release commits the sole Observation Context before refresh; neither preview nor callout may substitute the whole-night TripDecision for the selected-time SkyOpportunity. Rule/dataset identities are replay and traceability metadata inside the same implementation, not product variants.
- PostgreSQL/PostGIS is the sole current formal-spot truth. A server-owned, fail-closed publication policy evaluates the proposed final record—not only the requested status patch—against the core publication criteria in the next paragraph, and returns attributable missing/invalid evidence. Optional enrichment is not a second publication threshold. Production reads cannot project a spot as `PUBLISHED` unless this gate passes; source-code fixtures and all-`UNKNOWN` evidence never satisfy it.
- The same PostgreSQL owner accepts new locations as candidate records with explicit provenance. The owner revision of 2026-09-07 separates minimum intake, core publication readiness and optional enrichment. Minimum intake captures name/location, openness, legal entry, night safety and gate/responsible-party contact status; unknown answers may be submitted as leads without being treated as verified. A fresh core publication assessment requires an identifiable valid point, attributable current evidence for openness/legal entry/night safety and explicit danger, the existing coordinate visibility policy, and an audited owner review. Missing photographs, public phone numbers, ordinary facility details, route estimates, light-pollution or horizon enrichment alone no longer makes a verified core record unpublishable. Known serious road/access hazards remain material blockers; closed/prohibited/dangerous conditions must retain their restrictive lifecycle/action semantics, never become a positive or unrestricted public state.
  Authenticated operations still merge attributable evidence and register new sources transactionally; submission, approval and publication remain separate and cannot be bypassed by direct writes. The existing `spot-completeness-policy.ts` implements this core threshold in the shared publication assessor: optional enrichment absence is not a publication blocker, while core claims require current evidence bound to the same spot and a usable source. Asserted site media still requires its verification and provenance. This code does not establish deployment or current database acceptance. Candidate intake never seeds production startup, appears as a formal point before review, or fabricates missing facts. No separate manual completeness workflow or second canonical record is introduced.
- `workers/miniapp-api` also owns the authenticated contribution intake and moderation boundary. PostgreSQL stores user/admin reports, corrections, proposed places, upload-session identity and review history; a replaceable `MediaObjectStorePort` stores only MIME/size-validated, metadata-sanitized derivatives while raw client paths, EXIF and precise contributor coordinates are excluded from ordinary read models and logs. User submission, admin review, canonical fact merge and formal publication are distinct state transitions: neither approval nor an uploaded object may update the formal spot projection until operations explicitly merges attributable evidence and the existing completeness policy passes on the resulting record. Abandoned upload sessions expire and their objects are deleted; idempotency and contributor identity scope prevent duplicate or cross-user writes.
- The same identity boundary owns Settings account-data operations. A data export is a server-generated, identity-scoped, versioned JSON snapshot assembled from current durable records; it excludes session credentials, WeChat identity digests, internal object keys and raw media bytes, and the Mini Program never reconstructs the authoritative export from local cache. Account deletion is an idempotent server command with explicit confirmation: it removes the WeChat identity mapping, revokes every session, deletes mutable account preferences/library/plans/profile/import/media records, de-identifies retained moderation/publication evidence, and returns a deletion receipt before the client clears local state. Append-only review, merge, publication and audit evidence may remain only under the resulting unlinkable pseudonymous subject required for integrity; the UI must disclose that retention and cannot call local cache clearing an account deletion.
- Mobile navigation truth lives in one Expo Router route tree: a persistent five-tab navigator maps Tonight, Map, Trips, Sky, and Me to `/tonight`, `/map`, `/trips`, `/sky`, and `/me`, with a route-owned nested stack under each tab. A persisted destination preference may assist restoration, but it cannot become a second router or screen-identity source.

## Mini Program Product And Plan Flow

Plan detail and editor context restoration is local to the mounted plan query. It may use the map context as an initialization source, but does not write its restored snapshot back into the map's committed Observation Context. This preserves the opener's selected place/time across child navigation; plan save still uses the local context and server-side re-resolution. The map's own restoration coordinator remains unchanged. A plan opens its place information through the registered `spot/plan/index` page in the existing `spot` subpackage. That page gives the shared spot-detail renderer an explicit plan-local Observation Context override, so the shared renderer preserves the plan's place/time while the committed Map context and the native return stack remain untouched; ordinary spot-detail consumers continue to use the committed Map context.

The formal Map information panel's plan entry uses `features/spot/spot-plan-route.ts`: zero associated plans opens a spot-prefilled new editor, one opens its detail, and multiple open the spot-filtered list. The editor resolves an explicitly supplied spot through the existing service into a local context without replacing the map opener's context. New-plan drafts opened for a specific spot use an account-and-spot scope in `services/local-draft-keys.ts`; generic new drafts and existing-plan keys remain compatible, and account erasure recognizes both forms. These are routing/data boundaries, not evidence of verified native navigation or completed panel rendering.

User-authored plan reminder content is carried by the existing revisioned plan aggregate, not a second local checklist store. `packages/miniapp-contracts/src/plan-reminders.ts` owns the five-group/twenty-item validation and strips non-contract fields; drafts may retain unfinished text while submitted content must validate. Reminder IDs and item IDs remain stable across edits. Save recovery includes this content in the account-bound intent identity. An older client omitting existing reminder content is rejected rather than erasing it. `notifyOnWechat` expresses intent only: subscription authorization, schedule versions and delivery receipts remain server-owned responsibilities and are not established by saving this field.

Checklist completion uses `PUT /me/observation-plans/{planId}/checklist-completion` and the same plan aggregate revision/transaction. It changes only the identified item's explicit completion value, preserving the saved context snapshot, times and other user content without requiring Observation Context or forecast availability. Retry receipts are scoped by account, plan and item; stale revisions and missing items are rejected. The client publishes confirmed results through the existing plans query cache and fences account changes. Completion writes currently produce the existing plan update event; reminder scheduling must compare scheduling-relevant content rather than treat every checklist tick as a changed departure or authorization.

Mini Program plan navigation has an all-dates list at `content/plan/list/index` and an independently mounted editor at `content/plan/edit/index`; the editor currently composes the existing `content/plan/detail/index.tsx` form owner instead of duplicating its draft, revision and account logic. Explicit new intent takes priority over cached plans or an obsolete plan-id parameter. List rows and My rows keep the chosen plan identity; the all-plans header targets the list. Confirmed editor saves return to the opener, while failed navigation retains the successful save and exposes retryable navigation feedback. These route boundaries do not establish completion of the adopted detail rendering, reminder scheduling or runtime navigation verification.

Account display identity belongs to the authenticated Mini Program account, separately from preferences, external profile links and the WeChat identity digest. Nickname read/write uses `GET /me/profile` and `PUT /me/profile/nickname`; account avatar read/write uses the authenticated `/me/profile/avatar` pair. `packages/miniapp-contracts/src/account-profile.ts` owns nickname normalization plus the avatar's content version, MIME and 1–2.5 center zoom. `database/miniapp/migrations/011_account_profile.sql` stores nickname and the shared optimistic profile revision; migration 016 adds one active private avatar object reference and metadata. Avatar uploads accept bounded JPEG/PNG/WebP data, verify declared size and image structure, strip supported private metadata before writing to the existing private media store, and replace the previous object only after the revisioned profile write succeeds. Same-intent retries replay the saved record; altered payloads using the same key and stale revisions conflict. The client requests album or camera only after the avatar action, previews a circular center crop, and commits only on `使用此头像`; cancellation, failure and account changes preserve the saved identity. Account export includes profile metadata but not image bytes. Account deletion queues the active avatar object with other private media, clears profile fields and erases scoped replay payloads. This is app-owned identity and never writes the user's WeChat profile.

- `AstronomyService` reuses public formal-spot calculations after validating current publication facts and normalized weather validity. Its cache identity includes effective spot, exact time, profile/event, algorithm/catalog/rule and weather inputs; each result binds the current caller's context and never retains a private route origin in shared work. Map and overview request decision evidence without constructing star scenes; full-sky responses add the existing exact-time scene and target frames. `astronomy-service.ts` owns retention limits and expiry policy, while `provider-deadline.ts` bounds transport/body waits and lets a cancelled waiter leave shared work available to other callers. An expired deadline is attributable unavailable evidence and cannot make official-warning or publication gates permissive.

- Mini Program floating feedback consumes the existing shared notification queue from one host inside each actual page's theme root, including alternate page-state roots. A hidden page does not present or announce that host. The App component supplies providers and launch behavior, not a cross-page visual overlay: WEAPP renders separate page trees. Hosts never introduce another queue, duplicate a transaction or enter scrolling/navigation containers; the existing notification family owns arbitration and safe-area presentation.

- `AstronomyService` owns one exact presentation time axis per SkyReport. A valid committed Observation Context instant is not silently rounded to the nearest night sample: where calculation is available, it is included as a real calculated sample alongside the regular night cadence. Each returned hourly instant has an explicitly time-bound target frame as well as its catalog-star frame; top-level current targets describe the exact committed instant. The Mini Program selects the same frame instant for time-ruler preview, catalog stars and target directions, and missing exact frames remain unavailable rather than borrowing another instant or recalculating celestial coordinates on the client. Preview remains transient and cancellation restores the committed context; only the existing context update commits time. Payload/cache identity and opportunity-window behavior must be regression-checked when the presentation axis changes. No new location/time store, runtime provider, or persisted pose is introduced.

- Observation date and clock time are two controls over that same revisioned Observation Context. A date commit keeps the selected place and its IANA timezone, preserves the local clock, derives the corresponding starting observation night (including the previous-night key for after-midnight civil times), and atomically updates the local date, UTC instant, night bounds and fingerprint. Map dynamic layers, the Map spot-panel astronomy section and full Sky consume the same shared date-control semantics; only the current context update may publish the result, and superseded requests cannot overwrite a newer context. The LIGHT map layer remains tied to its published annual dataset and therefore hides both date and time controls instead of implying a date-sensitive result.

- Lunar presentation remains an attributed projection of the same Astronomy Engine calculation. Every real hourly sample carries the continuous geocentric phase angle plus one of eight semantic phase states; the selected report separately exposes that instant's illumination, topocentric altitude and the observer-bound rise/set search results. `MapSceneTimeFrame` carries only the semantic phase needed by the spot-panel ruler, while `MapSpotEvaluation` carries the selected lunar facts and source. The panel maps those states to the adopted symbolic assets; Map dynamic-layer time controls omit the lunar slot entirely. A null rise/set after a completed search means no event in that search interval, while unavailable report/evaluation state remains missing data rather than an invented event.

- The Map spot-panel astronomy chapter consumes the existing full `SkyReport` query for its current formal spot and Observation Context instead of widening the compact MapScene payload or recalculating facts on the client. Weather, lunar and target presentation select only an exactly matching hourly/target-frame instant; a missing exact slice remains unavailable. Satellite night-light evidence stays with `SpotSummary.lightPollution`, retains its estimate label, radiance unit and source, and never becomes a calibrated Bortle/SQM claim. Material weather alerts remain visible beside the affected evidence, while model provider/update/consistency and full source disclosure keep their existing owners. Under Skyline, the panel's vertical `scroll-view` exposes its chapters as direct children so native list virtualization and chapter anchors do not discard the whole document after scrolling; one wrapper must not enclose the entire scroll document.

- The independent Mini Program durable flow is Map discovery → dedicated Search/filter with `想去` favorite browsing → formal spot selection (plus authorized private draft/pending selection under the Map contract) → the Map-parallel basic-plus-astronomy information panel → objective route/facility/safety/guide/source and astronomy evidence → external navigation/favorite/share/contribution or `云观星` full-sky orientation. A separate My account-center branch owns identity summary, Plan, Contribution and Settings. The information panel opens the feedback editor, Map opens new-place intake, and My opens account-scoped creation and feedback records including drafts; all retain the existing contribution owner; submissions remain provisional through owner moderation and never bypass the canonical spot publication gate. My does not duplicate favorite browsing, and Settings owns the sole observation-mode entry. Settings also owns identity-scoped departure-condition and contribution-status reminder intent in the existing revisioned `UserPreferences` record; intent never claims that a platform subscription was granted or delivered.
  The current routes keep one contribution account-record owner while separating the registered WEAPP page entries: My passes `manage=1` to the two-group record manager; new-place creation remains on the mutable contribution editor; a formal spot opens `content/spot-feedback/index`. The dedicated formal page is required because importing a registered Taro page module through another subpackage produced an unresolved `wx://not-found` component in the official runtime. The manager derives creation/feedback status from submission, merge and publication axes and opens immutable attempts without turning review acceptance into formal publication.
  The adopted Mini Program Settings removes spot-selection preference editing and the in-app reduced-motion switch; this is a client surface retirement, not authorization to delete persisted preference records or remove platform reduced-motion adaptation. Existing production preference fields await migration. Nearby-location preference maps to the same `ASK_ONCE | MANUAL_ONLY` truth, while orientation and precise contribution coordinates remain per-use platform/form consent rather than durable global grants. Settings data export is read-only and server-generated; account deletion is confirmed, idempotent, server-owned, revokes the active identity/session before the client clears local state, and discloses any de-identified integrity evidence that must be retained. Feature-disabled profile-link/import surfaces are absent from the current route tree rather than retained as an old product path. A formal spot or current-account submitted pending proposal from the information panel can establish typed full-sky context; drafts and arbitrary MAP_POINT input cannot bypass that entry/authorization.
- A Mini Program plan is saved from its own submitted formal spot and local observing time. The existing BFF re-resolves those inputs through Observation Context; the supplied browsing context provides a recoverable route origin, not an overriding destination/time. The BFF preserves any validated map/user route origin in the versioned plan context snapshot, and restores it before estimating plan route nodes. Snapshot v1 remains read-compatible but cannot invent a missing route origin; new writes use v2. The client never submits route coordinates as independent plan truth, and a plan without a recoverable origin exposes route-unavailable state rather than fabricated distance or duration.

## Mini Program Decision Constraints

### Astronomical event ingestion and network boundary

Confirmed 2026-09-08: the current service cannot access overseas APIs. Consumer requests and scheduled jobs on that service must not depend on overseas connectivity, a developer workstation proxy, or clients fetching providers. An overseas domain is not evidence that a VPN is universally required; reachability must be checked from the intended execution environment. Current network limitation is a user-provided deployment constraint, not a measured diagnosis of every source.

Use one background ingestion pipeline for scheduled retrieval and authenticated operator import. Prefer authoritative sources reachable from the deployed service. Domestic candidate: [Purple Mountain Observatory almanac and eclipse forecasts](https://pmo.cas.cn/xwdt2019/kpdt2019/202203/t20220309_6386774.html), which publishes 2026 calendar material and dated solar/lunar eclipse forecasts. This establishes published material, not a stable complete JSON API, permission for bulk reuse, or current production reachability. IMO annual meteor calendars remain an attributable source for existing records; [USNO API documentation](https://aa.usno.navy.mil/data/api) describes an annual solar-eclipse list but limits its documented local-circumstance calculator to 2017–2024. Neither is a currently reachable production dependency. Do not assume one provider covers all event types or local visibility.

Default intended cadence is a configurable weekly update check, with bounded retry/backoff and a manual rerun; seed an attributable published catalog first. Sources have independently recorded coverage, terms/attribution, reachability, parser/schema version and automatic-publication eligibility. Fetch only allowlisted sources with conditional requests when supported, bounded downloads and timeouts. Preserve source URL, release/retrieval times, source-file hash, parser version, time scale/timezone and original precision. Normalize occurrence identity, compare changes and validate schema, temporal ordering, units, source coverage and duplicate/conflicting records. Never turn an ambiguous date or missing peak time into invented precision.

User-approved publication rule: stable structured feeds may publish automatically after validation and comparison with a previously approved baseline. First onboarding, parsing/schema failures, conflicting evidence, unexpected deletions/coverage collapse or materially changed critical times go to operator review. Critical-change rules are source/type-specific, versioned and approved on onboarding; until defined, changed critical times require review. A malformed or empty fetch cannot replace the current catalog. PDF/HTML extraction is a candidate until its adapter and interpretation are approved; model-generated extraction alone is not sufficient to publish scientific facts.

Stages are retrieve/import → candidate normalization and diff → validated automatic publication OR operator review → atomic version publication. Reuse the authenticated operations boundary and PostgreSQL/versioned dataset owner; both paths use the same validator, stable identities and idempotency. Keep prior versions and audit actor/source/reason, support rollback, and invalidate location/time projections by catalog plus algorithm version. Updating an occurrence never silently rewrites a user's saved observing/departure times. Operator import accepts bounded documented data packages with provenance; uploading a file alone does not publish it or execute embedded code.

Overseas-only automatic retrieval is possible only if a separately configured collector can reach the source and transfer a validated, authenticated/versioned package to a domestic endpoint or store reachable by production. It is an optional future deployment, not an installed collector, proxy purchase or workaround assumed to exist. The collector handles public event data only, not user plans or locations. Without such connectivity or a domestic source, retain the existing catalog and use operator import for new data; fully automatic freshness cannot be promised. Failure creates an operational update issue while consumer reads use the last published version with coverage/freshness semantics; outside coverage is unavailable, never “no events”.

The current implementation extends the code-shipped reviewed catalog with one shared catalog owner, PostgreSQL migration `017_astronomical_event_catalog_pipeline`, authenticated source/import/review/publish/rollback operations and the existing BullMQ worker. The worker uses a configurable bounded interval (seven days by default), conditional HTTPS retrieval, the shared package validator/diff policy and existing retry/dead-letter replay. Public event reads, plan identity validation, Observation Context fingerprints and astronomy report cache inputs all read the active catalog version; an unavailable source retains the reviewed built-in baseline or last published version. No domestic source adapter or overseas collector is configured by default, so automated freshness still depends on an operator-approved reachable structured source.

## Cloud-sky progressive imagery

The Mini Program's shared zoned-date owner must not assume Android WeChat implements `Intl.DateTimeFormat.formatToParts`. For the product's supported `Asia/Shanghai` and `Asia/Hong_Kong` dates in 2000–2100 it may use the equivalent fixed UTC+08:00 calendar/clock fallback; invalid input, other zones and dates outside that bounded range fail closed. Map, shared observation controls and Sky context gates reuse this owner instead of constructing their own `Intl` formatter.

The production Mini Program keeps the existing native CanvasContext renderer and one astronomy/camera owner; Aladin Lite and Stellarium Web Engine are not runtime dependencies because their DOM/WebGL/WASM assumptions do not fit the native WEAPP page. The checked-in `opengc-messier-deep-sky.v1` pack is built from OpenNGC v20260501 at pinned commit `36cb178a0f69dba8bfc03a99c10512831edf1c6b` under CC BY-SA 4.0. It contains the 51 Messier cross-identified galaxy/nebula rows admitted by the declared OpenNGC types, with stable `M:<number>` identity, ICRS J2000 center, angular extent and attributable manifest. Astronomy-core projects each row for the exact observer instant and supplies center/north/east tangent samples; this remains independent of the Hipparcos pack so either catalog can fail closed without corrupting the other.

`GET /v2/celestial-objects/:reference/image?level=OVERVIEW|MEDIUM|DETAIL` is the same-origin BFF boundary for processed NASA SkyView WISE 12 µm imagery. It requests J2000, TAN, JPEG, LogLog and Lanczos3 products on demand; accepts only catalog identities; validates content type, JPEG framing and a 4 MiB limit; coalesces identical work; caps upstream concurrency at two; and keeps a 32-entry seven-day memory LRU. Fields are `clamp(axis*3, 2°, 4°)` at 256px, `clamp(axis*1.5, .75°, 4°)` at 512px and `clamp(axis*.6, .25°, 2°)` at 512px. The 4° overview ceiling is deliberate: an 8° M31 request repeatedly exceeded the 30-second provider budget, while 4° still covers its roughly 3° major axis and completed in the runtime trial. Server request budgets are 35 seconds around a 30-second upstream deadline. This is processed archival infrared survey data, not live sky, current weather or a visibility promise; the client always discloses survey/band.

The client changes angular field of view from 45° down to 1.5° by pinch, keeps coordinates/time/sensor ownership fixed, and requests imagery only for an explicitly selected deep-sky object once the field is 15° or narrower. It writes the bounded binary response to `USER_DATA_PATH`, retains an already-present coarser image while a finer level loads, aborts superseded network work and draws via the center/north/east affine registration with SkyView north-up/east-left handedness. Observation warm-red mode suppresses survey imagery. Loading, retryable failure, source and maximum-resolution states remain lightweight overlays; the default 45° view has no persistent gesture tutorial. Official WEAPP proves request/write/draw API availability and the M31 load/retry state, but its unavailable direction sensors cannot prove physical registration, jitter, memory pressure, lifecycle recovery or target-device frame timing. Those remain device acceptance work; no manual heading substitute or generated imagery is introduced.

## Celestial object selection and lazy information

The current production slice extends the existing astronomy-core catalog pipelines, BFF astronomy/application adapter and miniapp-contracts while keeping projection/ephemeris on the current astronomy owner and selection/rendering in the sky client. It introduces no feature import into shared contracts, second client ephemeris, notification platform or per-object remote text generation. Bright stars and Messier deep-sky objects have separate source manifests and failure boundaries but share stable selection, modal and canvas-camera responsibilities.

- Identity: `hipparcos-bright-stars.v1` is the bounded production bright-star pack: all 1,627 rows returned by the official CDS VizieR `I/239/hip_main` query for `Vmag=-2..5.0`, with 425 current IAU WGSN proper names joined offline by the WGSN-published HIP identifier. The checked-in manifest binds the exact query inputs, retrieval time, response hashes, output hash, row/name counts and source notices. Each scene entry carries stable string reference `HIP:<number>`, original HIP source ID, nullable name, V magnitude and B−V colour index with bands stated explicitly. J1991.25 ICRS proper motion is propagated before the existing EQJ→EQD→horizontal projection. Pack order and `catalogIndex` remain frame-local; clients resolve through the matching catalog entry and never coerce identifiers to unsafe numbers or join by name/proximity. Sirius, Vega and Polaris are mandatory pack regressions. Solar-system IDs remain under the ephemeris owner. Galaxy/nebula identity is supplied separately by the pinned OpenNGC Messier pack described above.
- Picking: the sky client publishes a bounded identity snapshot only after the native canvas draw callback, containing only catalog objects actually projected and painted for that exact frame/catalog/hash/camera. Selection rejects a stale identity, applies bounded hit tolerance and deterministic distance→brightness→reference ordering, and offers at most four choices for overlaps. Pinch, drag and cancellation cannot become a tap. Sparse bright proper-name labels and a 24-at-a-time user disclosure share the same modal without creating a DOM node or request for every catalog row. The list is computed only while disclosed so high-frequency pose renders do not repeatedly sort the visible catalog.
- Content: `GET /v2/celestial-objects/:reference?locale=zh-CN` accepts stable `HIP:<number>` and admitted `M:<number>` references. HIP results return manifest-bound identity, HIP/HD aliases, V magnitude, B−V and spectral type; Messier results return type, NGC/common aliases, V magnitude where available, axes and position angle. Sirius, Vega, Polaris, M31 and M42 have small reviewed Chinese introductions and return `READY`; other known rows return `BASIC_ONLY` rather than inventing prose. Unknown or malformed identities fail closed. Static facts and narrative remain separate from place/time-dependent apparent position and observing evidence.
- Retrieval: only an explicitly selected identity starts the static information query. React Query deduplicates by reference/locale, while the BFF keeps a bounded 256-entry value cache keyed by stable identity and the content/catalog revision. Pose and time updates do not refetch prose. Closing/unmounting or selecting another object aborts the current request; response ownership prevents late data from replacing another object or reopening the modal. The current data is a local checked-in projection, so it performs no runtime third-party lookup and has no private observing context. Any later SIMBAD/editorial adapter must retain the original timeout, sanitation, rate/cost, negative-cache and attribution constraints below.
- Sources: [SIMBAD](https://simbad.cds.unistra.fr/simbad/) is a candidate for extrasolar basic data/cross-identification and bibliography, not a universal Chinese encyclopedia or solar-system ephemeris. Assess coverage, exact access/redistribution terms, deployed connectivity, request budget and cache rights before selection. Narrative editorial sources and survey image licensing are separately verified. Do not perform one external query per star/frame, bulk import without terms review, or promise introductions for every point because a catalog entry exists.
- Verification completed for this slice: both catalogs project exact hourly frames under the existing 1 MiB scene limit; catalog/version/hash changes invalidate scene caches; malformed/duplicate/oversize packs fail closed; stable HIP/M lookup and HTTP image headers/bytes have regressions; canvas tests cover exact displayed identity, stale frames, deterministic overlap order and pinch/drag/cancel rejection. Official WEAPP runtime inspection has shown a real 792-star frame plus five product targets and 833 catalog objects, deep-sky-first disclosure, M31 modal, pinch from 45° to 15°, retryable provider failure and successful `request`→filesystem image readiness with an empty error console. WXML/WXSS compile checks pass. Remaining acceptance is physical-device pose/registration and point picking, assistive focus return, warm-red/long-content/error interaction, progressive-level retention under interruption and device performance.

## Shared material rendering boundary

The first production Mini Program slice maps the shared LiquidGlassSurface responsibility to the global `components/liquid-glass-surface.scss` material class used by both the My plan card and celestial detail. It owns theme-aware translucent surface, border and solid reduced-transparency fallback only; pages continue to own geometry, content, modal and plan state. A React wrapper was rejected because Taro required-components lazy loading emitted an unresolved cross-subpackage component in the official runtime. Keeping one global style owner preserves the shared material contract without introducing that package boundary. Web candidate material.css/material.mjs remains a design demonstration rather than production WEAPP code.

The adopted shared spot-card contract is mapped in the same way: global `components/spot-identity-card.scss` is the single production owner for the 90px card geometry, region/name/address typography, attributable full-card media gradient, radius and pressed/reduced-motion behavior. Search supplies formal spot identity, attributable media and selection; contribution records supply their own immutable-attempt status extension below the base card. Missing address or media stays absent. The two subpackages keep minimal local WEAPP markup because both an imported JSX-returning renderer and a React wrapper failed in the official runtime (empty descendants and unresolved `wx://not-found`, respectively); they must keep the shared class structure and may not fork visual rules or move review/query state into the style owner. Reassess only when the actual Taro/WEAPP required-components boundary can load one cross-subpackage wrapper without the current failure.

Use the actual underlying composition for transmission/refraction, never a screenshot copy of the sky or duplicated DOM business content. Evaluate native/platform support and suitable established rendering before selecting the production adapter; browser SVG backdrop-filter support does not certify WEAPP. Resize-bound maps/filter IDs and resource cleanup belong to the adapter; do not regenerate maps per sensor frame or let observers/listeners accumulate after close/navigation. Bound GPU/memory work, preserve readable solid/reduced-transparency and warm-red behavior, and verify both consumers with dynamic backgrounds, scrolling, resizes, long content, reopening and lifecycle restoration.

Selection is staged, not deferred until whole-page implementation. The current production slice is the readable translucent/fallback path; official WEAPP simulator evidence covers both consumers and long celestial content, but does not establish native backdrop transmission, optical refraction, device performance or Android/iOS parity. The HTML candidate explores profile-derived SVG displacement, informed by [Kube's optical reconstruction](https://kube.io/blog/liquid-glass-css-svg/). This is a visual/mechanism reference, not an Apple implementation or WEAPP dependency. SVG backdrop filtering is not presumed portable. A shader route is a conditional alternative only if the actual scene can supply a supported texture/composition input; a Web demo that generates its own background does not satisfy live page sampling. DOM-capture libraries such as [ybouane/liquidglass](https://github.com/ybouane/liquidglass) are not a direct fit for the current no-copy composition boundary. Do not add Expo/Skia/CanvasKit or a DOM-capture pipeline solely to imitate a showcase.

Before integrating the production material broadly, compare the remaining supported path with the readable fallback in a small WEAPP slice containing both actual consumers on iOS and Android. Use matched viewport, backdrop and content: inspect transmission/curved-edge displacement and text contrast over bright, dark and changing backgrounds; record frame-time distribution, dropped frames, memory and repeated-open/close behavior on named representative devices. Include sky movement, My scrolling, long text, warm red, reduced transparency/motion, background/foreground restoration and rendering failure. Set acceptable performance budgets against the existing scene before selection, then carry the result and decisive tradeoffs here. A successful HTML preview, API syntax check or a single static screenshot does not select the renderer. If no path fits, expose the explicit fallback and the remaining visual gap; do not rename it as equivalent refraction. Device experimentation is later implementation work, outside the current Context/design-resource scope.

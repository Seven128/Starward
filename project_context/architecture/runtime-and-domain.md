# Architecture Detail: Runtime And Domain Components

This on-demand foundation node continues `project_context/architecture.md#component-map`. It owns the detailed cross-workspace runtime, provider, data, decision, publication, contribution and identity component boundaries; the parent remains the architecture entry and routing owner.

## Runtime And Domain Components

- The native API startup in `apps/api/src/start.ts` composes GFS primary and IFS comparison through one `OpenMeteoHttpClient` model family. `withModels` keeps weather requests and normalization independent while sharing only unresolved air-quality requests for the same complete upstream URL and UTC request date. The HTTP client owns this coalescing boundary; unrelated client families, endpoints, credentials, coordinates or dates do not share it. Success and failure both remove the pending entry, and an AQ failure retains weather with missing AQ. This introduces no settled raw-response cache or change to retention policy; forecast and night-report services retain their existing result-cache responsibility.
- Remote release keeps development/test/acceptance state separate from two distinct cloud environments. Staging and production use separate compute/runtime identities, mutable data, credentials, queues, caches, buckets, backups and Mini Program bindings; the same immutable backend image digest is promoted after staging, while each environment-bound WEAPP bundle retains its own fingerprint and platform credential.
- Mini Program production code is owned by `apps/wechat-miniapp/**`; its production journeys are the real WEAPP routes and `tools/miniapp/**` owns isolated build, WeChat DevTools observation and platform lifecycle. No browser/H5 Mini Program implementation or acceptance proxy exists. The package consumes a generated projection of only the Mini Program DESIGN profile and calls shared contracts/BFF through explicit client ports. It never directly calls external weather/map/media/content providers or imports the native App token module.
- `workers/miniapp-api/**` owns the Mini Program modular-monolith BFF and server-side Port/Adapter composition; `packages/miniapp-contracts/**` owns its shared typed API/domain boundary. It remains independent from the native App API composition, and any later consolidation must preserve these domain identities, capability gates and failure semantics instead of making the client call providers directly. Explicit `SAMPLE_DATA` fixture adapters are permitted only for deterministic tests or an explicitly identified development/acceptance scenario; every current non-test startup and commercial startup rejects that composition. A real-provider failure may expose attributable cache, partial, expired or unavailable state, but it never selects a fixture as the product success path.
- The generated public Mini Program transport manifest is limited to the HTTP methods accepted by WeChat `wx.request`: `GET`, `POST`, `PUT` and `DELETE`. `tools/miniapp/generate-miniapp-sdk.mjs` rejects another method such as `PATCH` before client generation; API routes serving this public manifest use the corresponding supported method so browser or Node-only tests cannot mask a WEAPP dispatch failure.
- Mini Program journey sharing uses BFF-owned public projections, never a client-assembled copy of a private plan aggregate. An authenticated plan owner may mint a bounded, opaque, expiring credential for one saved plan revision; public retrieval rechecks the plan and its shareable formal spot on every request, so deletion, revision, or delisting makes an old link unavailable. The public plan summary includes only destination identity/name, explicit observing/departure time semantics, spot timezone and optional attributable event; it excludes origin coordinates/address, notes, checklist/reminder state, account profile and internal authorization. Formal-spot sharing resolves current published facts through the same formal-spot owner and discloses no transient weather. The receiving UI distinguishes unavailable or revoked content from network failure and offers a route back to Map. The contract/operation manifest owns transport shapes; a shared Mini Program presentation owner handles source attribution and invalid-link recovery for both variants.
- The Mini Program BFF weather boundary uses QWeather as its sole forecast provider, with a separate official-alert adapter. Forecast failure or unsupported hours never activates Open-Meteo or a fixture. Each delivered hour retains its source identity; alerts retain independent effective/expiry instants and are evaluated at the exact selected time even without a forecast hour. An unavailable/expired alert feed cannot establish absence of alerts; a forecast outage must not discard an independently available alert feed. Layered cloud, multi-model comparison and fallback roles are retired from the product; retired fields cannot supply confidence or completeness requirements.
- `miniapp-contracts/local-time.ts` owns `observationNightBounds`: local noon through the following local noon, converting both boundaries independently. `WeatherPort.windowUtc` is an explicit end-exclusive override, not another user observation state. Composition intersects actual QWeather hours with this window, preserves internal gaps and does not shift the selected astronomy instant. Missing hours and missing returned fields remain distinct from source transport failure. Runtime requests 240 hours by default and permits explicit integer horizons 1–240; provider entitlement and actual returned hours determine usable coverage, not the configured request size. No current or historical forecast is relabelled as an observation.
- Forecast, official alerts and AQ normalize explicit-offset instants through `qweather-client.ts` without rolling impossible calendar dates into other days. Duplicate normalized hourly identities are excluded together instead of choosing first/last values; valid siblings remain partial. Forecast delivery removes elapsed end-exclusive hourly intervals both on cache reads and after waiting for independent alerts, preserving original retrieval times and cached rows. An entirely elapsed feed is expired and carries no usable weather rows.
- Astronomy's shared weather acquisition carries its original acquisition instant through concurrent waiters. Source/hour/alert deadlines bound cached computation and are rechecked after asynchronous projection. Map also rechecks after repository/cache waits; re-projection preserves the original request budget. `MapSceneData.forecastValidUntil` carries the earliest selected-time forecast expiry over candidates before filtering, including candidates excluded from an empty result. Existing `use-resource-query` owns transport, cache and errors; `use-forecast-query` adds presentation expiry for Map, Search, Sky and plan weather. It clears elapsed weather and dependent signals without mutating cached reports or shifting astronomy/plan time, revalidates each crossed boundary, and stops timers while hidden. An already expired cache revalidates on entry; an identical expired response cannot create a refresh loop. The shared WeatherAlerts wall-clock owner removes ended warnings independently of the selected astronomy time. Ordinary expiry is partial coverage, not a transport-error toast. Excluded candidates can only be recovered by a fresh server result.
- QWeather's current forecast and official-alert adapters each reuse `ComputationCache` for bounded process-local normalized-source caching and coalescing. Identity follows the actual rounded GCJ-02 request point and provider configuration; observation dates/windows remain composition inputs and do not duplicate the same current-source request. The source forecast TTL is 30 minutes, partial responses 60 seconds and unavailable responses five seconds; this is not a strict whole-product freshness ceiling because existing consumer caches retain their own bounded TTL. Alert-feed freshness is at most five minutes and expires sooner at the earliest future alert expiry; its `SourceSummary.validTo` carries that bound through Astronomy caches independently of individual alert lifetimes. Cache hits retain original retrieval time/state, expired sources are refreshed without serving stale success on failure, and each waiter may cancel independently of the shared deadline-bound request. This does not create a cross-process cache or establish deployed usage accounting.
- Mini Program development has exactly one current implementation, evolved in place from the existing owners. Proposal labels such as V1/V2/V2.1.1 establish Source precedence, migration history, or a wire-contract identifier only; they never authorize parallel services, repositories, state stores, UI trees, test suites, feature branches, or compatibility product paths. Product UI and ordinary operator copy describe the current capability directly and never expose those internal proposal/version labels. The current accepted proposal replaces superseded product behavior in the same owner. Any temporarily retained old-schema adapter must be isolated at an external boundary, have no default route or product semantics, and cannot become a second source of truth.
- Search now has 14 supported conditions: driving range and low-cloud threshold are removed. Startup cloning projects old persisted filter records onto current groups, preserving retained selections while removing the retired groups and driving parameters. The same owner retains committed, draft and opening-snapshot states. Map browsing performs no road estimate; any shown distance is explicitly straight-line. Field-verified drive-up access remains a separate static condition.
- `data-pipelines/dark-sky/**` owns offline acquisition validation and publication of operator-acquired EOG VIIRS night-light rasters. It accepts only digest-bound, licensed, EPSG:4326 source objects plus declared cloud-free coverage, publishes immutable dataset identity, relative product bands, source-linked spot samples and bounded PostGIS map-grid cells in one transaction, and never labels those relative bands as Bortle or SQM. Map rectangles contain only valid source pixels: complete blocks aggregate, mixed blocks split along valid row runs with matching adjacent spans merged, and missing coverage remains unpainted. The existing native-map cell budget rejects excessive fragmentation rather than extending valid values over holes; changed processing requires a new dataset identity when replacing an immutable publication. A missing real publication yields unavailable/partial product state rather than a generated geographic pattern or fixture fallback.
- `workers/miniapp-api/src/astronomical-event-catalog.ts` composes the versioned GMN annual meteor references from `meteor-event-catalog.ts` with the 2026 solar/lunar eclipse occurrences deterministically calculated by the pinned Astronomy Engine adapter. The same server astronomy boundary owns location/time projection; consumer code never calculates an ephemeris or scrapes providers. A peak/activity value may be shown only when the catalog carries an attributable reviewed model for that value. Dataset and algorithm versions are traceability identities inside this one implementation, not product variants.
- `packages/astronomy-core/**` owns shared astronomy calculation and product-scoped static catalogs. Mini Program uses the explicit `bsc5p-catalog` and `deep-sky-catalog` subpaths so its runtime does not load the independent native App Gaia/Hipparcos packs through the root facade. The Mini API release Dockerfile also removes the shared package's Gaia DR3 data pack and manifest after compilation and checks the final image excludes them while retaining BSC5P; this is a Mini commercial distribution boundary, not deletion of another product's source catalog. Rights-unresolved optical HiPS publications are injectable only in LOCAL/MEMORY_TEST with TRIAL scope; normal release profiles expose no optical publication until source rights and delivery are resolved. `data-pipelines/star-catalog/build_bsc5p.py` derives the complete bounded BSC5P subset from HEASARC VOTable and IAU identifiers; committed data and manifest bind acquisition, fields, units, source credit and bytes. No runtime catalog downloads occur. AstronomyService projects WGS84 place/time into every report frame; the client owns only horizontal-to-camera projection, selection and rendering. Missing or invalid catalogs fail closed while independent valid targets, weather and deep-sky content retain their own states.
- `workers/miniapp-api` owns two current, composable decision boundaries rather than one blended score: `SkyOpportunityEngine` evaluates normalized per-time-slice celestial, weather, darkness, moon, light-pollution and optional horizon evidence, keeps confidence separate from score, and owns the hysteresis/minimum-duration continuous-window segmenter; `TripDecisionEngine` accepts only a complete formal-spot evidence snapshot, references the resulting `SkyOpportunity`, and applies access, openness, road, legal and safety blockers before any suitability explanation for consumers that still expose those outputs. Mini Program discovery and its information panel do not display combined recommendations or the retired recommendation filters; underlying safety facts and navigation restrictions remain effective. PostgreSQL persists digest-bound, immutable SkyOpportunity and TripDecision replay snapshots separately so a rule can be re-evaluated without overwriting its historical input or conflating the two conclusions. Client surfaces consume these server results and never recreate either rule set. The hourly outbox sweep dispatches same-transaction events in weather → astronomy → decision order so the decision job reads astronomy nights published by that sweep; `created_at` alone cannot order those events because PostgreSQL gives them the same transaction timestamp.
  The MapScene boundary projects a viewport-bounded, compact loaded timeline from those same hourly SkyReport rows: each frame carries only per-spot dynamic signals plus polygons for the one requested dynamic layer, while source-dated light pollution and other static layer metadata remain single-copy. The client may preview those frames locally, but release commits the sole Observation Context before refresh; neither preview nor callout may substitute the whole-night TripDecision for the selected-time SkyOpportunity. Rule/dataset identities are replay and traceability metadata inside the same implementation, not product variants.
- PostgreSQL/PostGIS is the sole current formal-spot truth. A server-owned, fail-closed publication policy evaluates the proposed final record—not only the requested status patch—against the core publication criteria in the next paragraph, and returns attributable missing/invalid evidence. Optional enrichment is not a second publication threshold. Production reads cannot project a spot as `PUBLISHED` unless this gate passes; source-code fixtures and all-`UNKNOWN` evidence never satisfy it.
- The same PostgreSQL owner accepts new locations as candidate records with explicit provenance. The owner revision of 2026-09-07 separates minimum intake, core publication readiness and optional enrichment. Minimum intake captures name/location, openness, legal entry, night safety and gate/responsible-party contact status; unknown answers may be submitted as leads without being treated as verified. A fresh core publication assessment requires an identifiable valid point, attributable current evidence for openness/legal entry/night safety and explicit danger, the existing coordinate visibility policy, and an audited owner review. Missing photographs, public phone numbers, ordinary facility details, route estimates, light-pollution or horizon enrichment alone no longer makes a verified core record unpublishable. Known serious road/access hazards remain material blockers; closed/prohibited/dangerous conditions must retain their restrictive lifecycle/action semantics, never become a positive or unrestricted public state.
  Authenticated operations still merge attributable evidence and register new sources transactionally; submission, approval and publication remain separate and cannot be bypassed by direct writes. The existing `spot-completeness-policy.ts` implements this core threshold in the shared publication assessor: optional enrichment absence is not a publication blocker, while core claims require current evidence bound to the same spot and a usable source. Asserted site media still requires its verification and provenance. This code does not establish deployment or current database acceptance. Candidate intake never seeds production startup, appears as a formal point before review, or fabricates missing facts. No separate manual completeness workflow or second canonical record is introduced.
- `workers/miniapp-api` also owns the authenticated contribution intake and moderation boundary. PostgreSQL stores user/admin reports, corrections, proposed places, upload-session identity and review history; a replaceable `MediaObjectStorePort` stores only MIME/size-validated, metadata-sanitized derivatives while raw client paths, EXIF and precise contributor coordinates are excluded from ordinary read models and logs. User submission, admin review, canonical fact merge and formal publication are distinct state transitions: neither approval nor an uploaded object may update the formal spot projection until operations explicitly merges attributable evidence and the existing completeness policy passes on the resulting record. Abandoned upload sessions expire and their objects are deleted; idempotency and contributor identity scope prevent duplicate or cross-user writes.
- The same identity boundary owns Settings account-data operations. A data export is a server-generated, identity-scoped, versioned JSON snapshot assembled from current durable records; it excludes session credentials, WeChat identity digests, internal object keys and raw media bytes, and the Mini Program never reconstructs the authoritative export from local cache. Fresh-code reauthentication for export or deletion resolves only an existing active identity; a mismatched code must not create another account or change its delivery binding. Normal login remains the account-creation owner. Account deletion is an idempotent server command with explicit confirmation: it removes the WeChat identity mapping, revokes every session, deletes mutable account preferences/library/plans/profile/import/media records, de-identifies retained moderation/publication evidence, and returns a deletion receipt before the client clears local state. Append-only review, merge, publication and audit evidence may remain only under the resulting unlinkable pseudonymous subject required for integrity; the UI must disclose that retention and cannot call local cache clearing an account deletion.
- Mobile navigation truth lives in one Expo Router route tree: a persistent five-tab navigator maps Tonight, Map, Trips, Sky, and Me to `/tonight`, `/map`, `/trips`, `/sky`, and `/me`, with a route-owned nested stack under each tab. A persisted destination preference may assist restoration, but it cannot become a second router or screen-identity source.

## Mini Program Recent Regional Weather

`recent-weather-provider.ts` owns QWeather Geo city lookup and the preceding two regional calendar days of `/v7/historical/weather`. The independent `GET /v2/spots/{spotId}/recent-weather` delegates to `SpotEnvironmentService`, which validates the existing published-spot identity before spending upstream requests. It never invokes forecast/Astronomy or changes the selected Observation Context. `recent-weather.ts` owns this contract family; the client component owns disclosure, conditional relevance and recovery in the Map's current formal-spot document, after basic information and before terrain. The legacy field route is not a second consumer of this new capability.

`qweather-client.ts` is the shared JWT, coordinate conversion and bounded JSON request boundary used by forecast, alerts and history. Existing metered transport remains below source caches, with WEATHER_REGION and RECENT_HISTORY attempts classified separately. Region lookup is live per request cycle; only complete daily weather measurements cache for six hours, incomplete daily weather measurements for one minute. Failed days are not cached as valid days, and returned source timestamps remain the original retrieval times. Two sequential source phases each have a three-second limit, within the Mini Program's ten-second transport budget; the two dates run concurrently and retain a successful sibling when one fails. No-data responses and request failures have distinct meanings in the public contract.

The client keys recent-weather queries by formal spot and current regional calendar date, separately from astronomy/plan time. `use-calendar-day.ts` stops its timer while hidden, resumes the current date on show and invalidates the day identity at regional midnight; source timezone supersedes the spot's initial timezone after lookup. Cached previous-day payloads cannot reappear as current recent facts. History is supplemental evidence, never proof of field access, closure, flooding or icing.

History hours accept both the provider's legacy regional wall-time format and explicit-offset ISO instants. ISO values are validated by the shared QWeather time boundary and assigned to the freshly resolved region's calendar day. Invalid or foreign-day hours are omitted without discarding valid daily fields. Wind sample counts deduplicate regional clock-hour buckets across formats; they do not certify a complete elapsed day, including daylight-saving transitions. Weather-only cache fingerprints include the interpretation timezone, while retaining no Geo record.

GeoAPI data is live-use only under the selected source conditions. The adapter shares only in-flight composite requests, performs a fresh region lookup per completed request cycle, and retains only weather-day values under opaque weather-request fingerprints (not a coordinate-to-region index). The HTTP route returns `no-store`; `EtagInterceptor` respects this and does not send an ETag/304. `spot-environment-client.ts` bypasses response caching, and `response-cache.ts` retires old `spot-recent-weather:` entries/chunks and rejects new writes. The component includes visibility in its query identity with zero inactive retention, clears its derived regional clock and response on hide or failed refresh, and does not redisplay stale/offline Geo responses. Failure state survives cleanup independently of regional timezone/date changes until manual retry or resumed display. Active rendering state is temporary; weather caching permission does not authorize a retained geographic database.

## Mini Program Independent Air Quality

`air-quality-provider.ts` owns separate QWeather current and hourly AQ requests, per-point caches and attributed segments. `SpotEnvironmentService` shares the existing published-spot guard with regional history and exposes independent current/forecast states through `GET /v2/spots/{spotId}/air-quality`; one failed segment does not erase the other. Metered transport classifies AIR_CURRENT and AIR_HOURLY attempts without retaining request coordinates. Complete current data caches for one hour, forecast for at most six hours and no longer than its last actual hour; partial and failed results have shorter retry windows. Invalid calendar dates, conflicting duplicate identities and expired forecast hours cannot become fresh future evidence.

The contract keeps supplier AQI standard identity, original display/category and pollutant concentrations with units. Missing concentrations remain missing, including the documented China forecast limitation; current PM readings never fill future hours. Retrieval time is not inferred publication/measurement time. The Map's `AirQuality` consumer uses only the selected hour's own interval, lists actual coverage through the shared range disclosure, and keeps current readings separate from astronomy/plan time. It hides expired current readings, retains independent valid forecast, suspends periodic queries while hidden and provides local retry plus the shared top notification on errors. `spot-environment-client.ts` delegates to the existing request/session owner; AQ disables persisted response fallback and does not create another cache. Real account entitlement, availability and target-runtime rendering remain delivery obligations; these source/contract choices alone do not establish them.

`miniapp-contracts/air-quality.ts` owns the shared immutable expiry projection used at provider delivery and by the client: current readings have a product use deadline one hour after retrieval, and each forecast hour ends exclusively one hour after its source instant. This does not invent a measurement timestamp. Valid elapsed evidence is `EXPIRED`, separately from malformed/ambiguous responses and request failures; an existing failure remains a failure when some or all hours expire. Sources retain their original acquisition/publication facts. `useAirQualityQuery` reuses the shared forecast-boundary clock, clears elapsed values while idle or offline, and refreshes on foreground even when the retained evidence has not expired. That hook alone owns automatic resume/expiry refresh; `use-resource-query.refetch({cancelRefetch:false})` joins any fetch already started by TanStack on enable, while manual retry retains its existing behavior. AQ provenance consumes the projected segment sources so an expired reading cannot keep a fresh source badge.

## Mini Program Product And Plan Flow

Map, Search and Sky share `services/observation-context-version.ts` for expected Context version checks; an expired-ID recovery may adopt a new ID but cannot replace a newer selection or downgrade the same ID's revision. Sky's page-local `sky-context-session.ts` coordinates entry lookup and date/time commits with one synchronous request owner. Hide/unmount invalidates pending publication, and a successful current recovery advances that page's accepted ID before the store is updated. It does not create a second Context payload store or replace the API client's recovery policy. Lookup eligibility also controls the loading presentation: a page that no longer owns the selected Context exposes the existing return action instead of waiting on a disabled query.

`observation-context-service.ts` owns the current Greater Bay Area `MAP_POINT` timezone boundary. It rejects positions outside the declared trial box. The narrow Shenzhen/Hong Kong band uses the pinned Home Affairs Department 18-district boundary snapshot through `hong-kong-boundary.ts`; Macao membership uses the separately licensed, pinned `Asia/Macau` feature from Timezone Boundary Builder 2026d through `macao-boundary.ts`. Both source assets and their attribution/limitations are recorded in the [timezone asset README](../../workers/miniapp-api/assets/timezone/README.md), and the current `src` and release `dist` paths resolve the packaged `assets/` publication. The service exposes the Macao source on derived browsing Contexts and Map scenes; Map uses the shared attribution component to disclose its ODbL credit. A phone's timezone hint remains in the request contract for older clients but does not decide a browsing point's zone. These administrative/approximate geometry snapshots are not a general IANA database or a claim about maritime timezone coverage. Refresh either pinned snapshot with its source, checksum, attribution and representative border checks. The shared zone contract, bounded modern UTC+8 fallback, plan recovery and candidate publication admit `Asia/Macau` without replacing older Shanghai/Hong Kong identities. A 2026-09-26 capability comparison found [`geo-tz`](https://github.com/evansiroky/node-geo-tz) precise but roughly 74 MB unpacked with runtime data-file packaging, while [the maintained small lookup](https://github.com/photostructure/tz-lookup) explicitly estimates zones and reports material mismatches against precise data; neither is silently substituted for this limited resolver. Formal spots continue to use their published timezone; plan departure origins do not become browsing Contexts.

Plan detail and editor context restoration is local to the mounted plan query. It may use the map context as an initialization source, but does not write its restored snapshot back into the map's committed Observation Context. This preserves the opener's selected place/time across child navigation; plan save still uses the local context and server-side re-resolution. The map's own restoration coordinator remains unchanged. A plan opens its place information through the registered `spot/plan/index` page in the existing `spot` subpackage. That page gives the shared spot-detail renderer an explicit plan-local Observation Context override, so the shared renderer preserves the plan's place/time while the committed Map context and the native return stack remain untouched; ordinary spot-detail consumers continue to use the committed Map context.

The formal Map information panel's plan entry uses `features/spot/spot-plan-route.ts`: zero associated plans opens a spot-prefilled new editor, one opens its detail, and multiple open the spot-filtered list. The editor resolves an explicitly supplied spot through the existing service into a local context without replacing the map opener's context. New-plan drafts opened for a specific spot use an account-and-spot scope in `services/local-draft-keys.ts`; generic new drafts and existing-plan keys remain compatible, and account erasure recognizes both forms. These are routing/data boundaries, not evidence of verified native navigation or completed panel rendering.

User-authored plan reminder content is carried by the existing revisioned plan aggregate, not a second local checklist store. `packages/miniapp-contracts/src/plan-reminders.ts` owns the five-group/twenty-item validation and strips non-contract fields; drafts may retain unfinished text while submitted content must validate. Reminder IDs and item IDs remain stable across edits. Save recovery includes this content in the account-bound intent identity. An older client omitting existing reminder content is rejected rather than erasing it. `notifyOnWechat` expresses intent only: subscription authorization, schedule versions and delivery receipts remain server-owned responsibilities and are not established by saving this field.

PostgreSQL reminder scheduling separates active selection from delivery history. Changing or deleting a plan deactivates displaced schedules without overwriting attempted or terminal delivery states. Returning to an identical schedule version recalculates its current waiting/skipped state only when the old row was canceled and has no attempt count or delivery receipt; it never clears known/unknown delivery outcomes or grants subscription authorization. Pre-existing canceled rows with attempt evidence remain conservative and cannot be reset into a new send by toggling the preference. Account erasure retains its separate privacy-owned removal policy.

`PostgresReminderAttemptStore` reserves a first attempt under the existing account/schedule locks, after checking the active account, current plan/reminder version and intent, selected schedule, trigger and departure. The production dispatcher supplies the mapped plan revision, encrypted recipient binding and configured time window; reservation rejects a changed revision rather than consuming authorization for old content. It commits an UNKNOWN attempt and RESULT_UNKNOWN schedule before external work, so a crash cannot reset that version to sendable. The post-token final gate checks the bound attempt/challenge, live notification flag, account, plan revision, current intent, AppID/template, recipient and time boundary immediately before network submission. No account/schedule/outbox transaction remains open across HTTP. Only the reservation can record one terminal result without reactivating canceled history. Provider acceptance is SENT / PROVIDER_ACCEPTED, not a fabricated delivery receipt. Plan save/delete retain the active account serialization; stale writes after soft deletion fail, and erasure clears the reminder records explicitly.

`PostgresReminderSubscriptionStore` owns local subscription challenges (migration 022), bound to account, schedule version, AppID and template. Preparation requires a future eligible reminder, a current decryptable account destination and complete delivery readiness. An unattempted scheduled row can request fresh authorization when its accepted record does not match the current binding; matching accepted authorization never creates another prompt. The API projects that binding mismatch as AUTHORIZATION_REQUIRED. Concurrent preparation reuses an unexpired pending challenge; the five-minute lifetime bounds client reporting, not provider subscription validity. CLIENT_ACCEPTED is a local reported choice, not verified WeChat quota. Reservation consumes exactly one matching choice atomically with the attempt. Supersession/cancellation cancels unconsumed challenges, including when a schedule is later restored; account erasure removes them. HTTP preparation/reporting retain the existing session, validation and account-cache owner. Missing readiness returns unavailable/false without provider calls. Client transport fences account changes and refreshes the same account plans after recorded reports or explicitly unavailable preparation; neither preparing nor saving intent grants platform authorization.

Implementation boundary: PlanReminderDispatcher is now consumed by the existing NOTIFICATION/outbox owner. Complete readiness requires POSTGRES + WECHAT authentication, AppID/secret, the independent WECHAT_DELIVERY_IDENTITY_KEY, the actually approved WECHAT_REMINDER_TEMPLATE_ID and WECHAT_REMINDER_FIELDS_JSON, explicit WECHAT_REMINDER_DELIVERY_ENABLED=1, WECHAT_REMINDER_MINIPROGRAM_STATE (developer/trial/formal), WECHAT_REMINDER_MAX_LATENESS_SECONDS and the existing database NOTIFICATION_ENABLED=true flag. No template, flag or backend release profile alone selects/activates a WeChat version. Mapping supports thingN from REMINDER_TITLE or SPOT_NAME, and timeN from DEPARTURE_LOCAL_TIME; reminder title and departure roles are required. It preserves saved formal-spot wall time, rejects empty/control/oversized fields without truncating user content, and reloads actual plan data after awaiting the token. Other approved field types require a reviewed extension. Configuration is not proof of template approval or entitlement. These inputs are absent in the current task, so real sending remains CAPABILITY_GATED. Existing encrypted identity registration follows verified server login; old digests are not reversible. Missing or rotated-key destinations fail closed in API preparation/status and dispatch. A current verified login registers the same account destination. The dedicated reminder-destination/reverify operation uses the current session plus a fresh native code to update only that same active identity; mismatch never creates/switches an account, and the session is not replaced. Plan status distinguishes destination verification, unsupported reminder title and unavailable spot-name fields. The existing themed status dialog offers explicit same-account verification or the original editor for the title; invalid content is never silently shortened. Preparation binds the inspected plan revision and revalidates fields under its existing account transaction; unavailable preparation refreshes the account plans so reopening cannot loop on stale authorization state. Current published spot-name inputs share getSpot eligibility and payload.name through current-public-spot-query.ts; only templates using SPOT_NAME add that same qualified name to reservation and final submit qualification. Actual native recovery, platform authorization and delivery remain acceptance obligations. No public endpoint returns a destination or token.

`wechat-subscription-sender.ts` owns the bounded REST transport, while the production dispatcher owns eligibility and persistence. It snapshots exact fields, rejects redirects, applies the final gate after token acquisition, bounds waiting and never retries internally. The server-only WechatAccessTokenProvider uses stable_token with force_refresh=false, a validated expiry cache and sanitized errors. Explicit token failures 40001/40014/42001 retire only the matching cached token for a later independent attempt; template/quota failures do not cause refresh, and no consumed grant is resent. A token failure before reservation consumes no grant. A reserved but invalidated submit is NOT_ATTEMPTED; explicit provider errors are REJECTED; ambiguous post-submit outcomes remain UNKNOWN; errcode=0 means ACCEPTED, not user receipt. Finish/effect failures leave durable ownership, so BullMQ retry, dead-letter replay and restart cannot duplicate that schedule. Official platform retrieval for stable-token/send documentation was unavailable during this batch; platform compatibility/qualification and real delivery still require verification. Field guide: [Tencent CloudBase subscription guide](https://docs.cloudbase.net/recipes/add-subscribe-message-cloud-function); token-code implementation reference: [WxJava SDK author documentation](https://javadoc.io/static/com.github.binarywang/weixin-java-common/4.7.8-20251117.104752/me/chanjar/weixin/common/api/WxConsts.html). The project retains its existing backend.

Checklist completion uses `PUT /me/observation-plans/{planId}/checklist-completion` and the same plan aggregate revision/transaction. It changes only the identified item's explicit completion value, preserving the saved context snapshot, times and other user content without requiring Observation Context or forecast availability. Retry receipts are scoped by account, plan and item; stale revisions and missing items are rejected. The client publishes confirmed results through the existing plans query cache and fences account changes. Completion writes currently produce the existing plan update event; reminder scheduling must compare scheduling-relevant content rather than treat every checklist tick as a changed departure or authorization.

Mini Program plan navigation has an all-dates list at `content/plan/list/index` and an independently mounted editor at `content/plan/edit/index`; the editor currently composes the existing `content/plan/detail/index.tsx` form owner instead of duplicating its draft, revision and account logic. Explicit new intent takes priority over cached plans or an obsolete plan-id parameter. List rows and My rows keep the chosen plan identity; the all-plans header targets the list. It owns theme-aware translucent surface, border and solid reduced-transparency fallback only; pages continue to own geometry, content, modal and plan state. A React wrapper was rejected because Taro required-components lazy loading emitted an unresolved cross-subpackage component in the official runtime. Keeping one global style owner preserves the shared material contract without introducing that package boundary. Web candidate material.css/material.mjs remains a design demonstration rather than production WEAPP code.

The adopted shared spot-card contract is mapped in the same way: global `components/spot-identity-card.scss` is the single production owner for the 90px card geometry, region/name/address typography, attributable full-card media gradient, radius and pressed/reduced-motion behavior. Search supplies formal spot identity, attributable media and selection; contribution records supply their own immutable-attempt status extension below the base card. Missing address or media stays absent. The two subpackages keep minimal local WEAPP markup because both an imported JSX-returning renderer and a React wrapper failed in the official runtime (empty descendants and unresolved `wx://not-found`, respectively); they must keep the shared class structure and may not fork visual rules or move review/query state into the style owner. Reassess only when the actual Taro/WEAPP required-components boundary can load one cross-subpackage wrapper without the current failure.

Use the actual underlying composition for transmission/refraction, never a screenshot copy of the sky or duplicated DOM business content. Evaluate native/platform support and suitable established rendering before selecting the production adapter; browser SVG backdrop-filter support does not certify WEAPP. Resize-bound maps/filter IDs and resource cleanup belong to the adapter; do not regenerate maps per sensor frame or let observers/listeners accumulate after close/navigation. Bound GPU/memory work, preserve readable solid/reduced-transparency and warm-red behavior, and verify both consumers with dynamic backgrounds, scrolling, resizes, long content, reopening and lifecycle restoration.

Selection is staged, not deferred until whole-page implementation. The current production slice is the readable translucent/fallback path; official WEAPP simulator evidence covers both consumers and long celestial content, but does not establish native backdrop transmission, optical refraction, device performance or Android/iOS parity. The HTML candidate explores profile-derived SVG displacement, informed by [Kube's optical reconstruction](https://kube.io/blog/liquid-glass-css-svg/). This is a visual/mechanism reference, not an Apple implementation or WEAPP dependency. SVG backdrop filtering is not presumed portable. A shader route is a conditional alternative only if the actual scene can supply a supported texture/composition input; a Web demo that generates its own background does not satisfy live page sampling. DOM-capture libraries such as [ybouane/liquidglass](https://github.com/ybouane/liquidglass) are not a direct fit for the current no-copy composition boundary. Do not add Expo/Skia/CanvasKit or a DOM-capture pipeline solely to imitate a showcase.

Before integrating the production material broadly, compare the remaining supported path with the readable fallback in a small WEAPP slice containing both actual consumers on iOS and Android. Use matched viewport, backdrop and content: inspect transmission/curved-edge displacement and text contrast over bright, dark and changing backgrounds; record frame-time distribution, dropped frames, memory and repeated-open/close behavior on named representative devices. Include sky movement, My scrolling, long text, warm red, reduced transparency/motion, background/foreground restoration and rendering failure. Set acceptable performance budgets against the existing scene before selection, then carry the result and decisive tradeoffs here. A successful HTML preview, API syntax check or a single static screenshot does not select the renderer. If no path fits, expose the explicit fallback and the remaining visual gap; do not rename it as equivalent refraction. Device experimentation is later implementation work, outside the current Context/design-resource scope.

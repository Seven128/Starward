# Architecture Detail: Runtime And Domain Components

This on-demand foundation node continues `project_context/architecture.md#component-map`. It owns the detailed cross-workspace runtime, provider, data, decision, publication, contribution and identity component boundaries; the parent remains the architecture entry and routing owner.

## Runtime And Domain Components

- The native API startup in `apps/api/src/start.ts` composes GFS primary and IFS comparison through one `OpenMeteoHttpClient` model family. `withModels` keeps weather requests and normalization independent while sharing only unresolved air-quality requests for the same complete upstream URL and UTC request date. The HTTP client owns this coalescing boundary; unrelated client families, endpoints, credentials, coordinates or dates do not share it. Success and failure both remove the pending entry, and an AQ failure retains weather with missing AQ. This introduces no settled raw-response cache or change to retention policy; forecast and night-report services retain their existing result-cache responsibility.
- Remote release keeps development/test/acceptance state separate from two distinct cloud environments. Staging and production use separate compute/runtime identities, mutable data, credentials, queues, caches, buckets, backups and Mini Program bindings; the same immutable backend image digest is promoted after staging, while each environment-bound WEAPP bundle retains its own fingerprint and platform credential.
- Mini Program production code is owned by `apps/wechat-miniapp/**`; its production journeys are the real WEAPP routes and `tools/miniapp/**` owns isolated build, WeChat DevTools observation and platform lifecycle. No browser/H5 Mini Program implementation or acceptance proxy exists. The package consumes a generated projection of only the Mini Program DESIGN profile and calls shared contracts/BFF through explicit client ports. It never directly calls external weather/map/media/content providers or imports the native App token module.
- `workers/miniapp-api/**` owns the Mini Program modular-monolith BFF and server-side Port/Adapter composition; `packages/miniapp-contracts/**` owns its shared typed API/domain boundary. It remains independent from the native App API composition, and any later consolidation must preserve these domain identities, capability gates and failure semantics instead of making the client call providers directly. Explicit `SAMPLE_DATA` fixture adapters are permitted only for deterministic tests or an explicitly identified development/acceptance scenario; every current non-test startup and commercial startup rejects that composition. A real-provider failure may expose attributable cache, partial, expired or unavailable state, but it never selects a fixture as the product success path.
- The generated public Mini Program transport manifest is limited to the HTTP methods accepted by WeChat `wx.request`: `GET`, `POST`, `PUT` and `DELETE`. `tools/miniapp/generate-miniapp-sdk.mjs` rejects another method such as `PATCH` before client generation; API routes serving this public manifest use the corresponding supported method so browser or Node-only tests cannot mask a WEAPP dispatch failure.
- Mini Program journey sharing uses BFF-owned public projections, never a client-assembled copy of a private plan aggregate. An authenticated plan owner may mint a bounded, opaque, expiring credential for one saved plan revision; public retrieval rechecks the plan and its shareable formal spot on every request, so deletion, revision, or delisting makes an old link unavailable. The public plan summary includes only destination identity/name, explicit observing/departure time semantics, spot timezone and optional attributable event; it excludes origin coordinates/address, notes, checklist/reminder state, account profile and internal authorization. Formal-spot sharing resolves current published facts through the same formal-spot owner and discloses no transient weather. The receiving UI distinguishes unavailable or revoked content from network failure and offers a route back to Map. The contract/operation manifest owns transport shapes; a shared Mini Program presentation owner handles source attribution and invalid-link recovery for both variants.
- The Mini Program BFF weather boundary uses QWeather as its sole forecast provider, with a separate official-alert adapter. Forecast failure or unsupported hours never activates Open-Meteo or a fixture. Each delivered hour retains its source identity; alerts retain independent effective/expiry instants and are evaluated at the exact selected time even without a forecast hour. An unavailable/expired alert feed cannot establish absence of alerts; a forecast outage must not discard an independently available alert feed. Layered cloud, multi-model comparison and fallback roles are retired from the product; retired fields cannot supply confidence or completeness requirements.
- `miniapp-contracts/local-time.ts` owns `observationNightBounds`: local noon through the following local noon, converting both boundaries independently. `WeatherPort.windowUtc` is an explicit end-exclusive override, not another user observation state. Composition intersects actual QWeather hours with this window, preserves internal gaps and does not shift the selected astronomy instant. Missing hours and missing returned fields remain distinct from source transport failure. Runtime requests 240 hours by default and permits explicit integer horizons 1–240; provider entitlement and actual returned hours determine usable coverage, not the configured request size. No current or historical forecast is relabelled as an observation.
- Forecast, official alerts and AQ normalize explicit-offset instants through `qweather-client.ts` without rolling impossible calendar dates into other days. Duplicate normalized hourly identities are excluded together instead of choosing first/last values; valid siblings remain partial. Forecast delivery removes elapsed end-exclusive hourly intervals both on cache reads and after waiting for independent alerts, preserving original retrieval times and cached rows. An entirely elapsed feed is expired and carries no usable weather rows.
- Astronomy's shared weather acquisition carries its original acquisition instant through concurrent waiters. Source/hour/alert deadlines bound cached computation and are rechecked after asynchronous projection. Map also rechecks after repository/cache waits; re-projection preserves the original request budget. `MapSceneData.forecastValidUntil` carries the earliest selected-time forecast expiry over candidates before filtering, including candidates excluded from an empty result. Existing `use-resource-query` owns transport, cache and errors; `use-forecast-query` adds presentation expiry for Map, Search, Sky and plan weather. It clears elapsed weather and dependent signals without mutating cached reports or shifting astronomy/plan time, revalidates each crossed boundary, and stops timers while hidden. An already expired cache revalidates on entry; an identical expired response cannot create a refresh loop. The shared WeatherAlerts wall-clock owner removes ended warnings independently of the selected astronomy time. Ordinary expiry is partial coverage, not a transport-error toast. Excluded candidates can only be recovered by a fresh server result.
- QWeather's current forecast and official-alert adapters each reuse `ComputationCache` for bounded process-local normalized-source caching and coalescing. Identity follows the actual rounded GCJ-02 request point and provider configuration; observation dates/windows remain composition inputs and do not duplicate the same current-source request. The source forecast TTL is 30 minutes, partial responses 60 seconds and unavailable responses five seconds; this is not a strict whole-product freshness ceiling because existing consumer caches retain their own bounded TTL. Alert-feed freshness is at most five minutes and expires sooner at the earliest future alert expiry; its `SourceSummary.validTo` carries that bound through Astronomy caches independently of individual alert lifetimes. Cache hits retain original retrieval time/state, expired sources are refreshed without serving stale success on failure, and each waiter may cancel independently of the shared deadline-bound request. This does not create a cross-process cache or establish deployed usage accounting.
- Mini Program development has exactly one current implementation, evolved in place from the existing owners. Proposal labels such as V1/V2/V2.1.1 establish Source precedence, migration history, or a wire-contract identifier only; they never authorize parallel services, repositories, state stores, UI trees, test suites, feature branches, or compatibility product paths. Product UI and ordinary operator copy describe the current capability directly and never expose those internal proposal/version labels. The current accepted proposal replaces superseded product behavior in the same owner. Any temporarily retained old-schema adapter must be isolated at an external boundary, have no default route or product semantics, and cannot become a second source of truth.
- Search now has 14 supported conditions: driving range and low-cloud threshold are removed. Startup cloning projects old persisted filter records onto current groups, preserving retained selections while removing the retired groups and driving parameters. The same owner retains committed, draft and opening-snapshot states. Map browsing performs no road estimate; any shown distance is explicitly straight-line. Field-verified drive-up access remains a separate static condition.
- `data-pipelines/dark-sky/**` owns offline acquisition validation and publication of operator-acquired EOG VIIRS night-light rasters. It accepts only digest-bound, licensed, EPSG:4326 source objects plus declared cloud-free coverage, publishes immutable dataset identity, relative product bands, source-linked spot samples and bounded PostGIS map-grid cells in one transaction, and never labels those relative bands as Bortle or SQM. Map rectangles contain only valid source pixels: complete blocks aggregate, mixed blocks split along valid row runs with matching adjacent spans merged, and missing coverage remains unpainted. The existing native-map cell budget rejects excessive fragmentation rather than extending valid values over holes; changed processing requires a new dataset identity when replacing an immutable publication. A missing real publication yields unavailable/partial product state rather than a generated geographic pattern or fixture fallback.
- `workers/miniapp-api/src/astronomical-event-catalog.ts` composes the versioned GMN annual meteor references from `meteor-event-catalog.ts` with the 2026 solar/lunar eclipse occurrences deterministically calculated by the pinned Astronomy Engine adapter. The same server astronomy boundary owns location/time projection; consumer code never calculates an ephemeris or scrapes providers. A peak/activity value may be shown only when the catalog carries an attributable reviewed model for that value. Dataset and algorithm versions are traceability identities inside this one implementation, not product variants.
- `packages/astronomy-core/**` owns shared astronomy calculation and product-scoped static catalogs. Mini Program uses the explicit `bsc5p-catalog` and `deep-sky-catalog` subpaths so its runtime does not load the independent native App Gaia/Hipparcos packs through the root facade. `data-pipelines/star-catalog/build_bsc5p.py` derives the complete bounded BSC5P subset from HEASARC VOTable and IAU identifiers; committed data and manifest bind acquisition, fields, units, source credit and bytes. No runtime catalog downloads occur. AstronomyService projects WGS84 place/time into every report frame; the client owns only horizontal-to-camera projection, selection and rendering. Missing or invalid catalogs fail closed while independent valid targets, weather and deep-sky content retain their own states.
- `workers/miniapp-api` owns two current, composable decision boundaries rather than one blended score: `SkyOpportunityEngine` evaluates normalized per-time-slice celestial, weather, darkness, moon, light-pollution and optional horizon evidence, keeps confidence separate from score, and owns the hysteresis/minimum-duration continuous-window segmenter; `TripDecisionEngine` accepts only a complete formal-spot evidence snapshot, references the resulting `SkyOpportunity`, and applies access, openness, road, legal and safety blockers before any suitability explanation for consumers that still expose those outputs. Mini Program discovery and its information panel do not display combined recommendations or the retired recommendation filters; underlying safety facts and navigation restrictions remain effective. PostgreSQL persists digest-bound, immutable SkyOpportunity and TripDecision replay snapshots separately so a rule can be re-evaluated without overwriting its historical input or conflating the two conclusions. Client surfaces consume these server results and never recreate either rule set.
  The MapScene boundary projects a viewport-bounded, compact loaded timeline from those same hourly SkyReport rows: each frame carries only per-spot dynamic signals plus polygons for the one requested dynamic layer, while source-dated light pollution and other static layer metadata remain single-copy. The client may preview those frames locally, but release commits the sole Observation Context before refresh; neither preview nor callout may substitute the whole-night TripDecision for the selected-time SkyOpportunity. Rule/dataset identities are replay and traceability metadata inside the same implementation, not product variants.
- PostgreSQL/PostGIS is the sole current formal-spot truth. A server-owned, fail-closed publication policy evaluates the proposed final record—not only the requested status patch—against the core publication criteria in the next paragraph, and returns attributable missing/invalid evidence. Optional enrichment is not a second publication threshold. Production reads cannot project a spot as `PUBLISHED` unless this gate passes; source-code fixtures and all-`UNKNOWN` evidence never satisfy it.
- The same PostgreSQL owner accepts new locations as candidate records with explicit provenance. The owner revision of 2026-09-07 separates minimum intake, core publication readiness and optional enrichment. Minimum intake captures name/location, openness, legal entry, night safety and gate/responsible-party contact status; unknown answers may be submitted as leads without being treated as verified. A fresh core publication assessment requires an identifiable valid point, attributable current evidence for openness/legal entry/night safety and explicit danger, the existing coordinate visibility policy, and an audited owner review. Missing photographs, public phone numbers, ordinary facility details, route estimates, light-pollution or horizon enrichment alone no longer makes a verified core record unpublishable. Known serious road/access hazards remain material blockers; closed/prohibited/dangerous conditions must retain their restrictive lifecycle/action semantics, never become a positive or unrestricted public state.
  Authenticated operations still merge attributable evidence and register new sources transactionally; submission, approval and publication remain separate and cannot be bypassed by direct writes. The existing `spot-completeness-policy.ts` implements this core threshold in the shared publication assessor: optional enrichment absence is not a publication blocker, while core claims require current evidence bound to the same spot and a usable source. Asserted site media still requires its verification and provenance. This code does not establish deployment or current database acceptance. Candidate intake never seeds production startup, appears as a formal point before review, or fabricates missing facts. No separate manual completeness workflow or second canonical record is introduced.
- `workers/miniapp-api` also owns the authenticated contribution intake and moderation boundary. PostgreSQL stores user/admin reports, corrections, proposed places, upload-session identity and review history; a replaceable `MediaObjectStorePort` stores only MIME/size-validated, metadata-sanitized derivatives while raw client paths, EXIF and precise contributor coordinates are excluded from ordinary read models and logs. User submission, admin review, canonical fact merge and formal publication are distinct state transitions: neither approval nor an uploaded object may update the formal spot projection until operations explicitly merges attributable evidence and the existing completeness policy passes on the resulting record. Abandoned upload sessions expire and their objects are deleted; idempotency and contributor identity scope prevent duplicate or cross-user writes.
- The same identity boundary owns Settings account-data operations. A data export is a server-generated, identity-scoped, versioned JSON snapshot assembled from current durable records; it excludes session credentials, WeChat identity digests, internal object keys and raw media bytes, and the Mini Program never reconstructs the authoritative export from local cache. Fresh-code reauthentication for export or deletion resolves only an existing active identity; a mismatched code must not create another account or change its delivery binding. Normal login remains the account-creation owner. Account deletion is an idempotent server command with explicit confirmation: it removes the WeChat identity mapping, revokes every session, deletes mutable account preferences/library/plans/profile/import/media records, de-identifies retained moderation/publication evidence, and returns a deletion receipt before the client clears local state. Append-only review, merge, publication and audit evidence may remain only under the resulting unlinkable pseudonymous subject required for integrity; the UI must disclose that retention and cannot call local cache clearing an account deletion.
- Mobile navigation truth lives in one Expo Router route tree: a persistent five-tab navigator maps Tonight, Map, Trips, Sky, and Me to `/tonight`, `/map`, `/trips`, `/sky`, and `/me`, with a route-owned nested stack under each tab. A persisted destination preference may assist restoration, but it cannot become a second router or screen-identity source.

## Mini Program Recent Regional Weather

`recent-weather-provider.ts` owns QWeather Geo city lookup and the preceding two regional calendar days of `/v7/historical/weather`. The independent `GET /v2/spots/{spotId}/recent-weather` delegates to `SpotEnvironmentService`, which validates the existing published-spot identity before spending upstream requests. It never invokes forecast/Astronomy or changes the selected Observation Context. `recent-weather.ts` owns this contract family; the client component owns disclosure, conditional relevance and recovery in the Map's current formal-spot document, after basic information and before terrain. The legacy field route is not a second consumer of this new capability.

`qweather-client.ts` is the shared JWT, coordinate conversion and bounded JSON request boundary used by forecast, alerts and history. Existing metered transport remains below source caches, with WEATHER_REGION and RECENT_HISTORY attempts classified separately. Region lookup is live per request cycle; only complete daily weather measurements cache for six hours, incomplete daily weather measurements for one minute. Failed days are not cached as valid days, and returned source timestamps remain the original retrieval times. Two sequential source phases each have a three-second limit, within the Mini Program's ten-second transport budget; the two dates run concurrently and retain a successful sibling when one fails. No-data responses and request failures have distinct meanings in the public contract.

The client keys recent-weather queries by formal spot and current regional calendar date, separately from astronomy/plan time. `use-calendar-day.ts` stops its timer while hidden, resumes the current date on show and invalidates the day identity at regional midnight; source timezone supersedes the spot's initial timezone after lookup. Cached previous-day payloads cannot reappear as current recent facts. History is supplemental evidence, never proof of field access, closure, flooding or icing.

History hours accept both the provider's legacy regional wall-time format and explicit-offset ISO instants. ISO values are validated by the shared QWeather time boundary and assigned to the freshly resolved region's calendar day. Invalid or foreign-day hours are omitted without discarding valid daily fields. Wind sample counts deduplicate regional clock-hour buckets across formats; they do not certify a complete elapsed day, including daylight-saving transitions. Weather-only cache fingerprints include the interpretation timezone, while retaining no Geo record.

GeoAPI data is live-use only under the selected source conditions. The adapter shares only in-flight composite requests, performs a fresh region lookup per completed request cycle, and retains only weather-day values under opaque weather-request fingerprints (not a coordinate-to-region index). The HTTP route returns `no-store`; `EtagInterceptor` respects this and does not send an ETag/304. `spot-environment-client.ts` bypasses response caching, and `response-cache.ts` retires old `spot-recent-weather:` entries/chunks and rejects new writes. The component includes visibility in its query identity with zero inactive retention, clears its derived regional clock and response on hide or failed refresh, and does not redisplay stale/offline Geo responses. Failure state survives cleanup independently of regional timezone/date changes until manual retry or resumed display. Active rendering state is temporary; weather caching permission does not authorize a retained geographic database.

## Mini Program Independent Air Quality

`air-quality-provider.ts` owns separate QWeather current and hourly AQ requests, per-point caches and attributed segments. `SpotEnvironmentService` shares the existing published-spot guard with regional history and exposes independent current/forecast states through `GET /v2/spots/{spotId}/air-quality`; one failed segment does not erase the other. Metered transport classifies AIR_CURRENT and AIR_HOURLY attempts without retaining request coordinates. Complete current data caches for one hour, forecast for at most six hours and no longer than its last actual hour; partial and failed results have shorter retry windows. Invalid calendar dates, conflicting duplicate identities and expired forecast hours cannot become fresh future evidence.

The contract keeps supplier AQI standard identity, original display/category and pollutant concentrations with units. Missing concentrations remain missing, including the documented China forecast limitation; current PM readings never fill future hours. Retrieval time is not inferred publication/measurement time. The Map's `AirQuality` consumer uses only the selected hour's own interval, lists actual coverage through the shared range disclosure, and keeps current readings separate from astronomy/plan time. It hides expired current readings, retains independent valid forecast, suspends periodic queries while hidden and provides local retry plus the shared top notification on errors. `spot-environment-client.ts` delegates to the existing request/session owner; AQ disables persisted response fallback and does not create another cache. Real account entitlement, availability and target-runtime rendering remain delivery obligations; these source/contract choices alone do not establish them.

`miniapp-contracts/air-quality.ts` owns the shared immutable expiry projection used at provider delivery and by the client: current readings have a product use deadline one hour after retrieval, and each forecast hour ends exclusively one hour after its source instant. This does not invent a measurement timestamp. Valid elapsed evidence is `EXPIRED`, separately from malformed/ambiguous responses and request failures; an existing failure remains a failure when some or all hours expire. Sources retain their original acquisition/publication facts. `useAirQualityQuery` reuses the shared forecast-boundary clock, clears elapsed values while idle or offline, and refreshes on foreground even when the retained evidence has not expired. That hook alone owns automatic resume/expiry refresh; `use-resource-query.refetch({cancelRefetch:false})` joins any fetch already started by TanStack on enable, while manual retry retains its existing behavior. AQ provenance consumes the projected segment sources so an expired reading cannot keep a fresh source badge.

## Mini Program Product And Plan Flow

Map, Search and Sky share `services/observation-context-version.ts` for expected Context version checks; an expired-ID recovery may adopt a new ID but cannot replace a newer selection or downgrade the same ID's revision. Sky's page-local `sky-context-session.ts` coordinates entry lookup and date/time commits with one synchronous request owner. Hide/unmount invalidates pending publication, and a successful current recovery advances that page's accepted ID before the store is updated. It does not create a second Context payload store or replace the API client's recovery policy. Lookup eligibility also controls the loading presentation: a page that no longer owns the selected Context exposes the existing return action instead of waiting on a disabled query.

Plan detail and editor context restoration is local to the mounted plan query. It may use the map context as an initialization source, but does not write its restored snapshot back into the map's committed Observation Context. This preserves the opener's selected place/time across child navigation; plan save still uses the local context and server-side re-resolution. The map's own restoration coordinator remains unchanged. A plan opens its place information through the registered `spot/plan/index` page in the existing `spot` subpackage. That page gives the shared spot-detail renderer an explicit plan-local Observation Context override, so the shared renderer preserves the plan's place/time while the committed Map context and the native return stack remain untouched; ordinary spot-detail consumers continue to use the committed Map context.

The formal Map information panel's plan entry uses `features/spot/spot-plan-route.ts`: zero associated plans opens a spot-prefilled new editor, one opens its detail, and multiple open the spot-filtered list. The editor resolves an explicitly supplied spot through the existing service into a local context without replacing the map opener's context. New-plan drafts opened for a specific spot use an account-and-spot scope in `services/local-draft-keys.ts`; generic new drafts and existing-plan keys remain compatible, and account erasure recognizes both forms. These are routing/data boundaries, not evidence of verified native navigation or completed panel rendering.

User-authored plan reminder content is carried by the existing revisioned plan aggregate, not a second local checklist store. `packages/miniapp-contracts/src/plan-reminders.ts` owns the five-group/twenty-item validation and strips non-contract fields; drafts may retain unfinished text while submitted content must validate. Reminder IDs and item IDs remain stable across edits. Save recovery includes this content in the account-bound intent identity. An older client omitting existing reminder content is rejected rather than erasing it. `notifyOnWechat` expresses intent only: subscription authorization, schedule versions and delivery receipts remain server-owned responsibilities and are not established by saving this field.

PostgreSQL reminder scheduling separates active selection from delivery history. Changing or deleting a plan deactivates displaced schedules without overwriting attempted or terminal delivery states. Returning to an identical schedule version recalculates its current waiting/skipped state only when the old row was canceled and has no attempt count or delivery receipt; it never clears known/unknown delivery outcomes or grants subscription authorization. Pre-existing canceled rows with attempt evidence remain conservative and cannot be reset into a new send by toggling the preference. Account erasure retains its separate privacy-owned removal policy.

`PostgresReminderAttemptStore` reserves a first attempt under the existing account/schedule locks, after checking active account, current plan/reminder version and intent, selected schedule, trigger and departure. It commits an `UNKNOWN` attempt and `RESULT_UNKNOWN` schedule before external work; a crash cannot reset that version to sendable. Only its bound reservation may record one final result, without reactivating canceled history. Provider acceptance uses `SENT / PROVIDER_ACCEPTED`, not a fabricated delivery receipt. This store is not yet connected to the production dispatcher and does not establish subscription eligibility or missed-trigger policy. The dispatcher must add those checks and revalidate immediately before sending; the current worker's sweep must be replaced rather than followed by a sender that can no longer see eligible rows. Plan save/delete serialize on an active account; stale authenticated writes after soft account deletion are rejected. Soft deletion explicitly clears both reminder tables in the same transaction, because the retained user row cannot trigger physical-delete cascades.

`PostgresReminderSubscriptionStore` now owns local subscription challenges (migration `022`), bound to account, schedule version, AppID and template. It requires a future waiting reminder and an encrypted destination for the same AppID. Concurrent preparation reuses an unexpired pending challenge; the five-minute lifetime bounds client reporting, not WeChat subscription validity. Choices are stored as `CLIENT_ACCEPTED`, `REJECTED`, `BANNED` or `FILTERED`; only an identical replay within the valid unconsumed window is idempotent. Client acceptance is not verified provider quota. Attempt reservation consumes exactly one matching local accepted record in the same transaction as the durable attempt, with a unique database link. Canceling/superseding a reminder cancels its unconsumed pending/accepted records, including when the same schedule is later restored. Account soft deletion explicitly removes challenges along with attempts and schedules. Shared binding validation snapshots only AppID/templateId before awaiting; no caller-supplied extra property may replace a reservation identity. Authenticated HTTP preparation/reporting now reuse the existing session identity and plan-cache owner: POST `me/observation-plans/:planId/reminder-subscription` and PUT `me/reminder-subscriptions/:challengeId`. The optional `WECHAT_REMINDER_TEMPLATE_ID` defaults to absent; preparation also requires WECHAT auth, PostgreSQL and the delivery identity key. Missing configuration returns explicit unavailable/false without provider calls. Reports validate UUID and choice before storage and invalidate the account plan cache when recorded. The Mini Program `plan-subscription-client.ts` transport uses the generated operations through the existing authenticated requester, fences both request starts and late responses by account, and refreshes plan caches only after a recorded report. Preparation never opens a native prompt or automatically reports acceptance. Native authorization prompting in the page and production dispatcher/token/template-field mapping remain unconnected; neither this HTTP path nor a local accepted record enables sending. Public status remains unavailable for waiting or locally scheduled rows until the delivery capability exists.

Implementation boundary: the current `outbox-worker.ts` NOTIFICATION branch only sweeps missed schedules and reports `CAPABILITY_GATED`; it does not request subscription authorization or send WeChat messages. With the optional independent `WECHAT_DELIVERY_IDENTITY_KEY`, `auth-service.ts` now registers an AES-256-GCM encrypted OpenID after a successful server-side code exchange. The authenticated binding includes account and AppID; the existing identity row owns storage and account erasure. An old digest cannot be reversed: existing users retain their account and obtain an encrypted destination only at a subsequent verified login. Missing key disables registration; a wrong/rotated key fails decryption closed until a new verified login refreshes that destination. This is neither subscription authorization nor permission to send. Completing delivery still requires an approved template/field mapping, account-bound subscription authorization and a sender integrated with the existing schedule/attempt lifecycle. No template or feature-flag change alone enables delivery. Keep the checklist usable while notification remains unavailable; do not promise provider receipt reconciliation before an actual supported mechanism exists.

`wechat-subscription-sender.ts` owns the bounded REST transport adapter, not dispatch eligibility. It requires explicit enablement, an approved template configuration and injected server token acquisition; there is currently no production wiring. It snapshots the configured field set and contents before token acquisition, rejects redirects, bounds token/send/response waiting and never retries internally. A pre-send token failure is `NOT_ATTEMPTED`, an explicit provider error is `REJECTED`, an ambiguous post-send result is `UNKNOWN`, and `errcode=0` is only `ACCEPTED`, not proven user delivery. The future reminder dispatcher must bind AppID/token/recipient, claim one authorized current schedule durably, map the actual approved fields and persist the outcome before exposing delivery state. A local transport test cannot establish those missing responsibilities. Platform field and authorization lookup: [Tencent CloudBase subscription guide](https://docs.cloudbase.net/en/recipes/add-subscribe-message-cloud-function); this project keeps its existing backend rather than adopting a CloudBase deployment.

Checklist completion uses `PUT /me/observation-plans/{planId}/checklist-completion` and the same plan aggregate revision/transaction. It changes only the identified item's explicit completion value, preserving the saved context snapshot, times and other user content without requiring Observation Context or forecast availability. Retry receipts are scoped by account, plan and item; stale revisions and missing items are rejected. The client publishes confirmed results through the existing plans query cache and fences account changes. Completion writes currently produce the existing plan update event; reminder scheduling must compare scheduling-relevant content rather than treat every checklist tick as a changed departure or authorization.

Mini Program plan navigation has an all-dates list at `content/plan/list/index` and an independently mounted editor at `content/plan/edit/index`; the editor currently composes the existing `content/plan/detail/index.tsx` form owner instead of duplicating its draft, revision and account logic. Explicit new intent takes priority over cached plans or an obsolete plan-id parameter. List rows and My rows keep the chosen plan identity; the all-plans header targets the list. Confirmed editor saves return to the opener, while failed navigation retains the successful save and exposes retryable navigation feedback. These route boundaries do not establish completion of the adopted detail rendering, reminder scheduling or runtime navigation verification.

Account display identity belongs to the authenticated Mini Program account, separately from preferences, external profile links and the WeChat identity digest. Nickname read/write uses `GET /me/profile` and `PUT /me/profile/nickname`; account avatar read/write uses the authenticated `/me/profile/avatar` pair. `packages/miniapp-contracts/src/account-profile.ts` owns nickname normalization plus the avatar's content version, MIME and 1–2.5 center zoom. `database/miniapp/migrations/011_account_profile.sql` stores nickname and the shared optimistic profile revision; migration 016 adds one active private avatar object reference and metadata. Avatar uploads accept bounded JPEG/PNG/WebP data, verify declared size and image structure, strip supported private metadata before writing to the existing private media store, and replace the previous object only after the revisioned profile write succeeds. Same-intent retries replay the saved record; altered payloads using the same key and stale revisions conflict. The client requests album or camera only after the avatar action, previews a circular center crop, and commits only on `使用此头像`; cancellation, failure and account changes preserve the saved identity. Account export includes profile metadata but not image bytes. Account deletion queues the active avatar object with other private media, clears profile fields and erases scoped replay payloads. This is app-owned identity and never writes the user's WeChat profile.

- `AstronomyService` reuses public formal-spot calculations after validating current publication facts and normalized weather validity. Its cache identity includes effective spot, exact time, profile/event, algorithm/catalog/rule and weather inputs; each result binds the current caller's context and never retains a private route origin in shared work. Map and overview request decision evidence without constructing star scenes; full-sky responses add the existing exact-time scene and target frames. `astronomy-service.ts` owns retention limits and expiry policy, while `provider-deadline.ts` bounds transport/body waits and lets a cancelled waiter leave shared work available to other callers. An expired deadline is attributable unavailable evidence and cannot make official-warning or publication gates permissive.

- Mini Program floating feedback consumes the existing shared notification queue from one host inside each actual page's theme root, including alternate page-state roots. A hidden page does not present or announce that host. The App component supplies providers and launch behavior, not a cross-page visual overlay: WEAPP renders separate page trees. Hosts never introduce another queue, duplicate a transaction or enter scrolling/navigation containers; the existing notification family owns arbitration and safe-area presentation.

- `AstronomyService` owns one exact presentation time axis per SkyReport. A valid committed Observation Context instant is not silently rounded to the nearest night sample: where calculation is available, it is included as a real calculated sample alongside the regular night cadence. Each returned hourly instant has an explicitly time-bound target frame as well as its catalog-star frame; top-level current targets describe the exact committed instant. The Mini Program selects the same frame instant for time-ruler preview, catalog stars and target directions, and missing exact frames remain unavailable rather than borrowing another instant or recalculating celestial coordinates on the client. Preview remains transient and cancellation restores the committed context; only the existing context update commits time. ## Mini Program Decision Constraints

### Astronomical event ingestion and network boundary

The authenticated event workspace binds review to the active catalog version/hash (`reviewed_against`, migration `019_event_catalog_review_baseline`). Candidate diffs are recalculated against the current catalog for display; a stale or absent review baseline prevents publication. Publication uses a PostgreSQL transaction with the active-version precondition and locked candidate state/review baseline. Manual source registration can use atomic create-only semantics. Rollback rejects content equivalent to the active package, ignoring only publication version and retrieval timestamp, so a lost response followed by a fresh confirmation cannot duplicate the same restoration. Runtime refresh and activation use a local revision to prevent a delayed read from replacing a newer activated catalog. These guards share the existing catalog owner; they do not change saved plan identity or times.

The GMN data path is `data-pipelines/meteor-catalog` → versioned `src/data/gmn-annual-reference.ts` → `meteor-event-catalog.ts` → the existing event catalog/publication owner. It records actual input hashes, source/CC BY 4.0 attribution, annual monitoring longitude and bounded historical radiant drift; it carries no synthesized ZHR/activity or numeric fit confidence. Projection uses the current solar longitude and ECL J2000 → equatorial-of-date transform per instant, constrained by the event year, monitoring interval and fitted interval. Map/plan detail and Sky targets consume this same owner. Missing direction is distinct from geometric invisibility; missing meteor activity prevents an activity-dependent score.

Persisted copies of the exact retired built-in meteor baseline migrate through the existing immutable publication store. Migration checks the expected active version/hash inside the PostgreSQL publication transaction, so it cannot replace a concurrent operator publication. It preserves nonmeteor records and user plans; operator-edited meteor packages are not silently overwritten. The exact retired baseline remains historical evidence but cannot be activated by rollback; supported newer reviewed versions retain normal append-only rollback. Migration is a new publication, not a rollback. Event `sourceId` binds the precise source record; a GMN source requires annual-reference semantics and cannot carry invented exact annual peaks. Package validation, critical-field diff and cache identity include these semantics.

An overseas domain is not evidence that a VPN is universally required; reachability must be checked from the intended execution environment. Use one background ingestion pipeline for scheduled retrieval and authenticated operator import. Prefer authoritative sources reachable from the deployed service. Neither is a currently reachable production dependency. Do not assume one provider covers all event types or local visibility.

Default intended cadence is a configurable weekly update check, with bounded retry/backoff and a manual rerun; seed an attributable published catalog first. Sources have independently recorded coverage, terms/attribution, reachability, parser/schema version and automatic-publication eligibility. Fetch only allowlisted sources with conditional requests when supported, bounded downloads and timeouts. Preserve source URL, release/retrieval times, source-file hash, parser version, time scale/timezone and original precision. Normalize occurrence identity, compare changes and validate schema, temporal ordering, units, source coverage and duplicate/conflicting records. Never turn an ambiguous date or missing peak time into invented precision.

User-approved publication rule: stable structured feeds may publish automatically after validation and comparison with a previously approved baseline. First onboarding, parsing/schema failures, conflicting evidence, unexpected deletions/coverage collapse or materially changed critical times go to operator review. Critical-change rules are source/type-specific, versioned and approved on onboarding; until defined, changed critical times require review. A malformed or empty fetch cannot replace the current catalog. PDF/HTML extraction is a candidate until its adapter and interpretation are approved; model-generated extraction alone is not sufficient to publish scientific facts.

Stages are retrieve/import → candidate normalization and diff → validated automatic publication OR operator review → atomic version publication. Reuse the authenticated operations boundary and PostgreSQL/versioned dataset owner; both paths use the same validator, stable identities and idempotency. Keep prior versions and audit actor/source/reason, support rollback, and invalidate location/time projections by catalog plus algorithm version. Updating an occurrence never silently rewrites a user's saved observing/departure times. Operator import accepts bounded documented data packages with provenance; uploading a file alone does not publish it or execute embedded code.

Overseas-only automatic retrieval is possible only if a separately configured collector can reach the source and transfer a validated, authenticated/versioned package to a domestic endpoint or store reachable by production. It is an optional future deployment, not an installed collector, proxy purchase or workaround assumed to exist. The collector handles public event data only, not user plans or locations. Without such connectivity or a domestic source, retain the existing catalog and use operator import for new data; fully automatic freshness cannot be promised. Failure creates an operational update issue while consumer reads use the last published version with coverage/freshness semantics; outside coverage is unavailable, never “no events”.

The current implementation extends the code-shipped reviewed catalog with one shared catalog owner, PostgreSQL migration `017_astronomical_event_catalog_pipeline`, authenticated source/import/review/publish/rollback operations and the existing BullMQ worker. The worker uses a configurable bounded interval (seven days by default), conditional HTTPS retrieval, the shared package validator/diff policy and existing retry/dead-letter replay. Public event reads, plan identity validation, Observation Context fingerprints and astronomy report cache inputs all read the active catalog version; an unavailable source retains the reviewed built-in baseline or last published version. No domestic source adapter or overseas collector is configured by default, so automated freshness still depends on an operator-approved reachable structured source.

`GET /v2/celestial-objects/:reference/image?level=OVERVIEW|MEDIUM|DETAIL` is the same-origin BFF boundary for the adopted NASA/IPAC IRSA AllWISE W3 12 µm publication. A build-time pipeline requests exact ICRS J2000, TAN, north-up/east-left JPEG products from the IRSA-hosted AllWISE W3 HiPS through CDS hips2fits, then publishes the bounded files and a provenance/integrity manifest with the service. Runtime provider network access is forbidden: the service accepts only catalog identities and the three levels, validates the publication, path, byte length, SHA-256 and JPEG framing, and returns the local asset. Fields are `clamp(axis*3, 2°, 4°)` at 256px, `clamp(axis*1.5, .75°, 4°)` at 512px and `clamp(axis*.6, .25°, 2°)` at 512px. The 4° overview ceiling covers the roughly 3° major axis of M31 without introducing an unbounded publication. This is processed historical infrared survey imagery, not naked-eye appearance, live sky, current weather or a visibility promise; bounded stretch/resampling and source-survey saturation or detector artifacts may remain, and the client always discloses survey/band.

Image bytes and celestial-object provenance share the same injected `DeepSkyImageryService` and validated local manifest. Catalog facts survive an unavailable image publication without caching away later provenance recovery. AllWISE content acknowledgment, CDS/Aladin HiPS ODbL/DOI and OpenNGC catalog licensing remain distinct. Object details disclose these through the existing Provenance component on demand. `/v2/sky/deep-sky/:publicationHash/manifest` offers the machine-readable collection, processing requests and hash-bound image URLs; its hash identifies the stored manifest before delivery links are added. Downloads reject a mismatched publication. The commercial-use conditions and official references live in [the publication owner](../../data-pipelines/deep-sky/README.md#commercial-use-notices-and-distribution).

The client uses the current local/whole-dome scale and transition owners in `sky-zoom.ts` and `sky-browsing-camera.ts`, keeps coordinates/time/orientation ownership fixed, and requests imagery only for an explicitly selected deep-sky object once the field is 15° or narrower. It writes the bounded binary response to `USER_DATA_PATH`, retains an already-present coarser image while a finer level loads, aborts superseded requests and draws through `sky-survey-registration.ts` and the shared GPU inverse ray/plane owner, preserving the publication's north-up/east-left handedness. The adopted CDS TAN mapping uses plane half-width `tan(fieldDegrees/2)`, FITS `CRPIX=N/2`, and the JPEG row reversal; the reference texture coordinate is `(0.5−0.5/N, 0.5+0.5/N)`. ICRS north comes from the exact north sample; the old finite RA-offset east sample only checks handedness. Equal-distance corner anchors share one plane; the old screen-affine branch is retired. Old cached scenes without the registration marker retain object facts but require a report refresh before imagery. Invalid registration or GPU submission is a retryable image failure; explicit retry resets the shared renderer's shader latch and refreshes geometry as well as reloading the image. Observation warm-red mode suppresses survey imagery. Loading, retryable failure, source and maximum-resolution states remain lightweight overlays; the default 45° view has no persistent gesture tutorial. Orientation supports both device-follow and explicit manual drag mode. Official WEAPP establishes request/write/draw API availability only when the current published asset is actually exercised; physical registration, jitter, memory pressure, lifecycle recovery and target-device frame timing remain device acceptance work.

Image request, decode and failure presentation follow page visibility as well as selected object and level. Hiding cancels pending request/decode callbacks; returning starts current work through `LOADING`. Only successful current-level decode establishes `READY`; request/file success alone does not. A failed finer decode or retry retains the same object's last usable decoded image. Failure notifications bind object and level so an old error cannot be relabelled for a newly selected target.

## Celestial object selection and lazy information

The current production slice extends the existing astronomy-core catalog pipelines, BFF astronomy/application adapter and miniapp-contracts while keeping projection/ephemeris on the current astronomy owner and selection/rendering in the sky client. It introduces no feature import into shared contracts, second client ephemeris, notification platform or per-object remote text generation. Bright stars and Messier deep-sky objects have separate source manifests and failure boundaries but share stable selection, modal and canvas-camera responsibilities.

The BSC geometry owner exposes `bsc5pHorizontalFrame` for one exact observer/time: Astronomy Engine computes EQJ→HOR, then the owner converts north/west/up to an explicit row-major east/north/up matrix. `@starward/astronomy-core/stellar-vectors` owns only unit equatorial position, tangent velocity per Julian year, propagation, supplied-matrix application and horizontal coordinate conversion; it has no catalog I/O, clock or ephemeris dependency. Current `propagateBsc5p`, `positionBsc5pCatalog` and the BFF use these same primitives. The BFF's `stellar-geometry-provider.ts` supplies exact observation transforms; the separate static publication owns immutable stellar vectors. `miniapp-contracts/src/stellar-geometry.ts` owns representation validation: source version/hash, propagation origin, canonical observation instant, observer, elapsed Julian years, unit/tangent vectors, and finite orthogonal right-handed matrices. Expected identity/time/location come from the requested context, not the candidate frame. Source hash identifies the original publication, not the derived geometry bytes; local factory construction currently establishes that correspondence, and external transport must retain a trusted publication binding. The dynamic report uses `stellar-scene-v2`: one version/hash-bound catalog reference, observer, and geometry transform per exact time slice. It does not repeat catalog entries or point arrays. The projection algorithm revision participates in existing server cache identity.

- Identity: `packages/astronomy-core/data/bsc5p-bright-stars.v2.json` is the Mini Program base bright-star pack; its adjacent manifest is the exact query, hash, population, name-count, epoch, source and derivation authority. HEASARC supplies all rows in -2≤V≤6.5, with its 14 nonstellar HR identities explicitly excluded. Names join the current IAU table through exact unambiguous HR/HD identifiers, or exact Bayer (including component digits)/Flamsteed identifiers. Ambiguous components retain HR rather than inheriting a system name. Scene and detail keys are `HR:<number>`; HIP may appear only as an IAU-published alias. FK5 J2000 proper motion uses μalpha*cos(dec) and μdelta in arcsec/year, propagated on a unit vector before EQJ→EQD→horizontal rotation. Original V measurement system/uncertainty and nullable B−V remain explicit; no radial velocity, parallax or atmospheric refraction is invented. Frame-local catalogIndex always resolves against its matching catalog/hash. Sirius, Vega and Polaris remain named regressions. Solar-system and OpenNGC identities retain their independent owners.
- Extended bright-star acquisition: `data-pipelines/star-catalog/build_bsc5p.py` also produces the separately versioned `bsc5p-bright-stars.v2` asset and manifest for the complete BSC5P V≤6.5 subset. Its manifest owns the exact count and source bytes. `loadBsc5pStarCatalog` explicitly selects either checked-in publication and validates its population, values and manifest hash; rows and nested provenance are immutable. The default report and object-detail loader selects v2; v1 remains explicitly readable for publication identity and cache transition. Conflicting archive identities remain unresolved and cannot override a current explicit match. Archive positions/photometry and retired names are not imported; HIP aliases can represent multiple systems and cannot establish one-to-one component merges. - Static star publication: `GET /v2/sky/catalogs/:catalogVersion/:catalogHash` is owned by `StellarCatalogController` and `StellarCatalogPublicationService`, independently from observing/account state. Only matching local v1/v2 publications are admitted; unknown versions or hashes return 404 without runtime provider requests. `stellar-catalog-publication.ts` in contracts owns compact rows combining HR/name/original V/nullable B-V and the geometry factors, with attributable sources including v2's archived IAU identity source. Map and plan report consumers retain the compact response without requesting the full star data. `sky-stellar-scene.ts` attaches a local render model outside the shared report query, validates publication binding, and resolves only the currently selected exact frame through the pure vector owner. Its bounded current-frame cache is reused by drawing, listing, counts and picking; it never expands a full day of stars. Missing/invalid static data retains independent weather, solar-system and deep-sky content, with independent notification/retry; usable independent canvas content retains gesture and calibration entry. Cancellation follows the existing transport owner. Static catalog presence is a client cache fact: the BFF does not claim offline readiness from dynamic report availability alone.
- Picking: the sky client publishes a bounded identity snapshot only after the native canvas draw callback, containing only catalog objects actually projected and painted for that exact frame/catalog/hash/camera. Selection rejects a stale identity, applies bounded hit tolerance and deterministic distance→brightness→reference ordering, and offers at most four choices for overlaps. Pinch, drag and cancellation cannot become a tap. Sparse bright proper-name labels and a 24-at-a-time user disclosure share the same modal without creating a DOM node or request for every catalog row. The list is computed only while disclosed so high-frequency pose renders do not repeatedly sort the visible catalog.
- Content: `GET /v2/celestial-objects/:reference?locale=zh-CN` accepts canonical HR and admitted M references. - Retrieval: only an explicitly selected identity starts the static information query. Closing/unmounting or selecting another object aborts the current request; response ownership prevents late data from replacing another object or reopening the modal. Any later SIMBAD/editorial adapter must retain the original timeout, sanitation, rate/cost, negative-cache and attribution constraints below.
- Sources: [SIMBAD](https://simbad.cds.unistra.fr/simbad/) is a candidate for extrasolar basic data/cross-identification and bibliography, not a universal Chinese encyclopedia or solar-system ephemeris. Assess coverage, exact access/redistribution terms, deployed connectivity, request budget and cache rights before selection. Do not perform one external query per star/frame, bulk import without terms review, or promise introductions for every point because a catalog entry exists.
- Capacity and migration: the complete noon-to-noon time axis retains every exact transform and original numerical precision. The bounded scene ceiling is owned by `SKY_SCENE_MAX_SERIALIZED_BYTES`; this limit now applies to dynamic transforms and independent deep-sky samples, while the separately cached star publication retains its own existing response-cache limit. Native storage remains governed separately by the existing chunked response-cache budgets, not by sending an entire report through one storage key or setData. `sky-report-catalog.ts` projects both network/304 and persisted offline responses through the current compact scene/geometry identity boundary; retired star frames become unavailable without discarding independent weather, target frames or deep sky, and a current response restores selectable stars.

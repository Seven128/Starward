# Architecture Detail: Assurance And Lifecycle Components

This on-demand foundation node continues `project_context/architecture.md#component-map`. It owns detailed mobile feedback, Android verification, runtime-carrier and account-erasure lifecycle boundaries; the parent remains the architecture entry and routing owner.

## Assurance And Lifecycle Components

- Mobile development feedback uses that same React Native component/route tree through Expo Web or an installed development client. `tests/acceptance/start-mobile-web.mjs` and its session helper own the bounded Web/API process and restart-sensitive session identity. Browser diagnostics remain a support renderer, not a native runtime or visual authority; the archived page/control visuals cannot be used as current comparison baselines.
- `tools/long-task/verify-native-target.mjs` remains the single project Android Check executor and result aggregator. Its native verification-session module owns deterministic population planning, independent-device shard assignment, exact-input checkpoint identity and atomic fragment recovery; neither cached fragments nor diagnostic filters create another verifier, Authority, Check or completion state.
- The Android design-evidence module is a session-gated observation transport inside the same production React Native tree. One session-qualified launch establishes the current evidence session; bounded context switches may then retarget Control/Scenario attribution only when they present that exact session identity. Exact context/state acknowledgements expose only transport readiness: the verifier must still observe the production owner carrier, interaction and result in the same committed UI tree, and a missing carrier fails immediately after its acknowledged render context instead of triggering blind whole-page polling. These acknowledgements cannot activate in an ordinary user run, reset product authority, create evidence by declaration, or replace the unit's production-root journey.
- Each Outcome must expose a production runtime carrier wired into the application. Acceptance invokes that carrier with variable inputs, verifies committed database/file/native/external receipts, recreates the runtime against the same isolated data directory, reads state back, checks idempotent replay, and verifies invalid/failing operations cannot report success.

### Account erasure and retained evidence

- Account erasure covers current contribution payloads, historical revisions, moderation snapshots/events, related audit payloads and cached operation receipts. The PostgreSQL account-deletion transaction owns this bounded privacy-redaction exception to append-only history: remove original text, candidate coordinates, observation time, media metadata and contributor identity digests; retain structural identifiers and state under a fresh non-login pseudonymous subject. Recompute redacted revision digests and append an erasure event rather than claiming the old digest still describes the rewritten payload.
- Redacted contributions/cases cannot be mutated or merged again; redacted receipts cannot replay original content. Previously reviewed canonical place facts and publication/merge relationships are not automatically removed. Encrypted backups and independently published facts remain separate retention/recovery boundaries, not proof that online deletion erased every historical copy.

## Verification Detail

- Product requirements, confirmed design decisions and project-owned runtime checks define acceptance. Tiny Context has no compiled acceptance Authority. The retired 0.11.0 package overlay has been removed; see project_context/context-maintenance.md for resource interpretation.
- Active authority integrity is checked by `npm run design:system:verify`: it preserves the native App DESIGN→runtime projection and six-value observation palette while separately validating the selected Field Signal package membership/digests, canonical DESIGN projection, palette and four-layer whitespace contracts, semantic component-family inventory, closed warm-red observation palette, contrast/accessibility contracts, provider lineage and App-profile non-inheritance. `npm run design:targets:verify` separately protects unchanged legacy archives; passing it does not reactivate their visual styling.
- Web/Fast Refresh and filtered native diagnostics shorten the repair loop, while only complete current-snapshot target-runtime aggregation can satisfy the Android Assertions. Parallel native execution is valid only across disjoint selected serials with one attributed worker lifecycle per device. Within a shard, one Condition/Mode unit may share its root-proved cold-start prelude while every Control and Scenario retains a separately reset, attributed observation; final candidate verification does not consume repair-session checkpoints.
- A service class, endpoint, adapter declaration, generated report, or screen is not completion evidence by existence. Machine acceptance must execute the production path and its counterfactual must fail when the carrier, write, adapter invocation, or restart readback is removed.
- Mini Program acceptance additionally requires the same production candidate's deterministic checks, Taro builds, current WeChat DevTools observations, declared multi-size/mode/state/accessibility checks, and platform/device observations required by the current accepted Source, current Mini Program Screen Contract, active Field Signal system and `target-miniapp-field-signal-i21-selected-constraint-2026-09-03`. The retired `target-miniapp-sky-canvas-current-constraint` is historical audit evidence only and cannot supply a current comparison or acceptance binding. I21 resource integrity inspection proves only selected input identity, declared Fact closure and implementation-feasibility Source consistency; it does not prove runtime conformance.
